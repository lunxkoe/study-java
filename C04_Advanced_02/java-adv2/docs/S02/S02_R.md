# 문자 인코딩 정리

원문을 따라가면서 고칠 부분과 덧붙일 내용을 표시했다.
**[수정]** 은 사실과 다른 부분, **[보충]** 은 틀리진 않았지만 조건이 필요한 부분, **[추가]** 는 원문에 없지만 알아두면 좋은 내용이다.

---

## 비트와 바이트

컴퓨터 메모리는 결국 전구 더미다. 전기가 흐르면 1, 안 흐르면 0. 그 전구 하나가 1비트다.

비트가 N개면 표현할 수 있는 경우의 수는 2^N. 8비트를 묶은 게 1바이트고 256가지를 표현한다. 10진수 100을 저장하려면 2진수 `1100100`으로 바꿔서 넣는다.

여기까지는 문제없는데, 음수 표현 설명이 살짝 어긋난다.

> **[수정]** 원문은 "맨 앞 1비트로 부호를 구분하고 나머지 7비트로 숫자를 표현한다"고 설명한다. 결과 범위(-128 ~ 127)는 맞지만, 실제로 컴퓨터가 쓰는 방식은 **2의 보수**다. 부호-크기 방식이 아니다.

2의 보수에서는 `-1`이 `11111111`이고 `-128`이 `10000000`이다. 맨 앞 비트가 부호 역할을 하는 건 맞지만, 나머지 7비트가 "크기"는 아니다.

이걸 굳이 짚는 이유가 있다. 뒤에 나오는 인코딩 예제에서 바이트가 **음수로 출력**되는데, 2의 보수를 모르면 그 결과를 해석할 수 없다. 이건 따로 다룬다.

## 문자를 숫자로 바꾸는 법

숫자는 2진수로 바꾸면 되는데, 문자는 그런 공식이 없다. `A`를 2진수로 바꾸는 수학적 규칙 같은 건 세상에 없다.

그래서 사람들이 택한 방법은 단순하다. **표를 하나 만들고 문자마다 번호를 붙이는 것.**

- `A`를 표에서 찾아 65로 바꿔 저장 → **인코딩**
- 65를 표에서 찾아 `A`로 되돌려 출력 → **디코딩**

이 표가 문자 집합(charset)이다.

### ASCII

7비트로 128가지. 영어 알파벳, 숫자, 몇 가지 기호면 충분했던 시절의 표다.

### ISO-8859-1

서유럽 쪽에서 컴퓨터를 쓰기 시작하면서 128칸으로는 모자라졌다. 1비트를 더 써서 8비트, 256가지로 늘렸다. 앞의 0~127은 ASCII를 그대로 두고 128~255에 서유럽 문자를 채웠다. 그래서 ASCII와 호환된다.

### EUC-KR과 MS949

한글은 사정이 다르다. 조합 가능한 글자가 1만 자가 넘어서 256칸에 절대 안 들어간다. 그래서 **2바이트**를 쓴다. 2바이트면 65536가지다.

EUC-KR은 그중에서도 자주 쓰는 완성형 한글 2350자만 담았다.

> **[보충]** 원문에는 MS949 설명이 본문에 없고 예제 주석에만 짧게 나온다. 하지만 뒤의 예제에서 "뷁"이 EUC-KR로는 안 되고 MS949로는 되는 장면이 핵심이라, 정리해두는 게 좋다.
>
> **MS949(x-windows-949)는 EUC-KR을 확장한 문자 집합**이다. 마이크로소프트가 EUC-KR에 빠진 나머지 한글을 채워 넣어 11172자 전부를 담았다. EUC-KR ⊂ MS949 관계라서 **EUC-KR로 인코딩한 건 MS949로 읽을 수 있지만, 반대는 안 된다.**

EUC-KR의 특징은 영어는 1바이트, 한글은 2바이트로 저장된다는 점이다. ASCII 영역을 그대로 물려받았기 때문이다.

## 유니코드, 그리고 UTF-16과 UTF-8

> **[수정]** 소제목 오타. "전세계 **문잡** 집합" → **문자**

EUC-KR의 문제는 명확하다. 그 표가 없는 컴퓨터에서는 한글 문서를 못 연다. 나라마다 자기 표를 만들었으니 서로 문서를 주고받을 수 없었다.

그래서 **세상의 모든 문자를 하나의 표에 담자**는 게 유니코드다. 이걸 실제 바이트로 어떻게 저장할지에 대한 방식이 UTF-16과 UTF-8이고, 처음에는 UTF-16이 더 인기였다.

### UTF-16

기본 다국어는 2바이트로 표현한다. 영어, 유럽어, 한국어, 중국어, 일본어가 전부 2바이트다. 그 밖의 문자는 4바이트를 쓴다.

> **[수정]** 원문은 4바이트 영역을 "42억 가지"라고 적었다. 4바이트 = 32비트니까 산술적으로는 42억이 맞지만, **유니코드 코드포인트 자체가 U+0000 ~ U+10FFFF로 제한**되어 있다. 전체가 약 111만 개고, 4바이트로 표현하는 보조 평면은 약 100만 개다.

UTF-16의 결정적인 약점은 **ASCII와 호환되지 않는다**는 것이다. `A` 하나에도 2바이트를 쓴다(`[0, 65]`). 웹 문서의 대부분이 영문인데 용량이 두 배가 된다.

자바는 언어 내부적으로 UTF-16을 쓴다. `char`가 2바이트인 이유가 이것이다.

> **[추가]** 여기서 자바 개발자가 실제로 밟는 지뢰가 하나 있다. `char` 하나는 2바이트인데, 이모지 같은 보조 평면 문자는 4바이트다. 그래서 `char` 하나에 안 들어가고 **char 두 개(서로게이트 페어)**로 쪼개져 저장된다.
>
> ```java
> System.out.println("가".length());   // 1
> System.out.println("😀".length());   // 2  ← 글자는 하나인데
> ```
>
> 글자 수를 세거나 문자열을 자를 때 이 차이가 버그가 된다. 실제 글자 수는 `"😀".codePointCount(0, "😀".length())`로 세야 한다.

### UTF-8

8비트 기반의 가변 길이 인코딩이다. 문자에 따라 1~4바이트를 쓴다.

| 바이트 수 | 담는 문자 |
| --- | --- |
| 1 | ASCII 영문, 기본 라틴 문자 |
| 2 | 그리스어, 히브리어, 라틴 확장 |
| 3 | **한글**, 한자, 일본어 |
| 4 | 이모지, 고대 문자 |

한글은 3바이트라서 EUC-KR(2바이트)이나 UTF-16(2바이트)보다 용량을 더 쓴다. 대신 **ASCII를 1바이트로 그대로 호환**한다. 영문이 압도적으로 많은 웹에서 이 장점이 단점을 압도했고, 결국 사실상의 표준이 됐다.

> **[수정]** 마크다운 오타. `** 최신은 UTF-8을 사용하자**` — 별표 뒤에 공백이 있어서 굵게 표시가 안 된다. `**최신은 UTF-8을 사용하자**`

## 자바에서 문자 집합 다루기

```java
// 이 환경에서 쓸 수 있는 모든 Charset
SortedMap<String, Charset> charsets = Charset.availableCharsets();

// 이름으로 조회 (대소문자 구분 안 함)
Charset charset1 = Charset.forName("MS949");
Set<String> aliases = charset1.aliases();       // 별칭 목록

// 자주 쓰는 건 상수로 정의되어 있다
Charset charset3 = StandardCharsets.UTF_8;

// 시스템 기본값
Charset defaultCharset = Charset.defaultCharset();
```

> **[보충]** 예제에서 `Charset.forName("EUC_KR")`, `Charset.forName("MS_949")`처럼 밑줄을 쓰는데, 이건 **별칭**이다. 정식 이름은 각각 `EUC-KR`, `x-windows-949`다. 그래서 출력에 `MS_949`가 아니라 `x-windows-949`로 찍힌다. 처음 보면 "내가 쓴 이름이 아닌데?" 하고 당황할 수 있다.

### 기본 문자 집합은 믿을 게 못 된다

원문의 "지정하지 않으면 시스템의 기본 Charset으로 저장한다"가 실무에서 가장 무서운 문장이다.

> **[추가]** **Java 18부터 기본 문자 집합이 UTF-8로 통일됐다.** 그 전에는 OS와 로캘에 따라 달랐다. 한국어 윈도우에서 개발하면 MS949, 리눅스 서버는 UTF-8. 똑같은 코드가 **내 PC에서는 멀쩡하고 서버에서만 한글이 깨지는** 고전적인 원인이 이거였다.
>
> Java 17 이하를 쓴다면 실행 옵션으로 못을 박아두는 게 안전하다.
> ```
> java -Dfile.encoding=UTF-8 -jar app.jar
> ```
>
> 그리고 Java 18 이상이어도 **콘솔 출력은 여전히 별개**다. `System.out`은 콘솔 인코딩을 따라가기 때문에, 윈도우 터미널에서는 기본 charset이 UTF-8인데도 출력이 깨질 수 있다.

결론은 하나다. **파일을 읽고 쓸 때 문자 집합은 항상 명시한다.**

```java
// 환경에 따라 달라진다
Files.readString(path);
new String(bytes);
text.getBytes();

// 어디서 돌려도 같다
Files.readString(path, StandardCharsets.UTF_8);
new String(bytes, StandardCharsets.UTF_8);
text.getBytes(StandardCharsets.UTF_8);
```

## 인코딩 해보기

```java
private static void encoding(String text, Charset charset) {
    byte[] bytes = text.getBytes(charset);
    System.out.printf("%s -> [%s] 인코딩 -> %s %sbyte\n",
            text, charset, Arrays.toString(bytes), bytes.length);
}
```

```text
A -> [US-ASCII]      인코딩 -> [65]              1byte
A -> [ISO-8859-1]    인코딩 -> [65]              1byte
A -> [EUC-KR]        인코딩 -> [65]              1byte
A -> [UTF-8]         인코딩 -> [65]              1byte
A -> [UTF-16BE]      인코딩 -> [0, 65]           2byte

가 -> [EUC-KR]        인코딩 -> [-80, -95]        2byte
가 -> [x-windows-949] 인코딩 -> [-80, -95]        2byte
가 -> [UTF-8]         인코딩 -> [-22, -80, -128]  3byte
가 -> [UTF-16BE]      인코딩 -> [-84, 0]          2byte
```

영문 `A`는 UTF-16만 빼고 전부 65다. ASCII 호환이 이런 뜻이다.

### 왜 음수가 나올까

> **[추가]** 원문에 설명이 없는데, 처음 보면 무조건 걸리는 부분이다. 그리고 맨 앞의 2의 보수 이야기가 여기서 쓰인다.

EUC-KR에서 `가`의 실제 코드는 `0xB0 0xA1`, 10진수로 **176과 161**이다. 그런데 출력은 `-80, -95`다.

이유는 **자바의 `byte`가 부호 있는 타입**이기 때문이다. 표현 범위가 -128 ~ 127이라 176을 담을 수 없다.

```
176을 8비트로 쓰면  →  1011 0000
맨 앞 비트가 1      →  2의 보수로 해석하면 음수
176 - 256          →  -80
```

161도 마찬가지로 161 - 256 = -95. 비트 패턴은 그대로고 **해석만 달라진 것**이다. 실제 저장된 바이트는 여전히 `0xB0`다.

원래 값이 보고 싶으면 부호를 지워주면 된다.

```java
for (byte b : "가".getBytes(EUC_KR)) {
    System.out.printf("%d (0x%02X)%n", b & 0xFF, b);
}
// 176 (0xB0)
// 161 (0xA1)
```

`& 0xFF`는 하위 8비트만 남기고 int로 올리는 관용구다. 바이트를 다룰 때 계속 쓰게 된다.

### UTF_16과 UTF_16BE

> **[보충]** 예제가 `UTF_16`이 아니라 `UTF_16BE`를 쓰는데, 원문에 이유가 없다. 둘은 다르다.
>
> ```java
> "A".getBytes(StandardCharsets.UTF_16);     // [-2, -1, 0, 65]  ← 4바이트
> "A".getBytes(StandardCharsets.UTF_16BE);   // [0, 65]          ← 2바이트
> ```
>
> 앞의 `-2, -1`(0xFE 0xFF)은 **BOM(Byte Order Mark)**이다. 2바이트를 큰 단위부터 쓸지(BE) 작은 단위부터 쓸지(LE) 알려주는 표식이다. `UTF_16`은 이 표식을 붙이고, `UTF_16BE`는 "무조건 BE"라고 정해두고 표식을 생략한다. 예제에서 바이트를 깔끔하게 보려고 BE를 쓴 것이다.

## 디코딩이 어긋나면

인코딩할 때 쓴 문자 집합과 디코딩할 때 쓴 문자 집합이 다르면 어떻게 될까. 예제의 결과를 추려보면 이렇다.

```text
A  -> [US-ASCII] 인코딩 -> [65] -> [UTF-16BE] 디코딩 -> �
가 -> [US-ASCII] 인코딩 -> [63] -> [US-ASCII] 디코딩 -> ?
뷁 -> [EUC-KR]   인코딩 -> [63] -> [EUC-KR]   디코딩 -> ?
뷁 -> [MS949]    인코딩 -> [-108, -18] -> [EUC-KR] 디코딩 -> ��
가 -> [EUC-KR]   인코딩 -> [-80, -95]  -> [UTF-8]  디코딩 -> ��
가 -> [EUC-KR]   인코딩 -> [-80, -95]  -> [MS949]  디코딩 -> 가   ← 유일하게 성공
```

마지막 줄만 성공했다. MS949가 EUC-KR을 확장한 문자 집합이라 EUC-KR이 만든 바이트를 그대로 읽을 수 있기 때문이다. 반대 방향(`뷁`을 MS949로 인코딩 → EUC-KR로 디코딩)은 실패한다.

> **[보충]** 원문 주석 "MS_949가 EUC_KR을 받아서 되었기 때문에"는 의미는 맞는데 표현이 애매하다. **"MS949가 EUC-KR의 상위 집합이라 한쪽 방향으로만 호환된다"**가 정확하다.

### `?`와 `�`는 다른 문제다

> **[추가]** 원문은 깨진 결과를 한 덩어리로 다루는데, 사실 **깨지는 단계가 다르고 복구 가능성도 다르다.** 실무에서 원인을 찾을 때 이 구분이 제일 중요하다.

**물음표 `?`는 인코딩 단계에서 이미 잃어버린 것이다.**

`가`를 ASCII로 인코딩하면 `[63]`이 나온다. 63은 물음표(`?`)의 ASCII 코드다. ASCII 표에 한글이 없으니 "모르는 글자"를 물음표로 바꿔 저장한 것이다. 이 시점에 원본 정보가 사라졌다. **어떤 문자 집합으로 디코딩해도 복구할 수 없다.**

**`�`는 디코딩 단계의 실패다.**

바이트는 멀쩡히 남아 있는데 읽는 표가 달라서 해석을 못 한 것이다. `가`를 EUC-KR로 인코딩한 `[0xB0, 0xA1]`은 UTF-8 입장에서 유효하지 않은 바이트 조합이라 대체 문자(U+FFFD)를 찍는다. **원본 바이트가 살아 있으므로 올바른 문자 집합으로 다시 읽으면 복구된다.**

| 증상 | 깨진 단계 | 복구 |
| --- | --- | --- |
| `???` | 인코딩 (표에 문자가 없음) | ❌ 불가능 |
| `���` | 디코딩 (표가 다름) | ⭕ 가능 |
| `ê°€` 같은 이상한 글자 | 디코딩 (한 바이트씩 잘못 읽음) | ⭕ 가능 |

마지막 경우는 UTF-8 바이트를 ISO-8859-1로 읽었을 때 나온다. ISO-8859-1은 바이트 하나를 문자 하나에 1:1로 대응시키기 때문에 **어떤 바이트든 에러 없이 읽어버린다.** 그래서 대체 문자도 안 나오고 엉뚱한 글자가 나온다.

이 성질을 역으로 쓰면 복구가 된다.

```java
// UTF-8 로 저장된 걸 ISO-8859-1 로 잘못 읽어서 깨진 문자열
String broken = "ê°€";
String fixed = new String(broken.getBytes(StandardCharsets.ISO_8859_1),
                          StandardCharsets.UTF_8);
// 가
```

ISO-8859-1로 되돌려서 원래 바이트를 꺼낸 다음, UTF-8로 다시 읽는다. 레거시 시스템에서 한글이 깨져 넘어올 때 자주 쓰는 방법이다.

## UTF-8은 어떻게 길이를 구분할까

가변 길이인데 어디까지가 한 글자인지 어떻게 알까. 첫 바이트에 **몇 바이트짜리인지를 적어둔다.**

| 패턴 | 의미 |
| --- | --- |
| `0xxxxxxx` | 1바이트 문자 |
| `110xxxxx` | 2바이트 문자의 시작 |
| `1110xxxx` | 3바이트 문자의 시작 |
| `11110xxx` | 4바이트 문자의 시작 |
| `10xxxxxx` | 앞 문자에 이어지는 바이트 |

실제로 `가`의 UTF-8 바이트를 확인해보면 딱 맞는다.

```
가 = [0xEA, 0xB0, 0x80]

0xEA = 1110 1010   ← 1110 으로 시작 = 3바이트 문자
0xB0 = 1011 0000   ← 10 으로 시작 = 이어지는 바이트
0x80 = 1000 0000   ← 10 으로 시작 = 이어지는 바이트
```

> **[추가]** 이 패턴이 단순히 길이 표시용만은 아니다. UTF-8이 UTF-16을 밀어내고 표준이 된 이유가 여기에 있다.
>
> - **ASCII 바이트(0~127)가 다른 문자의 일부로 절대 등장하지 않는다.** 다중 바이트 문자의 모든 바이트는 최상위 비트가 1이기 때문이다. 그래서 기존 ASCII 기반 코드가 UTF-8 문자열을 만나도 깨지지 않는다.
> - **아무 데서나 읽기 시작해도 문자 경계를 찾을 수 있다.** `10`으로 시작하는 바이트를 만나면 "여긴 중간이구나" 하고 앞으로 되돌아가면 된다. 파일 중간부터 읽거나 네트워크로 쪼개져 들어올 때 유용하다.

## 한글이 깨지는 이유

원문이 정리한 두 가지가 정확하다.

1. EUC-KR(MS949)과 UTF-8은 **서로 호환되지 않는다.** 한쪽으로 인코딩하고 다른 쪽으로 디코딩하면 깨진다.
2. 한글을 지원하지 않는 문자 집합(ISO-8859-1 등)으로 디코딩하면 깨진다.

> **[추가]** 실제로 깨졌을 때 어디를 봐야 하는지도 정리해두면 쓸모가 있다. 텍스트가 거쳐 가는 길목마다 문자 집합 설정이 하나씩 있고, 그중 하나만 어긋나도 깨진다.
>
> | 길목 | 확인할 것 |
> | --- | --- |
> | 소스 파일 | 에디터 저장 인코딩, 빌드 도구의 `encoding` 설정 |
> | 파일 입출력 | `getBytes()` / `new String()`에 charset을 넘겼는지 |
> | JVM | `file.encoding` (Java 17 이하) |
> | 콘솔 | 터미널 인코딩, `stdout.encoding` |
> | 웹 | 응답 헤더 `Content-Type`, HTML `<meta charset>` |
> | DB | 커넥션 URL의 인코딩 파라미터, 테이블/컬럼 캐릭터셋 |
>
> 그리고 앞에서 정리한 대로, **`?`가 보이면 저장할 때 이미 망가진 것**이고 **`�`나 이상한 글자가 보이면 읽을 때 망가진 것**이다. 전자는 데이터를 다시 만들어야 하고, 후자는 읽는 쪽만 고치면 된다.

## 원문에서 고칠 곳

| 위치 | 내용 |
| --- | --- |
| 음수 표현 | 부호-크기가 아니라 **2의 보수** |
| 유니코드 소제목 | "전세계 **문잡** 집합" → **문자** |
| UTF-16 4바이트 | "42억 가지" → 유니코드 전체가 **약 111만 개** |
| UTF-8 결론 | `** 최신은...**` 별표 뒤 공백 때문에 굵게 안 됨 |
| 디코딩 예제 주석 | "MS_949가 EUC_KR을 받아서" → **MS949가 EUC-KR의 상위 집합** |

덧붙이면 좋은 것들은 이 정도였다. 자바 `byte`가 부호 있는 타입이라 바이트가 음수로 출력되는 이유, MS949와 EUC-KR의 포함 관계, Java 18부터 기본 인코딩이 UTF-8로 바뀐 것, `?`와 `�`의 차이, UTF-16 서로게이트 페어.

## 최종 정리

문자 저장의 전부를 한 문장으로 줄이면 이렇다.

> **문자는 표를 보고 숫자로 바뀌어 저장된다. 어떤 표로 바꿨는지 모르면 다시 읽을 수 없다.**

| 문자 집합 | 영문 | 한글 | ASCII 호환 | 비고 |
| --- | --- | --- | --- | --- |
| ASCII | 1byte | ❌ | — | 128자 |
| ISO-8859-1 | 1byte | ❌ | ⭕ | 서유럽 |
| EUC-KR | 1byte | 2byte | ⭕ | 완성형 2350자 |
| MS949 | 1byte | 2byte | ⭕ | EUC-KR 확장, 한글 전체 |
| UTF-16 | 2byte | 2byte | ❌ | 자바 `char`의 내부 표현 |
| UTF-8 | **1byte** | 3byte | ⭕ | **사실상 표준** |

실무에서 기억할 건 세 가지다.

- **문자 집합은 항상 명시한다.** `getBytes()`, `new String(bytes)`, 파일 입출력 전부. 기본값에 기대면 환경이 바뀔 때 깨진다.
- **`?`는 저장할 때 망가진 것이고, `�`는 읽을 때 망가진 것이다.** 전자는 복구가 안 되고 후자는 된다.
- **특별한 이유가 없으면 UTF-8.** 한글이 3바이트라 손해 보는 것 같아도, 호환성이 그 손해를 덮고도 남는다.
