# 한글은 왜 깨질까 — 문자 인코딩 정리

로컬에서는 멀쩡하던 한글이 서버에 올리자마자 `???`로 바뀌는 일. 안 겪어본 사람이 드물 것 같다.

보통은 어딘가에 `UTF-8`을 적어 넣으면 해결된다. 문제는 **왜 그게 해결책인지 모른 채로 넘어간다는 것**이다. 그러면 다음에 비슷한 증상이 나와도 또 검색하게 된다.

이 글은 그 아래를 한 번 파본 기록이다. 컴퓨터가 문자를 어떻게 저장하는지부터, 자바에서 바이트가 음수로 찍히는 이유, `?`와 `�`가 어떻게 다른지까지.

---

## 컴퓨터는 숫자만 안다

메모리는 결국 전구 더미다. 전기가 흐르면 1, 안 흐르면 0. 전구 하나가 1비트고, 8개를 묶으면 1바이트다. 비트가 N개면 2^N 가지를 표현할 수 있으니 1바이트는 256가지다.

숫자는 간단하다. 10진수 100은 2진수 `1100100`으로 바꿔서 넣으면 끝이다.

문제는 문자다. **`A`를 2진수로 바꾸는 수학 공식 같은 건 없다.**

그래서 사람들이 택한 방법은 의외로 단순했다. 표를 하나 만들고 문자마다 번호를 붙이는 것이다.

- `A`를 표에서 찾아 65로 바꿔 저장 → **인코딩**
- 65를 표에서 찾아 `A`로 되돌려 출력 → **디코딩**

이 표를 문자 집합(charset)이라고 부른다. 한글이 깨진다는 건 **저장할 때 본 표와 읽을 때 본 표가 다르다**는 뜻이다. 딱 그게 전부다.

---

## 표가 늘어난 역사

### ASCII

7비트, 128자. 영어 알파벳과 숫자, 기호 몇 개. 미국에서 컴퓨터를 쓰던 시절엔 이걸로 충분했다.

### ISO-8859-1

서유럽에서 컴퓨터를 쓰기 시작하니 128칸이 모자랐다. 1비트를 더 붙여 8비트, 256가지로 늘렸다. 앞의 0~127은 ASCII를 그대로 두고 뒤에 서유럽 문자를 채웠다. 그래서 **ASCII와 호환된다.** 이 "앞부분은 그대로 둔다"는 전략이 이후에도 계속 반복된다.

### EUC-KR

한글은 조합 가능한 글자가 1만 자가 넘는다. 256칸에 들어갈 리가 없다. 그래서 **2바이트**를 쓴다. 2바이트면 65536가지니까 넉넉하다.

다만 EUC-KR은 그중에서도 자주 쓰는 완성형 한글 **2350자만** 담았다. 당시 기준으로는 합리적인 선택이었지만, 이 선택이 나중에 "뷁"같은 글자를 못 쓰는 문제로 돌아온다.

영어는 1바이트, 한글은 2바이트다. ASCII 영역을 그대로 물려받았기 때문이다.

### MS949

마이크로소프트가 EUC-KR에 빠진 한글을 전부 채워 넣은 확장판이다. 11172자 전부가 들어 있다.

여기서 기억할 관계가 하나 있다.

```
EUC-KR ⊂ MS949
```

**EUC-KR로 저장한 건 MS949로 읽을 수 있지만, 반대는 안 된다.** 뒤의 예제에서 이 비대칭이 그대로 드러난다.

### 유니코드

EUC-KR의 근본적인 한계는 명확하다. **그 표가 설치되지 않은 컴퓨터에서는 한글 문서를 못 연다.** 나라마다 자기 표를 만들었으니 문서를 주고받을 수가 없었다.

그래서 나온 게 "세상의 모든 문자를 표 하나에 담자"는 유니코드다. 그리고 이걸 실제 바이트로 어떻게 저장할지가 UTF-16과 UTF-8이다.

---

## UTF-16과 UTF-8

### UTF-16

기본 다국어는 2바이트로 표현한다. 영어, 유럽어, 한국어, 중국어, 일본어가 전부 2바이트다. 이모지나 고대 문자 같은 나머지는 4바이트를 쓴다.

초반에는 UTF-16이 더 인기였다. 그런데 치명적인 약점이 있다.

```java
"A".getBytes(StandardCharsets.UTF_16BE);   // [0, 65] — 2바이트
```

**`A` 하나에도 2바이트를 쓰고, ASCII와 호환되지 않는다.** 웹 문서의 대부분이 영문인데 용량이 두 배가 되고, 기존 ASCII 기반 프로그램이 읽지 못한다.

자바는 언어 내부적으로 UTF-16을 쓴다. **`char`가 2바이트인 이유**가 이것이다.

> 여기서 자바 개발자가 실제로 밟는 지뢰가 하나 있다. `char` 하나는 2바이트인데 이모지는 4바이트라서, **char 두 개로 쪼개져 저장된다**(서로게이트 페어).
>
> ```java
> "가".length();    // 1
> "😀".length();    // 2   ← 글자는 하나인데
> ```
>
> 글자 수를 세거나 문자열을 자를 때 버그가 된다. 실제 글자 수는 `codePointCount()`로 세야 한다.

### UTF-8

1~4바이트를 쓰는 가변 길이 인코딩이다.

| 바이트 수 | 담는 문자 |
| --- | --- |
| 1 | ASCII 영문, 기본 라틴 문자 |
| 2 | 그리스어, 히브리어, 라틴 확장 |
| 3 | **한글**, 한자, 일본어 |
| 4 | 이모지, 고대 문자 |

한글이 3바이트라 EUC-KR이나 UTF-16보다 용량을 더 쓴다. 손해처럼 보이는데, **ASCII를 1바이트로 그대로 호환한다**는 장점이 이걸 압도했다. 영문이 대부분인 웹에서 이건 결정적이었고, 결국 사실상의 표준이 됐다.

## 자바에서 직접 확인해보기

```java
private static void encoding(String text, Charset charset) {
    byte[] bytes = text.getBytes(charset);
    System.out.printf("%s -> [%s] 인코딩 -> %s %sbyte\n",
            text, charset, Arrays.toString(bytes), bytes.length);
}
```

```text
A -> [US-ASCII]      인코딩 -> [65]              1byte
A -> [ISO-8859-1]    인코딩 -> [65]              1byte
A -> [EUC-KR]        인코딩 -> [65]              1byte
A -> [UTF-8]         인코딩 -> [65]              1byte
A -> [UTF-16BE]      인코딩 -> [0, 65]           2byte

가 -> [EUC-KR]        인코딩 -> [-80, -95]        2byte
가 -> [x-windows-949] 인코딩 -> [-80, -95]        2byte
가 -> [UTF-8]         인코딩 -> [-22, -80, -128]  3byte
가 -> [UTF-16BE]      인코딩 -> [-84, 0]          2byte
```

영문 `A`는 UTF-16만 빼고 전부 65다. "ASCII 호환"이 이런 뜻이다.

> 참고로 `Charset.forName("MS_949")`로 조회했는데 출력에는 `x-windows-949`로 찍힌다. 우리가 쓴 이름은 **별칭**이고 정식 이름이 따로 있기 때문이다. `EUC_KR`도 마찬가지로 정식 이름은 `EUC-KR`이다.

### 왜 음수가 나올까

처음 이 결과를 보면 여기서 멈추게 된다. `가`가 `-80, -95`라니.

EUC-KR에서 `가`의 실제 코드는 `0xB0 0xA1`, 10진수로 **176과 161**이다. 음수일 이유가 없다.

이유는 **자바의 `byte`가 부호 있는 타입**이라서다. 표현 범위가 -128 ~ 127이니 176을 담을 수 없다.

```
176을 8비트로 쓰면  →  1011 0000
맨 앞 비트가 1      →  2의 보수로 해석하면 음수
176 - 256          →  -80
```

비트 패턴은 그대로고 **해석만 달라진 것**이다. 메모리에 저장된 값은 여전히 `0xB0`다. 161도 161 - 256 = -95가 된다.

원래 값을 보고 싶으면 부호를 지워주면 된다.

```java
for (byte b : "가".getBytes(EUC_KR)) {
    System.out.printf("%d (0x%02X)%n", b & 0xFF, b);
}
// 176 (0xB0)
// 161 (0xA1)
```

`& 0xFF`는 하위 8비트만 남기고 int로 올리는 관용구다. 바이트를 다루다 보면 계속 쓰게 된다.

### UTF_16과 UTF_16BE는 다르다

예제에서 `UTF_16`이 아니라 `UTF_16BE`를 쓰는 데는 이유가 있다.

```java
"A".getBytes(StandardCharsets.UTF_16);     // [-2, -1, 0, 65]  ← 4바이트
"A".getBytes(StandardCharsets.UTF_16BE);   // [0, 65]          ← 2바이트
```

앞의 `-2, -1`(0xFE 0xFF)은 **BOM(Byte Order Mark)**이다. 2바이트를 큰 단위부터 쓸지(BE) 작은 단위부터 쓸지(LE) 알려주는 표식이다. `UTF_16`은 이 표식을 붙이고, `UTF_16BE`는 "무조건 BE"로 정해두고 생략한다.

## 표가 어긋나면 어떻게 되나

인코딩할 때와 디코딩할 때 다른 표를 쓰면 무슨 일이 생기는지 보자.

```text
A  -> [US-ASCII] 인코딩 -> [65] -> [UTF-16BE] 디코딩 -> �
가 -> [US-ASCII] 인코딩 -> [63] -> [US-ASCII] 디코딩 -> ?
뷁 -> [EUC-KR]   인코딩 -> [63] -> [EUC-KR]   디코딩 -> ?
뷁 -> [MS949]    인코딩 -> [-108, -18] -> [EUC-KR] 디코딩 -> ��
가 -> [EUC-KR]   인코딩 -> [-80, -95]  -> [UTF-8]  디코딩 -> ��
가 -> [EUC-KR]   인코딩 -> [-80, -95]  -> [MS949]  디코딩 -> 가   ← 성공
```

마지막 줄만 성공했다. MS949가 EUC-KR의 확장판이라 EUC-KR이 만든 바이트를 그대로 읽을 수 있기 때문이다. 반대로 `뷁`을 MS949로 저장하고 EUC-KR로 읽으면 실패한다. **한쪽 방향으로만 호환된다.**

그리고 `뷁`이 EUC-KR에서 `[63]` 한 바이트로 나온 게 눈에 띈다. 완성형 2350자에 없는 글자라서다.

### `?`와 `�`는 완전히 다른 문제다

이 구분이 이 글에서 제일 쓸모 있는 부분이라고 생각한다. 둘 다 "깨졌다"고 뭉뚱그리기 쉬운데, **깨진 단계가 다르고 복구 가능성도 다르다.**

**물음표 `?`는 저장할 때 이미 잃어버린 것이다.**

`가`를 ASCII로 인코딩하면 `[63]`이 나온다. 63은 물음표의 ASCII 코드다. ASCII 표에 한글이 없으니 "모르는 글자"를 물음표로 바꿔서 저장해버린 것이다. 이 순간 원본 정보가 사라졌다. **어떤 표로 읽어도 복구할 수 없다.**

**`�`는 읽을 때의 실패다.**

바이트는 멀쩡히 남아 있는데 읽는 표가 달라서 해석을 못 한 것이다. `[0xB0, 0xA1]`은 UTF-8 입장에서 유효하지 않은 조합이라 대체 문자(U+FFFD)를 찍는다. **원본 바이트가 살아 있으니 올바른 표로 다시 읽으면 복구된다.**

| 증상 | 깨진 단계 | 복구 |
| --- | --- | --- |
| `???` | 인코딩 (표에 문자가 없음) | ❌ 불가능 |
| `���` | 디코딩 (표가 다름) | ⭕ 가능 |
| `ê°€` 같은 이상한 글자 | 디코딩 (한 바이트씩 잘못 읽음) | ⭕ 가능 |

마지막 경우는 UTF-8 바이트를 ISO-8859-1로 읽었을 때 나온다. ISO-8859-1은 바이트 하나를 문자 하나에 1:1로 대응시켜서 **어떤 바이트든 에러 없이 읽어버린다.** 그래서 대체 문자도 안 뜨고 엉뚱한 글자가 나온다.

이 성질을 거꾸로 쓰면 복구가 된다.

```java
// UTF-8 로 저장된 걸 ISO-8859-1 로 잘못 읽어서 깨진 문자열
String broken = "ê°€";
String fixed = new String(broken.getBytes(StandardCharsets.ISO_8859_1),
                          StandardCharsets.UTF_8);
// 가
```

ISO-8859-1로 되돌려 원래 바이트를 꺼낸 다음 UTF-8로 다시 읽는 것이다. 레거시 시스템에서 깨진 한글이 넘어올 때 꽤 쓰인다.

## UTF-8은 어떻게 길이를 구분할까

가변 길이인데 어디까지가 한 글자인지 어떻게 알까. 답은 단순하다. **첫 바이트에 몇 바이트짜리인지 적어둔다.**

| 패턴 | 의미 |
| --- | --- |
| `0xxxxxxx` | 1바이트 문자 |
| `110xxxxx` | 2바이트 문자의 시작 |
| `1110xxxx` | 3바이트 문자의 시작 |
| `11110xxx` | 4바이트 문자의 시작 |
| `10xxxxxx` | 앞 문자에 이어지는 바이트 |

`가`의 UTF-8 바이트로 확인해보면 딱 맞는다.

```
가 = [0xEA, 0xB0, 0x80]

0xEA = 1110 1010   ← 1110 으로 시작 = 3바이트 문자
0xB0 = 1011 0000   ← 10 으로 시작 = 이어지는 바이트
0x80 = 1000 0000   ← 10 으로 시작 = 이어지는 바이트
```

이 패턴이 단순히 길이 표시용만은 아니다. UTF-8이 표준이 된 진짜 이유가 여기 있다.

- **ASCII 바이트(0~127)가 다른 문자의 일부로 절대 등장하지 않는다.** 다중 바이트 문자의 모든 바이트는 최상위 비트가 1이기 때문이다. 기존 ASCII 기반 코드가 UTF-8 문자열을 만나도 안 깨진다.
- **아무 데서나 읽기 시작해도 문자 경계를 찾을 수 있다.** `10`으로 시작하는 바이트를 만나면 "여긴 중간이구나" 하고 앞으로 되돌아가면 된다. 파일 중간부터 읽거나 네트워크로 쪼개져 들어올 때 유용하다.

## 기본 문자 집합에 기대지 말 것

```java
text.getBytes();           // 어떤 표를 쓸까?
new String(bytes);         // 어떤 표로 읽을까?
Files.readString(path);
```

문자 집합을 안 주면 **시스템 기본값**을 쓴다. 그리고 이게 "내 PC에서는 되는데요"의 주범이다.

**Java 18부터 기본 문자 집합이 UTF-8로 통일됐다.** 그전에는 OS와 로캘을 따라갔다. 한국어 윈도우에서 개발하면 MS949, 리눅스 서버는 UTF-8. 똑같은 코드가 환경에 따라 다르게 동작했다.

Java 17 이하를 쓴다면 실행 옵션으로 못을 박아두는 게 안전하다.

```
java -Dfile.encoding=UTF-8 -jar app.jar
```

그리고 Java 18 이상이어도 **콘솔 출력은 별개**다. `System.out`은 콘솔 인코딩을 따라가기 때문에, 기본 charset이 UTF-8인데도 윈도우 터미널에서는 깨질 수 있다.

결론은 하나다.

```java
// 환경에 따라 달라진다
new String(bytes);
text.getBytes();

// 어디서 돌려도 같다
new String(bytes, StandardCharsets.UTF_8);
text.getBytes(StandardCharsets.UTF_8);
```

## 깨졌을 때 어디를 봐야 하나

텍스트가 거쳐 가는 길목마다 문자 집합 설정이 하나씩 있다. 그중 하나만 어긋나도 깨진다.

| 길목 | 확인할 것 |
| --- | --- |
| 소스 파일 | 에디터 저장 인코딩, 빌드 도구의 `encoding` 설정 |
| 파일 입출력 | `getBytes()` / `new String()`에 charset을 넘겼는지 |
| JVM | `file.encoding` (Java 17 이하) |
| 콘솔 | 터미널 인코딩 |
| 웹 | 응답 헤더 `Content-Type`, HTML `<meta charset>` |
| DB | 커넥션 URL의 인코딩 파라미터, 테이블/컬럼 캐릭터셋 |

그리고 앞에서 정리한 구분이 여기서 시간을 아껴준다.

- **`?`가 보이면 저장할 때 이미 망가진 것** → 데이터를 다시 만들어야 한다
- **`�`나 이상한 글자가 보이면 읽을 때 망가진 것** → 읽는 쪽 설정만 고치면 된다

증상만 보고 어느 쪽인지 알 수 있으니, 엉뚱한 곳을 뒤지지 않아도 된다.

## 최종 정리

전부를 한 문장으로 줄이면 이렇다.

> **문자는 표를 보고 숫자로 바뀌어 저장된다. 어떤 표로 바꿨는지 모르면 다시 읽을 수 없다.**

| 문자 집합 | 영문 | 한글 | ASCII 호환 | 비고 |
| --- | --- | --- | --- | --- |
| ASCII | 1byte | ❌ | — | 128자 |
| ISO-8859-1 | 1byte | ❌ | ⭕ | 서유럽 |
| EUC-KR | 1byte | 2byte | ⭕ | 완성형 2350자 |
| MS949 | 1byte | 2byte | ⭕ | EUC-KR 확장, 한글 전체 |
| UTF-16 | 2byte | 2byte | ❌ | 자바 `char`의 내부 표현 |
| UTF-8 | **1byte** | 3byte | ⭕ | **사실상 표준** |

기억할 건 세 가지다.

- **문자 집합은 항상 명시한다.** 기본값에 기대는 순간 환경이 바뀔 때 깨진다.
- **`?`는 저장할 때, `�`는 읽을 때 망가진 것이다.** 전자는 복구가 안 되고 후자는 된다.
- **특별한 이유가 없으면 UTF-8.** 한글이 3바이트라 손해 보는 것 같아도 호환성이 그 손해를 덮고도 남는다.
