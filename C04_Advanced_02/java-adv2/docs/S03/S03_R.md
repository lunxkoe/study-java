# 자바 I/O 기본 정리

원문을 따라가면서 고칠 부분과 덧붙일 내용을 표시했다.
**[수정]** 은 사실과 다른 부분, **[보충]** 은 틀리진 않았지만 조건이 필요한 부분, **[추가]** 는 원문에 없지만 알아두면 좋은 내용이다.

---

## 스트림의 기본

자바 프로세스가 가진 데이터를 파일로 내보내려면 **출력 스트림**, 파일에 있는 데이터를 가져오려면 **입력 스트림**을 쓴다. 각 스트림은 **단방향**이다. 하나로 읽고 쓰는 게 아니라 방향마다 따로 만든다.

```java
FileOutputStream fos = new FileOutputStream("temp/hello.dat");
fos.write(65);
fos.write(66);
fos.write(67);
fos.close();

FileInputStream fis = new FileInputStream("temp/hello.dat");
System.out.println(fis.read());  // 65
System.out.println(fis.read());  // 66
System.out.println(fis.read());  // 67
System.out.println(fis.read());  // -1  ← 파일의 끝(EOF)
fis.close();
```

몇 가지 짚어둘 것.

- `FileOutputStream`은 파일이 없으면 만들어주지만 **폴더는 안 만든다.** `temp` 폴더는 미리 있어야 한다.
- `write()`와 `read()`는 **byte 단위**로 동작한다.
- 읽을 게 없으면 `-1`을 반환한다.
- `close()`는 빼먹으면 안 된다. 자바 객체는 GC가 알아서 치우지만 **파일 핸들 같은 외부 자원은 직접 닫아야 한다.**

> **[보충]** 원문 예제들은 전부 `close()`를 직접 호출한다. 흐름을 보여주기엔 괜찮지만, 중간에 예외가 나면 `close()`까지 도달하지 못한다. 자원 누수다.
>
> `FileOutputStream`과 `FileInputStream`은 `AutoCloseable`이니 try-with-resources를 쓰면 된다.
>
> ```java
> try (FileOutputStream fos = new FileOutputStream("temp/hello.dat")) {
>     fos.write(65);
> }   // 예외가 나든 말든 닫힌다
> ```
>
> 뒤에 나올 `BufferedOutputStream`의 "닫는 순서" 문제도 이걸 쓰면 상당 부분 사라진다.

### 숫자를 썼는데 파일에는 ABC

`65, 66, 67`을 저장했는데 텍스트 편집기로 열면 `ABC`로 보인다.

에디터가 파일을 열 때 **UTF-8이든 MS949든 어떤 문자 집합으로 디코딩해서 보여주기 때문**이다. 앞 글에서 정리한 그대로다. 파일에 들어 있는 건 여전히 숫자 65, 66, 67이고, 에디터가 ASCII 표를 보고 A, B, C로 바꿔 보여주는 것뿐이다.

바꿔 말하면 **파일에는 "문자"가 저장되지 않는다.** 바이트만 저장되고, 문자로 보이는 건 읽는 쪽의 해석이다.

## read()가 int를 반환하는 이유

`read()`는 바이트 하나를 읽는데 반환 타입이 `byte`가 아니라 `int`다. 원문 설명이 정확하다.

- 자바의 `byte`는 **-128 ~ 127**, 256가지를 전부 값 표현에 쓴다.
- 그래서 "파일 끝"을 나타낼 여분의 값이 없다.
- `int`로 올리면 **0 ~ 255**로 바이트 값을 부호 없이 표현하고, 거기에 **-1**을 EOF 신호로 쓸 수 있다.

> **[추가]** 앞 글에서 `"가".getBytes(EUC_KR)`이 `[-80, -95]`로 나오는 걸 봤는데, 정확히 그 문제를 여기서 피해 간 것이다.
>
> `read()`는 내부적으로 `& 0xFF`를 해서 돌려준다. 실제로 원문이 인용한 `BufferedInputStream.read()` 코드 마지막 줄이 그렇다.
>
> ```java
> return getBufIfOpen()[pos++] & 0xff;   // 버퍼의 byte 를 0~255 로 올려서 반환
> ```
>
> 그래서 `read()`로 받은 값은 항상 0~255다. 다시 바이트로 쓸 때만 `(byte) v`로 캐스팅한다.

`write(int)`도 같은 맥락인데, 이쪽은 의미가 조금 다르다.

```java
fos.write(-1);   // EOF 가 아니다. 그냥 바이트 0xFF 를 쓰는 것
```

`write()`는 넘긴 int의 **하위 8비트만** 쓴다. `-1`을 넘기면 `0xFF`가 저장될 뿐 특별한 의미는 없다. 원문이 이걸 짚어둔 게 좋다.

## byte[]로 읽고 쓰기

하나씩 말고 배열로 주고받을 수 있다.

```java
byte[] input = {65, 66, 67};
fos.write(input);

byte[] buffer = new byte[10];
int readCount = fis.read(buffer, 0, 10);
System.out.println("readCount = " + readCount);         // 3
System.out.println(Arrays.toString(buffer));            // [65, 66, 67, 0, 0, 0, 0, 0, 0, 0]
```

`read(byte[], offset, length)`의 인자는 각각 "읽은 데이터를 담을 배열", "배열에서 쓰기 시작할 위치", "읽어올 최대 길이"다. 반환값은 **실제로 읽은 바이트 수**고, 더 읽을 게 없으면 -1이다.

출력의 뒷부분이 0으로 채워진 건 배열을 10칸으로 만들었는데 3칸만 채웠기 때문이다.

> **[추가]** 여기서 실무에서 꼭 걸리는 함정이 하나 있다. 원문에는 없는 내용이다.
>
> **`read(byte[])`는 배열을 가득 채워준다는 보장이 없다.** 파일에서는 대개 요청한 만큼 읽히지만, **소켓에서는 1바이트만 읽고 돌아올 수 있다.** 네트워크 패킷이 아직 다 도착하지 않았으면 있는 만큼만 주고 반환한다.
>
> 그래서 이런 코드는 틀렸다.
>
> ```java
> byte[] buffer = new byte[1024];
> is.read(buffer);                        // 반환값을 안 본다
> String s = new String(buffer, UTF_8);   // 뒤쪽 0 까지 문자열에 들어간다
> ```
>
> 반환값을 반드시 확인하고, 읽은 만큼만 써야 한다.
>
> ```java
> int n;
> while ((n = is.read(buffer)) != -1) {
>     process(buffer, 0, n);              // 0 ~ n 까지만
> }
> ```
>
> 예제 출력의 `[65, 66, 67, 0, 0, ...]`에서 뒤의 0들이 바로 이 이야기다. 배열 전체를 쓰면 안 된다.

### 전부 한 번에 읽기

```java
byte[] readBytes = fis.readAllBytes();   // [65, 66, 67]
```

편한데 메모리를 통제할 수 없다. 원문 정리가 정확하다.

| | `read(byte[], off, len)` | `readAllBytes()` |
| --- | --- | --- |
| 메모리 사용 | 버퍼 크기만큼만 | 파일 크기만큼 전부 |
| 대용량 파일 | 조각내어 처리 가능 | `OutOfMemoryError` 위험 |
| 코드 | 루프 필요 | 한 줄 |

100MB 파일을 1MB 버퍼로 나눠 읽으면 메모리는 1MB만 쓴다.

## InputStream, OutputStream

파일, 네트워크, 콘솔이 각각 다른 방식으로 데이터를 주고받으면 쓰는 쪽이 피곤하다. 그래서 자바는 `InputStream`, `OutputStream`이라는 공통 타입을 두고 그 아래에 구현체들을 뒀다.

> **[수정]** 원문 목록에 "InputStream - 인터페이스", "OutputStream - 인터페이스"라고 적혀 있다. 둘 다 **추상 클래스**다. 원문도 맨 아래 참고에서 "인터페이스가 아닌 추상 클래스"라고 정정하고 있어서 앞뒤가 안 맞는다.
>
> 추상 클래스인 이유는 일부 메서드에 실제 동작이 들어 있기 때문이다. `read(byte[])`는 `read()`를 반복 호출하는 기본 구현이 이미 들어 있어서, 구현체는 `read()` 하나만 만들어도 동작한다.

| | 구현체 | 주요 메서드 |
| --- | --- | --- |
| `InputStream` | `FileInputStream`, `ByteArrayInputStream`, 소켓의 입력 스트림 | `read()`, `read(byte[])`, `readAllBytes()` |
| `OutputStream` | `FileOutputStream`, `ByteArrayOutputStream`, 소켓의 출력 스트림 | `write(int)`, `write(byte[])` |

> **[수정]** 클래스 이름 띄어쓰기. "File InputStream" → `FileInputStream`, "Socket OutputStream" → 소켓에서 꺼내는 출력 스트림(별도 클래스 이름이 아니라 `socket.getOutputStream()`으로 얻는다)

추상화의 실질적인 이득은 이거다. **`InputStream`을 받는 메서드를 하나 만들어두면, 파일이든 메모리든 네트워크든 그대로 처리된다.**

```java
void process(InputStream in) { ... }

process(new FileInputStream("a.txt"));
process(new ByteArrayInputStream(bytes));
process(socket.getInputStream());
```

원문이 "일관성, 유연성, 확장성, 재사용성"을 나열했는데, 결국 이 한 줄이다.

### 메모리 스트림과 콘솔 스트림

```java
ByteArrayOutputStream baos = new ByteArrayOutputStream();
baos.write(input);
ByteArrayInputStream bais = new ByteArrayInputStream(baos.toByteArray());
```

메모리에 읽고 쓰는 스트림이다. 원문 말대로 실무에서 데이터를 메모리에 담을 거면 그냥 컬렉션을 쓰지 이걸 쓰지 않는다. **스트림을 받는 코드를 테스트할 때** 쓸모가 있다. 파일 없이 스트림을 만들어 넘길 수 있으니까.

```java
PrintStream printStream = System.out;
printStream.write("Hello!\n".getBytes(UTF_8));   // OutputStream 이 주는 기능
printStream.println("Print!");                    // PrintStream 이 더한 기능
```

우리가 늘 쓰던 `System.out`이 `PrintStream`이고, 이게 `OutputStream`의 자식이다.

> **[추가]** `println(String)`이 "String을 내부적으로 byte로 변환한다"는 원문 설명에 하나만 덧붙이면 좋다. **변환할 때 문자 집합이 필요하다.**
>
> 앞 글에서 "Java 18부터 기본 charset이 UTF-8인데도 윈도우 콘솔에서는 한글이 깨질 수 있다"고 했는데, 그 지점이 정확히 여기다. `System.out`은 파일 기본 charset이 아니라 **콘솔 인코딩**으로 변환한다.
>
> 그리고 `PrintStream`은 **`IOException`을 밖으로 던지지 않는다.** 내부에 에러 플래그만 세워두고 삼킨다. `System.out.println()`에 try-catch를 안 붙여도 되는 이유이자, 출력 실패를 눈치채지 못하는 이유이기도 하다. 확인하려면 `checkError()`를 봐야 한다.

## 1바이트씩 쓰면 얼마나 느린가

```java
for (int i = 0; i < FILE_SIZE; i++) {   // 10MB
    fos.write(1);
}
```

```text
쓰기: 28569ms
읽기: 19243ms
```

10MB 파일 하나에 28초다. 10MB는 10,485,760바이트니까 **1000만 번 넘게 `write()`를 호출**한 셈이다.

`write()`, `read()`를 호출할 때마다 **OS 시스템 콜**이 일어난다. 시스템 콜은 사용자 모드에서 커널 모드로 넘어갔다 오는 작업이라 그 자체로 비용이 있다. 이걸 1000만 번 하면 이런 숫자가 나온다.

원문의 참고가 중요하다. **실제로 디스크에 1바이트씩 긁는 건 아니다.** OS가 페이지 캐시에 모아뒀다가 알아서 몰아서 쓴다. 그러니까 느린 원인은 디스크가 아니라 **시스템 콜 호출 횟수**다. 줄여야 할 건 그쪽이다.

> **[수정]** 오타들. "FILE_**ZIE**" → `FILE_SIZE`, "1000만**법**" → 1000만 번, "1byte**식**" → 1byte씩, 섹션 제목 "파일 입**축**력" → 입출력

## 버퍼를 직접 만들어 쓰기

```java
byte[] buffer = new byte[BUFFERED_SIZE];   // 8KB
int bufferIndex = 0;
for (int i = 0; i < FILE_SIZE; i++) {
    buffer[bufferIndex++] = 1;

    if (bufferIndex == BUFFERED_SIZE) {    // 가득 차면 한 번에
        fos.write(buffer);
        bufferIndex = 0;
    }
}

if (bufferIndex > 0) {                     // 마지막 남은 것 처리
    fos.write(buffer, 0, bufferIndex);
}
```

```text
쓰기: 31ms   (28569ms → 약 921배)
읽기:  8ms   (19243ms → 약 2405배)
```

시스템 콜 횟수가 10,485,760번에서 1,280번으로 줄었다. `10,485,760 / 8192 = 1,280`이다.

마지막의 `if (bufferIndex > 0)` 처리를 빼먹으면 **파일 끝부분이 날아간다.** 버퍼가 딱 떨어지지 않는 경우가 대부분이라 실전에서 자주 나는 버그다.

> **[보충]** 읽기가 쓰기보다 유난히 빠른 건(8ms vs 31ms) 코드가 더 좋아서가 아니다. 방금 쓴 파일이라 **OS 페이지 캐시에 그대로 남아 있어서** 실제 디스크를 안 건드린 것이다.
>
> 이 실험의 숫자들은 "디스크가 얼마나 빠른가"가 아니라 **"시스템 콜을 몇 번 했는가"**를 보여주는 것으로 읽어야 한다.

> **[수정]** "디스크나 파일 시스템에서 읽고 쓰는 기본 단위가 보통 **4KBm 8KB**" → 4KB나 8KB. 그리고 "파일에 쓸 수 있는 **최대 용량**이 4, 8KB"라는 표현은 오해를 부른다. 한 번에 8KB까지만 쓸 수 있다는 뜻이 아니라, **OS와 디스크가 어차피 블록 단위로 나눠 처리하기 때문에** 버퍼를 그보다 크게 잡아도 체감 이득이 별로 없다는 뜻이다.

## BufferedOutputStream

버퍼를 직접 관리하는 건 번거롭다. 그걸 대신해주는 보조 스트림이 있다.

```java
FileOutputStream fos = new FileOutputStream(FILE_NAME);
BufferedOutputStream bos = new BufferedOutputStream(fos, BUFFERED_SIZE);

for (int i = 0; i < FILE_SIZE; i++) {
    bos.write(1);      // 코드는 1바이트씩 쓰던 때와 똑같다
}
bos.close();
```

```text
307ms
```

28초가 0.3초가 됐다. 코드는 처음과 거의 같은데.

동작은 단순하다.

```text
bos.write(1) 을 8192번  →  [ 내부 버퍼 8KB ]
                                 │ 가득 차면
                                 ▼
                     fos.write(byte[8192])  →  시스템 콜 1회
                                 │
                            버퍼 비우고 다시 채움
```

### 구조: 상속이 아니라 감싸기

> **[수정]** 원문이 구조를 이렇게 적어뒀다.
>
> ```
> OutputStream
>   └ FileOutputStream
>       └ BufferedOutputStream
> ```
>
> 들여쓰기 때문에 `BufferedOutputStream`이 `FileOutputStream`을 상속한 것처럼 보이는데, **그렇지 않다.** 실제 관계는 이렇다.

```text
[ 상속 관계 ]                        [ 실제 연결 ]

OutputStream                         BufferedOutputStream
  ├─ FileOutputStream                     │ out 필드로 참조
  └─ FilterOutputStream                   ▼
        └─ BufferedOutputStream      FileOutputStream
                                          │
                                          ▼
                                      시스템 콜
```

`BufferedOutputStream`은 `FilterOutputStream`을 상속받고, **생성자로 받은 `OutputStream`을 필드로 들고 있다가 위임한다.** 상속이 아니라 **합성**이다.

> **[추가]** 이 구조를 앞에서 본 적이 있다. 동시성 컬렉션 글의 `SyncProxyList`가 똑같았다. 같은 인터페이스를 구현하면서 원본을 필드로 들고 있다가, 자기 일(락 걸기 / 버퍼링)을 한 뒤 원본에게 넘긴다.
>
> 그래서 이렇게 여러 겹으로 쌓을 수 있다.
>
> ```java
> new BufferedOutputStream(new GZIPOutputStream(new FileOutputStream("a.gz")));
> ```
>
> 이 패턴을 데코레이터라고 부른다. `FilterOutputStream`이라는 이름의 "Filter"가 그 뜻이다.

원문의 **기본 스트림 / 보조 스트림** 구분이 이 이야기다. `FileOutputStream`처럼 혼자 쓸 수 있는 게 기본 스트림, `BufferedOutputStream`처럼 남을 감싸야만 의미가 있는 게 보조 스트림이다.

### 닫는 순서

버퍼에 데이터가 남은 채로 프로그램이 끝나면 그 데이터는 파일에 안 들어간다. 그래서 `flush()`가 필요하고, `close()`는 내부적으로 `flush()`를 먼저 부른다.

```text
bos.close()
   ├─ flush()          버퍼에 남은 데이터를 fos 로 밀어냄
   └─ fos.close()      감싸고 있던 스트림까지 닫음
```

**마지막에 연결한 스트림(`bos`)을 닫아야 한다.** `fos.close()`만 부르면 버퍼에 남은 데이터가 그대로 사라진다. 원문이 "심각한 문제"라고 한 게 과장이 아니다. 파일 끝이 잘려 있는데 에러도 안 난다.

> **[보충]** try-with-resources를 쓰면 이 순서를 신경 쓸 일이 줄어든다.
>
> ```java
> try (BufferedOutputStream bos =
>          new BufferedOutputStream(new FileOutputStream(FILE_NAME))) {
>     bos.write(1);
> }   // bos.close() → flush() → fos.close() 까지 연쇄
> ```
>
> 바깥쪽만 닫으면 안쪽까지 따라 닫힌다.

## BufferedInputStream과 동기화 비용

읽기도 같은 방식이다.

```java
BufferedInputStream bis = new BufferedInputStream(fis, BUFFERED_SIZE);
while (-1 != (data = bis.read())) { ... }
```

```text
272ms
```

원문이 인용한 소스가 동작을 그대로 보여준다.

```java
public synchronized int read() throws IOException {
    if (pos >= count) {                       // 버퍼가 비었으면
        fill();                                // fis.read(buf) 로 가득 채움 (시스템 콜)
        if (pos >= count)
            return -1;
    }
    return getBufIfOpen()[pos++] & 0xff;      // 버퍼에서 1바이트 꺼내기 (시스템 콜 없음)
}
```

버퍼가 살아 있는 동안에는 배열에서 값 하나 꺼내는 게 전부다.

### 왜 직접 만든 버퍼보다 느릴까

| | 직접 버퍼 | BufferedXxx |
| --- | --- | --- |
| 쓰기 | 31ms | 307ms |
| 읽기 | 8ms | 272ms |

원문의 답이 정확하다. **`synchronized` 때문이다.** 위 코드 첫 줄에 붙어 있다.

`BufferedXxx`는 처음부터 멀티스레드를 고려해 만들어졌다. 그래서 `read()`를 1000만 번 호출하면 **락을 1000만 번 걸고 푼다.** 싱글 스레드로 쓰는 상황에서는 순수한 낭비다. 그리고 동기화를 뺀 버전은 표준 라이브러리에 없다.

> **[추가]** 그런데 이 손해는 **1바이트씩 호출할 때의 이야기**다. 덩어리로 넘기면 거의 사라진다.
>
> ```java
> public synchronized void write(byte b[], int off, int len) throws IOException {
>     if (len >= buf.length) {
>         flushBuffer();
>         out.write(b, off, len);   // 버퍼를 아예 우회한다
>         return;
>     }
>     ...
> }
> ```
>
> 버퍼 크기보다 큰 배열을 넘기면 **버퍼에 담지 않고 바로 아래 스트림으로 보낸다.** 락도 호출당 한 번만 걸린다. 그래서 실무에서 `bos.write(byte[])`로 쓰는 경우라면 `BufferedOutputStream`을 써도 성능 차이가 거의 없다.
>
> 즉 "`BufferedXxx`는 10배 느리다"가 아니라 **"1바이트씩 호출하면 10배 느리다"**가 맞다.

> **[보충]** 기본 버퍼 크기를 원문은 "4KB, 8KB"라고 적었는데, `BufferedInputStream`과 `BufferedOutputStream` 둘 다 **8192바이트(8KB)**로 고정되어 있다.

## 한 번에 쓰고 한 번에 읽기

```java
byte[] buffer = new byte[FILE_SIZE];   // 10MB 배열
for (int i = 0; i < FILE_SIZE; i++) buffer[i] = 1;
fos.write(buffer);
```

```text
쓰기: 26ms   (8KB 버퍼: 31ms)
읽기: 11ms   (8KB 버퍼:  8ms)
```

8KB 버퍼와 오차 범위다. **한 번에 다 넘긴다고 극적으로 빨라지지 않는다.** OS와 디스크가 어차피 4~8KB 블록 단위로 나눠 처리하기 때문에, 시스템 콜을 1280번에서 1번으로 줄여도 더 얻을 게 별로 없다.

대신 메모리는 10MB를 통째로 쓴다. 파일이 작을 때만 쓸 수 있는 방법이다.

> **[수정]** "나**우**어 처리해야 한다면" → 나누어

## 원문에서 고칠 곳

| 위치 | 내용 |
| --- | --- |
| InputStream/OutputStream 소개 | "인터페이스" → **추상 클래스** (원문 맨 아래 참고와 모순) |
| BufferedOutputStream 구조 | 상속처럼 그려져 있지만 **합성**. `FilterOutputStream`을 상속하고 대상 스트림은 필드로 들고 있다 |
| 기본 버퍼 크기 | "4KB, 8KB" → **8192바이트로 고정** |
| 버퍼 크기 한계 설명 | "파일에 쓸 수 있는 최대 용량이 4, 8KB" → **OS·디스크가 블록 단위로 처리하기 때문** |
| 클래스 이름 | "File InputStream" → `FileInputStream` |
| 오타 | FILE_**ZIE** / 1000만**법** / 1byte**식** / 4KB**m** 8KB / 입**축**력 / 데이**틀** / 불**현**할 / 모**다**서 / 나**우**어 |

덧붙이면 좋은 것들은 이 정도였다. try-with-resources, `read(byte[])`가 요청한 만큼 안 읽을 수 있다는 것, `read()`가 `& 0xFF`를 한다는 것, `PrintStream`의 인코딩과 예외 삼킴, 읽기가 빠른 건 페이지 캐시 때문이라는 것, 그리고 `write(byte[])`가 버퍼를 우회한다는 것.

## 최종 정리

이번 내용을 한 문장으로 줄이면 이렇다.

> **스트림은 바이트를 한 방향으로 흘려보내는 통로다. 느린 이유는 디스크가 아니라 시스템 콜 횟수이고, 해결책은 모아서 보내는 것이다.**

10MB 파일을 쓸 때 걸린 시간을 나란히 놓으면 선택 기준이 보인다.

| 방식 | 쓰기 | 읽기 | 메모리 |
| --- | --- | --- | --- |
| 1바이트씩 | 28569ms | 19243ms | 없음 |
| 직접 버퍼 8KB | **31ms** | **8ms** | 8KB |
| `BufferedXxx` | 307ms | 272ms | 8KB |
| 전체를 한 번에 | 26ms | 11ms | **10MB** |

(숫자는 환경마다 다르다. 중요한 건 자릿수 차이다.)

- **파일이 작으면** `readAllBytes()`로 한 번에. 제일 간단하고 충분히 빠르다.
- **파일이 크고 성능이 중요하면** 버퍼를 직접 다룬다. 메모리도 통제되고 제일 빠르다.
- **그 외에는** `BufferedXxx`. 코드가 단순해지고, 덩어리로 넘기면 성능 손해도 거의 없다.

그리고 어떤 방식을 쓰든 두 가지는 지킨다. **try-with-resources로 닫고, 여러 겹으로 감쌌으면 바깥쪽을 닫는다.**
