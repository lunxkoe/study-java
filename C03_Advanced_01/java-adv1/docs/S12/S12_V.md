# [Java] 동시성 컬렉션, ConcurrentHashMap을 써도 깨지는 이유

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

if (!map.containsKey(key)) {
    map.put(key, 1);
}
```

동시성 컬렉션을 썼으니 안전할 것 같지만, **이 코드는 깨진다.**

`ArrayList`가 왜 위험한지부터 시작해서, `Collections.synchronizedList()`의 한계를 거쳐, 동시성 컬렉션을 써도 여전히 남는 함정까지 정리한다.

---

## 다루는 내용

- 일반 컬렉션이 스레드 세이프하지 않은 이유
- 실제 `ArrayList` / `HashMap`에서 벌어지는 일
- 프록시 패턴과 `Collections.synchronizedXxx()`
- ⚠️ 동기화 프록시의 두 가지 함정
- `ConcurrentHashMap`이 빠른 이유
- ⭐ 동시성 컬렉션도 복합 연산은 안전하지 않다

---

# 1. 일반 컬렉션은 스레드 세이프하지 않다

## 1.1 용어

> **Thread-Safe**: 여러 스레드가 동시에 접근해도 올바르게 동작하는 것.

```java
List<String> list = new ArrayList<>();
list.add("A");      // 스레드 1
list.add("B");      // 스레드 2
```

`add()`는 "데이터 하나 추가"라서 원자적일 것 같지만, **전혀 아니다.**

## 1.2 직접 만들어보기

```java
public class BasicList implements SimpleList {

    private static final int DEFAULT_CAPACITY = 5;

    private final Object[] elementData;
    private int size;

    @Override
    public void add(Object e) {
        elementData[size] = e;    // ① 현재 위치에 저장
        sleep(100);               // 문제를 드러내기 위한 장치
        size++;                   // ② 크기 증가
    }

    @Override
    public Object get(int index) {
        return elementData[index];
    }
}
```

**눈으로 봐도 `add()`는 최소 두 단계다.** 그리고 이전 글에서 봤듯 `size++`는 그 자체로 또 세 단계다.

---

# 2. 왜 깨지는가

## 2.1 실행 결과

두 스레드가 각각 `add("A")`, `add("B")`를 호출하면 이렇게 된다.

```text
00:13:21.487 [     main] BasicList
00:13:21.603 [ Thread-1] Thread - 1: list.add("A")
00:13:21.603 [ Thread-2] Thread - 2: list.add("B")
00:13:21.603 [     main] [B, null] size = 2, capacity = 5
```

**`size`는 2인데 내용은 `[B, null]`이다.** 말이 안 되는 상태다.

## 2.2 무슨 일이 일어났나

```text
시간 ──────────────────────────────────────────▶

Thread-1: elementData[0] = "A"  ──sleep(100)──▶  size++ → 1
Thread-2: elementData[0] = "B"  ──sleep(100)──▶  size++ → 2
                  ▲                                  ▲
        ⚠️ 둘 다 size=0 을 보고                 우연히 겹치지 않아 2
           같은 칸에 썼다 → B 가 덮어씀

결과: elementData = ["B", null, ...],  size = 2
      → [B, null]
```

## 2.3 ⚠️ 여기서 중요한 구분

| 단계 | 이 실행에서 | 설명 |
| --- | --- | --- |
| `elementData[size] = e` | ⚠️ **충돌함** | 둘 다 `size=0`을 읽어 같은 칸에 씀 |
| `size++` | ✅ 충돌 안 함 | `sleep(100)` 뒤라 타이밍이 어긋남 |

**`size++`가 우연히 2가 된 것**이고, 겹쳤다면 `size=1`이 나왔을 것이다.

```text
[ 상황 1 ] size++ 가 순차적으로 실행 → size = 2  ← 이번 실행
[ 상황 2 ] size++ 가 동시에 실행     → size = 1
```

> ⭐ **한 번의 실행으로 두 가지 버그가 동시에 드러나지 않는다.** 이게 동시성 버그가 무서운 이유다. 한 증상을 고쳐도 다른 증상이 남아 있을 수 있다.

# 3. 실제 ArrayList와 HashMap에서는 더 험하다

예제의 `BasicList`는 단순화한 것이다. 실제 컬렉션은 훨씬 더 심하게 깨진다.

## 3.1 ArrayList

```java
// ArrayList.add() 의 실제 흐름
private void add(E e, Object[] elementData, int s) {
    if (s == elementData.length)
        elementData = grow();     // ⚠️ 배열 전체를 새로 만들고 복사
    elementData[s] = e;
    size = s + 1;
}
```

| 증상 | 원인 |
| --- | --- |
| 데이터 유실 | 같은 인덱스에 덮어쓰기 |
| `null`이 중간에 끼어듦 | `size`만 증가하고 값은 안 들어감 |
| `ArrayIndexOutOfBoundsException` | 리사이징 중 옛 배열에 쓰기 |
| `ConcurrentModificationException` | 순회 중 `modCount`가 바뀜 |

## 3.2 ⚠️ HashMap은 더 심각하다

```text
[ Java 7 이하 ]
리사이징 중 연결 리스트가 역순으로 재배치되는데,
두 스레드가 동시에 하면 ⭐ 순환 링크(A → B → A)가 만들어진다
  → get() 이 무한 루프
  → CPU 코어 하나가 100% 로 박혀버림
  → 스레드 덤프를 떠야만 원인을 알 수 있는 전설적인 장애

[ Java 8 이상 ]
구조가 바뀌어 무한 루프는 사라졌지만
  → 여전히 데이터 유실, 엔트리 손상, size 불일치 발생
```

> 💡 "멀티스레드에서 `HashMap`을 쓰면 안 된다"는 말은 단순한 권고가 아니라 **실제 운영 장애 사례에서 나온 것**이다.

> ⭐ **일반 컬렉션은 멀티스레드 환경에서 동기화 없이 절대 쓰면 안 된다.**

# 4. synchronized로 감싸기

컬렉션은 수많은 복잡한 연산으로 이루어져 있다. 여러 스레드가 접근해야 한다면 `synchronized`나 `Lock`으로 임계 영역을 만들면 된다.

```java
public class SyncList implements SimpleList {

    private final Object[] elementData;
    private int size;

    @Override
    public synchronized int size() {           // ⭐ 여기도 필요하다
        return size;
    }

    @Override
    public synchronized void add(Object e) {
        elementData[size] = e;
        sleep(100);
        size++;
    }

    @Override
    public synchronized Object get(int index) {
        return elementData[index];
    }

    @Override
    public synchronized String toString() { ... }
}
```

```text
00:27:16.471 [     main] SyncList
00:27:16.578 [ Thread-1] Thread - 1: list.add("A")
00:27:16.686 [ Thread-2] Thread - 2: list.add("B")
00:27:16.686 [     main] [A, B] size = 2, capacity = 5     ✅
```

로그의 시간 간격(578 → 686, 약 108ms)이 **직렬 실행**을 보여준다. 한 스레드가 `sleep(100)`을 포함한 `add()`를 끝내야 다음 스레드가 들어간다.

> 💡 `size()` 같은 단순 getter에도 `synchronized`가 필요하다. 이전 글에서 `getBalance()`에 대해 짚었던 것과 같다. **락을 잡지 않으면 happens-before 관계가 없어 낡은 값을 읽을 수 있다.**

# 5. 프록시 패턴

## 5.1 문제 의식

> 모든 컬렉션마다 동기화 버전을 새로 만들어야 할까?
> **기존 코드는 그대로 두고 `synchronized`만 덧씌울 수 없을까?**

## 5.2 코드

```java
public class SyncProxyList implements SimpleList {

    private final SimpleList target;      // ⭐ 진짜 일꾼

    public SyncProxyList(SimpleList target) {
        this.target = target;
    }

    @Override
    public synchronized int size() {
        return target.size();
    }

    @Override
    public synchronized void add(Object e) {
        target.add(e);                    // 락만 걸고 위임
    }

    @Override
    public synchronized Object get(int index) {
        return target.get(index);
    }

    @Override
    public synchronized String toString() {
        return target.toString() + " by " + this.getClass().getSimpleName();
    }
}
```

```text
00:53:05.819 [     main] SyncProxyList
00:53:05.928 [ Thread-1] Thread - 1: list.add("A")
00:53:06.029 [ Thread-2] Thread - 2: list.add("B")
00:53:06.029 [     main] [A, B] size = 2, capacity = 5 by SyncProxyList   ✅
```

**`BasicList`는 전혀 손대지 않았는데 동기화가 됐다.**

## 5.3 구조

```text
   main                프록시                    원본
    │                    │                        │
    │  add("A")          │                        │
    ├───────────────────▶│                        │
    │              🔒 락 획득                      │
    │                    │      target.add("A")   │
    │                    ├───────────────────────▶│
    │                    │                   실제 작업
    │                    │◀───────────────────────┤
    │              🔓 락 반납                      │
    │◀───────────────────┤                        │
    │                    │                        │

   ⭐ 프록시와 원본이 같은 인터페이스를 구현하므로
      호출하는 쪽은 차이를 모른다
```

## 5.4 프록시 패턴의 목적

| 목적 | 예시 |
| --- | --- |
| **접근 제어** | 권한 검사, 접근 제한 |
| **성능 향상** | 지연 생성, 캐싱 |
| **부가 기능 제공** | 로깅, 인증, **동기화**, 트랜잭션 |

> 💡 **스프링 AOP가 정확히 이 패턴이다.** `@Transactional`을 붙이면 스프링이 프록시를 만들어서 "트랜잭션 시작 → 원본 호출 → 커밋/롤백"으로 감싼다. 여기서 `synchronized`가 하던 자리에 트랜잭션이 들어간 것뿐이다.

# 6. Collections.synchronizedXxx()

## 6.1 자바가 이미 제공한다

```java
List<String> list = Collections.synchronizedList(new ArrayList<>());

list.add("data1");
System.out.println("list.getClass() = " + list.getClass());
```

```text
list.getClass() = class java.util.Collections$SynchronizedRandomAccessList
```

**우리가 만든 `SyncProxyList`와 정확히 같은 구조의 프록시**다.

| 메서드 | 감싸는 대상 |
| --- | --- |
| `Collections.synchronizedList()` | `List` |
| `Collections.synchronizedMap()` | `Map` |
| `Collections.synchronizedSet()` | `Set` |
| `Collections.synchronizedCollection()` | `Collection` |

## 6.2 그럼 모든 컬렉션을 동기화해두면 되지 않을까

**성능과의 트레이드오프가 있다.** 그래서 자바는 기본 컬렉션을 동기화하지 않는다.

`java.util.Vector`가 모든 메서드에 `synchronized`를 붙인 레거시인데, 지금은 쓰지 않는다. 이유가 성능만은 아니다.

```java
// ⚠️ Vector 여도 이건 안전하지 않다
if (!vector.contains(x)) {    // ① 각 메서드는 동기화되지만
    vector.add(x);             // ② 둘 사이에 다른 스레드가 끼어든다
}
```

> ⭐ **메서드 단위 동기화로는 복합 연산(check-then-act)을 막을 수 없다.**
> 이전 글들에서 반복해서 나온 문제고, 10장에서 다시 만난다.

> 💡 같은 계열의 레거시로 `Hashtable`, `StringBuffer`가 있다. `StringBuffer` 대신 `StringBuilder`를 쓰라는 것도 같은 맥락이다(대부분 단일 스레드라 동기화가 낭비).

## 6.3 프록시 방식의 한계

```text
   ┌──────── 하나의 락 ────────┐
   │                          │
   │  add()   get()   size()  │  ← 전부 같은 락
   │  remove() contains() ... │
   │                          │
   └──────────────────────────┘

   ⚠️ 읽기만 하는 스레드끼리도 서로 막는다
   ⚠️ 서로 다른 인덱스를 건드려도 서로 막는다
   ⚠️ 한 스레드가 락을 쥐면 나머지는 전부 BLOCKED
```

**잠금 범위가 너무 넓고, 정교한 동기화가 불가능하다.** 그래서 나온 게 `java.util.concurrent`의 동시성 컬렉션이다.

# 7. ⚠️ 동기화 프록시의 두 가지 함정

실무에서 실제로 사고가 나는 지점이라 따로 정리한다.

## 7.1 함정 ① — 순회는 여전히 직접 동기화해야 한다

```java
List<String> list = Collections.synchronizedList(new ArrayList<>());

// ❌ 위험 — ConcurrentModificationException
for (String s : list) {
    process(s);
}

// ✅ 올바른 방법 — 공식 문서가 요구하는 형태
synchronized (list) {
    for (String s : list) {
        process(s);
    }
}
```

`hasNext()`와 `next()` **각각은** 동기화되지만, **둘의 조합은 원자적이 아니다.** 그 사이에 다른 스레드가 `add()`하면 예외가 난다.

> 💡 `Collections.synchronizedList()`의 Javadoc이 이 코드를 그대로 예시로 싣고 **"반드시 이렇게 하라"**고 명시한다. 이걸 모르고 쓰다가 터지는 경우가 많다.

## 7.2 함정 ② — 원본 참조가 남아 있으면 무의미하다

```java
BasicList original = new BasicList();
SimpleList proxy = new SyncProxyList(original);

// 다른 곳에서
original.add("X");      // 💀 프록시를 우회 → 락이 걸리지 않는다
```

```text
   🔒 프록시의 락
        │
   프록시 ──────▶ 원본
        │           ▲
   보호됨 ✅        │
                   │
   다른 코드 ───────┘  💀 락 없이 직접 접근
```

**프록시는 `this`(프록시 자신)의 모니터 락을 쓴다.** 원본 객체의 락이 아니다. 원본을 직접 만질 수 있는 경로가 하나라도 남아 있으면 보호가 무너진다.

```java
// ✅ 안전한 관용구 — 원본 참조를 남기지 않는다
List<String> list = Collections.synchronizedList(new ArrayList<>());
//                                               ↑ 여기서 바로 생성, 변수에 안 담음
```

# 8. 동시성 컬렉션

## 8.1 종류

| 일반 | 동시성 대안 | 비고 |
| --- | --- | --- |
| `ArrayList` | `CopyOnWriteArrayList` | 읽기 위주 |
| `HashSet` | `CopyOnWriteArraySet` | 읽기 위주 |
| `TreeSet` | `ConcurrentSkipListSet` | 정렬 유지 |
| `HashMap` | ⭐ `ConcurrentHashMap` | 가장 많이 씀 |
| `TreeMap` | `ConcurrentSkipListMap` | 정렬 유지 |
| `ArrayDeque` | `ConcurrentLinkedQueue` / `Deque` | 논블로킹 |
| `LinkedHashMap` / `LinkedHashSet` | ❌ **없음** | `Collections.synchronizedXxx()` 사용 |

**입력 순서를 유지하면서 멀티스레드에서 쓸 수 있는 Set/Map 구현체는 제공되지 않는다.** 필요하면 `Collections.synchronizedMap(new LinkedHashMap<>())`처럼 감싸야 한다.

## 8.2 ⚠️ CopyOnWriteArrayList는 특이하다

이름 그대로 **쓸 때마다 배열 전체를 복사한다.**

```text
[ 읽기 ]                          [ 쓰기 ]

  여러 스레드가 동시에               ① 락 획득
  락 없이 읽는다                     ② 배열 전체 복사 (O(n))
       │                             ③ 복사본에 추가
       ▼                             ④ 참조 교체 (원자적)
  현재 배열 스냅샷                    ⑤ 락 반납
  ⚡ 완전히 자유                     🐢 매우 비쌈
```

| 특성 | |
| --- | --- |
| 읽기 | ⭐ **락 없음.** 완전 동시 |
| 쓰기 | ⚠️ **O(n) 복사.** 매우 비쌈 |
| 순회 중 수정 | ✅ `ConcurrentModificationException` **안 남** (스냅샷을 순회) |
| 순회 중 본 데이터 | 🟡 시작 시점의 스냅샷 (최신이 아닐 수 있음) |

> **용도: 읽기가 압도적으로 많고 쓰기가 거의 없을 때.**
> 이벤트 리스너 목록, 설정값 목록 같은 것. **일반적인 리스트 대체용이 아니다.**

## 8.3 블로킹 큐

이전 글에서 다룬 내용이다.

| 구현체 | 특징 |
| --- | --- |
| `ArrayBlockingQueue` | 고정 크기. **공정 모드 선택 가능** (성능 저하 있음) |
| `LinkedBlockingQueue` | 크기 선택. ⚠️ **기본이 무한** |
| `PriorityBlockingQueue` | 우선순위 순서로 꺼냄 |
| `SynchronousQueue` | **버퍼 없음.** 생산자와 소비자가 직접 거래 |
| `DelayQueue` | 지연 시간이 지난 요소만 꺼낼 수 있음. 스케줄링에 사용 |

# 9. ConcurrentHashMap이 빠른 이유

프록시 방식과 뭐가 다른지 보면 "동시성 컬렉션"의 의미가 분명해진다.

## 9.1 락의 범위

```text
[ Collections.synchronizedMap ]      [ ConcurrentHashMap (Java 8+) ]

  ┌──── 🔒 하나의 락 ────┐            버킷0 [A]  ← 🔒 이 버킷만
  │ 버킷0 버킷1 버킷2 ... │            버킷1 [B]  ← 🔒 독립적으로
  │                      │            버킷2 []   ← CAS 로 그냥 삽입
  └──────────────────────┘            버킷3 [C]  ← 🔒 독립적으로
   ⚠️ 하나만 건드려도
      전부 막힌다                     ✅ 서로 다른 버킷은 동시에 가능
```

| 버전 | 방식 |
| --- | --- |
| Java 7 | **세그먼트 락** — 16개 구역으로 나눠 각각 락 |
| Java 8+ | ⭐ **버킷 단위** — 빈 버킷은 **CAS**로 삽입, 충돌 시 해당 버킷 헤드에만 `synchronized` |

> ⭐ 이전 글에서 배운 **CAS가 여기서 쓰인다.** 충돌이 없으면(빈 버킷) 락 없이 CAS로 끝내고, 충돌할 때만 락을 건다. 낙관적 접근의 전형이다.

## 9.2 특징 두 가지

```java
map.put(null, "v");    // 💥 NullPointerException
map.put("k", null);    // 💥 NullPointerException
```

**null 키도 값도 허용하지 않는다.** 이전 글의 `BlockingQueue`와 같은 이유다 — `get()`이 `null`을 "없음"의 신호로 쓰는데, 값도 `null`일 수 있으면 구분할 수 없다.

```java
map.size();     // 🟡 동시 수정 중이라면 근사값일 수 있다
```

# 10. ⭐ 동시성 컬렉션도 복합 연산은 안전하지 않다

이 글에서 가장 중요한 내용이다.

## 10.1 착각하기 쉬운 코드

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// ❌ 안전하지 않다!
if (!map.containsKey(key)) {     // ① 각 메서드는 원자적이지만
    map.put(key, 1);              // ② 둘 사이에 끼어들 수 있다
}

// ❌ 이것도 안전하지 않다
Integer count = map.get(key);     // ①
map.put(key, count + 1);          // ② read-modify-write
```

```text
Thread-1: containsKey(k) → false
Thread-2: containsKey(k) → false      ⚠️ 둘 다 통과
Thread-1: put(k, 1)
Thread-2: put(k, 1)                    ⚠️ 하나가 덮어씀
```

**`ConcurrentHashMap`을 썼는데도 깨진다.** 이전 글들에서 계속 나온 check-then-act 문제다.

> ⭐ **"스레드 세이프한 컬렉션"의 의미는 "개별 메서드 호출이 안전하다"이지, "내가 쓰는 로직이 안전하다"가 아니다.**

## 10.2 해결 — 원자적 복합 연산 메서드

`ConcurrentHashMap`은 복합 연산을 **원자적으로 묶어주는 메서드**를 제공한다. 이게 진짜 존재 이유다.

```java
// ✅ 없을 때만 넣기
map.putIfAbsent(key, 1);

// ✅ 없으면 계산해서 넣기 (비싼 초기화에 유용)
map.computeIfAbsent(key, k -> expensiveInit(k));

// ✅ 있으면 갱신
map.computeIfPresent(key, (k, v) -> v + 1);

// ✅ 카운팅 관용구
map.merge(key, 1, Integer::sum);

// ✅ 조건부 교체 / 삭제 (CAS 스타일!)
map.replace(key, oldValue, newValue);
map.remove(key, expectedValue);
```

| 메서드 | 의미 |
| --- | --- |
| `putIfAbsent(k, v)` | 없을 때만 삽입 |
| `computeIfAbsent(k, fn)` | 없으면 함수로 만들어 삽입 |
| `computeIfPresent(k, fn)` | 있으면 함수로 갱신 |
| `compute(k, fn)` | 있든 없든 함수로 계산 |
| `merge(k, v, fn)` | 없으면 v, 있으면 `fn(기존, v)` |
| `replace(k, old, new)` | ⭐ **CAS와 같은 형태** |

> 💡 `replace(k, old, new)`가 `compareAndSet(expected, new)`와 똑같은 모양이다. **동시성 컬렉션이 CAS의 아이디어를 컬렉션 수준으로 올린 것**이라는 게 여기서 보인다.

## 10.3 그래도 안 되면 락을 써라

`computeIfAbsent` 같은 메서드로도 표현할 수 없는 복합 로직이라면 결국 락이 필요하다.

```java
synchronized (lock) {
    // 여러 컬렉션에 걸친 일관성이 필요한 작업
}
```

> ⚠️ 단, `compute*` 계열 **람다 안에서 무거운 작업이나 다른 락 획득을 하면 안 된다.** 그 버킷의 락을 쥔 채로 실행되므로 데드락이나 성능 저하를 부른다. 이전 글의 "락 안에서 느린 일을 하지 마라"가 그대로 적용된다.

# 11. 선택 가이드

## 11.1 특성 비교

| | 일반 컬렉션 | `Collections.synchronizedXxx` | 동시성 컬렉션 |
| --- | --- | --- | --- |
| 스레드 안전 | ❌ | ✅ (메서드 단위) | ✅ (메서드 단위) |
| 락 범위 | — | ⚠️ **컬렉션 전체** | ⭐ **부분 / 락프리** |
| 읽기 동시성 | — | ❌ 서로 막음 | ⭐ 가능 |
| 순회 시 별도 동기화 | — | ⚠️ **필요** | ✅ 불필요 |
| `ConcurrentModificationException` | 발생 | 발생 | ✅ 거의 없음 |
| 복합 연산 | — | ❌ 직접 락 | ⭐ **전용 메서드 제공** |

## 11.2 무엇을 쓸 것인가

```text
여러 스레드가 이 컬렉션을 건드리나?
   │
   ├─ 아니오 → ⭐ 일반 컬렉션 (ArrayList, HashMap) — 가장 빠르다
   │
   └─ 예
       │
       ├─ Map 이 필요하다           → ⭐ ConcurrentHashMap
       │
       ├─ 생산자-소비자 큐          → ⭐ BlockingQueue
       │
       ├─ 읽기만 거의 전부 (리스너)  → ⭐ CopyOnWriteArrayList
       │
       ├─ 정렬이 필요하다            → ConcurrentSkipList(Map|Set)
       │
       ├─ 입력 순서 유지가 필요      → Collections.synchronizedMap(new LinkedHashMap<>())
       │                               (순회 시 직접 동기화 필수)
       │
       └─ 여러 컬렉션에 걸친 일관성  → 직접 락 (synchronized / ReentrantLock)
```

## 11.3 사실 제일 좋은 건 공유하지 않는 것

```java
// ✅ 불변 컬렉션 — 스레드 안전이 공짜
List<String> config = List.of("a", "b", "c");
Map<String, String> m = Map.of("k", "v");

// ✅ 스레드마다 따로
ThreadLocal<List<String>> buffer = ThreadLocal.withInitial(ArrayList::new);

// ✅ 각자 계산 후 합치기
list.parallelStream().collect(Collectors.toList());
```

지금까지의 모든 글에서 반복된 결론이 여기서도 같다. **동기화를 고르기 전에 공유를 없앨 수 있는지부터 본다.**

# 마무리 정리

## 한 줄 요약

> **"스레드 세이프한 컬렉션"은 "개별 메서드가 안전하다"는 뜻이지, "내 로직이 안전하다"는 뜻이 아니다.**
> `containsKey` 후 `put` 하는 순간, `ConcurrentHashMap`이어도 깨진다.

## 헷갈리기 쉬운 포인트 10가지

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | `list.add()`는 한 줄이니 원자적이다 | **최소 2단계**, 리사이징까지 포함하면 더 |
| 2 | 멀티스레드 `HashMap`은 그냥 좀 느린 것 | Java 7에선 **무한 루프 장애**까지 났다 |
| 3 | `Vector`는 느려서 안 쓴다 | **복합 연산도 못 막는다**는 게 더 큰 이유 |
| 4 | `Collections.synchronizedList()`면 순회도 안전 | **직접 `synchronized`로 감싸야** 한다 |
| 5 | 프록시로 감싸면 원본도 보호된다 | **원본 직접 접근은 막지 못한다** |
| 6 | `CopyOnWriteArrayList`는 그냥 안전한 리스트다 | 쓰기가 **O(n) 복사**. 읽기 전용에 가까운 용도 |
| 7 | 동시성 컬렉션은 락을 안 쓴다 | `ConcurrentHashMap`은 **버킷 단위로 쓴다** |
| 8 | `ConcurrentHashMap`에 null을 넣을 수 있다 | **`NullPointerException`** |
| 9 | 동시성 컬렉션이면 내 로직도 안전하다 | **복합 연산은 여전히 깨진다** |
| 10 | `map.get()` 후 `map.put()`이면 충분하다 | `merge()` / `compute*()`를 써야 한다 |
