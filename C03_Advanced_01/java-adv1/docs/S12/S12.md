# 동시성 컬렉션

## 동시성 컬렉션이 필요한 이유 1 - 시작

### java.util 컬렉션 프레임워크
- 멀티 스레드 환경에서 안전할까?
- 참고로 여러 스레드에서 동시에 접근해도 괜찮은 경우를 **Thread-Safe**하다고 함

### 문제가 되는 상황
```java
public class SimpleListMainV0 {

    public static void main(String[] args) {
        List<String> list = new ArrayList<>();

        // 스레드1, 스레드2가 동시에 실행 가정
        list.add("A"); // 스레드 1 실행 가정
        list.add("B"); // 스레드 2 실행 가정
        System.out.println(list);
    }
}
```
- 여기서 스레드 1과 스레드 2가 동시에 실행한다고 **가정**
  - 스레드 1 list에 A를 추가
  - 스레드 2 list에 B를 추가

- add() 메서드를 생각해보면 단순히 컬렉션에 데이터를 하나 추가하는 것 뿐 (느낌상 원자적 연산)
- 하지만 **원자적 연산이 아님**

### 간단한 컬렉션 프레임워크 제작으로 원자적 연산이 아님을 보기
```java
public class BasicList implements SimpleList {

    private static final int DEFAULT_CAPACITY = 5;

    private final Object[] elementData;
    private int size;

    public BasicList() {
        this.elementData = new Object[DEFAULT_CAPACITY];
    }

    public BasicList(int size) {
        this.elementData = new Object[size];
    }

    @Override
    public int size() {
        return size;
    }

    @Override
    public void add(Object e) {
        elementData[size] = e;
        sleep(100); // 멀티스레드 문제를 쉽게 확인하는 코드
        size++;
    }

    @Override
    public Object get(int index) {
        return elementData[index];
    }

    @Override
    public String toString() {
        return Arrays.toString(Arrays.copyOf(elementData, size))
                + " size = " + size + ", capacity = " + elementData.length;
    }
}
```
- add(E e): 눈으로만 봐도 원자적 연산이 아님

## 동시성 컬렉션이 필요한 이유 2 - 동시성 문제

### 멀티스레드 문제 확인
- add() - 원자적이지 않은 연산
- 메서드를 까보면 원자적이지 않음
  - 심지어 size++도 원자적인 연산이 아님

### 예제 코드
```java
public class SimpleListMainV1 {

    public static void main(String[] args) throws InterruptedException {
        test(new BasicList());
    }

    private static void test(SimpleList list) throws InterruptedException {
        log(list.getClass().getSimpleName());

        // A를 리스트에 저장하는 코드
        Runnable addA = new Runnable() {

            @Override
            public void run() {
                list.add("A");
                log("Thread - 1: list.add(\"A\")");
            }
        };

        // B를 리스트에 저장하는 코드
        Runnable addB = new Runnable() {

            @Override
            public void run() {
                list.add("B");
                log("Thread - 2: list.add(\"B\")");
            }
        };

        Thread thread1 = new Thread(addA, "Thread-1");
        Thread thread2 = new Thread(addB, "Thread-2");

        thread1.start();
        thread2.start();

        thread1.join();
        thread2.join();

        log(list);
    }
}
```
- 실행 결과
    ```text
    00:13:21.487 [     main] BasicList
    00:13:21.603 [ Thread-1] Thread - 1: list.add("A")
    00:13:21.603 [ Thread-2] Thread - 2: list.add("B")
    00:13:21.603 [     main] [B, null] size = 2, capacity = 5
    ```
    - size는 2인데, [A, null]
    - 이게 도대체 무슨 말도 안되는 상황일까?

### 발생 이유
- elementData[size] = e를 동시에 실행하게 되면 A를 먼저 넣고, B를 넣거나 혹은 그 반대 상황이 발생하게 되면서 덮어써버림
- size++
  - 상황 1
    - 스레드 1이 size++를 한 이후
    - 스레드 2가 size++
  - 상황 2
    - 스레드 1, 2가 size를 같이 읽음
    - size++을 동시에 하면 결국 1이 되어버림

### 결론
- 일반적인 컬렉션들은 절대로!!! 스레드 세이프 하지 않음!!!
- 멀티 스레드 상황에서 일반적으로는 일반적인 컬렉션 프레임워크를 사용하면 절대 안됨!!!

## 동시성 컬렉션이 필요한 이유 3 - 동기화

### 컬렉션의 연산들
- 컬렉션은 수 많은 복잡한 연산으로 이루어져있음
- 따라서 여러 스레드가 접근해야한다면 synchronized, Lock 등을 사용해서 임계 영역을 적절히 만들면 문제를 해결 할 수 있음
```java
public class SyncList implements SimpleList {

    private static final int DEFAULT_CAPACITY = 5;

    private final Object[] elementData;
    private int size;

    public SyncList() {
        this.elementData = new Object[DEFAULT_CAPACITY];
    }

    public SyncList(int size) {
        this.elementData = new Object[size];
    }

    @Override
    public int size() {
        return size;
    }

    @Override
    public synchronized void add(Object e) {
        elementData[size] = e;
        sleep(100); // 멀티스레드 문제를 쉽게 확인하는 코드
        size++;
    }

    @Override
    public synchronized Object get(int index) {
        return elementData[index];
    }

    @Override
    public synchronized String toString() {
        return Arrays.toString(Arrays.copyOf(elementData, size))
                + " size = " + size + ", capacity = " + elementData.length;
    }
}
```
- 실행 결과
    ```text
    00:27:16.471 [     main] SyncList
    00:27:16.578 [ Thread-1] Thread - 1: list.add("A")
    00:27:16.686 [ Thread-2] Thread - 2: list.add("B")
    00:27:16.686 [     main] [A, A] size = 2, capacity = 5
    ```
    - 정확하게 나온 것을 확인할 수 있음
    - 한 번에 하나의 스레드만 해당 메서드를 호출할 수 있음을 알 수 있음

### 그렇다면?
- 모든 컬렉션들을 받아서 동기화 처리를 일일히 해주어야할까?
- **프록시 도입**

## 동기성 컬렉션이 필요한 이유 4 - 프록시 도입

### 프록시가 필요한 상황
- 기존 코드를 그대로 사용하면서 synchronized 기능만 살짝 추가하고 싶다면?

### 프록시
- 대리자, 대신 처리해주는 자라는 뜻
```java
public class SyncProxyList implements SimpleList {

    private final SimpleList target;

    public SyncProxyList(SimpleList target) {
        this.target = target;
    }

    @Override
    public synchronized int size() {
        return target.size();
    }

    @Override
    public synchronized void add(Object e) {
        target.add(e);
    }

    @Override
    public synchronized Object get(int index) {
        return target.get(index);
    }
}
```
- 해당 클래스는 SimpleList의 기능을 구현함
- 또한 target으로 들어오는 SimpleList에 대한 Wrapper 역할을 함
- **다만 모든 메서드에 synchronized를 걸어줌으로써 동기화 문제를 해결함**

### 프록시 사용
```java
public class SimpleListMainV3 {

    public static void main(String[] args) throws InterruptedException {
        test(new SyncProxyList(new BasicList()));
    }

    private static void test(SimpleList list) throws InterruptedException {
        log(list.getClass().getSimpleName());

        // A를 리스트에 저장하는 코드
        Runnable addA = new Runnable() {

            @Override
            public void run() {
                list.add("A");
                log("Thread - 1: list.add(\"A\")");
            }
        };

        // B를 리스트에 저장하는 코드
        Runnable addB = new Runnable() {

            @Override
            public void run() {
                list.add("B");
                log("Thread - 2: list.add(\"B\")");
            }
        };

        Thread thread1 = new Thread(addA, "Thread-1");
        Thread thread2 = new Thread(addB, "Thread-2");

        thread1.start();
        thread2.start();

        thread1.join();
        thread2.join();

        log(list);
    }
}
```
- 실행 결과
    ```text
    00:53:05.819 [     main] SyncProxyList
    00:53:05.928 [ Thread-1] Thread - 1: list.add("A")
    00:53:06.029 [ Thread-2] Thread - 2: list.add("B")
    00:53:06.029 [     main] [A, B] size = 2, capacity = 5 by SyncProxyList
    ```
    - 동기화가 잘 이루어진 것을 확인할 수 있음

### 동작원리
- Wrapper 느낌으로 락을 걸고 실제 BasicList의 메서드를 호출함
- 프록시는 원본과 인터페이스가 같기 때문에, 메인 입장에서 아무런 문제가 없음
- **프록시 패턴**

### 프록시 패턴의 주요 목적
- 접근 제어: 실제 객체에 대한 접근을 제한하거나 통제할 수 있음
- 성능 향상: 실제 객체의 생성을 지연시키거나 캐싱하여 성능을 최적화할 수 있음
- 부가 기능 제고: 실제 객체에 추가적인 기능(로깅, 인증, 동기화 등)을 투명하게 제공할 수 있음
- 참고: 스프링의 AOP 기능은 사실 이런 프록시 패턴을 극한으로 적용하는 예

## 자바 동시성 컬렉션 1 - synchronized

### 동기화의 트레이드 오프
- 모든 컬렉션에 동기화를 해두면 좋지 않을까?
  - 성능과의 트레이드 오프가 발생함
  - 동기화를 항상 걸어두는 것은 좋지 않음
  - java.util.Vector => 메서드에 synchronized 동기화가 되어있음
    - 성능이 좋지 않아서 더 이상 사용하지 않음

### 자바의 synchronized 프록시 제공
```java
public class SynchronizedListMain {

    public static void main(String[] args) {
        List<String> list = Collections.synchronizedList(new ArrayList<>());

        list.add("data1");
        list.add("data2");
        list.add("data3");

        System.out.println("list.getClass() = " + list.getClass());
        System.out.println("list = " + list);
    }
}
```
- 실행 결과
    ```text
    list.getClass() = class java.util.Collections$SynchronizedRandomAccessList
    list = [data1, data2, data3]
    ```
    - java.util.Collections$SynchronizedRandomAccessList: 프록시
    - SynchronizedRandomAccessList(프록시)

### 프록시 방식의 단점
- 동기화 오버헤드가 발생함
- 전체 컬렉션에 대해 동기화가 이루어지기 때문에 잠금 범위가 너무 넓어짐
- 특정 스레드가 모니터 락을 점유하고 있는 순간 다른 스레드 모두가 락을 위해서 blocked 되어있는 상태
- 정교한 동기화가 불가능함
- 해결 방안: java.util.concurrent 패키지에 동시성 컬렉션을 제공함

## 자바 동시성 컬렉션 2 - 동시성 컬렉션

### 동시성 컬렉션의 종류
- List
  - CopyOnWriteArrayList -> ArrayList의 대안
- Set
  - CopyOnWriteArraySet -> HashSet의 대안
  - ConcurrentSkipListSet -> TreeSet의 대안
- Map
  - ConcurrentHashMap -> HashMap의 대안
  - ConcurrentSkipListMap -> TreeMap의 대안
- Queue
  - ConcurrentLinkedQueue: 동시성 큐, 논 블로킹 큐
- Deque
  - ConcurrentLinkedDeque: 동시성 데크, 논 블로킹 큐

- 참고로 LinkedHashSet, LinkedHashMap처럼 입력 순서르 유지하는 동시에 멀티스레드 환경에서 사용할 수 있는 Set, Map 구현체는 제공하지 않음
  - 필요하면 Collections.synchronizedXxx()를 사용해야함

### 스레드를 차단하는 블로킹 큐
- ArrayBlockingQueue
  - 크기가 고정된 블로킹 큐
  - 공정 모드를 사용할 수 있음
  - 공정 모드를 사용하면 성능이 저하될 수 있음
- LinkedBlockingQueue
  - 크기가 무한하거나 고정된 블로킹 큐
- PriorityBlockingQueue
  - 우선순위가 높은 요소를 처리하는 블로킹 큐
- SynchronousQueue
  - 데이터를 저장하지 않는 블로킹 큐
  - 생산자가 데이터를 추가하면 소비자가 그 데이터를 받을 때까지 대기함
  - 쉽게 이야기해서 중간에 큐 없이 생산자, 소비자가 직접 거래함
- DelayQueue
  - 지연된 요소를 처리하는 블로킹 큐
  - 각 요소는 지정된 지연 시간이 지난 후에야 소비될 수 있음
  - 일정 시간이 지난 후 작업을 처리해야하는 스케줄링 작업에 사용됨
