# [Java] CAS와 원자적 연산, 락 없이 안전하게 값 바꾸기

`volatile`을 붙였는데도 결과가 틀린다.

```java
private volatile int value;

public void increment() {
    value++;        // 스레드 1000개가 한 번씩 호출
}
```

```text
VolatileInteger result: 989     ← 1000이 아니다
```

이전 글에서 `volatile`로 메모리 가시성을 해결했는데, 이 문제는 그걸로 안 풀린다. **두 스레드가 "정확히 최신인 같은 값"을 읽어도 결과는 똑같이 깨지기 때문**이다.

이번 글은 `synchronized`도 `Lock`도 쓰지 않고 이 문제를 푸는 방법, **CAS**에 대한 이야기다.

---

## 다루는 내용

- 원자성과 가시성은 다른 축이다
- `volatile`로 왜 안 되는가
- ⚠️ 성능 테스트를 읽을 때 조심할 것
- CAS 연산과 하드웨어 지원
- CAS로 `incrementAndGet` 직접 만들기
- ⭐ ABA 문제
- 스핀락 구현과 그 한계
- 낙관 vs 비관, 그리고 `LongAdder`

# 1. 원자성과 가시성은 다른 축이다

## 1.1 원자적 연산이란

> **더 이상 나눌 수 없는 단위로 수행되는 연산.**
> 중간 상태가 다른 스레드에게 보이지 않는다.

```java
int i = 0;        // ✅ 원자적 — 대입 하나
i = i + 1;        // ❌ 원자적이지 않음
                  //    ① i 를 읽고 ② 1을 더하고 ③ i 에 저장
```

## 1.2 ⚠️ volatile은 원자성과 무관하다

`volatile int i = 0`이 원자적인 건 **`volatile` 때문이 아니다.** `int` 변수에 대한 단순 대입이 **원래** 원자적이다. `volatile`은 **가시성**을 위한 키워드고, 원자성과는 완전히 다른 축이다.

| | 원자성 없음 | 원자성 있음 |
| --- | --- | --- |
| **가시성 없음** | `int i; i++;` ⚠️ | `int i; i = 5;` ⚠️ |
| **가시성 있음** | `volatile int i; i++;` ⚠️ | `volatile int i; i = 5;` ✅ |

이전 글의 `runFlag`가 오른쪽 아래 칸이다. **대입은 원래 원자적이었고, 부족한 건 가시성이었다.** 이번 글의 `value++`는 왼쪽 칸이다. **가시성을 채워도 원자성이 없어서** 여전히 깨진다.

> ⚠️ 그래서 **"원자적이면 멀티스레드에서 안전하다"는 말은 틀렸다.**
> ```java
> boolean flag = false;    // 대입은 원자적이지만
> // → volatile 이 없으면 다른 스레드가 영원히 못 볼 수 있다
> ```
> **원자성과 가시성을 둘 다 갖춰야 안전하다.**

> 💡 64비트의 예외: 이전 글에서 다룬 워드 티어링 때문에, `long`/`double`은 `volatile` 없이는 **대입조차 원자적이지 않을 수 있다.**

# 2. 문제 재현

## 2.1 코드

```java
public interface IncrementInteger {
    void increment();
    int get();
}
```

```java
public class BasicInteger implements IncrementInteger {
    private int value;

    @Override
    public void increment() {
        value++;              // ⚠️ 3단계
    }

    @Override
    public int get() {
        return value;
    }
}
```

```java
private static final int THREAD_COUNT = 1000;

private static void test(IncrementInteger target) throws InterruptedException {
    Runnable runnable = () -> {
        sleep(10);            // 동시 실행을 유도하기 위한 장치
        target.increment();
    };

    List<Thread> threads = new ArrayList<>();
    for (int i = 0; i < THREAD_COUNT; i++) {
        Thread thread = new Thread(runnable);
        threads.add(thread);
        thread.start();
    }
    for (Thread thread : threads) {
        thread.join();        // ⭐ 가시성도 함께 확보
    }

    System.out.println(target.getClass().getSimpleName() + " result: " + target.get());
}
```

```text
BasicInteger result: 996      ← 1000이 아니다
```

## 2.2 무슨 일이 일어났나

```text
스레드 1: i 를 읽음   → 0
스레드 2: i 를 읽음   → 0        ⚠️ 같은 값을 읽었다
스레드 1: i + 1      → 1
스레드 2: i + 1      → 1
스레드 1: i = 1
스레드 2: i = 1                  ⚠️ 두 번 증가했는데 1
```

**갱신 손실(lost update)**이다. 이전 글의 은행 예제가 `check-then-act`였다면, 이번엔 `read-modify-write`다.

> 💡 `sleep(10)`이 없으면 1000이 나올 수도 있다. 스레드 생성 자체가 느려서 앞선 스레드가 이미 끝나버리기 때문이다. **1000개를 같은 시점에 몰아넣어 충돌을 만들어내는 장치**다.

> 💡 `join()`이 없었다면 결과가 더 엉망이었을 것이다. 이전 글에서 정리한 대로 `join()`이 happens-before를 만들어 최종 값의 가시성을 보장한다.

# 3. volatile로는 왜 안 되나

```java
private volatile int value;

public void increment() {
    value++;
}
```

```text
VolatileInteger result: 989     ← 여전히 틀렸다
```

```text
value++ 는 여전히 3단계다

① value 를 읽는다      ← volatile 이 "최신 값"을 보장
② 1을 더한다
③ value 에 저장한다     ← volatile 이 "즉시 반영"을 보장

⭐ 하지만 ①②③ 사이에 다른 스레드가 끼어드는 것은 막지 못한다
```

**두 스레드가 "정확히 최신인 같은 값"을 읽어도 결과는 똑같이 깨진다.** 문제의 근본이 값이 낡았다는 게 아니라 **연산이 쪼개져 있다**는 것이기 때문이다.

> 💡 996 → 989로 **더 나빠진 게 아니다.** 이 수치는 실행할 때마다 달라진다. 충돌이 일어나는 타이밍 창이 바뀐 것뿐이고, 두 값 모두 "틀렸다"는 점에서 동일하다.

# 4. synchronized와 AtomicInteger

## 4.1 synchronized

```java
@Override
public synchronized void increment() {
    value++;
}

@Override
public synchronized int get() {
    return value;
}
```

```text
SynchronizedInteger result: 1000     ✅
```

**한 번에 하나의 스레드만 들어갈 수 있으므로** 3단계가 통째로 원자적이 된다.

## 4.2 AtomicInteger

```java
public class MyAtomicInteger implements IncrementInteger {

    private final AtomicInteger atomicInteger = new AtomicInteger(0);

    @Override
    public void increment() {
        atomicInteger.incrementAndGet();
    }

    @Override
    public int get() {
        return atomicInteger.get();
    }
}
```

```text
MyAtomicInteger result: 1000     ✅
```

**락을 쓰지 않았는데도 정확하다.** 어떻게 가능한지가 이 글의 본론이다.

| 메서드 | 동작 |
| --- | --- |
| `incrementAndGet()` | +1 후 **새 값** 반환 (`++i`) |
| `getAndIncrement()` | **옛 값** 반환 후 +1 (`i++`) |
| `addAndGet(n)` / `getAndAdd(n)` | n만큼 더하기 |
| `compareAndSet(expect, update)` | ⭐ CAS |
| `updateAndGet(fn)` | **임의의 함수**를 원자적으로 적용 |

```java
counter.updateAndGet(v -> Math.min(v + 1, MAX));   // 내부에서 CAS 루프를 돈다
```

`AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference<T>` 등이 있다.

# 5. ⚠️ 성능 테스트를 읽을 때 조심할 것

네 구현을 1억 번씩 돌려보면 이런 결과가 나온다.

```text
BasicInteger: ms = 14
VolatileInteger: ms = 839
SynchronizedInteger: ms = 2186
MyAtomicInteger: ms = 881
```

**"AtomicInteger가 synchronized보다 2.5배 빠르다"**로 읽기 쉬운데, 두 가지를 먼저 짚어야 한다.

## 5.1 이 테스트는 단일 스레드다

```java
public static void test(IncrementInteger incrementInteger) {
    for (int i = 0; i < COUNT; i++) {       // ⚠️ main 스레드 혼자 1억 번
        incrementInteger.increment();
    }
}
```

**스레드를 하나도 만들지 않는다.** 측정한 것은 **"경쟁이 전혀 없을 때의 순수 오버헤드"**다. 멀티스레드 성능이 아니다.

## 5.2 `BasicInteger: 14ms`는 측정된 값이 아니다

계산해보면 바로 드러난다.

```text
1억 번 ÷ 14ms = 초당 71억 번 = 0.14 나노초/연산
```

**메모리는커녕 L1 캐시도 이 속도로는 못 읽는다.**

> ⭐ **JIT가 `value`를 레지스터에 올려두고 루프를 최적화해버린 것이다.**
> 심하면 `value += 100_000_000`으로 접어버릴 수도 있다.

이전 글에서 무한 루프를 만들었던 **바로 그 최적화**다.

| | 이전 글 (`runFlag`) | 이번 글 (`BasicInteger`) |
| --- | --- | --- |
| JIT가 하는 일 | 읽기를 레지스터로 호이스팅 | 증가를 레지스터에서 처리 |
| 결과 | 💀 무한 루프 | ⚡ 비현실적으로 빠름 |
| 본질 | **메모리를 건드리지 않는다** | **동일** |

## 5.3 그럼 나머지 수치는 무엇을 말하나

| 구현 | 연산당 시간 | 의미 |
| --- | --- | --- |
| `VolatileInteger` | 약 8.4 ns | **volatile 쓰기 배리어** 비용 |
| `MyAtomicInteger` | 약 8.8 ns | **CAS 명령 + 배리어** 비용 |
| `SynchronizedInteger` | 약 22 ns | **경쟁 없는 락** 획득/해제 비용 |

여기서 읽을 수 있는 건 이것이다.

> ✅ **경쟁이 없을 때** CAS는 volatile 쓰기 수준이고, 락은 그보다 2~3배 비싸다.

## 5.4 경쟁이 생기면 그림이 달라진다

```text
성능
 ▲
 │  synchronized ────────────────────────
 │       ╲                          ╱
 │        ╲                    ╱
 │  CAS ───╲──────────────╱
 │          ╲        ╱   ⚠️ 충돌이 심해지면 재시도 루프가 CPU를 태운다
 │           ╲   ╱
 │  LongAdder ──────────────────────────  ⭐ 셀 분산으로 충돌 자체를 줄임
 │
 └──────────────────────────────────────▶ 경쟁 수준
   없음        낮음        높음      매우 높음
```

| 경쟁 수준 | 유리한 쪽 | 이유 |
| --- | --- | --- |
| 없음 / 낮음 | ⭐ **CAS** | 블로킹·컨텍스트 스위칭이 없다 |
| 중간 | CAS (보통) | 재시도가 가끔 |
| 높음 | 상황에 따라 | CAS는 재시도로 CPU를 태우고, 락은 스위칭 비용 |
| 카운터 + 매우 높음 | ⭐ **`LongAdder`** | 10장 참고 |

> 💡 제대로 측정하려면 **JMH**를 써야 한다. `System.currentTimeMillis()` + 루프 방식은 JIT 워밍업, 데드 코드 제거, 루프 최적화 때문에 신뢰할 수 없다. `BasicInteger: 14ms`가 그 증거다.

# 6. CAS 연산

## 6.1 락 기반 방식의 무게

```text
[ 락 기반 ]
① 락이 있는지 확인
② 락을 획득하고 임계 영역 진입
③ 작업 수행
④ 락 반납

⚠️ 실패하면 BLOCKED / WAITING 으로 상태 전환 → 컨텍스트 스위칭
```

직관적이지만 상대적으로 무거운 방식이다. **스레드 상태가 계속 바뀐다.**

## 6.2 CAS란

> **Compare And Swap** — 락을 걸지 않고 원자적 연산을 수행하는 방법.
> 락을 쓰지 않아 **락 프리(lock-free)** 기법이라고 부른다.

```java
AtomicInteger atomicInteger = new AtomicInteger(0);

boolean result1 = atomicInteger.compareAndSet(0, 1);   // 현재 0이면 1로
boolean result2 = atomicInteger.compareAndSet(0, 1);   // 이미 1이라 실패
```

```text
start value = 0
result1 = true,  value = 1
result2 = false, value = 1
```

**`compareAndSet(expected, new)`: 현재 값이 `expected`면 `new`로 바꾸고 `true`, 아니면 그대로 두고 `false`.**

그리고 핵심은 이거다. **이 메서드는 원자적으로 실행된다.**

## 6.3 어떻게 원자적일 수 있나

```text
"값을 확인하고, 예상과 같으면 바꾼다"

⚠️ 소프트웨어로만 보면 이것도 2단계다
⭐ 그런데 CPU가 이 둘을 하나의 명령으로 제공한다
```

| 아키텍처 | 명령 |
| --- | --- |
| x86 | `LOCK CMPXCHG` |
| ARM (v8 이전) | `LDREX` / `STREX` (Load-Linked / Store-Conditional) |
| ARM v8.1+ | `CAS` 명령 |

자바에서 여기까지 내려가는 경로는 이렇다.

```text
AtomicInteger.compareAndSet()
        │
        ▼
VarHandle / Unsafe.compareAndSetInt()     (JDK 9+ 는 VarHandle)
        │
        ▼
JIT 인트린식 → 네이티브 CAS 명령으로 치환
        │
        ▼
LOCK CMPXCHG
```

> ⚠️ **"성능에 큰 영향이 없다"를 정확히 하면**: CAS 명령은 **메모리 배리어를 동반**하고, 해당 **캐시 라인을 배타적으로 가져와야** 한다. 경쟁이 없으면 저렴하지만, 여러 코어가 같은 변수를 두드리면 **캐시 라인 핑퐁**이 일어나 급격히 비싸진다. 5.4의 곡선이 꺾이는 이유다.

# 7. CAS로 incrementAndGet 만들기

## 7.1 코드

```java
public static int incrementAndGet(AtomicInteger atomicInteger) {
    int getValue;
    boolean result;
    do {
        getValue = atomicInteger.get();                              // ① 현재 값 읽기
        result = atomicInteger.compareAndSet(getValue, getValue + 1); // ② CAS (원자적)
    } while (!result);                                                // ③ 실패하면 재시도

    return getValue + 1;
}
```

두 스레드로 돌려보면 이런 로그가 나온다.

```text
[ Thread-1] getValue: 0
[ Thread-0] getValue: 0        ⚠️ 둘 다 0을 읽었다
[ Thread-1] result: true       ✅ 먼저 성공
[ Thread-0] result: false      ❌ 값이 1로 바뀌어서 실패
[ Thread-0] getValue: 1        🔁 다시 읽고
[ Thread-0] result: true       ✅ 이번엔 성공
AtomicInteger resultValue: 2
```

## 7.2 ⭐ 왜 이게 안전한가

```text
        ┌──────────────────────────────────────┐
        │  ① get()          ← 원자적이지만     │
        │  ② +1 계산        ← 여기 틈이 있다   │
        │  ③ compareAndSet  ← ⭐ 원자적         │
        └──────────────────────────────────────┘

핵심: ①과 ③ 사이에 값이 바뀌면 ③이 실패한다
      → 틈이 있어도 "틈을 감지할 수 있다"
      → 감지하면 처음부터 다시
```

> ⭐ **락은 "끼어들지 못하게" 막고, CAS는 "끼어들었는지 확인"한다.**
> 이게 비관과 낙관의 차이다.

## 7.3 ⚠️ `return atomicInteger.get()`으로 바꾸면 안 된다

```java
return getValue + 1;        // ✅ 내가 성공시킨 값
return atomicInteger.get(); // ❌ 그 사이 다른 스레드가 또 올렸을 수 있다
```

```text
Thread-0: CAS(1, 2) 성공 → 값은 2
Thread-1: CAS(2, 3) 성공 → 값은 3       ← 끼어듦
Thread-0: return get()  → 3 반환 💥     ← "내가 만든 값"이 아니다
```

**`incrementAndGet()`의 계약은 "내 증가의 결과"를 돌려주는 것**이지, "지금 값"이 아니다.

## 7.4 💡 lock-free이지 wait-free는 아니다

| 용어 | 의미 | CAS 루프는? |
| --- | --- | --- |
| **lock-free** | 전체 시스템은 반드시 진전한다 | ✅ 그렇다 |
| **wait-free** | **모든 개별 스레드**가 유한 단계에 끝난다 | ❌ 아니다 |

운이 나쁜 스레드는 **계속 실패하며 무한히 재시도**할 수 있다(기아). 실무에서 거의 문제되진 않지만, "락 프리 = 항상 빠르다"는 아니다.

# 8. ⭐ ABA 문제

CAS에는 유명한 함정이 하나 있다.

## 8.1 무엇이 문제인가

```text
CAS 는 "값이 같으면 아무 일도 없었다"고 가정한다
⚠️ 하지만 "A → B → A" 로 돌아왔을 수도 있다

시간 ─────────────────────────────────────────▶

Thread-1: A 를 읽음 ─────────────────────▶ CAS(A, C) 성공! ✅
                                              ▲
Thread-2:     A → B 로 변경                   │
Thread-3:            B → A 로 변경 ───────────┘
                     ⚠️ Thread-1 은 이 사이 변화를 전혀 모른다
```

## 8.2 언제 문제가 되나

| 상황 | ABA가 문제인가 |
| --- | --- |
| 단순 카운터 (`AtomicInteger`) | ❌ **대체로 괜찮다.** 값만 맞으면 되니까 |
| 참조를 다루는 락프리 스택/큐 | ⚠️ **치명적** |

락프리 스택에서는 이런 일이 벌어진다.

```text
스택: A → B → C

Thread-1: top = A, next = B 를 읽음 → CAS 준비
Thread-2: A 를 pop, B 를 pop, A 를 다시 push  → 스택: A → C
Thread-1: CAS(top, A→B) 성공 💥
          → top 이 B 를 가리키는데, B 는 이미 제거된 노드
          → 스택 구조가 깨진다
```

## 8.3 해결 — 버전 태그

```java
AtomicStampedReference<Node> top = new AtomicStampedReference<>(null, 0);

int[] stampHolder = new int[1];
Node current = top.get(stampHolder);
int stamp = stampHolder[0];

// 값과 "버전"을 함께 비교한다
top.compareAndSet(current, newNode, stamp, stamp + 1);
```

| 클래스 | 용도 |
| --- | --- |
| `AtomicStampedReference<T>` | 참조 + **정수 버전**을 함께 CAS |
| `AtomicMarkableReference<T>` | 참조 + **boolean 마크**를 함께 CAS |

**값이 A로 돌아와도 버전은 증가해 있으므로** 변경을 감지할 수 있다.

> 💡 데이터베이스의 **낙관적 락**(버전 컬럼)이 정확히 같은 아이디어다. JPA의 `@Version`이 그것이다.

# 9. 스핀락 구현

## 9.1 CAS 없이 만들어보기

`synchronized`도 `ReentrantLock`도 쓰지 않고 락을 직접 만들어보자.

```java
public class SpinLockBad {

    private volatile boolean lock = false;

    public void lock() {
        while (true) {
            if (!lock) {          // ① 락 사용 여부 확인
                sleep(100);       // 문제를 드러내기 위한 장치
                lock = true;      // ② 락의 값 변경
                break;
            } else {
                log("락 획득 실패 - 스핀 대기");
            }
        }
        log("락 획득 완료");
    }

    public void unlock() {
        lock = false;
        log("락 반납 완료");
    }
}
```

```text
18:39:01.863 [ Thread-1] 락 획득 완료
18:39:01.863 [ Thread-2] 락 획득 완료     ← ⚠️ 둘 다 획득!
```

## 9.2 원인 — 또 check-then-act다

```text
① 락 사용 여부 확인 (check)
② 락의 값 변경     (act)

⚠️ ①과 ② 사이에 다른 스레드가 똑같이 ①을 통과한다
```

**이전 글의 은행 예제와 구조가 완전히 똑같다.** `volatile`로 가시성은 확보했지만, **쪼개진 두 단계**가 문제다. 1.2의 표로 보면 왼쪽 아래 칸이다.

## 9.3 CAS로 수정

```java
public class SpinLock {

    private final AtomicBoolean lock = new AtomicBoolean(false);

    public void lock() {
        log("락 획득 시도");
        while (!lock.compareAndSet(false, true)) {   // ⭐ 확인과 변경이 하나의 연산
            log("락 획득 실패 - 스핀 대기");
        }
        log("락 획득 완료");
    }

    public void unlock() {
        lock.set(false);          // 대입 하나 = 원자적
        log("락 반납 완료");
    }
}
```

```text
[ Thread-2] 락 획득 완료
[ Thread-1] 락 획득 실패 - 스핀 대기     ✅ 하나만 획득
[ Thread-2] 비즈니스 로직 실행
[ Thread-2] 락 반납 완료
[ Thread-1] 락 획득 완료
```

> ⭐ **핵심: 쪼개진 두 연산을 하나의 원자적 연산으로 합친다.**
> 이게 CAS가 하는 일의 전부다.

## 9.4 ⚠️ 스핀락의 치명적 단점

임계 영역이 조금만 길어져도 이렇게 된다.

```java
log("비즈니스 로직 실행");
sleep(1);                  // 락을 1ms 동안 쥐고 있으면?
```

```text
[ Thread-2] 락 획득 실패 - 스핀 대기
[ Thread-2] 락 획득 실패 - 스핀 대기
[ Thread-2] 락 획득 실패 - 스핀 대기
... (10여 회 반복)
```

**`RUNNABLE` 상태로 계속 돌기 때문에 CPU를 그대로 태운다.** 이전 글의 `yield()` 논의와 정확히 같은 문제다.

| | 락 대기 시 | CPU |
| --- | --- | --- |
| `synchronized` | `BLOCKED` (스케줄러에서 제외) | ~0% |
| `ReentrantLock` | `WAITING` (park) | ~0% |
| **스핀락** | ⚠️ **`RUNNABLE`** | **100%** |

제자리에서 회전하는 것처럼 보인다고 해서 **스핀 락(바쁜 대기)**이라고 부른다.

## 9.5 💡 이 스핀락은 학습용이다

실제로 쓰려면 빠진 게 많다.

| 빠진 것 | 결과 |
| --- | --- |
| **재진입 불가** | 같은 스레드가 다시 `lock()` → 💀 자기 자신과 데드락 |
| **소유자 확인 없음** | 아무 스레드나 `unlock()` 호출 가능 |
| `Thread.onSpinWait()` 없음 | 전력·성능 손해 |
| 공정성 없음 | 기아 가능 |

```java
while (!lock.compareAndSet(false, true)) {
    Thread.onSpinWait();      // ⭐ Java 9+ — 스핀 중임을 CPU에 알림
}
```

# 10. 낙관 vs 비관, 그리고 LongAdder

## 10.1 두 접근법

| | 락 (비관적) | CAS (낙관적) |
| --- | --- | --- |
| 가정 | "누군가 방해할 것이다" | "대부분 충돌하지 않는다" |
| 방식 | 먼저 막고 들어간다 | 일단 하고 충돌하면 재시도 |
| 대기 상태 | `BLOCKED` / `WAITING` | `RUNNABLE` (스핀) |
| CPU (대기 중) | ~0% | ⚠️ 소모 |
| 컨텍스트 스위칭 | ⚠️ 발생 | 없음 |
| 복잡한 로직 | ✅ 가능 | ❌ 어렵다 |

## 10.2 선택 기준

```text
임계 영역이 얼마나 오래 걸리나?
   │
   ├─ 나노초 단위 (변수 증가, 플래그 교체)   → ⭐ CAS
   │
   ├─ 마이크로초 단위 (짧은 계산)            → CAS 또는 락
   │
   └─ 밀리초 이상 (DB, 네트워크, 파일 I/O)   → ⭐ 반드시 락
                                              (CAS 쓰면 CPU만 태운다)
```

> ⭐ **기본은 락, 아주 짧은 연산에 한정해서 CAS.**
> 대부분의 애플리케이션은 공유 자원에서 충돌할 가능성보다 충돌하지 않을 가능성이 훨씬 높다. 주문 수 증가 같은 단순 연산이라면 CAS가 좋다. 반면 데이터베이스나 다른 서버의 응답을 기다리는 것처럼 **수 밀리초 이상 걸리는 작업에 CAS를 쓰면 안 된다.**

## 10.3 💡 사실 "락 vs CAS"라는 대립 구도가 정확하진 않다

```text
ReentrantLock 내부
   │
   ▼
AQS 의 state 를 compareAndSetState() 로 변경  ← ⭐ CAS 다!
   │
   ▼
실패하면 LockSupport.park() 로 재운다
```

**`ReentrantLock` 자체가 CAS 위에 세워져 있다.** 차이는 "CAS가 실패했을 때 무엇을 하느냐"다.

| | 실패 시 |
| --- | --- |
| `AtomicInteger` | **즉시 재시도** (스핀) |
| `ReentrantLock` | 몇 번 시도 후 **park()로 재운다** |

그래서 정확한 대비는 **"스핀 vs 파킹"**이다. CAS는 `AtomicXXX`뿐 아니라 `ConcurrentHashMap`, `ConcurrentLinkedQueue`, AQS(즉 모든 `Lock`)에 다 들어 있다.

## 10.4 LongAdder — CAS의 충돌 문제를 푼 도구

카운터에 스레드가 많이 몰리면 `AtomicLong`은 재시도 루프에서 시간을 다 쓴다. Java 8의 `LongAdder`가 이걸 해결한다.

```text
[ AtomicLong ]                      [ LongAdder ]

  모든 스레드가                       스레드마다 다른 칸을 두드린다
  하나의 변수를 두드린다
                                      Cell[0] ← Thread-1
    value ← Thread-1                  Cell[1] ← Thread-2
          ← Thread-2                  Cell[2] ← Thread-3
          ← Thread-3                  Cell[3] ← Thread-4
          ← Thread-4
                                      sum() = Cell[0]+[1]+[2]+[3]
  ⚠️ 캐시 라인 핑퐁                   ✅ 충돌 자체가 줄어든다
  ⚠️ 재시도 폭증
```

```java
LongAdder counter = new LongAdder();
counter.increment();        // 각자 자기 셀에 CAS
long total = counter.sum(); // 읽을 때 합산
```

| | `AtomicLong` | `LongAdder` |
| --- | --- | --- |
| 쓰기 경쟁 심함 | ⚠️ 느림 | ⭐ **빠름** |
| 읽기가 잦음 | ⭐ `get()`이 O(1) | ⚠️ `sum()`이 셀 순회 |
| 정확한 순간값 | ⭐ 보장 | ⚠️ **스냅샷이 아님** |
| CAS 기반 로직 | ⭐ `compareAndSet()` 가능 | ❌ 없음 |

> **통계·모니터링 카운터라면 `LongAdder`, 정확한 현재값이나 CAS가 필요하면 `AtomicLong`.**

> 💡 관련 용어로 **false sharing**이 있다. 서로 다른 변수가 같은 캐시 라인(보통 64바이트)에 있으면 한쪽만 써도 다른 쪽 캐시가 무효화된다. `LongAdder`의 `Cell`은 `@Contended`로 이걸 방지한다.

# 마무리 정리

## 한 줄 요약

> **락은 "끼어들지 못하게" 막고, CAS는 "끼어들었는지 확인"한다.**
> 그래서 임계 영역이 **나노초 단위일 때만** CAS가 이긴다. 길어지면 CPU만 태운다.

## 헷갈리기 쉬운 포인트 10가지

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | `volatile`을 붙이면 `i++`도 안전하다 | **원자성은 별개.** 여전히 3단계 |
| 2 | 원자적이면 멀티스레드에서 안전하다 | **가시성도 필요**하다 |
| 3 | `volatile int i = 0`은 volatile이라 원자적 | `int` **대입이 원래** 원자적 |
| 4 | 996 → 989는 volatile이 악화시킨 것 | **매 실행마다 다른** 값일 뿐 |
| 5 | 성능 표가 멀티스레드 비교다 | **단일 스레드** 측정이다 |
| 6 | `BasicInteger: 14ms`는 진짜 속도다 | **JIT가 루프를 최적화**한 결과 |
| 7 | CAS는 항상 락보다 빠르다 | **경쟁이 심하면 역전**될 수 있다 |
| 8 | CAS는 블로킹이 없어 효율적이다 | **스핀도 CPU를 쓰는 대기**다 |
| 9 | 값이 같으면 아무 일도 없었던 것이다 | **ABA 문제**. 돌아왔을 수 있다 |
| 10 | 락과 CAS는 대립하는 기술이다 | **`ReentrantLock`도 내부는 CAS** |

## 동시성 도구 최종 지도

| 필요한 것 | 도구 |
| --- | --- |
| 가시성만 | `volatile` |
| 단일 변수 원자 연산 | ⭐ `AtomicXXX` (CAS) |
| 경쟁 심한 카운터 | ⭐ `LongAdder` |
| 참조 + ABA 방지 | `AtomicStampedReference` |
| 여러 줄을 묶는 임계 영역 | `synchronized` |
| 타임아웃·취소·공정성 | `ReentrantLock` |
| 스레드 간 협력 | `Condition`, `BlockingQueue` |
| 아예 공유하지 않기 | ⭐ 불변 객체, `ThreadLocal` |
