# CAS - 동기화와 원자적 연산

## 원자적 연산 - 소개

### 원자적 연산
- 컴퓨터 과학에서 사용하는 원자적 연산의 의미는 해당 연산이 더 이상 나눌 수 없는 단위로 수행된다는 것을 의미
- 예시
    ```java
    volatile int i = 0;
    ```
    - 이 연산은 둘로 쪼갤 수 없는 원자적 연산

    ```java
    i = i + 1
    ```
    - 이 연산은 원자적 연산이 아님
      - i의 값을 읽음
      - 읽은 i에 1을 더함
      - 더한 값을 i에 대입함
- 원자적 연산은 멀티스레드 상황에서 아무런 문제가 발생하지 않음
- 원자적 연산이 아닌 경우에는 synchronized 블럭이나 Lock 등을 사용해서 안전한 임계 영역을 만들어야 함

### 문제가 되는 상황
- 하나의 스레드가 작업을 전부 완료하고, 다른 스레드가 작업을 완료하는 경우는 문제가 되지 않음
- **동시에 여러 스레드가 작업을 하는 경우**
    ```text
    스레드 1: i를 읽음 => i = 0
    스레드 2: i를 읽음 => i = 0
    스레드 1: i+1 = 1
    스레드 2: i+1 = 1
    스레드 1: i=1
    스레드 2: i=1
    결과: i=1
    기대한 결과: 2
    ```

## 원자적 연산 - 시작

### 예제 코드
```java
public interface IncrementInteger {

    void increment();

    int get();
}
```

```java
public class BasicInteger implements IncrementInteger {

    private int value;

    @Override
    public void increment() {
        value++;
    }

    @Override
    public int get() {
        return value;
    }
}
```

```java
public class IncrementThreadMain {

    private static int THREAD_COUNT = 1000;

    public static void main(String[] args) throws InterruptedException {
        test(new BasicInteger());
    }

    private static void test(IncrementInteger incrementInteger) throws InterruptedException {
        Runnable runnable = new Runnable() {

            @Override
            public void run() {
                sleep(10); // 너무 빠리 실행되기 때문에, 다른 스레드와 동시 실행을 위해 잠깐 쉬었다가 실행
                incrementInteger.increment();
            }
        };

        List<Thread> threads = new ArrayList<>();
        for (int i = 0; i < THREAD_COUNT; i++) {
            Thread thread = new Thread(runnable);
            threads.add(thread);
            thread.start();
        }

        for (Thread thread : threads) {
            thread.join();
        }

        int result = incrementInteger.get();
        System.out.println(incrementInteger.getClass().getSimpleName() + " result: " + result);
    }
}
```
- 실행 결과
    ```text
    BasicInteger result: 996
    ```
    - 1000이 나오지 않음
    - volatile을 적용하면 될까?

## 원자적 연산 - volatile, synchronized

### volatile 적용
```java
public class VolatileInteger implements IncrementInteger {

    private volatile int value;

    @Override
    public void increment() {
        value++;
    }

    @Override
    public int get() {
        return value;
    }
}
```
- 실행 결과
    ```text
    VolatileInteger result: 989
    ```
    - 문제가 해결되지 않음
    - 왜 해결이 되지 않을까?
      - volatile은 여러 CPU의 캐시 메모리를 무시하고 메인 메모리에 동기화되지 않는 문제를 해결할 뿐임
      - 하지만 이 문제는 메인 메모리를 직접 사용해도 발생하는 문제임
      - 이 문제의 근본은 연산자체가 나누어져있기 때문임

### synchronized 적용
```java
public class SynchronizedInteger implements IncrementInteger {

    private int value;

    @Override
    public synchronized void increment() {
        value++;
    }

    @Override
    public synchronized int get() {
        return value;
    }
}
```
- 실행 결과
    ```text
    SynchronizedInteger result: 1000
    ```
    - 해결된 이유: 증가 연산을 호출하는 것을 한 번에 하나의 스레드만 할 수 있기 때문

## 원자적 연산 - AtomicInteger

### AtomicInteger
- 이름 그대로 원자적 Integer라는 뜻

### 예제 코드
```java
public class MyAtomicInteger implements IncrementInteger {

    private final AtomicInteger atomicInteger = new AtomicInteger(0);

    @Override
    public void increment() {
        atomicInteger.incrementAndGet();
    }

    @Override
    public int get() {
        return atomicInteger.get();
    }
}
```
- 실행 결과
    ```text
    MyAtomicInteger result: 1000
    ```

### AtomicInteger 기능
- 멀티 스레드 상황에서 안전하고 또 다향한 값 증가, 감소 연산을 제공함
- 특정 값을 증가하거나 감소해야하는데 여러 스레드가 해당 값을 공유해야 한다면, AtomicInteger를 사용하면 됨
- 참고
  - AtomicInteger, AtomicLong, AtomicBoolean 등 다양한 AtomicXXX가 존재함

## 원자적 연산 - 성능 테스트

### 성능 테스트
```java
public class IncrementPerformanceMain {

    private static final long COUNT = 100_000_000;

    public static void main(String[] args) {
        test(new BasicInteger());
        test(new VolatileInteger());
        test(new SynchronizedInteger());
        test(new MyAtomicInteger());
    }

    public static void test(IncrementInteger incrementInteger) {
        long startMs = System.currentTimeMillis();

        for (int i = 0; i < COUNT; i++) {
            incrementInteger.increment();
        }

        long endMs = System.currentTimeMillis();
        System.out.println(incrementInteger.getClass().getSimpleName() + ": ms = " + (endMs - startMs));
    }
}
```
- 실행 결과
    ```text
    BasicInteger: ms = 14
    VolatileInteger: ms = 839
    SynchronizedInteger: ms = 2186
    MyAtomicInteger: ms = 881
    ```
    
### 실행 결과 분석
- BasicInteger
  - 가장 빠름
  - CPU 캐시를 적극 사용함
  - 안전한 임게 영역도 없고, volatile도 사용하지 않기 때문에 멀티스레드 상황에는 사용할 수 없음
  - 단일 스레드가 사용하는 경우 효율적임

- VolatileInteger
  - volatile을 사용해서 CPU 캐시를 사용하지 않고 메인 메모리를 사용함
  - 안전한 임게 영역이 없기 때문에 멀티스레드 상황에는 사용할 수 없음
  - 단일 스레드가 사용하기에는 BasicInteger보다 느림
  - 멀티 스레드 환경에서도 안전하지 않음

- SynchronizedInteger
  - synchronized를 사용한 안전한 임계 영역이 있기 때문에 멀티 스레드 상황에서 사요할 수 있음
  - 다만 연산을 원자적으로 하기보다는 스레드 자체의 연산을 한 번에 하나의 스레드가 연산을 할 수 있도록 막는 것이기 때문에 성능이 좋지 않음

- MyAtomicInteger
  - 자바가 제공하는 AtomicInteger를 사용함
  - 멀티 스레드 환경에서 안전하게 동작함
  - 성능도 synchronized, Lock(ReentrantLock)을 사용하느 경우보다 빠름

### AtomicInteger의 비밀
- Lock을 사용하지 않음
- 메서드 락을 사용하지 않고, 원자적 연산을 만들어냄
- 그래서 락을 사용하는 것보다 빠름 - **CAS 연산**

## CAS 연산 1

### 락 기간 방식의 문제점
- 동작 방식
  - 락이 있는지 확인함
  - 락을 획득하고 임계영역에 들어감
  - 작업을 수행함
  - 락을 반납함

- 락을 사용하는 방식은 직관적이지만 상대적으로 무거운 방식임
- 스레드 상태로 계속 바뀜

### CAS
- 락을 걸지 않고, 원자적인 연산을 수행할 수 있는 방법
- Compare And Swap (CAS)
- 락을 사용하지 않기 때문에 락 프리(lock free) 기법이라고도 함
- 참고로 락을 완전히 대체하는 것이 아니고, 작은 단위의 일부 영역에 적용할 수 있음

### 예제 코드
```java
public class CasMainV1 {

    public static void main(String[] args) {
        AtomicInteger atomicInteger = new AtomicInteger(0);
        System.out.println("start value = " + atomicInteger.get());


        boolean result1 = atomicInteger.compareAndSet(0, 1);
        // - 현재 값이 0이면 1로 바꿔달라는 의미
        System.out.println("result1 = " + result1 + ", value = " + atomicInteger.get());

        boolean result2 = atomicInteger.compareAndSet(0, 1);
        // - 위에서 1로 변경이 되었기 때문에 false가 나옴
        System.out.println("result2 = " + result2 + ", value = " + atomicInteger.get());
    }
}
```
- 실행 결과
    ```text
    start value = 0
    result1 = true, value = 1
    result2 = false, value = 1
    ```
    
### compareAndSet(expectedValue, newValue)
- 현재 값이 expectedValue이면 newValue로 변경하라는 메서드
  - 변경하면 true를 반환
  - 변경하지 못하면 false를 반환

- 핵심: **이 메서드는 원자적으로 실행된다는 점*
  - 제공하는 기능이 바로 CAS 연산

### 내부 동작
- 메인 메모리에서 값을 확인
- 예상했던 값이면 새로운 값으로 변경
- 이 연산은 사실 원자적인 연산이 아님
  - 그렇다면 어떻게 원자적으로 연산이 일어날 수 있는 것일까?
    - **하드웨어의 지원**

### CPU 하드웨어의 지원
- CPU는 다음 두 과정을 하나로 묶어서 원자적인 명령으로 만들어버림
  - 값을 확인
  - 읽은 값이 예상했던 값이면 원하는 값으로 변경
- 따라서 중간에 다른 스레드가 개입할 수 없음
- 성능에 아주 큰 영향을 미치진 않음 (영향이 가긴함)

### 궁금증
- 어떻게 락을 대체한다는 걸까?
- 다음 시간에 알아보자

## CAS 연산 2

### AtomicInteger.incrementAndGet() 메서드를 구현
```java
public class CasMainV2 {

    public static void main(String[] args) {
        AtomicInteger atomicInteger = new AtomicInteger(0);
        System.out.println("start value = " + atomicInteger.get());

//        int result1 = atomicInteger.incrementAndGet();
//        System.out.println("result1 = " + result1);
//
//        int result2 = atomicInteger.incrementAndGet();
//        System.out.println("result2 = " + result2);

        // incrementAndGet 구현
        int resultValue1 = incrementAndGet(atomicInteger);
        System.out.println("resultValue1 = " + resultValue1);

        int resultValue2 = incrementAndGet(atomicInteger);
        System.out.println("resultValue2 = " + resultValue2);
    }

    public static int incrementAndGet(AtomicInteger atomicInteger) {
        int getValue;
        boolean result;
        do {
            getValue = atomicInteger.get();
            log("getValue: " + getValue);
            result = atomicInteger.compareAndSet(getValue, getValue + 1); // 이건 원자적으로 수행됨
            log("result: " + result);
        } while (!result);

        return getValue + 1;
    }
}
```
- 실행 결과
    ```text
    start value = 0
    17:45:03.421 [     main] getValue: 0
    17:45:03.424 [     main] result: true
    resultValue1 = 1
    17:45:03.425 [     main] getValue: 1
    17:45:03.426 [     main] result: true
    resultValue2 = 2
    ```
    - 락을 걸지 않고, CAS 연산을 사용해서 값을 증가시킴
    - CAS 부분이 원자적으로 연산이라는 점을 생각해야됨
    - 그래서 동시에 두 스레드가 값을 업데이트 칠 수 있지 않나요라는 질문을 상쇄할 수 있음
    - 다른 스레드가 중간에 getValue를 변경하면 안되는 것임
    - 실패하면 while 문에서 다시 실행하게 됨 (false를 반환하기 때문에)
    - 주의사항
      - return atomicInteger.get()을 해도 되지 않을까?
      - 원자적 연산이 성공한 시점에서 getValue를 변경해주어야함
      - 만약 atomicInteger.get()을 return 하게 되면 다른 스레드가 atomicInteger.compareAndSet()을 호출해서 다른 값이 반환될 수도 있음

## CAS 연산 3

### 예제 코드
```java
public class CasMainV3 {

    private static int THREAD_COUNT = 2;

    public static void main(String[] args) throws InterruptedException {
        AtomicInteger atomicInteger = new AtomicInteger(0);
        System.out.println("start value = " + atomicInteger.get());

        Runnable runnable = new Runnable() {

            @Override
            public void run() {
                incrementAndGet(atomicInteger);
            }
        };

        List<Thread> threads = new ArrayList<>();
        for (int i = 0; i < THREAD_COUNT; i++) {
            Thread thread = new Thread(runnable);
            threads.add(thread);
            thread.start();
        }

        for (Thread thread : threads) {
            thread.join();
        }

        int result = atomicInteger.get();
        System.out.println(atomicInteger.getClass().getSimpleName() + " resultValue: " + result);
    }
    
    public static int incrementAndGet(AtomicInteger atomicInteger) {
        int getValue;
        boolean result;
        do {
            getValue = atomicInteger.get();
            sleep(100); // 스레드 동시 실행을 위한
            log("getValue: " + getValue);
            result = atomicInteger.compareAndSet(getValue, getValue + 1); // 이건 원자적으로 수행됨
            log("result: " + result);
        } while (!result);

        return getValue + 1;
    }

}
```
- 실행 결과
    ```text
    start value = 0
    18:09:20.558 [ Thread-1] getValue: 0
    18:09:20.558 [ Thread-0] getValue: 0
    18:09:20.559 [ Thread-1] result: true
    18:09:20.559 [ Thread-0] result: false
    18:09:20.667 [ Thread-0] getValue: 1
    18:09:20.667 [ Thread-0] result: true
    AtomicInteger resultValue: 2
    ```
    - 중간에 false가 발생하는 것을 확인할 수 있음
    - false가 발생하고 다시 true를 반환해서 최종적으로 2가 정상적으로 증가됨을 확인할 수 있음

### 결론
- 현재 변수의 값을 읽어옴
- 변수의 값을 1 증가 시핌
  - 원래 값이 같은지 확인 (CAS 연산 사용)
- 동일하다면 증가된 값을 변수에 저장하고 종료함
- 동일하지 않다면 다른 스레드가 값을 중간에 변경한 것이므로, 다시 처음으로 돌아가 위 과정을 반복함

### 단점
- 충돌이 빈번하게 발생하는 상황에서는 성능에 문제가 생길 수 있음
- 반복문을 계속 돌기 때문에 CPU 자원을 많이 소모하게 됨

### CAS vs Lock 방식 비교
- 비관적 접근법
- 데이터에 접근하기 전에 항상 락을 획득
- 다른 스레드의 접근을 막음
- 다른 스레드가 방해할 것이다라고 가정 (비관적)

### CAS 방식
- 낙관적 접근법
- 락을 사용하지 않고 데이터에 바로 접근
- 충돌이 발생하면 그때 재시도
- 대부분의 경우 충돌이 없을 것이다라고 가정 (낙관적)

### 정리
- 충돌이 많이 없는 경우에는 CAS 연산이 빠른 것을 확인할 수 있음
- 충돌이 많이 발생하지 않는 연산은 어떤 것들이 있을까? 언제 CAS 연산을 사용하면 좋을까?
- 사실 간단한 CPU 연산은 너무 빨리 처리되기 때문에 충돌이 자주 발생하지 않음
- 충돌이 발생하기도 전에 이미 연산을 완료하는 경우가 더 많음
- **간단한 CPU 연산에는 락보다는 CAS를 사용하는 것이 효과적임**

## CAS 락 구현 1

### CAS를 활용해서 락을 구현
- synchronized, Lock(ReentrantLock) 없이 CAS를 활용해서 락을 구현해보기
- **스핀 락**

### 구현
```java
public class SpinLockBad {

    private volatile boolean lock = false;
    // - true: 누군가 락을 가져감

    public void lock() {
        log("락 획득 시도");
        while (true) {
            if (!lock) { // 락 사용 여부 확인
                sleep(100); // 문제 상황 확인용, 스레드 대기
                lock = true;
                break;
            } else {
                // 락을 획득할 대까지 스핀 대기(바끈 대기) 함 - runnable 상태
                log("락 획득 실패 - 스핀 대기");
            }
        }
        log("락 획득 완료");
    }

    public void unlock() {
        lock = false;
        log("락 반납 완료");
    }
}
```
- 핵심: 스레드를 대기하지 않고 runnable 상태로 락 획득을 계속 시도함
- volatile을 사용해서 메모리 가시성 문제를 해결 (바로 상태 반영을 확인할 수 있도록)

```java
public class SpinLockMain {

    public static void main(String[] args) {
        SpinLockBad spinLock = new SpinLockBad();

        Runnable task = new Runnable() {

            @Override
            public void run() {
                spinLock.lock();
                try {
                    // critical section
                    log("비즈니스 로직 실행");
                } finally {
                    spinLock.unlock();
                }
            }
        };

        Thread thread1 = new Thread(task, "Thread-1");
        Thread thread2 = new Thread(task, "Thread-2");

        thread1.start();
        thread2.start();
    }
}
```
- 실행 결과
    ```text
    18:39:01.743 [ Thread-1] 락 획득 시도
    18:39:01.743 [ Thread-2] 락 획득 시도
    18:39:01.863 [ Thread-1] 락 획득 완료
    18:39:01.863 [ Thread-2] 락 획득 완료
    18:39:01.863 [ Thread-1] 비즈니스 로직 실행
    18:39:01.863 [ Thread-2] 비즈니스 로직 실행
    18:39:01.863 [ Thread-1] 락 반납 완료
    18:39:01.863 [ Thread-2] 락 반납 완료
    ```

- CAS 연산 사용
- 참고로 락을 반납하는 연산은 하나의 원자적인 연산 (lock = false)

## CAS 락 구현 2

### CAS 연산을 사용해서 락 구현
```java
public class SpinLock {

    private final AtomicBoolean lock = new AtomicBoolean(false);
    // - true: 누군가 락을 가져감

    public void lock() {
        log("락 획득 시도");
        while (!lock.compareAndSet(false, true)) {
            log("락 획득 실패 - 스핀 대기");
        }
        log("락 획득 완료");
    }

    public void unlock() {
        lock.set(false);
        log("락 반납 완료");
    }
}
```

### 핵심
- 두 개로 쪼개진 연산을 하나의 연산으로 원자적으로 실행될 수 있게 해야한다는 것임
  - 락 사용 여부 확인
  - 락의 값 변경
  - **해결: CAS 연산 사용 - AtomicBoolean**

### CAS 단점
- 치명적인 단점

public class SpinLockMain {

    public static void main(String[] args) {
//        SpinLockBad spinLock = new SpinLockBad();
        SpinLock spinLock = new SpinLock();

        Runnable task = new Runnable() {

            @Override
            public void run() {
                spinLock.lock();
                try {
                    // critical section
                    log("비즈니스 로직 실행");
                    sleep(1); // 오래 걸리는 로직에서 스핀 락 사용 X
                } finally {
                    spinLock.unlock();
                }
            }
        };

        Thread thread1 = new Thread(task, "Thread-1");
        Thread thread2 = new Thread(task, "Thread-2");

        thread1.start();
        thread2.start();
    }
}

## 정리

### 락과 CAS 사용 방식
- CAS 장점
  - 낙관적 동기화: 락을 걸지 않고도 값을 안전하게 업데이트 할 수 있음
  - 락 프리: CAS는 락을 사용하지 않기 때문에 락을 획득하기 위해 대기하는 시간이 없음
    - 스레드가 블로킹 되지 않으며, 병렬 처리가 더 효율적일 수 있음

- CAS 단점
  - 충돌이 빈번한 경우: 여러 스레드가 동시에 동일한 변수에 접근하여 업데이트를 시도할 때 충돌이 발생할 수 있음
  - 충돌이 발생하면 CAS는 루프를 돌며 재시도해햐함
  - 반복적인 재시도로 인해 오버헤드가 발생
  - 스핀락과 유사한 오버해드

- 동기화 락의 장점
  - 충돌 관리: 여러 스레드가 경쟁할 경우에도 안정적으로 동작함
  - 안전성: 복잡한 상황에서도 락은 일관성 있는 동작을 보장함
  - 스레드 대기: 락을 대기하는 스레드는 CPU를 거의 사용하지 않음

- 동기화 락의 단점
  - 락 획득 대기 시간
  - 컨텍스트 스위칭 오버헤드

### 결론 
- 일반적으로 동기화 락을 사용하고, 아주 특별한 경우에 한정해서 CAS를 사용해서 최적화해야함
- 임계 영역이 필요는 하지만 연산이 길지 않고 매우매우매우 짧게 끝날 때 사용해야함
- 데이터베이스를 기다린다거나, 다른 서버의 요청을 기다리는 것처럼 오래 기다리는 작업에 CAS를 사용하면 안됨

### 실무 관점
- 대부분의 애플리케이션들은 공유 자원을 사용할 때 충돌할 가능성보다 충돌하지 않을 가능성이 훨씬 높음
- 주문 수 증가 예시
  - 주문 수 증가는 단순한 연산이라 CAS 연산을 사용하는 것이 좋음
  - 반면에 데이터베이스를 기다린다거나, 다른 서버의 요청을 기다리는 것처럼 수 밀리초 이상의 시간이 걸리는 작업이면 CAS를 사용하면 안됨
