# 생산자 소비자 문제 - 2

## Lock Condition - 예제 4

### 문제
- 생산자가 생산자를 깨우고, 소비자가 소비자를 깨우는 비효율 문제를 어떻게 해결할 수 있을까?

### 해결 방안
- 핵심:
  - 생산자 스레드는 데이터를 생성하고, 대기 중인 소비자 스레드에게 알려줌
  - 소비자 스레드는 데이터를 소비하고, 대기 중인 생산자 스레드에게 알려줌
  - **생산자/소비자 용 대기 집합을 따로 관리할 수 있으면 됨**

- 결론:
  - **Lock, ReentrantLock을 사용**

### synchronized, wait(), notify() => Lock, ReentrantLock을 재구현
```java
public class BoundedQueueV4 implements BoundedQueue {

    private final Lock lock = new ReentrantLock();
    private final Condition condition = lock.newCondition(); // 새로운 스레드 대기 집합

    private final Queue<String> queue = new ArrayDeque<>();
    // - synchronized를 사용해서 한 번 한 스레드에서만 호출할 수 있기 때문에 동기화 문제가 발생하지 않음
    private final int max;

    public BoundedQueueV4(int max) {
        this.max = max;
    }

    @Override
    public void put(String data) {
        lock.lock();
        try {
            while (queue.size() == max) {
                log("[put] 큐가 가득 참. 대기: " + data);
                try {
                    condition.await(); // 여기서 기다림
                    log("[put] 생산자 깨어남"); // Runnable
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }

            queue.offer(data);
            log("[put] 생산자 데이터 저장, notify() 호출");
            condition.signal();
        } finally {
            lock.unlock();
        }
    }

    @Override
    public String take() {
        lock.lock();
        try {
            while (queue.isEmpty()) {
                log("[take] 큐에 데이터가 없음. 소비자 대기");
                try {
                    condition.await(); // 여기서 기다림
                    log("[take] 소비자 깨어남");
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }
            String data = queue.poll();
            log("[take] 소비자 데이터 획득, notify() 호출");
            condition.signal();
            return data;
        } finally {
            lock.unlock();
        }
    }

    @Override
    public String toString() {
        return queue.toString();
    }
}
```

### Condition
- ReentrantLock을 사용하는 스레드가 대기하는 스레드 대기 공간
- lock.newCondition() 메서드를 호출하면 스레드 대기 공간이 만들어짐
- 참고: Object.wait()에서 사용한 스레드 대기 공간은 모든 객체 인스턴스가 내부에 기본으로 가지고 있음
  - Lock(ReentrantLock)을 사용하는 경우, 스레드 대기 공간을 직접 만들어서 사용해야함

### condition.wait()
- Object.wait()와 유사한 기능
- 지정한 condition에 현재 스레드를 대기 상태로 보관함
- 이때 ReentrantLock에서 획득한 락을 반납하고 대기 상태로 condition에 보관함

### condition.signal()
- Object.notify()와 유사한 기능
- 지정한 condition에 대기 중인 스레드 하나를 깨움
- 깨어난 스레드는 condition에서 빠져나옴

## 생산자 소비자 대기 공간 분리 - 예제 5 코드

### 해결 방안
- consumerCondition
- producerCondition
- **대기 공간 분리**

### 예제 코드
```java
public class BoundedQueueV5 implements BoundedQueue {

    private final Lock lock = new ReentrantLock();
    private final Condition producerCond = lock.newCondition();
    private final Condition consumerCond = lock.newCondition();

    private final Queue<String> queue = new ArrayDeque<>();
    private final int max;

    public BoundedQueueV5(int max) {
        this.max = max;
    }

    @Override
    public void put(String data) {
        lock.lock();
        try {
            while (queue.size() == max) {
                log("[put] 큐가 가득 참. 대기: " + data);
                try {
                    producerCond.await(); // 생산자용 스레드 여기서 기다림
                    log("[put] 생산자 깨어남"); // Runnable
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }

            queue.offer(data);
            log("[put] 생산자 데이터 저장, notify() 호출");
            consumerCond.signal(); // 소비자용 스레드를 깨움
        } finally {
            lock.unlock();
        }
    }

    @Override
    public String take() {
        lock.lock();
        try {
            while (queue.isEmpty()) {
                log("[take] 큐에 데이터가 없음. 소비자 대기");
                try {
                    consumerCond.await(); // 소비자용 스레드 여기서 기다림
                    log("[take] 소비자 깨어남");
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }
            String data = queue.poll();
            log("[take] 소비자 데이터 획득, notify() 호출");
            producerCond.signal(); // 생성자용 스레드를 깨움
            return data;
        } finally {
            lock.unlock();
        }
    }

    @Override
    public String toString() {
        return queue.toString();
    }
}
```

### Condition 분리
- consumerCond: 소비자를 위한 스레드 대기 공간
- producerCond: 생산자를 위한 스레드 대기 공간

### 핵심 아이디어
- 생산자는 소비자를 깨움
- 소비자는 생산자를 깨움

## 생산자 소비자 대기 공간 분리 - 예제 5 분석

### 분석
- put(data)
  - 큐가 가득 차면 생산자 스레드 대기 집합에서 wait()
  - 큐에 데이터를 생산하면 소비자 스레드 대기 집합에 signal()

- take()
  - 큐가 비어있으면 소비자 스레드 대기 집합에서 wait()
  - 큐에 데이터를 소비하면 생산자 스레드 대기 집합에 signal()

### Object.notify() vs Condition.siganl()
- Object.notify()
  - 대기 중인 스레드 중 임의의 하나를 선택해서 깨움
  - 스레드가 깨어나는 순서는 정의되어있지 않음
  - 보통 먼저 들어온 스레드가 먼저 수행되지만 구현에 따라 다를 수 있음
  - synchronized 블록 내에서 모니터 락을 가지고 있는 스레드가 호출해야함

- Condition.signal()
  - 대기 중인 스레드 중 하나를 깨우며, 일반적으로 FIFO 순서로 깨움
  - 자바 구현에 따라 달라질 수 있지만 Condition 내부에서 Queue 구조를 사용하기 때문에 FIFO 순서로 깨움
  - ReentrantLock을 가지고 있는 스레드가 호출해야함

### 헷갈리지 말아야할 점
- 현재 락은 lock 하나임
- 생산자/소비자 스레드를 깨운다고 한 들, 저 락이라는 것은 객체 인스턴스에 딱 하나만 존재함
- 그래서 저 락을 가지고 있는 스레드가 호출해야하는 원리는 달라지지 않음

## 스레드 대기

### synchronized 대기
- 대기 1: 락 획득 대기
  - Blocked 상태로 락 획득 대기
  - synchronized를 시작할 때 락이 없으면 대기
  - 다른 스레드가 synchronized를 빠져나갈 때 대기가 풀리며 락 획득 시도

- 대기 2: wait() 대기
  - Waiting 상태로 대기
  - wait()를 호출 했을 때 스레드 대기 집합에서 대기
  - 다른 스레드가 notify()를 호출 했을 때 빠져나감 => Waiting -> Blocked

### 락 대기 집합
- entrySet으로 부르기도 함
- 자바 내부에서 관리
- 여기서 Blocked 상태의 스레드들을 관리함

### synchronized vs ReentrantLock 대기
- synchronized
  - 대기 1: 모니터 락 획득 대기
    - 자바 객체 내부의 락 대기 집합에서 관리
    - Blocked 상태로 락 획득 대기
    - synchronized를 시작할 때 락이 없으면 대기
    - 다른 스레드가 synchronized를 빠져나갈 때 락 획득을 시도, 락을 획득하면 락 대기 집합을 빠져나감 (blocked -> runnable)

  - 대기 2: wait() 대기
    - wait()를 호출 했을 때, 자바 객체 내부의 스레드 대기 집합에서 관리
    - Waiting 상태로 대기
    - 다른 스레드가 notify()를 호출 했을 때 스레드 대기 집합을 빠져나감

- Lock(ReentrantLock)
  - 대기 1: ReentrantLock 락 획득 대기
    - ReentrantLock의 대기 큐에서 관리
    - **Waiting 상태로 대기**
    - lock.lock()을 호출 했을 때 락이 없으면 대기
    - 다른 스레드가 lock.unlock()을 호출 했을 때 대기가 풀리며 락 획득 시도, 락을 획득하면 대기 큐를 빠져나감

  - 대기 2: await() 대기
    - condition.await()를 호출 했을 때, condition 객체의 스레드 대기 공간에서 관리
    - Waiting 상태로 대기
    - 다른 스레드가 condition.signal()을 호출 했을 때, condition 객체의 스레드 대기 공간에서 빠져나감

### 주의할 점
- synchronized에서 락 획득 대기 상태에서는 interrupt를 받을 수 없음 (blocked)
- ReentrantLock에서도 락 획득 대기 상태가 waiting 상태이지만 interrupt를 받을 수 없음 (lock.lock()일 경우에만 해당)
  - 인터럽트를 받을 수 있는 메소드가 따로 정의되어있음
  - lock.lock()이 인터럽트를 받지 않는 이유
    - 관리가 복잡해짐
    - lockInterruptibly()를 사용할 때 unlock을 InterruptedException에서 처리하면 안됨
    - 락을 획득하지 못한 상태에서 인터럽트가 걸렸기 때문에 unlock()을 호출을 애초에 할 수 없음
    - 또한 lockInterruptibly()는 InterruptedException을 애초에 처리하도록 함

## BlockingQueue - 예제 6

### BlockingQueue
- java.util.concurrent.blockingQueue라는 특별한 멀티스레드 자료 구조를 제공함
- 이름 그대로 스레드를 차단할 수 있는 큐

- 데이터 추가 차단: 큐가 가득 차면 데이터 추가 작업(put()) 시도하는 스레드는 공간이 생길 때까지 차단
- 데이터 획득 차단: 큐가 비어 있으면 획득 작업(take()) 시도하는 스레드는 큐에 데이터가 들어올 때까지 차단

### 주요 메서드
- 데이터 추가 메서드: add(), offer(), put(), offer(타임아웃)
- 데이터 획득 메서드: take(), poll(timeout), remove(..)
- 큐를 상속받기 때문에 큐의 기능들도 사용할 수 있음

### 주요 구현체
- ArrayBlockingQueue: 배열 기반으로 구현되어있고, 버퍼의 크기가 고정되어있음
- LinkedBlockingQueue: 링크 기반으로 구현되어 있고, 버퍼의 크기를 고정할 수도, 무한하게 사용할 수도 있음
- BlockingDeque도 있음

### 사용 예제
```java
public class BoundedQueueV6_1 implements BoundedQueue {

    private final BlockingQueue<String> queue;

    public BoundedQueueV6_1(int max) {
        this.queue = new ArrayBlockingQueue<>(max);
    }

    @Override
    public void put(String data) {
        try {
            queue.put(data);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }

    @Override
    public String take() {
        try {
            return queue.take();
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }

    @Override
    public String toString() {
        return queue.toString();
    }
}
```

- ReentrantLock도 사용함
- 조금 다른 점은 lock.lock()이 아닌 lock.lockInterruptibly()를 사용함

## BlockingQueue 기능 설명

### 기능이 많은 이유
- 정말 여러 가지 상황이 발생할 수 있기 때문

### 큐가 가득 찾을 때 생각할 수 있는 선택지는 4가지가 있음
- 예외를 던진다. 예외를 받아서 처리함
- 대기하지 않음. 즉시 false를 반환
- 대기함
- 특정 시간만큼만 대기함


### BlockingQueue의 다양한 기능들
- Throws Exception
    - add(e): 저장된 요소를 큐에 추가하며, 큐가 가득 차면 IllegalStateException을 던짐
    - remove(): 큐에서 요소를 제거하며 반환함. 큐가 비어잇으면 NoSuchElementException을 던짐
    - element(): 큐의 머리 요소를 반환하지만 큐에서 제거하지 않음. 큐가 비어있으면 NoSuchElementException을 던짐

- Special Value
  - offer(e): 지정된 요소를 큐에 추가하려고 시도하고 큐가 가득차면 false를 반환함
  - poll(): 큐에서 요소를 제거하고 반환함. 큐가 비어있으면 null을 반환함
  - peek(): 큐의 머리 요소를 반환하지만, 요소를 큐에서 제거하지 않음. 큐가 비어있으면 null을 반환함

- Blocks
  - put(e)
  - take()
  - Examine: 해당 사항 없음 (조회 기능이 없음)

- Times Out
  - offer(e, time, unit): 지정된 요소를 큐에 추가하려고 시도함. 지정된 시간 동안 큐가 비워지지 않으면 false를 반환
  - poll(time, unit): 큐에서 요소를 제거하고 반환함. 큐에 요소가 없다면 지정된 시간 동안 요소가 준비되기를 기다리다가 시간이 초과되면 null을 반환함
  - Examine: 해당 사항 없음 (조회 기능이 없음)
