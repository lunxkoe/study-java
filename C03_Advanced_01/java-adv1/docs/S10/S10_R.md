## 1. V4 — Condition 도입

### 1.1 문제 재확인

앞 글의 결론이다.

> 생산자와 소비자가 **같은 대기 집합**을 쓰기 때문에 `notify()`가 엉뚱한 쪽을 깨운다.
> **대기 집합을 따로 관리할 수 있으면** 해결된다.

`synchronized`의 대기 집합은 객체당 **딱 하나**라 쪼갤 방법이 없다. 그래서 `ReentrantLock`으로 넘어간다.

### 1.2 코드

```java
public class BoundedQueueV4 implements BoundedQueue {

    private final Lock lock = new ReentrantLock();
    private final Condition condition = lock.newCondition();   // ⭐ 대기 공간을 직접 만든다

    private final Queue<String> queue = new ArrayDeque<>();
    private final int max;

    @Override
    public void put(String data) {
        lock.lock();
        try {
            while (queue.size() == max) {
                log("[put] 큐가 가득 참. 대기: " + data);
                try {
                    condition.await();              // ⭐ 락 반납 + 대기
                    log("[put] 생산자 깨어남");
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
            }
            queue.offer(data);
            log("[put] 생산자 데이터 저장, signal() 호출");   // 🔴 원문은 "notify()"
            condition.signal();
        } finally {
            lock.unlock();
        }
    }
    // take() 도 대칭
}
```

### 1.3 정정 노트

🔴 **소제목의 `condition.wait()`는 존재하지 않는 메서드다.**
`Condition` 인터페이스에는 `wait()`가 없다. **`await()`**가 맞다. 실제 코드는 `await()`를 쓰고 있는데 설명 소제목만 `wait()`로 되어 있다.

🔴 **로그 문구가 `notify() 호출`로 남아 있다.**
이제 `condition.signal()`을 호출하므로 **`signal() 호출`**로 바꿔야 코드와 로그가 맞는다. (V5에도 그대로 남아 있다.)

🔴 **주석이 이전 버전에서 복사됐다.**

```java
private final Queue<String> queue = new ArrayDeque<>();
// - synchronized를 사용해서 한 번 한 스레드에서만 호출할 수 있기 때문에 ...
```

이제 `synchronized`를 쓰지 않는다. **`ReentrantLock`으로 보호하기 때문에 안전하다**로 고쳐야 한다.

🟡 **`toString()`이 여전히 락 밖에서 호출된다.** 앞 글에서 지적한 문제가 그대로다. `ArrayDeque`를 락 없이 순회하므로 실제 코드라면 버그다.

### 1.4 V4가 아직 해결하지 못한 것

**Condition을 하나만 만들었으므로 V3(`wait/notify`)와 동작이 사실상 같다.** 생산자와 소비자가 같은 대기 공간을 쓰니 여전히 엉뚱한 쪽을 깨운다. V4는 **도구를 바꾼 단계**이고, 실제 해결은 V5다.

## 2. Condition의 정확한 API

### 2.1 `Object`의 것과 대응

| `Object` (모니터) | `Condition` | 차이 |
| --- | --- | --- |
| `wait()` | `await()` | |
| `wait(ms)` | `await(time, unit)` | 시간 단위 지정 가능 |
| — | `awaitNanos(nanos)` | ⭐ **남은 시간을 반환** |
| — | `awaitUninterruptibly()` | ⭐ **인터럽트 무시** |
| — | `awaitUntil(Date)` | 절대 시각 |
| `notify()` | `signal()` | |
| `notifyAll()` | `signalAll()` | |
| **객체당 1개 (고정)** | ⭐ **락당 여러 개** | 핵심 차이 |

### 2.2 💡 `Object`에 없는 두 가지

**① `awaitNanos()`는 남은 시간을 반환한다**

```java
long remaining = TimeUnit.SECONDS.toNanos(5);
while (!조건()) {
    if (remaining <= 0) return false;      // 진짜 타임아웃
    remaining = condition.awaitNanos(remaining);   // ⭐ 남은 시간만큼만 다시 대기
}
```

`wait(5000)`은 spurious wakeup으로 깨어나면 **다시 5초를 처음부터 기다린다.** 총 대기 시간이 5초를 넘어버린다. `awaitNanos()`는 남은 시간을 돌려주므로 **전체 타임아웃을 정확히 지킬 수 있다.**

**② `awaitUninterruptibly()`는 인터럽트를 무시한다**

`lock()`과 `lockInterruptibly()`의 관계가 `await()`에도 그대로 있다.

### 2.3 제약

```java
lock.lock();
try {
    condition.await();     // ✅ 락을 쥔 상태
} finally {
    lock.unlock();
}

condition.await();         // 💥 IllegalMonitorStateException
```

**`Condition`은 자기를 만든 `Lock`에 종속적이다.** `wait()`가 `synchronized` 안에서만 되는 것과 같은 원리다.

## 3. V5 — 대기 공간 분리

### 3.1 코드

```java
public class BoundedQueueV5 implements BoundedQueue {

    private final Lock lock = new ReentrantLock();
    private final Condition producerCond = lock.newCondition();   // 생산자 대기실
    private final Condition consumerCond = lock.newCondition();   // 소비자 대기실

    private final Queue<String> queue = new ArrayDeque<>();
    private final int max;

    @Override
    public void put(String data) {
        lock.lock();
        try {
            while (queue.size() == max) {
                producerCond.await();      // 생산자는 여기서 대기
            }
            queue.offer(data);
            consumerCond.signal();         // ⭐ 소비자만 정확히 깨운다
        } finally {
            lock.unlock();
        }
    }

    @Override
    public String take() {
        lock.lock();
        try {
            while (queue.isEmpty()) {
                consumerCond.await();      // 소비자는 여기서 대기
            }
            String data = queue.poll();
            producerCond.signal();         // ⭐ 생산자만 정확히 깨운다
            return data;
        } finally {
            lock.unlock();
        }
    }
}
```

### 3.2 구조

```text
   ┌──────────────── ReentrantLock (락은 여전히 1개) ────────────────┐
   │                                                                │
   │   🔒 lock                                                       │
   │                                                                │
   │   💤 producerCond   "자리 나면 깨워줘"                           │
   │      [producer3] [producer4]                                   │
   │                                                                │
   │   💤 consumerCond   "데이터 오면 깨워줘"                         │
   │      [consumer1] [consumer2]                                   │
   │                                                                │
   └────────────────────────────────────────────────────────────────┘

   생산자가 데이터를 넣으면 → consumerCond.signal()  ✅ 소비자만 깨운다
   소비자가 데이터를 빼면  → producerCond.signal()  ✅ 생산자만 깨운다
```

> ⭐ **핵심 아이디어: 생산자는 소비자를 깨우고, 소비자는 생산자를 깨운다.**
> 자기 편을 깨우는 헛수고가 구조적으로 사라진다.

### 3.3 🟡 여기서 `signal()`이 안전한 이유

앞 글에서 `notify()`가 위험하다고 했는데, 여기서는 왜 `signal()`로 충분할까? 앞 글에서 정리한 **두 조건**을 확인해보면 된다.

| 조건 | V3 (`notify`) | V5 (`signal`) |
| --- | --- | --- |
| ① 대기자가 **모두 같은 조건**을 기다리는가 | ❌ 생산자·소비자 혼재 | ✅ **Condition마다 균일** |
| ② 신호 하나로 **정확히 하나**만 진행 가능한가 | ✅ | ✅ |
| 결론 | ⚠️ `notifyAll()` 필요 | ✅ **`signal()`로 충분** |

**대기 공간을 나눈 순간 ①이 자동으로 충족된다.** 이게 `signalAll()`을 안 써도 되는 근거다.

💡 실제 `ArrayBlockingQueue`도 내부에서 `signal()`을 쓴다. 같은 이유에서다.

### 3.4 ⭐ 헷갈리지 말 것 — Condition은 여러 개, 락은 하나

원문이 짚은 내용인데 정말 중요하다.

```text
Condition   : 여러 개  (대기 공간)
Lock        : 딱 하나  (입장권)
```

```java
consumerCond.signal();
// ⚠️ 이 순간 소비자가 실행되는 게 아니다
// ⚠️ 깨어난 소비자도 lock 을 다시 얻어야 한다
// ⚠️ signal() 을 호출한 생산자가 unlock() 할 때까지 기다린다
```

**대기 공간을 나눈 것이지 락을 나눈 게 아니다.** `put()`과 `take()`는 여전히 동시에 실행될 수 없다.

## 4. ⭐ notify와 signal의 정밀한 차이

### 4.1 원문 비교 정리

🔴 **오타**: `Condition.siganl()` → **`signal()`**

| | `Object.notify()` | `Condition.signal()` |
| --- | --- | --- |
| 깨우는 순서 | **정의되지 않음** | 일반적으로 **FIFO** |
| 근거 | 명세에 없음 | AQS의 조건 큐가 FIFO |
| 호출 조건 | 모니터 락 보유 | 해당 `Lock` 보유 |

### 4.2 💡 "FIFO로 깨운다"와 "FIFO로 실행된다"는 다르다

원문이 "일반적으로 FIFO"라고 정확히 표현했는데, 한 단계 더 들어가면 이렇다.

```text
signal() 호출
    │
    ▼
① 조건 큐에서 FIFO 로 하나를 꺼낸다        ← 여기는 FIFO ✅
    │
    ▼
② 락 대기 큐로 옮긴다
    │
    ▼
③ 락을 획득해야 실행                        ← 여기는 락의 공정성 설정 ⚠️
```

**비공정 락(기본값)이라면 ③에서 새치기가 일어날 수 있다.** 조건 큐에서 FIFO로 나왔어도, 마침 도착한 다른 스레드가 락을 먼저 가져갈 수 있다. 앞 글의 **"공정 모드에서도 `tryLock()`은 새치기한다"**와 같은 층위의 이야기다.

### 4.3 💡 상태 변화가 다르다

이건 놓치기 쉬운 부분이다.

| | `notify()` | `signal()` |
| --- | --- | --- |
| 대기 중 상태 | `WAITING` | `WAITING` |
| 신호 직후 | ⭐ `WAITING` → **`BLOCKED`** | ⭐ `WAITING` → **`WAITING`** |
| 락 획득 후 | `RUNNABLE` | `RUNNABLE` |

```text
[ synchronized ]                    [ ReentrantLock ]

wait() → 대기 집합 (WAITING)         await() → 조건 큐 (WAITING)
   │                                    │
notify()                             signal()
   │                                    │
   ▼                                    ▼
진입 집합 (BLOCKED)                  락 대기 큐 (⭐ 여전히 WAITING)
   │                                    │
락 획득                               락 획득
   │                                    │
   ▼                                    ▼
RUNNABLE                             RUNNABLE
```

`ReentrantLock`은 락 대기조차 `LockSupport.park()`로 구현되어 있어서 **`BLOCKED`가 아예 나타나지 않는다.** 앞 글에서 본 `t2 state: WAITING`이 이것이다. 스레드 덤프를 읽을 때 `synchronized` 기반인지 `Lock` 기반인지 구분하는 단서가 된다.

## 5. 스레드 대기 총정리

원문의 정리가 좋다. 표로 합치면 이렇다.

| | 대기 1 — **락 획득** | 대기 2 — **조건 대기** |
| --- | --- | --- |
| **`synchronized`** | | |
| 관리 장소 | 객체의 **진입 집합**(entry set) | 객체의 **대기 집합**(wait set) |
| 상태 | `BLOCKED` | `WAITING` |
| 들어가는 계기 | `synchronized` 진입 실패 | `wait()` 호출 |
| 나오는 계기 | 다른 스레드가 블록을 벗어남 | `notify()` / `notifyAll()` |
| 인터럽트 | ❌ **반응 안 함** | ✅ 반응 |
| **`ReentrantLock`** | | |
| 관리 장소 | `ReentrantLock`의 **대기 큐** | `Condition`의 **대기 공간** |
| 상태 | ⭐ `WAITING` | `WAITING` |
| 들어가는 계기 | `lock.lock()` 실패 | `condition.await()` |
| 나오는 계기 | 다른 스레드가 `unlock()` | `signal()` / `signalAll()` |
| 인터럽트 | ⚠️ **`lock()`은 ❌ / `lockInterruptibly()`는 ✅** | ✅ 반응 |

```text
       synchronized                        ReentrantLock
 ┌─────────────────────────┐        ┌─────────────────────────┐
 │  🔒 모니터 락            │        │  🔒 lock                 │
 │                         │        │                         │
 │  🚪 진입 집합  BLOCKED   │        │  🚪 대기 큐    WAITING   │
 │                         │        │                         │
 │  💤 대기 집합  WAITING   │        │  💤 Condition1 WAITING  │
 │     (딱 1개, 고정)       │        │  💤 Condition2 WAITING  │
 │                         │        │     (원하는 만큼)        │
 └─────────────────────────┘        └─────────────────────────┘
```

## 6. lock() vs lockInterruptibly()

### 6.1 원문 설명 정리

🟡 **원문의 "lock.lock()이 인터럽트를 받지 않는 이유" 설명이 다소 뒤엉켜 있다.** 정리하면 두 가지다.

**이유 ① — `synchronized`와 같은 계약을 제공하기 위해**

`lock()`은 "무슨 일이 있어도 락을 얻는다"는 단순한 계약이다. `synchronized`를 `Lock`으로 갈아끼울 때 동작이 달라지지 않아야 한다.

**이유 ② — 인터럽트를 허용하면 `unlock()` 처리가 까다로워진다**

원문이 짚은 부분인데, 코드로 보면 명확하다.

```java
// ❌ 흔히 저지르는 실수
try {
    lock.lockInterruptibly();
    // 임계 영역
} catch (InterruptedException e) {
    log("인터럽트");
} finally {
    lock.unlock();      // 💥 락을 못 얻었는데 unlock → IllegalMonitorStateException
}
```

**예외가 던져졌다는 건 락을 획득하지 못했다는 뜻**이므로, `unlock()`을 호출하면 안 된다.

```java
// ✅ 올바른 형태 — lock 획득을 try 밖으로
public void doWork() throws InterruptedException {
    lock.lockInterruptibly();          // 실패하면 여기서 예외 → try 진입 안 함
    try {
        // 임계 영역
    } finally {
        lock.unlock();                 // ✅ 반드시 락을 쥔 상태
    }
}
```

앞 글에서 정리한 **"`lock()`은 `try` 블록 밖에 있어야 한다"**와 같은 원칙이다.

### 6.2 정리

| | `lock()` | `lockInterruptibly()` |
| --- | --- | --- |
| 인터럽트 | ❌ 무시 (플래그는 복원) | ✅ `InterruptedException` |
| 예외 | 없음 | `throws InterruptedException` |
| 획득 실패 시 | 없음 (반드시 획득) | **락을 안 가진 상태로 탈출** |
| `try` 위치 | 락 획득 **후** | 락 획득 **후** (동일) |

## 7. BlockingQueue

### 7.1 우리가 만든 것이 이미 있다

```java
public class BoundedQueueV6_1 implements BoundedQueue {

    private final BlockingQueue<String> queue;

    public BoundedQueueV6_1(int max) {
        this.queue = new ArrayBlockingQueue<>(max);
    }

    @Override
    public void put(String data) {
        try {
            queue.put(data);              // 가득 차면 대기
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }

    @Override
    public String take() {
        try {
            return queue.take();          // 비어 있으면 대기
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
}
```

🔴 **오타**: `java.util.concurrent.**blockingQueue**` → **`BlockingQueue`** (인터페이스명은 대문자)

### 7.2 ⭐ 내부 구현이 V5와 똑같다

`ArrayBlockingQueue`의 실제 소스를 보면 이렇다.

```java
public class ArrayBlockingQueue<E> {
    final ReentrantLock lock;
    private final Condition notEmpty;    // ⭐ consumerCond 와 같은 역할
    private final Condition notFull;     // ⭐ producerCond 와 같은 역할

    public void put(E e) throws InterruptedException {
        Objects.requireNonNull(e);
        lock.lockInterruptibly();        // ⭐ lock() 이 아니다
        try {
            while (count == items.length)
                notFull.await();
            enqueue(e);                  // enqueue 안에서 notEmpty.signal()
        } finally {
            lock.unlock();
        }
    }
}
```

원문의 지적이 정확하다. **차이는 `lock()` 대신 `lockInterruptibly()`를 쓴다는 것.** `put()`이 `throws InterruptedException`을 선언하므로, 락 획득 단계부터 취소 가능하게 만든 것이다.

| | V5 (직접 구현) | `ArrayBlockingQueue` |
| --- | --- | --- |
| 락 | `ReentrantLock` | `ReentrantLock` |
| Condition | `producerCond` / `consumerCond` | `notFull` / `notEmpty` |
| 락 획득 | `lock()` | ⭐ `lockInterruptibly()` |
| 구조 | 동일 | 동일 |

> 💡 **"직접 만들어본 것과 표준 라이브러리가 같은 구조"**라는 걸 확인하는 게 이 단계의 목적이다.

## 8. 4가지 선택지

### 8.1 ⭐ 외워야 할 표

원문이 텍스트로 풀어놓은 내용인데, **표로 보면 한눈에 들어온다.** `BlockingQueue` 문서의 표준 표이기도 하다.

| 동작 | **예외 발생** | **특수값 반환** | **블로킹** | **타임아웃** |
| --- | --- | --- | --- | --- |
| **삽입** | `add(e)` | `offer(e)` | ⭐ `put(e)` | `offer(e, time, unit)` |
| **제거** | `remove()` | `poll()` | ⭐ `take()` | `poll(time, unit)` |
| **검사** | `element()` | `peek()` | — | — |

```text
큐가 가득 찼을 때 무엇을 할 것인가?

  ① 예외를 던진다        → add(e)        IllegalStateException
  ② 즉시 실패를 알린다   → offer(e)      false 반환
  ③ 기다린다             → put(e)        ⭐ 생산자-소비자의 기본
  ④ 잠깐만 기다린다      → offer(e,t,u)  시간 초과 시 false
```

🔴 **원문 설명 정정**: `offer(e, time, unit)`은 "지정된 시간 동안 큐가 **비워지지** 않으면" → **"공간이 생기지 않으면"**이 정확하다.

🟡 **`remove()`와 `remove(Object)`는 다르다.** 전자는 **머리 요소**를 제거하고, 후자는 **특정 요소**를 찾아 제거한다(있으면 `true`).

💡 **표에 없는 유용한 메서드**

| 메서드 | 용도 |
| --- | --- |
| `drainTo(Collection)` | 큐의 요소를 **한 번에 전부** 옮긴다 (배치 처리) |
| `drainTo(Collection, max)` | 최대 개수 지정 |
| `remainingCapacity()` | 남은 공간 |

### 8.2 실행 결과에서 읽을 것

**타임아웃 예제 (V6_3)**

```text
21:01:06.136 [producer3] 저장 시도 결과: false      ← offer(1 나노초) 실패
21:01:06.137 [producer3] [생산 완료] data3 -> [data1, data2]   ← ⚠️ 로그가 오해를 부름

21:01:06.576 [     main] consumer3: TIMED_WAITING   ← poll(2000ms) 대기 중
21:01:08.472 [consumer3] [소비 완료] null <- []     ← 2초 뒤 null
```

🟡 **`저장 시도 결과: false`인데 `[생산 완료]`가 찍힌다.** `ProducerTask`가 결과와 무관하게 로그를 남기기 때문이다. 실제 코드라면 반환값을 확인해서 분기해야 한다.

**예외 예제 (V6_4)**

```text
Exception in thread "producer3" java.lang.IllegalStateException: Queue full
    at java.util.AbstractQueue.add(...)
...
21:03:57.099 [     main] producer3: TERMINATED      ← ⭐ 이 스레드만 죽었다
```

🔴 **원문의 "RuntimeException이 발생"은 뭉뚱그린 표현이다.** 정확히는 `IllegalStateException`(삽입)과 `NoSuchElementException`(제거)이다. 둘 다 `RuntimeException`의 하위 타입이긴 하다.

💡 **여기서 주목할 것**: 예외가 터졌는데도 **프로그램이 계속 돌아간다.** producer3만 `TERMINATED`가 되고 나머지는 멀쩡하다. 앞 글에서 정리한 **"`run()`에서 언체크 예외가 나면 그 스레드만 죽고, main은 잡을 수 없다"**가 실증된 장면이다.

## 9. 구현체 선택과 실무 주의점 💡

### 9.1 구현체 비교

| 구현체 | 크기 | 특징 |
| --- | --- | --- |
| `ArrayBlockingQueue` | **고정** (필수) | 배열 기반. 락 1개 + Condition 2개 |
| `LinkedBlockingQueue` | 선택 (기본 **무한**) | ⭐ **락 2개**(put/take)라 처리량이 높다 |
| `SynchronousQueue` | **0** | 버퍼가 없다. 생산자와 소비자가 직접 만나야 진행 |
| `PriorityBlockingQueue` | 무한 | 우선순위 순서로 꺼냄 |
| `DelayQueue` | 무한 | 지연 시간이 지난 요소만 꺼낼 수 있음 |
| `LinkedBlockingDeque` | 선택 | 양쪽 끝에서 입출력 |

💡 **`LinkedBlockingQueue`가 더 빠른 이유**

```text
[ ArrayBlockingQueue ]              [ LinkedBlockingQueue ]

    🔒 lock (1개)                       🔒 putLock      🔒 takeLock
        │                                   │               │
   put ─┴─ take                          put              take
   ⚠️ 서로 막는다                       ✅ 동시에 진행 가능
```

배열은 머리와 꼬리가 같은 공간을 공유하므로 락을 나눌 수 없지만, 연결 리스트는 머리와 꼬리가 분리되어 있어 가능하다.

### 9.2 ⚠️ `LinkedBlockingQueue`의 기본 크기는 무한이다

```java
new LinkedBlockingQueue<>();          // ⚠️ 크기 = Integer.MAX_VALUE
new LinkedBlockingQueue<>(1000);      // ✅ 명시하자
```

**사실상 무한 큐**가 되어, 소비가 느리면 **메모리가 계속 쌓이다가 OOM**이 난다. 그리고 `put()`이 절대 블로킹되지 않으므로 **백프레셔(backpressure)가 사라진다.**

> ⭐ **한정된 버퍼의 진짜 가치는 "생산자를 자연스럽게 늦추는 것"이다.**
> 큐가 가득 차면 `put()`이 막히고, 그 자체가 흐름 제어가 된다. 무한 큐를 쓰면 이 안전장치를 스스로 없애는 셈이다.

💡 `Executors.newFixedThreadPool()`이 내부적으로 무한 `LinkedBlockingQueue`를 쓴다. 다음 단계에서 스레드 풀을 배울 때 다시 만나게 될 함정이다.

### 9.3 ⚠️ `BlockingQueue`는 null을 허용하지 않는다

```java
queue.put(null);     // 💥 NullPointerException
```

`poll()`이 **null을 "비어 있음"의 신호로 쓰기 때문**이다. null을 허용하면 "값이 null인지" "큐가 비었는지" 구분할 수 없다. 앞 글들에서 반복해서 나온 **"반환값 하나로 두 가지 의미를 담을 수 없다"**는 문제와 같은 맥락이다.

### 9.4 메서드 선택 가이드

```text
데이터를 넣어야 한다
   │
   ├─ 넣을 때까지 기다려도 되나?        → ⭐ put(e)        (기본)
   ├─ 못 넣으면 다른 일을 해야 하나?     → offer(e)
   ├─ 잠깐만 기다려볼까?                → offer(e, t, u)
   └─ 못 넣는 건 버그인가?              → add(e)          (예외)

데이터를 꺼내야 한다
   │
   ├─ 올 때까지 기다려도 되나?          → ⭐ take()        (기본)
   ├─ 없으면 다른 일을 해야 하나?        → poll()
   ├─ 잠깐만 기다려볼까?                → poll(t, u)
   └─ 없는 건 버그인가?                 → remove()        (예외)
```

## 10. 전체 여정 정리 💡

### 10.1 생산자-소비자 문제 해결 과정

| 단계 | 방법 | 결과 |
| --- | --- | --- |
| V1 | 버리고 `null` 반환 | ❌ 데이터 유실 |
| V2 | `synchronized` + `sleep()` | 💀 **락을 쥔 채 자서 전체 정지** |
| V3 | `synchronized` + `wait/notify` | ✅ 동작. ⚠️ 헛깨움 |
| V4 | `ReentrantLock` + `Condition` 1개 | ✅ 도구만 교체. V3와 동일 |
| V5 | `ReentrantLock` + `Condition` **2개** | ⭐ 헛깨움 해결 |
| V6 | `BlockingQueue` | ⭐ **이미 만들어져 있음** |

### 10.2 핵심 통찰 세 가지

**① 락을 쥔 채 기다리지 마라**

```text
sleep()  → 락 유지  💀
wait()   → 락 반납  ✅
await()  → 락 반납  ✅
```

**② 대기 공간을 목적별로 나눠라**

```text
대기자가 섞여 있으면  → notifyAll() 로 전부 깨워야 안전
대기 공간을 나누면    → signal() 하나로 정확히 필요한 쪽만
```

**③ 조건 확인은 항상 `while`로**

```text
재경쟁으로 조건이 바뀔 수 있고 (이유 ①)
아무 이유 없이 깨어날 수도 있다 (이유 ② — spurious wakeup)
```

### 10.3 지금까지 배운 동시성 도구 지도

```text
                      공유 상태가 있다
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
    가시성만 필요        원자성 필요         협력·조율 필요
        │                   │                   │
    volatile          synchronized          wait / notify
                      AtomicLong            Condition
                      ReentrantLock         BlockingQueue ⭐
```

> 실무에서는 대부분 **오른쪽 끝**에서 끝난다. `BlockingQueue` 하나면 생산자-소비자는 해결된다. 왼쪽을 배우는 건 **그 안에서 무슨 일이 벌어지는지 알기 위해서**다.

### 이번 글의 핵심 한 줄

> **`Condition`은 여러 개, 락은 하나다.**

> 그렇게 만든 것이 `BlockingQueue`다.
