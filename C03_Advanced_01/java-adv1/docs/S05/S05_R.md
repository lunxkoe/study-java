## 1. 인터럽트 이전 — volatile 플래그

### 1.1 코드

```java
public class ThreadStopMainV1 {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread thread = new Thread(task, "work");
        thread.start();

        sleep(4000);
        log("작업 중단 지시 runFlag = false");
        task.runFlag = false;
    }

    static class MyTask implements Runnable {

        volatile boolean runFlag = true;

        @Override
        public void run() {
            while (runFlag) {
                log("작업 중");
                sleep(3000);
            }
            log("자원 정리");
            log("자원 종료");
        }
    }
}
```

```text
20:57:57.362 [     work] 작업 중
20:58:00.368 [     work] 작업 중
20:58:01.347 [     main] 작업 중단 지시 runFlag = false   ← 여기서 지시
20:58:03.371 [     work] 자원 정리                        ← 2초 뒤에야 반응
20:58:03.373 [     work] 자원 종료
```

```text
시간 ────────────────────────────────────────────────▶
       0s      1s      2s      3s      4s      5s      6s

work  │작업중│←─ sleep(3000) ─→│작업중│←─ sleep(3000) ─→│종료
                                             ▲            ▲
main                                    runFlag=false   여기서야 반응
                                             └── 2초 낭비 ──┘
```

### 1.2 이 방식의 한계

| 문제 | 설명 |
| --- | --- |
| **반응이 느리다** | `sleep(3000)` 중이면 최대 3초 뒤에나 플래그를 확인 |
| **깨울 방법이 없다** | 대기 중인 스레드를 밖에서 깨울 수단이 전혀 없음 |
| **플래그를 직접 만들어야 한다** | 클래스마다 중단 메커니즘을 새로 설계 |

### 1.3 보강 노트

🟡 **`volatile`을 "여러 스레드가 공유하는 값에 붙이는 키워드"로만 알고 넘어가면 아까운 지점입니다.**

이 예제에서 `volatile`이 없으면 **무한 루프에 빠질 수 있습니다.** 값이 안 보여서가 아니라, JIT 컴파일러가 이런 최적화를 하기 때문입니다.

```java
// 원래 코드
while (runFlag) { ... }

// volatile 이 없으면 JIT 가 이렇게 바꿔버릴 수 있다
boolean temp = runFlag;      // 루프 밖으로 읽기를 끌어냄 (hoisting)
while (temp) { ... }         // → main 이 false 로 바꿔도 영원히 모름
```

`volatile`은 **"이 변수는 매번 메인 메모리에서 다시 읽어라"**를 컴파일러와 CPU에 강제합니다.

💡 **다만 `volatile`은 가시성만 보장하고 원자성은 보장하지 않습니다.**

```java
volatile boolean runFlag = true;   // ✅ 적합 — 읽기/쓰기 각각이 원자적
volatile int count = 0;
count++;                            // ❌ 여전히 위험 — 읽기+증가+쓰기 3단계
```

`boolean` 플래그처럼 **"한쪽이 쓰고 다른 쪽이 읽기만" 하는 경우**가 `volatile`의 전형적인 용도입니다. 이전 글의 `SumTask.result`도 같은 패턴이었습니다(다만 그건 `join()`이 가시성을 보장해줬죠).

## 2. interrupt() 등장

### 2.1 코드

```java
public class ThreadStopMainV2 {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread thread = new Thread(task, "work");
        thread.start();

        sleep(4000);
        log("작업 중단 지시 thread.interrupt()");
        thread.interrupt();
        log("work 스레드 인터럽트 상태1 = " + thread.isInterrupted());
    }

    static class MyTask implements Runnable {

        @Override
        public void run() {
            try {
                while (true) {
                    log("작업 중");
                    Thread.sleep(3000);
                }
            } catch (InterruptedException e) {
                log("work 스레드 인터럽트 상태2 = " + Thread.currentThread().isInterrupted());
                log("interrupt message = " + e.getMessage());
                log("state = " + Thread.currentThread().getState());
            }

            log("자원 정리");
            log("자원 종료");
        }
    }
}
```

```text
21:14:04.815 [     work] 작업 중
21:14:07.834 [     work] 작업 중
21:14:08.800 [     main] 작업 중단 지시 thread.interrupt()
21:14:08.800 [     main] work 스레드 인터럽트 상태1 = true   ← 플래그가 켜짐
21:14:08.800 [     work] work 스레드 인터럽트 상태2 = false  ← 예외가 끄고 감
21:14:08.801 [     work] interrupt message = sleep interrupted
21:14:08.802 [     work] state = RUNNABLE
21:14:08.802 [     work] 자원 정리
21:14:08.802 [     work] 자원 종료
```

**`sleep(3000)` 중이었는데 즉시 깨어났습니다.** 이게 플래그 방식과의 결정적 차이입니다.

### 2.2 ⭐ 핵심 메커니즘

```text
[ main 스레드 ]                    [ work 스레드 ]

thread.interrupt()
      │                            sleep(3000) 으로 TIMED_WAITING
      ▼
① 인터럽트 플래그 = true  ────────▶ ② JVM 이 감지
      │                                  │
      │                                  ▼
      │                            ③ sleep() 을 즉시 중단
      │                                  │
      │                                  ▼
      │                            ④ ⭐ 플래그를 false 로 되돌림
      │                                  │
      │                                  ▼
      │                            ⑤ InterruptedException 던짐
      │                                  │
      │                                  ▼
      └─ (이 사이 어딘가에서 읽음)  ⑥ RUNNABLE 상태로 catch 블록 실행
```

> ⭐ **한 줄 요약: `InterruptedException`이 던져지는 순간, 인터럽트 상태는 `false`로 초기화된다.**
> 이 글의 나머지 내용은 전부 이 한 줄에서 파생됩니다.

### 2.3 정정 · 보강 노트

🔴 **오타 정정**
- "직접 깨우서 작동하는" → **깨워서**
- "인터럽트를 받고 깨워난 경우" → **깨어난**
- "호출하며 대기 중이 때만" → **대기 중일 때만**
- "InterruptException" → **InterruptedException**
- "기대데로 동작함" → **기대대로**

🟡 **`상태1 = true`가 항상 `true`인 건 아닙니다. 이건 경쟁 상태입니다.**

```java
thread.interrupt();
log("상태1 = " + thread.isInterrupted());   // ⚠️ true 일 수도, false 일 수도
```

`interrupt()`를 호출한 직후, work 스레드가 이미 깨어나서 플래그를 지웠을 수도 있습니다. 실행 로그의 타임스탬프를 보면 `상태1`과 `상태2`가 **같은 밀리초(21:14:08.800)**에 찍혔습니다. 어느 쪽이 먼저일지는 실행마다 다릅니다.

> ⚠️ **`isInterrupted()`의 반환값으로 흐름을 제어하려는 코드는 위험합니다.** 이전 글의 `getState()`와 같은 문제입니다.

🟡 **원문 "스레드가 runnable 상태여야 catch의 예외 코드도 실행될 수 있음"을 풀어쓰면:**
`catch` 블록의 코드도 결국 CPU를 써서 실행해야 하는 코드입니다. 그래서 `TIMED_WAITING` 상태로는 실행할 수 없고, **반드시 `RUNNABLE`로 돌아온 뒤에야** 실행됩니다. 로그의 `state = RUNNABLE`이 이걸 확인해주는 것입니다.

💡 **`interrupt()`는 "명령"이 아니라 "요청"입니다.**

```java
new Thread(() -> {
    while (true) {
        // 인터럽트를 확인하지도, sleep 하지도 않는다
        heavyComputation();
    }
}).start();

thread.interrupt();   // ⚠️ 아무 일도 일어나지 않는다
```

인터럽트는 **협력적(cooperative) 중단**입니다. 대상 스레드가 확인해주지 않으면 그냥 플래그만 켜진 채로 끝입니다. 스레드를 강제로 죽이는 방법은 자바에 (안전하게는) 존재하지 않습니다.

💡 **`interrupt()`를 걸었는데 대기 중이 아니면 예외가 안 납니다. 플래그만 켜집니다.**
그리고 **나중에 `sleep()`을 호출하는 순간 즉시 예외가 터집니다.** 이게 3장에서 문제가 되는 지점입니다.

## 3. 인터럽트 상태와 예외의 관계

### 3.1 while에서 직접 확인하기 (V3)

```java
static class MyTask implements Runnable {
    @Override
    public void run() {
        while (!Thread.currentThread().isInterrupted()) {   // 확인만, 변경 X
            log("작업 중");
        }
        log("상태2 = " + Thread.currentThread().isInterrupted());   // true
        log("자원 정리");
        log("자원 종료");
    }
}
```

```text
21:37:40.025 [     main] 작업 중단 지시 thread.interrupt()
21:37:40.025 [     main] work 스레드 인터럽트 상태1 = true
21:37:40.025 [     work] work 스레드 인터럽트 상태2 = true   ← ⚠️ 여전히 true
21:37:40.026 [     work] 자원 정리
```

`sleep()`을 쓰지 않았으니 예외가 안 났고, 따라서 **플래그가 지워지지 않았습니다.**

### 3.2 그래서 무슨 문제가 생기나

자원 정리 코드에 `sleep()`이 하나만 끼어들어도 바로 터집니다.

```java
log("상태2 = " + Thread.currentThread().isInterrupted());   // true

try {
    log("자원 정리");
    Thread.sleep(1000);          // ⚠️ 플래그가 true 라서 즉시 예외!
    log("자원 종료");            // ❌ 도달 못 함
} catch (InterruptedException e) {
    log("자원 정리 실패 - 자원 정리 중 인터럽트 발생");
    log("상태3 = " + Thread.currentThread().isInterrupted());   // false
}
```

```text
21:41:14.054 [     work] work 스레드 인터럽트 상태2 = true
21:41:14.054 [     work] 자원 정리
21:41:14.055 [     work] 자원 정리 실패 - 자원 정리 중 인터럽트 발생   ← 1초를 못 기다림
21:41:14.055 [     work] work 스레드 인터럽트 상태3 = false          ← 이제야 꺼짐
```

```text
[ 기대한 동작 ]                   [ 실제 동작 ]

while 탈출 ✅                     while 탈출 ✅
    │                                 │
    ▼                                 ▼
자원 정리 ✅                      자원 정리 시작
    │                                 │
    ▼                                 ▼
정상 종료 ✅                      sleep() → 💥 즉시 예외
                                      │
                                      ▼
                                  자원 정리 실패 ❌
```

> ⭐ **인터럽트 플래그가 켜진 채로 남아 있으면, 그 뒤의 모든 블로킹 호출이 연쇄적으로 터집니다.**
> 자바가 "예외를 던질 때 플래그를 끄는" 이유가 바로 이것입니다.
> **"신호는 한 번만 전달된다. 받았으면 소비해야 한다."**

### 3.3 보강 노트

🟡 **V3의 `while` 루프는 CPU를 100% 태웁니다.**

```java
while (!Thread.currentThread().isInterrupted()) {
    log("작업 중");   // 대기 없이 무한히 반복 → busy waiting
}
```

로그를 보면 같은 밀리초 안에 여러 줄이 찍힙니다. 인터럽트 확인 타이밍을 보여주기 위한 예제라 이렇게 짠 것이고, 실제 코드에서는 이러면 안 됩니다. (이 문제가 8장의 `yield` 이야기로 이어집니다.)

🔴 **원문에서 "왜 예외를 받으면 false로 바꿀까?" 절의 두 번째 코드도 클래스명이 `ThreadStopMainV3`입니다.** 앞의 코드와 다른 버전이니 `ThreadStopMainV3_1` 같은 이름으로 구분하는 게 헷갈리지 않습니다.

## 4. isInterrupted() vs interrupted()

### 4.1 두 메서드 비교

| | `thread.isInterrupted()` | `Thread.interrupted()` |
| --- | --- | --- |
| 종류 | **인스턴스** 메서드 | ⭐ **static** 메서드 |
| 대상 | **아무 스레드나** 조회 가능 | ⭐ **호출한 스레드 자신만** |
| 상태 변경 | ❌ 안 함 | ✅ `true`면 **`false`로 초기화** |
| 용도 | **관찰** (모니터링, 로깅) | **소비** (직접 처리할 때) |

```java
// 상태가 true 일 때
thread.isInterrupted();   // true  → 다시 호출해도 true
Thread.interrupted();     // true  → 다시 호출하면 false
```

### 4.2 V4 코드

```java
static class MyTask implements Runnable {
    @Override
    public void run() {

        while (!Thread.interrupted()) {   // 🔴 원문 주석 "확인만 / 변경 X" 는 틀림
            log("작업 중");
        }
        log("상태2 = " + Thread.currentThread().isInterrupted());   // false

        try {
            log("자원 정리");
            Thread.sleep(1000);    // ✅ 플래그가 꺼져 있으므로 정상 대기
            log("자원 종료");       // ✅ 도달함
        } catch (InterruptedException e) {
            log("자원 정리 실패");
        }
    }
}
```

```text
21:48:17.876 [     work] 작업 중
21:48:17.877 [     work] work 스레드 인터럽트 상태2 = false   ← 초기화됨
21:48:17.877 [     work] 자원 정리
21:48:18.878 [     work] 자원 종료                            ← ✅ 1초 뒤 정상 완료
```

### 4.3 🔴 원문의 주석이 잘못됐습니다

```java
// V3 — 이 주석은 맞음
while (!Thread.currentThread().isInterrupted()) { // 인터럽트 상태 확인만 / 변경 X

// V4 — 이 주석은 틀림 (V3에서 복사된 것으로 보임)
while (!Thread.interrupted()) { // 인터럽트 상태 확인만 / 변경 X   ← ❌
```

`Thread.interrupted()`는 **확인 + 초기화**를 동시에 합니다. V4의 요점 자체가 "초기화가 된다"는 것이므로, 이 주석이 남아 있으면 정반대로 이해하게 됩니다.

```java
while (!Thread.interrupted()) { // 인터럽트 상태 확인 + true 면 false 로 초기화
```

### 4.4 💡 아주 잘 속는 함정 두 가지

**함정 1: `Thread.interrupted()`는 static이라 "누구에게 물어보든" 자기 자신을 봅니다.**

```java
Thread worker = new Thread(...);
worker.start();

// main 스레드에서
worker.interrupted();   // ⚠️⚠️ worker 가 아니라 "main" 의 상태를 확인하고 지운다!
```

이전 글의 `thread1.sleep(1000)`과 완전히 같은 함정입니다. **static 메서드를 인스턴스 참조로 호출하면 컴파일러가 클래스 호출로 바꿔버립니다.**

| 이렇게 쓰면 | 실제로는 |
| --- | --- |
| `worker.interrupted()` | `Thread.interrupted()` = **호출한 스레드**의 상태 |
| `Thread.currentThread().interrupted()` | 같음. 의미는 맞지만 장황함 |
| `worker.isInterrupted()` | ✅ 진짜 worker의 상태 (변경 안 함) |

**함정 2: 이름이 헷갈립니다.**

```text
isInterrupted()  →  is  = "~인가?"       →  묻기만 함     (인스턴스)
interrupted()    →  과거분사             →  묻고 지움     (static)
```

외우는 요령: **`is`가 붙으면 순수한 질문, `is`가 없으면 "받아서 처리했다"는 뜻**으로 생각하면 됩니다.

## 5. 인터럽트 상태 복원 패턴 💡

원문이 마지막에 한 줄로만 언급한 내용입니다.

> "자원 정리도 하지 않고 빠르게 종료해야 한다면 스레드를 다시 인터럽트 상태로 변경하는 것도 방법"

이게 실무에서는 **가장 중요한 규칙**이라 따로 정리합니다.

### 5.1 ⭐ 절대 규칙

> **`InterruptedException`을 잡았다면, 반드시 둘 중 하나를 하라.**
> **① 다시 던지거나 ② 인터럽트 상태를 복원하라.**
> **절대 그냥 삼키지 마라.**

```java
// ❌ 최악 — 신호를 삼켜버림
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // 아무것도 안 함 → 호출자는 종료 요청이 왔다는 걸 영원히 모름
}

// ❌ 나쁨 — 로그만 남기는 것도 삼키는 것
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    log.error("인터럽트", e);
}

// ✅ 방법 1 — 그대로 던진다 (가능하면 이게 제일 좋음)
public void doWork() throws InterruptedException {
    Thread.sleep(1000);
}

// ✅ 방법 2 — 못 던지는 자리(run() 등)라면 상태를 복원한다
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // ⭐ 플래그를 다시 켠다
    return;                                // 그리고 빠르게 종료
}
```

### 5.2 왜 복원해야 하나

```text
[ 삼켰을 때 ]
main ──interrupt()──▶ work
                        │
                   sleep() 예외 발생 → 플래그 false
                        │
                   catch 에서 아무것도 안 함
                        │
                        ▼
                   ⚠️ work 는 계속 돌아감
                   ⚠️ 상위 호출자는 "중단 요청이 있었다"는 사실조차 모름

[ 복원했을 때 ]
main ──interrupt()──▶ work
                        │
                   sleep() 예외 발생 → 플래그 false
                        │
                   catch 에서 interrupt() 재호출 → 플래그 true
                        │
                        ▼
                   ✅ 상위 루프의 isInterrupted() 가 true 를 봄
                   ✅ 스레드 풀도 이 스레드가 중단됐음을 인지
```

라이브러리 코드라면 더 중요합니다. **내가 신호를 삼키면 나를 호출한 사람이 중단할 방법을 잃습니다.**

### 5.3 이전 글에서 만든 sleep 유틸의 정체

```java
// 학습용으로 만들었던 것
public static void sleep(long millis) {
    try {
        Thread.sleep(millis);
    } catch (InterruptedException e) {
        throw new RuntimeException(e);   // ⚠️ 여기서 플래그가 꺼진 채로 끝난다
    }
}
```

`RuntimeException`으로 감싸 던지면 **인터럽트 상태가 복원되지 않습니다.** 예제를 짧게 쓰려는 장치일 뿐, 실무 코드에서는 이렇게 쓰면 안 됩니다. 이번 글의 원리를 이해했다면 왜 위험한지 이제 보일 겁니다.

💡 **어떤 선택지가 있나**

| 상황 | 올바른 처리 |
| --- | --- |
| 메서드 시그니처를 바꿀 수 있음 | `throws InterruptedException`으로 **그대로 전파** |
| `run()` 안이라 못 던짐 | `Thread.currentThread().interrupt()` 후 **종료** |
| 자원 정리가 꼭 필요함 | 플래그를 끈 채로 정리 → 정리 후 복원 |
| 정리 없이 즉시 종료해야 함 | 복원 후 바로 `return` |

## 6. 인터럽트가 통하지 않는 경우 💡

원문에 없지만, 실무에서 반드시 마주치는 내용입니다.

### 6.1 어떤 메서드가 인터럽트에 반응하나

| ✅ `InterruptedException`을 던짐 | ❌ 반응하지 않음 |
| --- | --- |
| `Thread.sleep()` | `synchronized` 진입 대기 (`BLOCKED`) |
| `Object.wait()` | `ReentrantLock.lock()` |
| `Thread.join()` | `InputStream.read()` (전통적 블로킹 I/O) |
| `BlockingQueue.take()` / `put()` | `Socket.read()` |
| `Lock.lockInterruptibly()` | `Scanner.next()` |
| `Condition.await()` | CPU 연산 루프 |
| `Future.get()` | |
| `CountDownLatch.await()` | |
| `Semaphore.acquire()` | |

### 6.2 ⚠️ 블로킹 I/O는 인터럽트로 못 깨웁니다

```java
Thread t = new Thread(() -> {
    socket.getInputStream().read();   // 여기서 영원히 대기
});
t.start();
t.interrupt();   // ⚠️ 아무 일도 안 일어난다. 플래그만 켜질 뿐
```

깨우려면 **자원을 닫아야** 합니다.

```java
socket.close();   // → read() 가 SocketException 을 던지며 탈출
```

> 💡 예외적으로 NIO의 `InterruptibleChannel`은 인터럽트에 반응해서 `ClosedByInterruptException`을 던집니다. 대신 채널이 닫혀버립니다.

### 6.3 ⚠️ 이번 글 프린터 예제의 숨은 문제

```java
Scanner userInput = new Scanner(System.in);
String input = userInput.next();   // ⚠️ main 은 여기서 블로킹
```

`Scanner.next()`는 인터럽트에 반응하지 않습니다. 그래서 **main 스레드는 `interrupt()`로 깨울 수 없습니다.** 예제에서는 사용자가 `q`를 입력해야만 진행되는 구조라 문제가 드러나지 않지만, 구조적으로는 이런 제약이 있다는 걸 알아두면 좋습니다.

### 6.4 `Thread.stop()`은 왜 쓰면 안 되나

🟡 **원문의 "삭제된 기능"을 정확히 하면:**

| 버전 | `Thread.stop()` |
| --- | --- |
| ~ Java 18 | deprecated이지만 **동작함** |
| Java 20+ | 호출 시 **`UnsupportedOperationException`** |

이유는 명확합니다.

```java
synchronized (account) {
    account.balance -= 1000;      // ← 여기서 stop() 당하면?
    target.balance += 1000;       // ← 실행 안 됨
}                                  // ← 락은 풀리지만 데이터는 깨진 상태
```

`stop()`은 **어느 시점에서든 스레드를 즉시 죽입니다.** 락은 해제되지만 데이터는 중간 상태로 남고, `finally`도 실행 보장이 없습니다. **"안전하게 강제 종료하는 방법은 없다"**는 결론에서 나온 것이 인터럽트라는 협력적 방식입니다.

## 7. 프린터 예제

### 7.1 V1 — 플래그 방식

```java
static class Printer implements Runnable {

    volatile boolean work = true;
    Queue<String> jobQueue = new ConcurrentLinkedQueue<>();

    @Override
    public void run() {
        while (work) {
            if (jobQueue.isEmpty()) {
                continue;            // ⚠️ busy waiting
            }
            String job = jobQueue.poll();
            log("출력 시작: " + job + ", 대기 문서: " + jobQueue);
            sleep(3000);
            log("출력 완료");
        }
        log("프린터 종료");
    }
}
```

🔴 **이 코드에는 원문이 (yield 절에 가서야) 지적하는 문제가 이미 있습니다.**

```java
if (jobQueue.isEmpty()) {
    continue;   // ⚠️ 쉬지 않고 무한 반복 → CPU 코어 하나를 100% 점유
}
```

문서가 비어 있을 때 이 스레드는 **아무 일도 안 하면서 CPU를 통째로 태웁니다.** 노트북이라면 팬이 돌아가는 게 느껴질 정도입니다.

🟡 **`q` 입력 후 반응이 최대 3초 지연됩니다.** `sleep(3000)`으로 출력 중이면 그게 끝나야 `work`를 확인하기 때문입니다. 1장의 한계가 그대로 재현됩니다.

💡 **`ConcurrentLinkedQueue`를 쓰는 이유를 구체적으로:**

```java
Queue<String> q = new LinkedList<>();   // ❌ 스레드 안전하지 않음
```

`LinkedList`에 두 스레드가 동시에 `offer()`하면, 내부 노드의 `next` 포인터가 엉켜서 **데이터 유실, 무한 루프, `NullPointerException`** 중 하나가 발생합니다. 심지어 **매번 터지지도 않아서** 더 나쁩니다.

### 7.2 V2 — 인터럽트 도입

```java
@Override
public void run() {
    while (!Thread.interrupted()) {
        if (jobQueue.isEmpty()) {
            continue;
        }
        String job = jobQueue.poll();
        log("출력 시작: " + job + ", 대기 문서: " + jobQueue);
        try {
            Thread.sleep(3000);
        } catch (InterruptedException e) {
            log("인터럽트!");
            break;                  // ⭐ 이 break 는 필수다
        }
        log("출력 완료");
    }
    log("프린터 종료");
}
```

| 인터럽트가 도착한 시점 | 탈출 경로 |
| --- | --- |
| `sleep(3000)` 중 | `InterruptedException` → `catch` → `break` |
| `isEmpty()` 루프 중 | `Thread.interrupted()`가 `true` → while 탈출 |

💡 **`break`가 빠지면 무한 루프가 됩니다.**

```java
} catch (InterruptedException e) {
    log("인터럽트!");
    // break 가 없다면?
}
// → 예외가 이미 플래그를 false 로 지웠다
// → while (!Thread.interrupted()) 가 다시 true 로 통과
// → 종료 신호가 영원히 사라짐
```

`Thread.interrupted()`와 `InterruptedException`이 **둘 다 플래그를 소비**하기 때문에 생기는 상황입니다. 5장의 "복원하거나 즉시 종료하라"가 여기서도 그대로 적용됩니다.

## 8. yield — 양보하기

### 8.1 RUNNABLE의 내부 구조

```text
                  ┌──────────── RUNNABLE ────────────┐
                  │                                  │
                  │   ┌──────────┐    ┌──────────┐   │
                  │   │ RUNNING  │◀──▶│  READY   │   │
                  │   │(CPU 실행)│    │(큐 대기) │   │
                  │   └──────────┘    └──────────┘   │
                  │                                  │
                  └──────────────────────────────────┘
                    ⭐ 자바에서는 이 둘을 구분할 수 없다
                       getState() 는 둘 다 RUNNABLE 로 반환
```

`Thread.yield()`는 **RUNNING → READY로 자발적으로 내려가는** 메서드입니다. 상태는 계속 `RUNNABLE`입니다.

### 8.2 세 가지 방식 비교

```java
for (int i = 0; i < 10; i++) {
    System.out.println(Thread.currentThread().getName() + " - " + i);
    // 1. 아무것도 안 함
    // 2. sleep(1);
    // 3. Thread.yield();
}
```

| | 상태 변화 | CPU 양보 | 특징 |
| --- | --- | --- | --- |
| **아무것도 안 함** | 없음 | ❌ | 타임 슬라이스를 다 쓸 때까지 독점 |
| **`sleep(1)`** | `RUNNABLE` → `TIMED_WAITING` → `RUNNABLE` | ✅ | 상태 전환 2회. **양보할 사람이 없어도 무조건 1ms 쉼** |
| **`yield()`** | 없음 (`RUNNABLE` 유지) | ✅ | 줄 사람 없으면 **바로 다시 실행** |

> ⭐ `sleep(1)`의 문제를 원문이 잘 표현했습니다.
> **"양보할 사람이 없는데 혼자서 양보한 이상한 상황"**
> `yield()`는 대기 중인 스레드가 없으면 즉시 자기가 다시 CPU를 받습니다. 낭비가 없죠.

### 8.3 보강 노트

🟡 **`yield()`도 "힌트"입니다. 보장이 아닙니다.**

```java
Thread.yield();
// ① OS가 무시할 수 있다
// ② 양보했는데 스케줄러가 나를 다시 고를 수 있다
// ③ 어떤 스레드가 실행될지 지정할 수 없다
```

원문의 "반드시 다른 스레드에게 넘기는 것은 아님"이 정확합니다. **우선순위와 마찬가지로, `yield()`로 실행 순서를 제어하려는 코드는 버그입니다.**

💡 **자바 공식 문서가 직접 "쓰지 말라"고 합니다.**
`Thread.yield()`의 Javadoc에는 **"이 메서드를 쓰는 것이 적절한 경우는 드물다"**는 취지의 경고가 들어 있습니다. 실제 용도는 거의 **디버깅과 테스트**(경쟁 상태를 재현하기 위해 일부러 전환을 유발) 정도입니다.

💡 **Java 9부터는 `Thread.onSpinWait()`이 있습니다.**

```java
while (!condition) {
    Thread.onSpinWait();   // CPU 에게 "나 스핀 중이야" 힌트 (x86의 PAUSE 명령)
}
```

CPU를 양보하지는 않지만, **전력 소모를 줄이고 스핀 루프 자체의 효율을 높입니다.** 아주 짧은 대기(수십 나노초)가 확실한 경우에만 씁니다.

## 9. 원문 점검 결과 요약

### 🔴 정정

| # | 원문 | 정정 |
| --- | --- | --- |
| 1 | V4의 `while (!Thread.interrupted())` 주석 "확인만 / 변경 X" | **확인 + 초기화**. V3에서 복사된 주석으로 보임. 정반대 의미 |
| 2 | "직접 깨우서" / "깨워난" / "대기 중이 때" / "기대데로" | **깨워서 / 깨어난 / 대기 중일 때 / 기대대로** |
| 3 | "InterruptException" | **InterruptedException** |
| 4 | "thread.stop()은 삭제된 기능" | Java 18까지 **동작**, **Java 20+** 에서 `UnsupportedOperationException` |
| 5 | 프린터 V1의 `continue` busy-wait | yield 절에 가서야 언급. **V1 시점에 이미 CPU 100%** |
| 6 | 두 번째 V3 코드도 클래스명이 `ThreadStopMainV3` | 다른 버전이므로 이름 구분 필요 |

### 🟡 보강

| # | 항목 | 보강 내용 |
| --- | --- | --- |
| 1 | `상태1 = true` | **경쟁 상태**. work가 먼저 지우면 false가 나올 수 있음 |
| 2 | `volatile` "공유 변수에 붙이는 키워드" | **JIT 호이스팅**을 막는 것. 가시성만 보장, 원자성은 ❌ |
| 3 | "runnable 상태여야 catch 코드 실행" | catch 블록도 CPU를 쓰는 코드이므로 |
| 4 | V3의 while 루프 | **busy waiting**으로 CPU 100% |
| 5 | `ConcurrentLinkedQueue` 필요성 | `LinkedList` 사용 시 **노드 포인터 파손** → 유실/무한루프/NPE |
| 6 | 프린터 V1의 `q` 반응 | `sleep(3000)` 때문에 **최대 3초 지연** |
| 7 | `yield()` | **공식 문서가 사용을 권하지 않음**. 주 용도는 테스트/디버깅 |

### 💡 추가

| # | 내용 | 위치 |
| --- | --- | --- |
| 1 | `interrupt()`는 **명령이 아니라 요청** (협력적 중단) | 2.3 |
| 2 | 대기 중이 아니면 **플래그만 켜지고**, 다음 블로킹 호출에서 터짐 | 2.3 |
| 3 | ⭐ **인터럽트 상태 복원 패턴** — 삼키지 마라 | 5장 |
| 4 | `Thread.interrupted()`를 **인스턴스 참조로 호출하는 함정** | 4.4 |
| 5 | 인터럽트에 반응하는 메서드 / 반응하지 않는 메서드 목록 | 6.1 |
| 6 | ⚠️ **블로킹 I/O는 인터럽트로 못 깨운다** → `close()` | 6.2 |
| 7 | `Scanner.next()`도 인터럽트 불가 | 6.3 |
| 8 | `Thread.stop()`이 위험한 구체적 이유 (락 + 중간 상태) | 6.4 |
| 9 | V2의 `break`가 **필수인 이유** | 7.2 |
| 10 | `Thread.onSpinWait()` (Java 9+) | 8.3 |
| 11 | ⭐ `BlockingQueue`로 busy-wait 자체를 없애기 | 부록 |

### 이번 글의 핵심 한 줄

> **인터럽트는 플래그 하나를 켜는 요청이고, 신호는 한 번만 전달된다.**
> 받았으면 **처리하거나 복원하거나** — 삼키는 것만은 하지 말 것.

# 부록. yield의 컨텍스트 스위칭 비용은 괜찮은 걸까?

문서 마지막에 남긴 질문입니다.

> "근데 여기서 발생하는 컨텍스트 스위칭 비용도 간과할 수 없는 거 아닌가? — 잘 모르겠음"

## A-1. 결론부터

**맞는 지적입니다. 그리고 그 의심이 정확히 올바른 결론으로 이어집니다.**

> ⭐ **`yield()`는 busy-wait보다 "덜 나쁜" 임시방편일 뿐, 좋은 해결책이 아닙니다.**
> 진짜 답은 **"양보하는 것"이 아니라 "아예 잠드는 것"**입니다.

## A-2. 컨텍스트 스위칭이 실제로 얼마나 비싼가

| 비용 | 내용 | 대략적 크기 |
| --- | --- | --- |
| **직접 비용** | 레지스터 저장/복원, 커널 모드 진입, 스케줄러 실행 | 1~5 μs |
| **간접 비용** ⭐ | **L1/L2 캐시 오염, TLB 플러시** → 새 스레드가 캐시 미스를 겪음 | 수십 μs까지 |

간접 비용이 훨씬 큽니다. 내 스레드가 다시 CPU를 받았을 때, 아까 캐시에 올려뒀던 데이터가 다른 스레드에 밀려 사라져 있기 때문입니다.

## A-3. 그럼 busy-wait과 yield 중 뭐가 나은가

```java
// ① 아무것도 안 함
while (queue.isEmpty()) {
    continue;
}

// ② yield
while (queue.isEmpty()) {
    Thread.yield();
}
```

| | busy-wait (`continue`) | `yield()` |
| --- | --- | --- |
| CPU 점유 | **코어 하나 100%** | 여전히 높음 (런큐에 계속 있음) |
| 컨텍스트 스위칭 | 적음. 단, **타임 슬라이스가 끝나면 어차피 강제로 발생** | **자발적으로 빈발** |
| 다른 스레드 영향 | 스케줄링 기회를 빼앗음 | 기회를 나눠줌 |
| 전력/발열 | 최악 | 나쁨 |

> 💡 **중요한 관점**: busy-wait이라고 컨텍스트 스위칭을 안 하는 게 아닙니다. 타임 슬라이스(보통 수 ms)를 다 쓰면 **OS가 강제로 전환**합니다. 즉 스위칭 자체는 어차피 일어나고, busy-wait은 거기에 **CPU 100% 낭비까지 더한 것**입니다.

그래서 `yield()`가 더 낫긴 합니다. 다만 **비교 대상이 잘못된 것**이 문제입니다.

## A-4. ⭐ 진짜 답 — 스레드를 재우면 스위칭 자체가 사라진다

핵심 통찰은 이겁니다.

> **`RUNNABLE` 상태로 남아 있는 한, 스케줄러는 계속 이 스레드를 고려 대상에 넣습니다.**
> `WAITING`으로 내려가면 **스케줄러의 후보 목록에서 아예 빠집니다.**

```text
[ yield 방식 ]                        [ BlockingQueue 방식 ]

printer: RUNNABLE ↔ RUNNABLE          printer: WAITING
  yield → 스케줄링 → yield → ...        (스케줄러가 쳐다보지도 않음)
  초당 수만 번 전환                        │
  CPU 사용률 높음                          │ 문서가 들어옴
                                           ▼
                                      딱 한 번 깨어남
                                      CPU 사용률 ~0%
```

```java
// ❌ busy-wait + yield
Queue<String> jobQueue = new ConcurrentLinkedQueue<>();

while (!Thread.interrupted()) {
    if (jobQueue.isEmpty()) {
        Thread.yield();
        continue;
    }
    String job = jobQueue.poll();
    ...
}

// ✅ BlockingQueue — 대기 자체를 큐에 맡긴다
BlockingQueue<String> jobQueue = new LinkedBlockingQueue<>();

try {
    while (true) {
        String job = jobQueue.take();   // ⭐ 비어 있으면 WAITING 으로 잠듦
        log("출력 시작: " + job);
        Thread.sleep(3000);
        log("출력 완료");
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // 상태 복원
}
log("프린터 종료");
```

## A-5. 세 방식 최종 비교

| | busy-wait | `+ yield()` | `BlockingQueue.take()` |
| --- | --- | --- | --- |
| CPU 사용률 (유휴 시) | **~100%** | 높음 | ⭐ **~0%** |
| 컨텍스트 스위칭 | 강제 전환 (타임 슬라이스) | **매우 빈번** | ⭐ **데이터 도착 시 1회** |
| 응답 지연 | 즉시 | 즉시 | ⭐ **즉시** |
| 인터럽트 반응 | 루프 조건에서 | 루프 조건에서 | ⭐ **즉시 예외** |
| 코드 복잡도 | 낮음 | 낮음 | ⭐ **가장 단순** |
| 전력/발열 | 최악 | 나쁨 | ⭐ **최선** |

`take()`가 모든 항목에서 이깁니다. **응답 지연이 없으면서도 CPU를 안 쓴다**는 게 핵심입니다. 스레드가 자는 동안 큐가 대신 "문서가 들어오면 깨워주는" 역할을 하기 때문입니다.

## A-6. 그럼 `yield()`는 언제 쓰나

거의 안 씁니다. 굳이 꼽으면:

| 상황 | 대안 |
| --- | --- |
| 큐/버퍼에서 데이터 대기 | ✅ `BlockingQueue.take()` |
| 조건 충족 대기 | ✅ `wait()/notify()`, `Condition.await()` |
| 다른 스레드 종료 대기 | ✅ `join()` |
| 락 대기 | ✅ `synchronized`, `ReentrantLock` |
| 락 프리 알고리즘의 **아주 짧은** 스핀 | ✅ `Thread.onSpinWait()` (Java 9+) |
| 경쟁 상태를 일부러 재현하는 테스트 | 🟡 `yield()` |

> ⭐ **정리**: 원문의 "다른 스레드에게 양보하는 게 전체 관점에서 더 효율적"은 **busy-wait과 비교했을 때만** 맞습니다. 하지만 `yield()`를 넣어야 한다는 생각이 들 때가, 사실은 **"대기 방식 자체가 잘못됐다"는 신호**입니다.
>
> **양보할 궁리를 하지 말고, 잘 자는 방법을 찾으세요.**

## A-7. 강의 흐름에서 yield를 배우는 이유

그럼 왜 배울까요? `BlockingQueue`가 **어떻게 CPU를 안 쓰면서 대기하는지** 이해하려면, 먼저 "안 그러면 어떻게 되는지"를 봐야 하기 때문입니다.

```text
① 플래그 방식        →  반응이 느리다              →  인터럽트 필요
② 인터럽트           →  busy-wait 은 CPU 낭비      →  대기 방식 개선 필요
③ yield             →  양보해도 근본은 안 바뀐다   →  ⭐ 재우는 법 필요
④ wait/notify       →  직접 만들기는 어렵다        →  고수준 도구 필요
⑤ BlockingQueue     →  ✅ 정답
```

지금 `yield()`를 보는 건 **②에서 ⑤로 가는 길 위의 한 걸음**입니다. 질문에서 느낀 찜찜함이 정확히 다음 단계로 넘어가야 할 이유였습니다.
