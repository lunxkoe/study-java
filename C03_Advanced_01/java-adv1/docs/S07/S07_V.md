# [Java] synchronized로 동시성 문제 해결하기, 그리고 락을 쥐는 시간

잔액 1000원짜리 계좌에서 800원씩 두 번 출금했더니 **잔액이 -600원**이 됐다. 검증 로직은 분명히 있었다.

```java
if (balance < amount) {
    return false;          // 검증은 통과했는데?
}
balance -= amount;
```

이전 글에서 `volatile`로 메모리 가시성 문제를 풀었다. 그런데 **이 문제는 `volatile`로 풀리지 않는다.** 검증할 때 읽은 값이 진짜로 최신 값이었기 때문이다.

이번 글은 그 다음 층위의 문제, **원자성**에 대한 이야기다.

# 1. 문제 재현

## 1.1 공유 자원

여러 스레드가 함께 접근하는 자원을 **공유 자원**이라고 한다. 여기서는 `balance`다. 멀티스레드를 쓸 때는 공유 자원에 대한 접근을 적절히 동기화해서 동시성 문제를 막는 게 중요하다.

```java
public class BankAccountV1 implements BankAccount {

    private int balance;

    public BankAccountV1(int balance) {
        this.balance = balance;
    }

    @Override
    public boolean withdraw(int amount) {
        log("거래 시작: " + getClass().getSimpleName());

        log("[검증 시작] 출금액: " + amount + ", 잔액: " + balance);
        if (balance < amount) {                    // ① 검증 (check)
            log("[검증 실패] 출금액: " + amount + ", 잔액: " + balance);
            return false;
        }

        log("[검증 완료] 출금액: " + amount + ", 잔액: " + balance);
        sleep(1000);                                // 출금에 걸리는 시간
        balance -= amount;                          // ② 출금 (act)
        log("[출금 완료] 출금액: " + amount + ", 잔액: " + balance);

        log("거래 종료: " + getClass().getSimpleName());
        return true;
    }

    @Override
    public int getBalance() {
        return balance;
    }
}
```

단일 스레드로는 아무 문제가 없다.

```text
18:02:24.460 [       t1] [검증 시작] 출금액: 800, 잔액: 1000
18:02:24.461 [       t1] [검증 완료] 출금액: 800, 잔액: 1000
18:02:25.471 [       t1] [출금 완료] 출금액: 800, 잔액: 200
18:02:25.472 [     main] 최종 잔액: 200               ← ✅ 정상
```

## 1.2 동시에 출금하면

```java
Thread t1 = new Thread(new WithdrawTask(bankAccount, 800), "t1");
Thread t2 = new Thread(new WithdrawTask(bankAccount, 800), "t2");

t1.start();

sleep(500);   // 검증 완료까지 잠시 대기
log("t1 state: " + t1.getState());
log("t2 state: " + t2.getState());

t1.join();
t2.join();
log("최종 잔액: " + bankAccount.getBalance());
```

# 2. 무엇이 깨진 걸까

## 2.1 타임라인

```text
시간 ──────────────────────────────────────────────────▶
        0ms              500ms             1000ms

t1   │검증: 1000 ≥ 800 ✅│←── sleep(1000) ──→│ balance -= 800
                                              │
t2   │검증: 1000 ≥ 800 ✅│←── sleep(1000) ──→│ balance -= 800
     ▲                                        │
     │                                        ▼
  둘 다 같은 1000을 보고 통과              최종 -600
```

t1, t2가 같은 인스턴스를 각자의 스택 프레임에 `this`로 올리고, 동시에 같은 `balance` 필드에 접근한다. 검증 로직은 **둘 다 통과**했다. 그래서 1600원이 나갔다.

## 2.2 ⭐ 이건 "갱신 손실"이 아니라 "check-then-act" 문제다

동시성 버그는 크게 두 종류인데, 이 예제에서 터진 건 앞쪽이다. 구분해두면 훨씬 명확해진다.

| | check-then-act | lost update (갱신 손실) |
| --- | --- | --- |
| 깨지는 지점 | **검증과 실행 사이**의 시간 틈 | `balance -= amount` **연산 자체** |
| 이 예제의 결과 | **-600** (둘 다 성공) | 200 (한 번만 반영) |
| 원인 | 검증 시점의 값이 실행 시점엔 낡음 | 읽기→계산→쓰기가 원자적이지 않음 |
| `volatile`로 해결? | ❌ 불가능 | ❌ 불가능 |
| `AtomicInteger`로? | ❌ 단순 연산으로는 불가 | ✅ `addAndGet()` |

최종 잔액이 **200이 아니라 -600**이라는 게 중요한 단서다. 뺄셈이 두 번 다 반영됐으니 **갱신은 손실되지 않았다.** 문제는 **1000원을 보고 통과한 검증이 실행 시점에는 이미 유효하지 않았다**는 것이다.

> ⭐ **`sleep(1000)`은 check와 act 사이의 틈을 1초로 벌려서 문제를 100% 재현하게 만든 장치다.**
> 실제 코드에서는 이 틈이 나노초 단위라 **가끔만 터진다.** 그래서 더 위험하다.

## 2.3 `balance -= amount`도 원자적이지 않다

이건 별개의 버그다.

```java
balance -= amount;

// 실제로는 3단계
// ① balance 를 읽는다        (read)
// ② amount 를 뺀다           (modify)
// ③ balance 에 저장한다       (write)
```

만약 두 스레드가 ①을 동시에 실행해서 **같은 1000원을 읽으면**, 각자 200을 계산해서 저장하고 결과는 200이 된다. 800원이 공짜로 생기는 셈이다. 이전 글의 `count++`와 정확히 같은 구조다.

이 예제에서는 `sleep(1000)` 덕분에 두 뺄셈이 시간적으로 벌어져 드러나지 않았을 뿐이다.

## 2.4 ⚠️ volatile을 붙이면 될까? — 안 된다

```java
private volatile int balance;   // 붙여도 -600 이 그대로 나온다
```

| `volatile`이 보장하는 것 | 이 문제에 도움이 되나 |
| --- | --- |
| 가시성 — 최신 값을 읽는다 | 🟡 값은 최신으로 읽지만 |
| 순서 — 재정렬 방지 | 🟡 순서는 문제가 아니었고 |
| **원자성 — 보장 안 함** | ❌ **여기가 깨진 지점** |

t2가 검증할 때 `balance`는 **진짜로 1000이었다.** 최신 값을 정확히 읽었는데도 문제가 생긴 것이다. 가시성이 아니라 **"검증부터 실행까지를 한 덩어리로 묶는 것"**이 필요하다.

> ⭐ **`volatile`은 "값을 언제 보느냐"의 문제를 풀고, `synchronized`는 "누가 언제 들어오느냐"의 문제를 푼다.** 층위가 다르다.

# 3. 임계 영역

## 3.1 근본 원인

```text
공유 자원(balance)을  →  여러 단계(검증 / 출금)로 나누어 사용하기 때문
                              │
                              ▼
                     그 사이에 다른 스레드가 끼어들 수 있다
```

**단계가 하나뿐이었다면 문제가 없었다.** 단계를 나누는 순간 "그 사이"라는 틈이 생긴다.

> **임계 영역(Critical Section)**
> 여러 스레드가 동시에 접근하면 데이터 불일치나 예상치 못한 동작이 발생할 수 있는 코드 구간.
> **한 번에 하나의 스레드만 접근하도록 보호해야 한다.**

물론 t1이 출금을 완전히 끝낸 다음에 t2가 시작하도록 만들면 문제는 사라진다. 다만 그러면 멀티스레드를 쓸 이유가 없어진다. 그래서 **꼭 필요한 구간만** 한 번에 하나씩 통과시키는 게 목표다.

## 3.2 함께 알아두면 좋은 용어

| 용어 | 의미 |
| --- | --- |
| **경쟁 상태 (Race Condition)** | 실행 타이밍에 따라 결과가 달라지는 상태 |
| **상호 배제 (Mutual Exclusion)** | 한 번에 하나만 들어가게 하는 것 |
| **원자성 (Atomicity)** | 여러 단계가 쪼개지지 않는 하나의 동작처럼 보이는 성질 |

`synchronized`는 **상호 배제를 통해 원자성을 만들어내는 도구**다.

# 4. synchronized 메서드

## 4.1 적용

```java
@Override
public synchronized boolean withdraw(int amount) {
    // ... 내용 동일
}
```

```text
19:00:15.125 [       t1] [검증 시작] 출금액: 800, 잔액: 1000
19:00:15.126 [       t1] [검증 완료] 출금액: 800, 잔액: 1000
19:00:15.583 [     main] t1 state: TIMED_WAITING     ← sleep 중
19:00:15.584 [     main] t2 state: BLOCKED           ← 락 대기 중
19:00:16.127 [       t1] [출금 완료] 출금액: 800, 잔액: 200
19:00:16.128 [       t2] 거래 시작: BankAccountV2    ← 이제야 진입
19:00:16.128 [       t2] [검증 시작] 출금액: 800, 잔액: 200
19:00:16.129 [       t2] [검증 실패] 출금액: 800, 잔액: 200   ← ✅ 정상
19:00:16.129 [     main] 최종 잔액: 200
```

## 4.2 동작 원리

**모든 객체는 내부에 자신만의 락(모니터 락)을 가지고 있다.** `synchronized` 메서드에 진입하려면 그 인스턴스의 락이 반드시 필요하다.

```text
        BankAccountV2 인스턴스 @x001
        ┌──────────────────────────────┐
        │  balance = 1000              │
        │  🔒 모니터 락 (모든 객체가 가짐)  │
        └──────────────────────────────┘
                   ▲
        ┌──────────┴──────────┐
        │                     │
   t1: 락 획득 ✅         t2: 락 획득 실패 ❌
        │                     │
   withdraw() 진입        BLOCKED 로 대기
        │                     │  (CPU 스케줄링에서 제외)
   sleep(1000)                │
        │                     │
   balance -= 800             │
        │                     │
   메서드 종료 → 락 반납 ──────▶ 락 획득 ✅
                              │
                         withdraw() 진입
                         검증 실패 → false
```

## 4.3 ⭐ 로그에서 읽어낼 것

```text
t1 state: TIMED_WAITING     ← sleep(1000) 중
t2 state: BLOCKED           ← 모니터 락 대기 중
```

이전 글들에서 정리한 두 상태가 한 화면에 잡혔다. 그런데 여기에 더 중요한 게 있다.

> ⭐ **t1은 자고 있는데도 락을 쥐고 있다.**
> **"`sleep()`은 락을 반납하지 않는다"**가 그대로 드러난 장면이다. (`wait()`였다면 반납했을 것이다.)
> 그래서 t2는 **t1이 자는 1초 동안 아무것도 못 하고 통째로 기다린다.**

이 사실이 8장의 논의로 이어진다.

## 4.4 락 획득 순서는 보장되지 않는다

`synchronized`는 **불공정(non-fair) 락**이다.

```text
대기 큐: [t2(10초 대기)] [t3(5초 대기)]
                  ▲
                  │  t4 가 방금 도착
                  │
          ⚠️ t4 가 t2, t3 을 제치고 가져갈 수 있다 (barging)
```

- 오래 기다린 순서대로 주지 않는다
- 이론적으로 **기아(starvation)** — 특정 스레드가 영원히 락을 못 얻는 상황이 가능하다
- 대신 **성능은 공정 락보다 좋다** (컨텍스트 스위칭이 적음)
- 순서가 꼭 필요하면 `new ReentrantLock(true)`. 단, 훨씬 느리다

## 4.5 volatile 없이도 가시성이 해결되는 이유

`synchronized`를 쓰면 `volatile`을 따로 붙이지 않아도 가시성 문제가 해결된다. 근거는 이전 글에서 정리한 happens-before의 **모니터 락 규칙**이다.

```text
t1: synchronized 진입
    balance = 200
    synchronized 해제      ──┐
                             │ ⭐ 해제 → 획득 happens-before
                             ▼
t2:                      synchronized 획득
                         balance 읽기 → ✅ 반드시 200 이 보인다
```

> ⚠️ **단, "락을 잡고 접근할 때만" 보장된다.**
> ```java
> public int getBalance() {   // 락을 안 잡는다
>     return balance;
> }
> ```
> `getBalance()`는 happens-before 관계를 만들지 않으므로 **낡은 값을 읽을 수 있다.** 이 예제에서는 `join()`이 가시성을 만들어줘서 정상 값이 나오는 것뿐이다. **getter에도 `synchronized`(또는 `volatile`)가 필요하다.**

# 5. 모니터 락 깊게 보기

세 가지는 꼭 알아두자.

## 5.1 ⚠️ 락의 대상 — 인스턴스 vs 클래스

```java
class Counter {
    synchronized void a() { }          // 🔒 this 에 락
    synchronized static void b() { }   // 🔒 Counter.class 에 락
}
```

| 형태 | 락 대상 | 동등한 블록 |
| --- | --- | --- |
| `synchronized` 인스턴스 메서드 | **`this`** | `synchronized (this) { }` |
| `synchronized` static 메서드 | **클래스 객체** | `synchronized (Counter.class) { }` |

> ⚠️ **이 둘은 서로 다른 락이다.** `a()`와 `b()`는 **동시에 실행될 수 있다.**

```java
class Wrong {
    private static int count;                      // static 공유 자원

    synchronized void increment() { count++; }     // ⚠️ this 에 락
    // → 인스턴스가 2개면 락도 2개. count 는 전혀 보호되지 않는다
}
```

static 필드를 인스턴스 메서드의 `synchronized`로 보호하려 했다면, 그건 보호가 아니다.

## 5.2 ⭐ 재진입 가능(reentrant)하다

```java
class Foo {
    synchronized void outer() {
        inner();          // ✅ 데드락 안 걸림
    }
    synchronized void inner() { }
}
```

같은 스레드가 **이미 가진 락을 다시 획득하는 건 허용된다.** JVM이 락마다 **획득 횟수(카운터)**를 세고, 0이 될 때 완전히 해제한다.

```text
t1: outer() 진입 → 락 획득, 카운터 = 1
    inner() 진입 → 이미 내 락, 카운터 = 2
    inner() 종료 → 카운터 = 1  (아직 해제 안 됨)
    outer() 종료 → 카운터 = 0  ⭐ 여기서 해제
```

재진입이 안 됐다면 **자기가 자기를 기다리는 데드락**이 생겼을 것이다. `ReentrantLock`의 이름도 여기서 왔다.

## 5.3 예외가 나도 락은 자동으로 풀린다

```java
synchronized void risky() {
    balance -= 1000;
    throw new RuntimeException("펑");   // 💥
}   // ⭐ 락은 자동 해제된다
```

컴파일된 바이트코드를 보면 `monitorenter` / `monitorexit`가 **예외 핸들러와 함께** 짝지어져 있다. 그래서 `try-finally`를 직접 쓸 필요가 없다.

> 💡 이게 `ReentrantLock`과의 큰 차이다. `ReentrantLock`은 반드시 직접 풀어줘야 한다.
> ```java
> lock.lock();
> try {
>     // ...
> } finally {
>     lock.unlock();   // ⭐ 빠뜨리면 영원히 안 풀림
> }
> ```

> ⚠️ 다만 **락이 풀린다고 데이터가 멀쩡한 건 아니다.** 위 예제에서 `balance`는 이미 1000이 빠진 채로 남는다. **락은 일관성을 지켜주지 않는다. 배타성만 지켜준다.**

# 6. synchronized 코드 블록

## 6.1 메서드 전체를 잠글 필요는 없다

`synchronized` 메서드는 **메서드 전체**를 임계 영역으로 만든다. 그런데 정말 보호가 필요한 건 일부뿐인 경우가 많다. 한 번에 하나의 스레드만 실행되는 구간이 길수록 전체 처리량이 떨어지므로, **꼭 필요한 곳만** 좁게 잡아야 한다.

```java
@Override
public boolean withdraw(int amount) {
    log("거래 시작: " + getClass().getSimpleName());    // 공유 자원 안 건드림

    synchronized (this) {                               // ⭐ 여기부터
        log("[검증 시작] ... 잔액: " + balance);
        if (balance < amount) {
            log("[검증 실패] ...");
            return false;
        }
        log("[검증 완료] ...");
        sleep(1000);
        balance -= amount;
        log("[출금 완료] ... 잔액: " + balance);
    }                                                    // ⭐ 여기까지

    log("거래 종료: " + getClass().getSimpleName());     // 공유 자원 안 건드림
    return true;
}

@Override
public synchronized int getBalance() {
    return balance;
}
```

`synchronized (this)`의 `this`는 **락을 획득할 인스턴스의 참조**다. `BankAccountV3` 인스턴스의 락을 쓰므로 `this`를 넣는다.

> 💡 블록 한가운데서 `return false`를 해도 **락은 안전하게 풀린다**(5.3). 다만 검증 실패 시 "거래 종료" 로그가 안 찍힌다는 점은 이전 버전과 동작이 달라진 부분이다.

# 7. 락 객체를 무엇으로 할 것인가

실무에서 사고가 잦은 지점이라 따로 정리한다.

## 7.1 ⚠️ `this`를 락으로 쓰면 외부에 노출된다

```java
// 내 클래스
class BankAccount {
    public boolean withdraw(int amount) {
        synchronized (this) { ... }
    }
}

// 남의 코드
BankAccount account = ...;
synchronized (account) {        // ⚠️ 내 락을 외부에서 잡아버림
    Thread.sleep(100000);       // ⚠️ 내 withdraw() 가 100초 동안 멈춤
}
```

**락 객체가 `public`이면, 그 락은 사실상 공개 API다.** 내가 통제할 수 없는 곳에서 잠글 수 있다.

## 7.2 ✅ 전용 락 객체를 쓰자

```java
public class BankAccountV4 implements BankAccount {

    private int balance;
    private final Object lock = new Object();   // ⭐ private final

    @Override
    public boolean withdraw(int amount) {
        synchronized (lock) {
            // ...
        }
    }
}
```

| | `synchronized (this)` | `private final Object lock` |
| --- | --- | --- |
| 외부에서 잠글 수 있나 | ⚠️ 가능 | ✅ 불가능 |
| 락을 여러 개로 쪼갤 수 있나 | ❌ 하나뿐 | ✅ 용도별로 분리 가능 |
| 코드 간결성 | 간단 | 필드 하나 추가 |

이전 글에서 **"`Thread` 객체를 락으로 쓰지 마라"**고 했던 것과 같은 원칙이다.

## 7.3 ⚠️ 절대 락으로 쓰면 안 되는 것들

```java
private String lock = "LOCK";           // ❌ 문자열 리터럴 — String Pool 공유!
private Integer lock = 0;               // ❌ Integer 캐시 (-128~127) 공유
private Boolean lock = Boolean.FALSE;   // ❌ 싱글턴
```

문자열 리터럴은 **JVM 전체가 하나의 객체를 공유**한다. 전혀 무관한 라이브러리가 같은 문자열로 락을 걸면 서로의 코드가 막힌다. 디버깅이 거의 불가능한 버그가 된다.

```java
private final Object lock = new Object();   // ✅ 항상 이렇게
```

# 8. ⭐ 임계 영역을 진짜로 줄이기

## 8.1 방금 만든 V3는 사실 거의 줄이지 못했다

"임계 영역을 작게 유지하자"는 방향으로 코드 블록을 썼는데, **실제로 줄어든 건 로그 두 줄뿐이다.**

```text
[ V2: synchronized 메서드 ]        [ V3: synchronized 블록 ]

┌─ 🔒 락 ──────────────────┐        거래 시작 로그         ← 락 밖 ✅
│ 거래 시작 로그           │        ┌─ 🔒 락 ─────────────┐
│ 검증                     │        │ 검증                │
│ sleep(1000)  ⚠️          │        │ sleep(1000)  ⚠️     │ ← 여전히 안!
│ balance -= amount        │        │ balance -= amount   │
│ 거래 종료 로그           │        └─────────────────────┘
└──────────────────────────┘        거래 종료 로그         ← 락 밖 ✅

  락 보유 시간: 약 1000ms              락 보유 시간: 약 1000ms
                                       (거의 그대로)
```

**`sleep(1000)`이 락 안에 그대로 있다.** 이게 진짜 병목이다. 4.3에서 확인했듯 **자는 동안에도 락은 반납되지 않으므로**, 다른 스레드는 1초를 통째로 기다린다.

## 8.2 왜 sleep을 뺄 수 없나

`sleep(1000)`은 "출금에 걸리는 시간"을 흉내 낸 것이다. 실제로는 **외부 시스템 호출(은행 전산망, DB 커밋)**이라고 보면 된다.

```text
검증 → [외부 시스템 호출 1초] → 잔액 차감
  ▲                              ▲
  └──── 이 전체를 락으로 묶으면 ────┘
        1초 동안 다른 거래가 전부 멈춘다
```

문제는 **check-then-act를 유지하려면 검증과 차감이 같은 락 안에 있어야 한다**는 것이다. 그렇다고 1초짜리 I/O를 락 안에 두면 처리량이 초당 1건으로 떨어진다.

## 8.3 실무의 해법 — 예약 후 확정 패턴

```java
public boolean withdraw(int amount) {
    // ① 짧은 임계 영역: 검증 + 차감을 원자적으로
    synchronized (lock) {
        if (balance < amount) return false;
        balance -= amount;              // ⭐ 먼저 빼둔다 (예약)
    }
    // 락 보유 시간: 마이크로초 단위

    // ② 느린 작업은 락 밖에서
    try {
        externalBankApi.transfer(amount);   // 1초 걸리는 I/O
    } catch (Exception e) {
        synchronized (lock) {
            balance += amount;              // ③ 실패 시 롤백
        }
        return false;
    }
    return true;
}
```

| | 원래 V3 | 예약 후 확정 |
| --- | --- | --- |
| 락 보유 시간 | **약 1000ms** | **마이크로초 단위** |
| 동시 처리 가능 건수 | 초당 1건 | 초당 수천 건 |
| 정합성 | ✅ | ✅ (롤백으로 보정) |
| 복잡도 | 낮음 | 보상 로직 필요 |

> ⭐ **핵심 원칙: 락 안에서는 절대 느린 일을 하지 마라.**

| 락 안에 두면 안 되는 것 | 이유 |
| --- | --- |
| `sleep()` | 자면서 락을 쥔다 |
| 네트워크 I/O, DB 호출 | 수백 ms ~ 수 초 |
| 파일 읽기/쓰기 | 느림 |
| 다른 객체의 `synchronized` 호출 | **데드락 위험** |
| 무거운 연산, 로깅 | 필요 이상으로 길어짐 |

> 💡 학습 예제에서 `sleep`을 락 안에 두는 건 **"락이 잡혀 있다"는 사실을 눈으로 보여주기 위한 장치**다. 실제 코드에서 따라 하면 안 된다는 것만 알아두면 된다.

# 9. synchronized의 한계

## 9.1 할 수 없는 것들

| 한계 | 설명 |
| --- | --- |
| ⏱ **타임아웃 불가** | "1초만 기다리고 포기"가 안 된다 |
| ✋ **취소 불가** | `BLOCKED`는 **인터럽트에 반응하지 않는다** |
| 🔓 **범위 고정** | 블록 안에서 획득하고 블록 끝에서 해제. 유연하지 않음 |
| 📖 **읽기/쓰기 구분 없음** | 읽기만 하는 스레드끼리도 서로 막는다 |
| ⚖️ **공정성 선택 불가** | 항상 불공정 |

## 9.2 ReentrantLock이 해결하는 것

```java
private final ReentrantLock lock = new ReentrantLock();

// 타임아웃
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }
} else {
    log("1초 기다렸는데 못 얻음 — 포기");
}

// 인터럽트 가능
lock.lockInterruptibly();

// 공정 모드
new ReentrantLock(true);
```

| | `synchronized` | `ReentrantLock` |
| --- | --- | --- |
| 해제 | ✅ 자동 | ⚠️ `finally`에서 직접 |
| 타임아웃 | ❌ | ✅ `tryLock(time)` |
| 인터럽트 | ❌ (`BLOCKED`) | ✅ `lockInterruptibly()` |
| 공정성 | 불공정 고정 | ✅ 선택 가능 |
| 읽기/쓰기 분리 | ❌ | ✅ `ReadWriteLock` |
| 코드 간결성 | ✅ | 장황함 |

> 💡 **성능은 요즘 거의 차이가 없다.** 예전에는 `ReentrantLock`이 빨랐지만 JVM의 락 최적화가 발전하면서 비슷해졌다. **기능이 더 필요할 때만 `ReentrantLock`을 쓰고, 기본은 `synchronized`**가 권장된다.

## 9.3 가상 스레드를 쓴다면 JDK 버전 확인

| JDK | 상황 |
| --- | --- |
| 21~23 | 가상 스레드가 `synchronized` 안에서 블로킹되면 **캐리어 스레드를 고정(pinning)**시켜 성능이 급락 → `ReentrantLock` 권장 |
| 24+ | JEP 491로 해결됨 → `synchronized`도 안전 |

# 마무리 정리

## 한 줄 요약

> **`volatile`은 "값을 언제 보느냐"를 풀고, `synchronized`는 "누가 언제 들어오느냐"를 푼다.**
> 그리고 **락을 쥐고 있는 시간이 곧 처리량의 상한**이다.

## 헷갈리기 쉬운 포인트 10가지

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | `volatile`을 붙이면 이 버그도 해결된다 | **원자성은 보장 안 함.** 최신 값 읽고도 깨진다 |
| 2 | 잔액이 200이 나와야 정상 | 이 예제는 **-600**. lost update가 아니라 check-then-act |
| 3 | `balance -= amount`는 한 줄이니 원자적 | **읽기→계산→쓰기 3단계** |
| 4 | `sleep` 중이면 락이 풀린다 | **안 풀린다.** `wait()`만 반납한다 |
| 5 | 락은 오래 기다린 순서로 준다 | **불공정 락.** barging·기아 가능 |
| 6 | 인스턴스 메서드 `synchronized`가 static 필드를 지켜준다 | **락 대상이 다르다.** 전혀 안 지켜짐 |
| 7 | `synchronized` 안에서 `synchronized`를 부르면 데드락 | **재진입 가능**하다 |
| 8 | 예외가 나면 락이 안 풀린다 | **자동으로 풀린다.** 단 데이터는 안 지켜줌 |
| 9 | 아무 객체나 락으로 써도 된다 | `String`·`Integer`는 **공유 객체라 위험** |
| 10 | 코드 블록으로 바꾸면 임계 영역이 작아진다 | **안에 뭐가 있는지**가 중요. `sleep`이 있으면 의미 없음 |

## 동시성 도구 총정리

| | 가시성 | 원자성 | 블로킹 | 언제 |
| --- | --- | --- | --- | --- |
| `final` / 불변 객체 | ✅ | — | ❌ | **가능하면 항상 1순위** |
| `volatile` | ✅ | ❌ | ❌ | 한 스레드만 쓰는 플래그 |
| `Atomic*` | ✅ | ✅ (단일 변수) | ❌ | 카운터, CAS |
| `synchronized` | ✅ | ✅ (블록 전체) | ✅ | **여러 단계를 묶어야 할 때** |
| `ReentrantLock` | ✅ | ✅ | ✅ | 타임아웃·취소·공정성이 필요할 때 |

다음 글에서는 `wait()`와 `notify()`를 다룬다. 락을 **쥔 채로 기다리는 것**이 아니라, **반납하고 기다리는 법**에 대한 이야기다.
