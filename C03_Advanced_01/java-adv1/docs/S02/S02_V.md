# [Java] 스레드 생성과 실행, 메모리 구조부터 제대로 이해하기

멀티스레드를 처음 배우면 `Thread`, `Runnable`, `start()`, `run()`, 데몬 스레드가 한꺼번에 쏟아진다. 그런데 이걸 사용법으로만 외우면 조금만 응용해도 바로 막힌다.

- `run()`을 직접 호출하면 왜 안 될까?
- 여러 스레드가 "같은 객체의 `run()`을 실행한다"는 게 정확히 무슨 뜻일까?
- 익명 클래스로 만든 객체는 언제 사라질까?

세 질문의 답은 전부 **자바 메모리 구조** 하나로 풀린다. 그래서 이 글은 메모리 구조를 먼저 깔고, 그 위에 스레드를 올리는 순서로 정리했다.

# 1. 자바 메모리 구조

스레드 이야기를 하기 전에 메모리부터 봐야 한다. 스레드는 결국 **"메모리의 어느 부분을 나눠 쓰고, 어느 부분을 공유하느냐"**의 문제이기 때문이다.

## 1.1 전체 그림

```text
┌──────────────────────── JVM 런타임 데이터 영역 ─────────────────────────┐
│                                                                        │
│  ┌── 메서드 영역 (Method Area) ───────────────── 모든 스레드 공유 ──┐   │
│  │  · 클래스 정보 : 바이트코드, 메서드/필드 메타데이터              │   │
│  │  · static 영역 : static 변수                                     │   │
│  │  · 런타임 상수 풀 : 심볼릭 레퍼런스, 상수                        │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                        │
│  ┌── 힙 영역 (Heap) ──────────────────────────── 모든 스레드 공유 ──┐   │
│  │  · 객체 인스턴스, 배열                                           │   │
│  │  · GC의 주 무대                                                  │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                        │
│  ┌── 스택 영역 (JVM Stack) ───────────────── 스레드마다 1개씩! ─────┐   │
│  │   [ main 스택 ]    [ Thread-0 스택 ]    [ Thread-1 스택 ]  ...   │   │
│  │     프레임              프레임               프레임              │   │
│  │     프레임              프레임                                   │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                        │
│  ┌── PC 레지스터 · 네이티브 메서드 스택 ──── 스레드마다 1개씩 ──────┐   │
│  └──────────────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────────┘
```

| 영역 | 저장 대상 | 공유 범위 | 생성 시점 | GC 대상 |
| --- | --- | --- | --- | --- |
| **메서드 영역** | 클래스 정보, 바이트코드, static 변수, 런타임 상수 풀 | 모든 스레드 공유 | 클래스 로딩 시 | 클래스 언로딩 시에만 |
| **힙 영역** | 객체 인스턴스, 배열 | 모든 스레드 공유 | `new` 실행 시 | ✅ 주 대상 |
| **스택 영역** | 스택 프레임(지역 변수, 피연산자 스택, 반환 주소) | **스레드마다 독립** | 스레드 시작 시 | ❌ (프레임 pop으로 해제) |
| **PC 레지스터** | 현재 실행 중인 바이트코드 주소 | **스레드마다 독립** | 스레드 시작 시 | ❌ |
| **네이티브 메서드 스택** | native 메서드 호출 정보 | **스레드마다 독립** | 스레드 시작 시 | ❌ |

> ⭐ **가장 중요한 한 줄**
> 메서드 영역과 힙은 **모두가 같이** 쓰고, 스택은 **스레드마다 따로** 쓴다.

자바를 실행하면 스택이 1개인 것처럼 보이는데, 이건 스택이 원래 하나여서가 아니라 처음에 `main` 스레드 하나만 있기 때문이다. 스레드를 3개 더 만들면 스택도 3개 더 생긴다.

## 1.2 알아두면 좋은 디테일

**메서드 영역은 JVM 명세상의 '논리적 개념'이다**

실제 HotSpot JVM에서는 이게 **Metaspace**라는 이름으로, 심지어 JVM 힙이 아닌 **네이티브 메모리**에 구현되어 있다. Java 7까지는 PermGen(힙의 일부)이었고 Java 8부터 Metaspace로 바뀌었다. "메서드 영역 = 특정 물리 메모리 블록"이 아니라 **"역할의 이름"**으로 이해하는 게 정확하다.

**static 변수와 문자열 리터럴은 Java 8부터 사실상 힙에 있다**

| 항목 | Java 6 이하 | Java 7 | Java 8 이상 |
| --- | --- | --- | --- |
| static 변수 | PermGen | PermGen | **힙** (Class 객체가 들고 있음) |
| String Pool | PermGen | **힙** | **힙** |
| 클래스 메타데이터 | PermGen | PermGen | **Metaspace** (네이티브 메모리) |

개념을 설명할 때는 "static 변수는 메서드 영역"이라고 말해도 되지만, 면접이나 GC 튜닝 맥락에서는 위 표가 정확한 답이다.

**런타임 상수 풀은 리터럴만 담는 곳이 아니다**

클래스·메서드·필드에 대한 **심볼릭 레퍼런스**가 대부분을 차지한다. 문자열 리터럴 자체는 힙의 String Pool에 있고, 상수 풀은 그걸 가리키는 참조를 갖는다.

> 💡 사실 모든 객체가 반드시 힙에 생기는 것도 아니다. JIT의 **탈출 분석(Escape Analysis)** 이 "이 객체는 메서드 밖으로 절대 새어나가지 않는다"고 판단하면 객체를 아예 만들지 않고 필드를 지역 변수로 쪼개버린다(스칼라 치환). 지금 외울 필요는 없고, "힙/스택은 개념 모델이고 실제 실행은 더 영악하다" 정도만 알아두자.

## 1.3 ⭐ 나뉘는 것 vs 공유되는 것

멀티스레드에서 **버그가 생기는 지점을 찾는 지도**다. 앞으로 나올 모든 이야기가 이 표로 수렴한다.

| 구분 | 어디에 | 공유? | 동시성 문제 |
| --- | --- | --- | --- |
| 지역 변수 (기본형) | 스택 | ❌ 스레드마다 별도 | 안전 |
| 매개변수 | 스택 | ❌ 스레드마다 별도 | 안전 |
| 참조 변수 **자체** | 스택 | ❌ 스레드마다 별도 | 안전 |
| 참조가 **가리키는 객체** | 힙 | ✅ **공유 가능** | ⚠️ **위험** |
| 인스턴스 필드 | 힙 | ✅ **공유 가능** | ⚠️ **위험** |
| static 변수 | 메서드 영역(논리) | ✅ **항상 공유** | ⚠️⚠️ **가장 위험** |

# 2. 스레드 만들기 ① Thread 상속

## 2.1 코드

```java
public class HelloThread extends Thread {

    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName() + ": run()");
    }
}
```

`Thread`를 상속하고 `run()`을 재정의하면, 그 안에 쓴 코드가 새 스레드에서 실행된다.

| API | 설명 |
| --- | --- |
| `Thread` 상속 + `run()` 재정의 | 스레드가 실행할 코드를 정의 |
| `Thread.currentThread()` | **static 메서드.** 이 줄을 *실행 중인* 스레드 객체를 반환 |
| `.getName()` | 스레드 이름 조회 (`main`, `Thread-0` …) |

> ⚠️ `Thread.currentThread()`는 "이 객체"가 아니라 **"이 코드를 지금 실행하고 있는 스레드"**를 반환한다. `HelloThread` 인스턴스의 `run()` 안에 있어도, `main` 스레드가 `run()`을 직접 호출하면 `main`이 반환된다. (3장에서 다룬다)

## 2.2 실행해보기

```java
public class HelloThreadMain {

    public static void main(String[] args) {
        // main 메서드는 JVM이 만들어준 "main" 이름의 스레드가 실행한다
        System.out.println(Thread.currentThread().getName() + ": main() start");

        HelloThread helloThread = new HelloThread();
        System.out.println(Thread.currentThread().getName() + ": start() 호출 전");

        helloThread.start();   // ⭐ run()이 아니라 start()

        System.out.println(Thread.currentThread().getName() + ": start() 호출 후");
        System.out.println(Thread.currentThread().getName() + ": main() end");
    }
}
```

```text
main: main() start
main: start() 호출 전
main: start() 호출 후
main: main() end
Thread-0: run()
```

`main`이 `start()`를 호출하고 **기다리지 않고 바로 다음 줄로 넘어간다**. 그래서 `main`이 전부 끝난 뒤에야 `Thread-0`의 출력이 찍혔다.

> ⚠️ 이 결과는 실행할 때마다 달라질 수 있다. 어떤 스레드에 CPU를 줄지는 OS 스케줄러가 결정하기 때문이다.

## 2.3 ⭐ 스택은 언제 생기는가

여기가 많이들 오해하는 지점이다. **`new Thread()`를 했다고 스레드가 시작되는 게 아니다.**

**① `new HelloThread()` 직후 — 힙에 객체만 생긴다. 스택은 여전히 1개**

```text
   메서드 영역              힙 영역                    스택 영역
 ┌──────────────┐     ┌──────────────────┐     ┌────────────────┐
 │ HelloThread  │     │ HelloThread 인스 │     │  main 스택     │
 │  클래스 정보 │◀────│ 턴스 @x001       │◀────│  main() 프레임 │
 │  run() 코드  │     │ (아직 잠자는 중) │     │   helloThread  │
 └──────────────┘     └──────────────────┘     └────────────────┘
                                          ⛔ Thread-0 스택 아직 없음
```

**② `start()` 호출 순간 — 이때 비로소 OS 스레드와 전용 스택이 생성된다**

```text
   메서드 영역              힙 영역                    스택 영역
 ┌──────────────┐     ┌──────────────────┐   ┌────────────┐ ┌──────────────┐
 │ HelloThread  │     │ HelloThread 인스 │   │ main 스택  │ │Thread-0 스택 │
 │  run() 코드  │◀────│ 턴스 @x001       │◀──│main()프레임│ │ run() 프레임 │
 └──────▲───────┘     └────────▲─────────┘   └────────────┘ └──────┬───────┘
        │                      │                                   │
        └──── 이 코드를 읽어 실행 ──── this 로 가리킴 ──────────────┘
```

**③ `run()` 종료 — Thread-0 스택이 통째로 제거된다**

| 시점 | 힙의 Thread 객체 | 전용 스택 | 상태 |
| --- | --- | --- | --- |
| `new Thread()` | ✅ 생성됨 | ❌ 없음 | `NEW` |
| `start()` 호출 | ✅ | ✅ **여기서 생성** | `RUNNABLE` |
| `run()` 종료 | ✅ (참조 남아있으면) | ❌ **제거됨** | `TERMINATED` |

> 💡 스레드 스택은 공짜가 아니다. 플랫폼 스레드 1개당 기본 **약 1MB**(OS·JVM 설정에 따라 다름)의 스택이 할당된다. 스레드를 수천 개 만들면 메모리가 터지는 이유이고, 나중에 배울 **스레드 풀**이 존재하는 이유다.

## 2.4 스레드 이름

이름을 주지 않으면 `Thread-0`, `Thread-1`, `Thread-2`… 순서대로 번호가 붙는다. 무작위가 아니라 순번이다.

```java
Thread t = new Thread(runnable, "order-worker");   // 생성 시 지정 (권장)
t.setName("order-worker");                         // 또는 나중에 변경
```

> 💡 실무에서는 스레드 이름을 반드시 지어준다. 장애 상황에서 스레드 덤프를 떴을 때 `Thread-47`보다 `payment-worker-3`이 압도적으로 유용하기 때문이다.

## 2.5 ⭐ 스레드 간 실행 순서는 보장되지 않는다

```text
시간 ──────────────────────────────────────────────▶

main    │■■■■■■■■│           │■■■■│
Thread-0│        │■■■■■■■■■■■│    │■■■■■■│
        ▲        ▲
        │        └─ 어디서 전환될지 아무도 모름
        └─ start() 호출
```

| 보장되는 것 | 보장되지 않는 것 |
| --- | --- |
| 한 스레드 **내부**에서의 문장 실행 순서 | 스레드 **간** 실행 순서 |
| `start()` 이후 언젠가 `run()`이 실행됨 | `run()`이 언제 시작되는지 |
| — | 어느 스레드가 먼저 끝나는지 |
| — | 한 스레드가 얼마나 오래 CPU를 잡는지 |

> ⚠️ 그래서 **멀티스레드 코드는 "여러 번 돌려봤는데 잘 되더라"로 검증할 수 없다.** 운 좋게 통과한 것일 수도 있다.

# 3. start() vs run()

## 3.1 이렇게 하면 멀티스레드가 아니다

```java
public class BadThreadMain {
    public static void main(String[] args) {
        HelloThread helloThread = new HelloThread();
        helloThread.run();   // ❌ 그냥 메서드 호출일 뿐
    }
}
```

```text
main: main() start
main: start() 호출 전
main: run()          ← ⚠️ Thread-0 이 아니라 main!
main: start() 호출 후
main: main() end
```

`Thread-0`이 아니라 `main`이 찍혔다. 새 스레드는 만들어지지도 않았고, `main`이 그냥 남의 메서드 하나를 호출한 것뿐이다.

## 3.2 비교

| | `run()` 직접 호출 | `start()` 호출 |
| --- | --- | --- |
| 실행 주체 | **호출한 스레드** (여기선 main) | **새로 만들어진 스레드** |
| 새 스택 생성 | ❌ | ✅ |
| OS 스레드 생성 | ❌ | ✅ |
| 동작 방식 | **동기** — 끝날 때까지 다음 줄로 안 감 | **비동기** — 바로 다음 줄로 넘어감 |
| 실행 위치 | main 스택에 `run()` 프레임이 쌓임 | Thread-0 스택에 `run()` 프레임이 쌓임 |
| 결과 | 일반 메서드 호출 | 진짜 멀티스레드 |

```text
[ run() 직접 호출 ]              [ start() 호출 ]

main 스택                        main 스택        Thread-0 스택
┌─────────────┐                  ┌────────────┐   ┌─────────────┐
│ run() 프레임│ ← 여기 쌓임      │main()프레임│   │ run() 프레임│
├─────────────┤                  └────────────┘   └─────────────┘
│main() 프레임│                       ▲                  ▲
└─────────────┘                       └── 동시에 각자 진행 ──┘
```

이때 `HelloThread` 객체가 아예 안 만들어진 건 아니다. **힙에 객체는 있지만 스레드로는 한 번도 시작되지 않았고 전용 스택도 없다.** 이 객체의 상태는 끝까지 `NEW`다. 말하자면 "잠재적 스레드"인 셈이다.

## 3.3 start()는 두 번 호출할 수 없다

```java
Thread t = new Thread(runnable);
t.start();
t.start();   // ❌ IllegalThreadStateException
```

한 번 실행이 끝난(`TERMINATED`) 스레드도 재사용할 수 없다. **`Thread` 객체는 일회용이다.** 이것도 나중에 스레드 풀이 필요해지는 이유 중 하나다.

# 4. 스레드의 6가지 상태

지금 한 번 잡아두면 이후 `sleep()`, `join()`, `synchronized`를 배울 때 훨씬 수월하다.

```text
             new Thread()
                  │
                  ▼
             ┌─────────┐
             │   NEW   │  객체만 생성, 아직 스택 없음
             └────┬────┘
                  │ start()
                  ▼
             ┌──────────┐   synchronized 락 대기   ┌─────────┐
             │ RUNNABLE │ ───────────────────────▶ │ BLOCKED │
             │          │ ◀─────────────────────── │         │
             └─┬──▲───┬─┘        락 획득           └─────────┘
               │  │   │
    wait()     │  │   │ sleep(n), join(n), wait(n)
    join()     │  │   │
               ▼  │   ▼
        ┌─────────┴┐ ┌──────────────┐
        │ WAITING  │ │ TIMED_WAITING│
        └──────────┘ └──────────────┘
                  │
                  │ run() 종료 또는 예외
                  ▼
            ┌────────────┐
            │ TERMINATED │  (재시작 불가)
            └────────────┘
```

| 상태 | 의미 | 진입 계기 |
| --- | --- | --- |
| `NEW` | 객체만 생성됨 | `new Thread()` |
| `RUNNABLE` | 실행 중이거나 CPU를 기다리는 중 | `start()` |
| `BLOCKED` | `synchronized` 락 획득 대기 | 락 경합 |
| `WAITING` | 다른 스레드의 신호를 무기한 대기 | `wait()`, `join()` |
| `TIMED_WAITING` | 시간 제한을 두고 대기 | `sleep(n)`, `join(n)` |
| `TERMINATED` | 실행 종료 | `run()` 반환 또는 예외 |

> ⚠️ **`RUNNABLE`이라고 지금 CPU를 쓰고 있는 건 아니다.** JVM은 "실행 중"과 "실행 대기(Ready)"를 구분하지 않고 둘 다 `RUNNABLE`로 표시한다. 심지어 **I/O 대기 중인 스레드도 `RUNNABLE`** 로 보인다(OS 관점에선 블로킹 상태인데도). 스레드 덤프를 읽을 때 자주 헷갈리는 부분이다.

# 5. 데몬 스레드

## 5.1 개념

스레드는 **사용자 스레드(user, non-daemon)**와 **데몬 스레드(daemon)** 두 가지로 나뉜다.

| | 사용자 스레드 | 데몬 스레드 |
| --- | --- | --- |
| 역할 | 프로그램의 **주요** 작업 | 백그라운드 **보조** 작업 |
| JVM 종료 | **이 스레드가 다 끝나야** JVM 종료 | JVM을 붙잡지 **못함** |
| 종료 방식 | 자기 일을 끝까지 함 | 사용자 스레드 전멸 시 **강제 종료** |
| 예시 | `main`, 웹 요청 처리 스레드 | GC 스레드, 모니터링, 캐시 정리 |

> ⭐ **핵심 규칙**
> JVM은 데몬 스레드의 완료를 기다리지 않는다.
> **사용자 스레드가 하나도 남지 않는 순간 JVM은 종료된다.**

```text
[ 사용자 스레드만 있을 때 ]        [ 데몬 스레드가 섞여 있을 때 ]

main    │■■■■│                     main    │■■■│
user-1  │■■■■■■■■■■│               daemon  │■■■■■✂ ← 강제로 잘림
                   ▲                            ▲
              여기서 JVM 종료              여기서 JVM 종료
             (마지막 사용자 스레드)        (사용자 스레드 = 0)
```

## 5.2 예제

```java
public class DaemonThreadMain {

    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName() + ": main() start");

        DaemonThread daemonThread = new DaemonThread();
        daemonThread.setDaemon(true);   // ⭐ 반드시 start() 이전에
        daemonThread.start();

        System.out.println(Thread.currentThread().getName() + ": main() end");
    }

    static class DaemonThread extends Thread {
        @Override
        public void run() {
            System.out.println(Thread.currentThread().getName() + ": run() start");
            try {
                Thread.sleep(10000);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);   // 원인 예외를 꼭 넘기자
            }
            System.out.println(Thread.currentThread().getName() + ": run() end");
        }
    }
}
```

```text
main: main() start
main: main() end
```

- `Thread-0: run() start`는 **찍힐 수도, 안 찍힐 수도** 있다. 타이밍 문제다.
- `Thread-0: run() end`는 **거의 확실히 안 찍힌다.** `main`이 끝나는 순간 사용자 스레드가 0이 되어 JVM이 종료되고, 10초를 자던 데몬 스레드는 그대로 잘려나간다.
- `setDaemon(true)`를 지우고 실행하면 10초 뒤 `run() end`까지 정상 출력된다.

## 5.3 ⚠️ 데몬 여부의 기본값은 false가 아니다

여기가 은근히 헷갈린다. `setDaemon()`을 호출하지 않으면 **부모 스레드의 데몬 여부를 그대로 상속한다.** `Thread` 생성자 안에서 이런 식으로 결정된다.

```java
this.daemon = parent.isDaemon();
```

```java
// main(사용자 스레드)이 만든 스레드  → 사용자 스레드  (결과적으로 false처럼 보임)
// 데몬 스레드가 만든 스레드          → 데몬 스레드!   (여기서 사고가 난다)
```

즉 `false`가 기본값이라서가 아니라, **대부분의 스레드를 `main`이 만들기 때문에** false로 보이는 것이다. 데몬 스레드 안에서 새 스레드를 만들면 그 스레드도 데몬이 되고, 조용히 잘려나간다.

> ⚠️ `setDaemon()`은 **`start()` 호출 전에만** 가능하다. 이미 시작된 스레드에 호출하면 `IllegalThreadStateException`이 발생한다.

## 5.4 ⭐ run()에서 예외는 어떻게 되는가

`run()`에서 체크 예외를 던지려고 하면 컴파일 에러가 난다. 이유는 단순하다.

```java
public interface Runnable {
    void run();   // ⭐ throws 절이 없다
}
```

부모의 `run()`에 `throws`가 없으니, 오버라이딩 규칙상 자식이 체크 예외를 새로 던질 수 없다. 그래서 `try-catch`로 감싸야 한다.

| 예외 종류 | `run()` 밖으로 던질 수 있나? | 이유 |
| --- | --- | --- |
| **체크 예외** (`InterruptedException`, `IOException` …) | ❌ 불가능 | 부모 `run()`에 `throws`가 없어서 컴파일 에러 |
| **언체크 예외** (`RuntimeException` 계열) | ✅ **가능** | 선언 없이 던질 수 있음 |

그리고 언체크 예외를 던지면 어떻게 되는지가 진짜 핵심이다.

```text
run()에서 RuntimeException 발생
        │
        ▼
해당 스레드만 종료 (다른 스레드는 멀쩡히 동작)
        │
        ▼
Thread.UncaughtExceptionHandler 가 호출됨
        │
        ▼
기본 핸들러가 stderr 에 스택 트레이스 출력
        │
        ▼
⚠️ main 스레드는 이 예외를 절대 catch 할 수 없다
```

```java
// main에서 감싸도 소용없다 — 예외는 Thread-0의 스택에서 발생하므로
try {
    thread.start();
} catch (Exception e) {
    // ❌ 여기로 절대 오지 않음
}
```

스택이 스레드마다 분리되어 있다는 1장의 내용이 여기서 그대로 이어진다. **예외는 스택을 타고 올라가는데, 스택이 다르면 올라갈 길이 없다.**

## 5.5 ⚠️ 데몬 스레드에 정리 작업을 맡기지 말 것

JVM이 종료될 때 데몬 스레드는 "정리할 기회 없이" 잘린다. 그래서 **`finally`와 `try-with-resources`가 실행되지 않을 수 있다.**

```java
// ❌ 위험한 패턴
Thread daemonThread = new Thread(() -> {
    try {
        writeToFile();
    } finally {
        flushAndClose();   // JVM 종료 시 실행 안 될 수 있음 → 데이터 유실
    }
});
daemonThread.setDaemon(true);
```

파일 쓰기, DB 커밋, 락 해제 같은 작업은 데몬 스레드에 맡기면 안 된다.

# 6. 스레드 만들기 ② Runnable

자바에서 스레드를 만드는 방법은 두 가지다.

1. `Thread` 클래스를 **상속**
2. `Runnable` 인터페이스를 **구현** ← ⭐ 실무에서는 거의 이 방식

## 6.1 코드

```java
public class HelloRunnable implements Runnable {

    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName() + ": run()");
    }
}
```

```java
public class HelloRunnableMain {

    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName() + ": main() start");

        HelloRunnable helloRunnable = new HelloRunnable();   // ① 할 일
        Thread thread = new Thread(helloRunnable);           // ② 일꾼에게 할 일을 쥐여줌
        thread.start();                                      // ③ 일 시작

        System.out.println(Thread.currentThread().getName() + ": main() end");
    }
}
```

> ⭐ **핵심: "스레드(일꾼)"와 "스레드가 실행할 작업(할 일)"의 분리**

```text
[ Thread 상속 ]                    [ Runnable 구현 ]

  ┌──────────────────┐              ┌────────┐      ┌──────────────┐
  │   HelloThread    │              │ Thread │─────▶│ HelloRunnable│
  │  ─────────────   │              │(일꾼)  │target│   (할 일)    │
  │  일꾼 + 할 일이  │              └────────┘      └──────────────┘
  │  한 덩어리       │                  ▲                  ▲
  └──────────────────┘            교체 가능          재사용 가능
```

## 6.2 비교

| 기준 | `Thread` 상속 | `Runnable` 구현 ⭐ |
| --- | --- | --- |
| 다른 클래스 상속 | ❌ 불가 (자바는 단일 상속) | ✅ 자유 |
| 역할 분리 | ❌ 일꾼 = 할 일 | ✅ 일꾼 ≠ 할 일 |
| 작업 재사용 | ❌ 어려움 | ✅ 여러 스레드가 공유 가능 |
| 스레드 풀(`ExecutorService`)과 호환 | ❌ | ✅ (나중에 필수) |
| 람다로 축약 | ❌ | ✅ 함수형 인터페이스 |
| 코드 길이 | 살짝 짧음 | 객체 생성 한 단계 추가 |

**결론: 특별한 이유가 없으면 `Runnable`을 쓰자.**

## 6.3 ⚠️ "공유할 수 있다"는 장점이자 함정

여러 스레드가 하나의 `Runnable`을 공유할 수 있다는 건 분명 장점이다. 다만 그 `Runnable`이 **인스턴스 필드(상태)를 갖는 순간 동시성 문제의 온상**이 된다.

```java
class CountRunnable implements Runnable {
    private int count = 0;      // ⚠️ 힙에 1개 → 모든 스레드가 공유

    @Override
    public void run() {
        count++;                // ⚠️ 원자적이지 않음 (읽기 → +1 → 쓰기)
    }
}
```

→ **상태 없는(stateless) `Runnable`은 공유해도 안전, 상태 있는 `Runnable`은 위험.**

> 💡 `Runnable`은 `@FunctionalInterface`라서 람다로 쓸 수 있다. 나중에 배울 `Callable<V>`는 **반환값과 체크 예외를 허용**한다는 점에서 `Runnable`의 두 가지 한계를 해결한 인터페이스다.

# 7. 로그 유틸 만들기

멀티스레드를 공부할 때는 **"이 줄을 누가 언제 실행했는지"**가 보여야 한다. 그래서 간단한 로거를 하나 만들어두고 시작하자.

```java
package util;

import java.time.LocalTime;
import java.time.format.DateTimeFormatter;

public abstract class MyLogger {

    private static final DateTimeFormatter formatter =
            DateTimeFormatter.ofPattern("HH:mm:ss.SSS");

    public static void log(Object obj) {
        String time = LocalTime.now().format(formatter);
        System.out.printf("%s [%9s] %s\n", time, Thread.currentThread().getName(), obj);
    }
}
```

| 조각 | 의미 |
| --- | --- |
| `HH:mm:ss.SSS` | 24시간제 시:분:초.**밀리초** — 스레드 전환 순간을 보려면 ms 단위가 필수 |
| `%9s` | 문자열을 **9칸 오른쪽 정렬** → `main`/`Thread-0`이 세로로 줄 맞춰져 읽기 편함 |
| `Thread.currentThread().getName()` | **이 로그를 남긴 스레드**가 누구인지 |

```java
import static util.MyLogger.log;   // ⭐ static import 가 있어야 log(...)로 쓸 수 있다

public class MyLoggerMain {
    public static void main(String[] args) {
        log("hello thread");
        log(123);
    }
}
```

```text
21:19:51.121 [     main] hello thread
21:19:51.128 [     main] 123
```

> 💡 `abstract class`로 만든 건 인스턴스화를 막기 위해서인데, 사실 `abstract`는 `new`만 막을 뿐 상속은 여전히 가능하다. 더 견고한 관용구는 이쪽이다.
> ```java
> public final class MyLogger {          // 상속 차단
>     private MyLogger() {               // 인스턴스화 차단
>         throw new AssertionError();
>     }
>     public static void log(Object obj) { ... }
> }
> ```

> ⚠️ `System.out`은 스레드 안전하지만 느리다. `PrintStream`의 메서드는 내부적으로 동기화되어 있어 한 줄이 깨지지는 않지만, 여러 스레드가 동시에 출력하면 **줄 단위 순서가 뒤섞이고**, 그 동기화 때문에 **모든 스레드가 콘솔 앞에서 줄을 선다**(성능 병목). 학습용으로는 완벽하지만 실무에서는 SLF4J + Logback을 쓴다.

# 8. 여러 스레드 만들기

```java
import static util.MyLogger.log;

public class ManyThreadMainV1 {

    public static void main(String[] args) {
        log("main() start");

        HelloRunnable helloRunnable = new HelloRunnable();   // ⭐ 인스턴스는 딱 1개

        Thread thread1 = new Thread(helloRunnable);
        thread1.start();

        Thread thread2 = new Thread(helloRunnable);
        thread2.start();

        Thread thread3 = new Thread(helloRunnable);
        thread3.start();

        log("main() end");
    }
}
```

```text
21:19:51.121 [     main] main() start
21:19:51.128 [     main] main() end
21:19:51.129 [ Thread-0] run()
21:19:51.129 [ Thread-2] run()      ← 순서 뒤바뀜! 매번 다름
21:19:51.130 [ Thread-1] run()
```

메모리 상태를 그려보면 이렇다.

```text
   메서드 영역                    힙 영역
 ┌──────────────────┐      ┌────────────────────────┐
 │ HelloRunnable    │      │ HelloRunnable @x001    │◀──┐
 │   run() 바이트코드│      └────────────────────────┘   │ 셋 다
 │   ── 딱 1벌 ──   │      ┌──────────┬──────────┬────┴──────┐
 └──────────────────┘      │Thread@a  │Thread@b  │ Thread@c  │
                           │target→x001│target→x001│target→x001│
                           └──────────┴──────────┴───────────┘

   ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌────────────┐
   │ main 스택  │  │Thread-0스택│  │Thread-1스택│  │Thread-2스택│
   │main()프레임│  │run()프레임 │  │run()프레임 │  │run()프레임 │
   └────────────┘  └────────────┘  └────────────┘  └────────────┘
                     this=x001       this=x001       this=x001
```

**세 스레드가 같은 `HelloRunnable` 인스턴스의 `run()`을 실행한다.**

그런데 이 문장이 정확히 무슨 뜻일까? `run()`이라는 메서드 코드는 힙이 아니라 메서드 영역에 있는데, "인스턴스의 `run()`을 실행한다"는 표현은 어딘가 앞뒤가 안 맞는 것 같다. 11장에서 이 부분을 제대로 파헤친다.

# 9. Runnable을 만드는 4가지 방법

## V1. 정적 중첩 클래스

```java
public class InnerRunnableMainV1 {
    public static void main(String[] args) {
        log("main() start");

        MyRunnable myRunnable = new MyRunnable();
        Thread thread = new Thread(myRunnable);
        thread.start();

        log("main() end");
    }

    static class MyRunnable implements Runnable {
        @Override
        public void run() {
            log("run() start");
        }
    }
}
```

## V2. 익명 클래스 — 변수에 담기

```java
Runnable runnable = new Runnable() {
    @Override
    public void run() {
        log("run() start");
    }
};
Thread thread = new Thread(runnable);
thread.start();
```

## V3. 익명 클래스 — 변수 없이 바로 전달

```java
Thread thread = new Thread(new Runnable() {
    @Override
    public void run() {
        log("run() start");
    }
});
thread.start();
```

## V4. 람다 ⭐

```java
Thread thread = new Thread(() -> log("run()"));
thread.start();
```

## 비교

| 방식 | 재사용 | 코드 길이 | 컴파일 결과 | 언제 쓰나 |
| --- | --- | --- | --- | --- |
| V1 정적 중첩 클래스 | ✅ | 김 | `Outer$MyRunnable.class` | 이름이 의미를 갖고, 여러 곳에서 쓸 때 |
| V2 익명 클래스(변수) | △ | 중간 | `Outer$1.class` | 한 번만 쓰지만 변수로 참조가 필요할 때 |
| V3 익명 클래스(인라인) | ❌ | 중간 | `Outer$1.class` | 그 자리에서 한 번만 쓸 때 |
| V4 **람다** | ❌ | **짧음** | **클래스 파일 없음** (런타임 생성) | **로직이 짧을 때 — 기본 선택** |

## ⚠️ 람다는 익명 클래스의 축약형이 아니다

겉보기만 비슷하고 구현 방식이 완전히 다르다.

| | 익명 클래스 | 람다 |
| --- | --- | --- |
| 클래스 파일 | 컴파일 시 `Outer$1.class` **생성됨** | **생성되지 않음** (`invokedynamic`으로 런타임 생성) |
| 인스턴스 | `new` 할 때마다 **매번 새로** | 캡처 없는 람다는 **재사용될 수 있음** |
| `this` | **익명 클래스 자신** | **바깥 클래스** |
| 적용 대상 | 아무 인터페이스/클래스 | **함수형 인터페이스만** |

```java
// this 차이 — 실수하기 쉬운 지점
new Runnable() {
    @Override public void run() {
        System.out.println(this);   // 익명 클래스 인스턴스 (Outer$1@...)
    }
};

Runnable r = () -> System.out.println(this);   // 바깥 인스턴스 (static 컨텍스트면 컴파일 에러)
```

# 10. Thread 주요 메서드

| 메서드 | 설명 | 주의점 |
| --- | --- | --- |
| `start()` | 새 스레드에서 `run()` 실행 | **단 한 번만** 호출 가능 |
| `run()` | 작업 내용. **직접 호출 금지** | 직접 호출하면 그냥 메서드 호출 |
| `Thread.sleep(ms)` | 현재 스레드를 지정 시간 대기 | **static** / `InterruptedException` / **락을 놓지 않음** |
| `join()` | 그 스레드가 끝날 때까지 대기 | 호출한 스레드가 `WAITING` 상태로 |
| `interrupt()` | 인터럽트 신호 전송 | **강제 종료가 아니라 "요청"** — 무시될 수도 있음 |
| `setName(String)` | 이름 지정 | 실무 필수 |
| `setDaemon(boolean)` | 데몬 여부 | **`start()` 이전에만** |
| `setPriority(1~10)` | 우선순위 | OS에 대한 **힌트일 뿐**, 보장 없음 |
| `isAlive()` | 살아있는지 | `NEW`와 `TERMINATED`면 false |
| `getState()` | 현재 상태 | 디버깅/모니터링용 |
| `Thread.currentThread()` | 실행 중인 스레드 조회 | **static** |

> ⚠️ `Thread.stop()`, `suspend()`, `resume()`은 **deprecated**다. 락을 쥔 채 스레드를 죽여 데이터가 깨지기 때문이다. 스레드 종료는 `interrupt()`로 **협력적으로** 처리한다.

> 💡 **Java 21의 가상 스레드(Virtual Thread)**
> 지금 다룬 건 OS 스레드와 1:1로 매핑되는 **플랫폼 스레드**다. Java 21부터는 JVM이 관리하는 가벼운 가상 스레드가 정식 도입되어 수십만 개도 만들 수 있다. 다만 **플랫폼 스레드를 제대로 이해해야 가상 스레드도 이해된다.**
> ```java
> Thread.ofPlatform().name("worker").start(runnable);   // 기존 방식
> Thread.ofVirtual().name("v-worker").start(runnable);  // Java 21+
> ```

# 11. (심화) run() 코드는 대체 어디에 있을까

8장에서 남겨둔 질문이다.

> "모든 스레드는 같은 `HelloRunnable` 인스턴스의 `run()`을 실행한다."
>
> 인스턴스가 하나인 건 알겠는데, **`run()` 메서드 자체는 메서드 영역에 있는 거 아닌가?**

## 11.1 그 의심이 정확하다

맞다. **`run()`의 바이트코드는 `HelloRunnable` 클래스당 메서드 영역에 딱 1벌만 존재한다.** 인스턴스를 1개 만들든 100만 개 만들든 **코드는 복사되지 않는다.**

그럼 힙의 인스턴스는 뭘 갖고 있을까?

```text
힙의 HelloRunnable 인스턴스 @x001 안에 든 것
┌────────────────────────────────────────┐
│ ① 인스턴스 필드 (= 상태/데이터)        │  ← 인스턴스마다 다름
│ ② 자기 클래스 정보를 가리키는 포인터   │  ← 메서드 영역을 가리킴
│ ③ 객체 헤더 (해시코드, 락 정보, GC 정보)│
└────────────────────────────────────────┘

❌ run() 메서드의 코드는 여기 없다
```

> ⭐ **객체 = "데이터" + "내 클래스가 뭔지 알려주는 명찰"**
> 메서드 코드는 명찰을 따라간 메서드 영역에 있다.

## 11.2 그럼 "실행한다"는 건 누가 뭘 하는 걸까

핵심은 이거다.

> ⭐ **메서드를 "실행하는" 주체는 객체가 아니라 스레드다.**
> 객체는 아무것도 실행하지 않는다. 객체는 그냥 힙에 누워 있는 데이터 덩어리다.

스레드가 `runnable.run()`을 실행할 때 벌어지는 일을 단계별로 보면 이렇다.

```text
① 스레드가 "run()을 호출하자"고 결정
        │
        ▼
② 그 스레드의 스택에 run() 스택 프레임을 새로 push
   (프레임 = 지역 변수 배열 + 피연산자 스택 + 반환 주소)
        │
        ▼
③ 프레임의 지역 변수 0번 슬롯에 this 를 넣는다
   ⭐ this = 힙에 있는 인스턴스(@x001)의 참조값
        │
        ▼
④ 스레드가 메서드 영역에 있는 run() 바이트코드를 한 줄씩 읽어 실행
   (PC 레지스터가 "지금 몇 번째 줄" 인지 기억)
        │
        ▼
⑤ 필드에 접근할 일이 있으면 this 를 타고 힙의 @x001 로 찾아감
        │
        ▼
⑥ run() 끝나면 프레임 pop → 지역 변수 전부 사라짐
```

그래서 **"인스턴스의 `run()`을 실행한다"의 정확한 의미**는 이렇게 풀어쓸 수 있다.

> **"메서드 영역에 있는 그 코드를, `this`가 이 인스턴스를 가리키는 상태로 실행한다"**

## 11.3 세 영역의 역할 분담

| 영역 | 담당 | 몇 개? | 한 줄 요약 |
| --- | --- | --- | --- |
| **메서드 영역** | **코드** (어떻게 할지) | **클래스당 1벌** | 레시피 |
| **힙** | **상태** (무엇을 가지고) | **인스턴스당 1개** | 재료가 든 냉장고 |
| **스택** | **실행 문맥** (누가, 어디까지 했는지) | **스레드당 1개** | 요리사 개인 도마 |

> 🍳 요리사 3명(스레드)이 **같은 레시피 책**(메서드 영역의 코드)을 보고, **각자 자기 도마**(스택)에서 작업하는데, **냉장고는 하나를 같이** 쓴다(힙 인스턴스).
> → 도마 위 재료는 안 섞이지만(지역 변수 안전), **냉장고는 서로 헤집는다(필드 공유 = 동시성 문제).**

## 11.4 ⭐ 8장에서 실제로 벌어진 일

```java
HelloRunnable helloRunnable = new HelloRunnable();   // 힙에 딱 1개
new Thread(helloRunnable).start();   // Thread-0
new Thread(helloRunnable).start();   // Thread-1
new Thread(helloRunnable).start();   // Thread-2
```

```text
            메서드 영역                            힙 영역
    ┌───────────────────────────┐        ┌──────────────────────┐
    │ HelloRunnable 클래스      │        │ HelloRunnable @x001  │
    │   run() 바이트코드        │◀───────│   (필드 = 상태)      │
    │   ──── 딱 1벌 ────        │ 클래스 └──────────▲───────────┘
    └─────────▲─────────────────┘ 포인터            │
              │                                     │
      "같은 코드를 읽는다"                  "this 가 전부 같은 객체"
              │                                     │
    ┌─────────┴─────────────────────────────────────┴───────────┐
    │  Thread-0 스택      Thread-1 스택        Thread-2 스택     │
    │  ┌──────────────┐  ┌──────────────┐    ┌──────────────┐    │
    │  │ run() 프레임 │  │ run() 프레임 │    │ run() 프레임 │    │
    │  │ this = x001  │  │ this = x001  │    │ this = x001  │    │
    │  │ 지역변수(독립)│  │ 지역변수(독립)│    │ 지역변수(독립)│    │
    │  └──────────────┘  └──────────────┘    └──────────────┘    │
    └────────────────────────────────────────────────────────────┘
        ⭐ 프레임은 3개 (독립)   ⭐ 코드는 1벌   ⭐ this 는 같은 객체
```

| 무엇이 | 몇 개인가 | 결과 |
| --- | --- | --- |
| `run()` **바이트코드** | **1벌** (메서드 영역) | 어차피 읽기 전용이라 몇 개가 읽어도 무해 |
| `run()` **스택 프레임** | **3개** (스레드마다) | 지역 변수가 섞이지 않음 → 안전 |
| `run()`이 가리키는 **인스턴스** | **1개** (힙) | ⚠️ **필드를 건드리면 여기서 충돌** |

## 11.5 눈으로 확인하기

```java
public class SharedInstanceTest {

    static class CountRunnable implements Runnable {
        private int count = 0;                  // 힙 — 공유됨

        @Override
        public void run() {
            int localVar = 0;                   // 스택 — 스레드마다 독립

            for (int i = 0; i < 10_000; i++) {
                localVar++;
                count++;                        // ⚠️ 경쟁 상태
            }

            log("localVar=" + localVar + ", count=" + count + ", this=" + this);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        CountRunnable shared = new CountRunnable();   // 인스턴스 1개

        Thread t1 = new Thread(shared, "t1");
        Thread t2 = new Thread(shared, "t2");
        Thread t3 = new Thread(shared, "t3");
        t1.start(); t2.start(); t3.start();
        t1.join(); t2.join(); t3.join();

        log("최종 count = " + shared.count + " (기대값 30000)");
    }
}
```

```text
[ t1] localVar=10000, count=17234, this=CountRunnable@2f92e0f4
[ t3] localVar=10000, count=24901, this=CountRunnable@2f92e0f4
[ t2] localVar=10000, count=28553, this=CountRunnable@2f92e0f4
[main] 최종 count = 28553 (기대값 30000)     ← ⚠️ 값이 샌다
```

여기서 읽어낼 것이 세 가지다.

1. **`localVar`는 셋 다 정확히 `10000`** → 스택은 스레드마다 독립이라 절대 안 섞인다
2. **`count`는 30000에 미달** → 힙의 필드를 공유하니 증가분이 유실된다 (`count++`는 읽기 → 증가 → 쓰기 3단계라 원자적이지 않다)
3. **`this` 해시가 셋 다 동일** → "같은 인스턴스의 `run()`을 실행한다"는 말의 물증

3번이 바로 그 문장의 의미이고, 2번이 앞으로 배울 `synchronized`, `volatile`, `AtomicInteger`가 존재하는 이유다.

## 11.6 인스턴스를 3개 만들면?

```java
new Thread(new CountRunnable()).start();
new Thread(new CountRunnable()).start();
new Thread(new CountRunnable()).start();
```

| | 코드(메서드 영역) | 인스턴스(힙) | 프레임(스택) | 필드 공유 |
| --- | --- | --- | --- | --- |
| 인스턴스 1개 공유 | **1벌** | **1개** | 3개 | ⚠️ **됨** |
| 인스턴스 3개 | **1벌** (변함없음) | **3개** | 3개 | ✅ 안 됨 |

**인스턴스를 몇 개 만들든 `run()` 코드는 언제나 1벌이다.** 달라지는 건 오직 **`this`가 가리키는 대상**뿐이다.

## 11.7 용어 하나만 짚고 가기

"코드 영역"이라고 부르기 쉬운데, 자바 문맥에서는 다음이 정확하다.

| 용어 | 어디서 쓰는 말 |
| --- | --- |
| **메서드 영역 (Method Area)** | ✅ JVM 명세의 공식 용어 |
| **코드 영역 / text 영역** | C/C++ 등 **네이티브 프로세스** 메모리 레이아웃 용어 |
| **Metaspace** | HotSpot JVM의 실제 구현 이름 (Java 8+) |

## 11.8 보너스 — static 메서드는 왜 인스턴스가 필요 없을까

이제 답이 자연스럽게 나온다.

```java
MyLogger.log("hello");   // 인스턴스 없이 호출
```

| | 인스턴스 메서드 `run()` | static 메서드 `log()` |
| --- | --- | --- |
| 코드 위치 | 메서드 영역 | 메서드 영역 (**똑같음**) |
| `this` 슬롯 | ✅ 프레임 0번에 `this` | ❌ **없음** |
| 힙 인스턴스 | 필요 | **불필요** |
| 접근 가능한 데이터 | 인스턴스 필드 + static | **static만** |

**코드가 메서드 영역에 있다는 건 둘 다 똑같다.** 차이는 오직 **"스택 프레임에 `this`를 넣느냐 마느냐"** 하나뿐이다. 그래서 `MyLogger.log()`는 인스턴스 없이도 잘 돌아가고, `run()`은 "누구의 `run()`인지"가 반드시 필요하다.

# 12. (심화) 익명 클래스 객체는 언제 GC 될까

9장의 V2, V3처럼 익명 클래스로 `Runnable`을 만들면, 이 객체도 힙에 생길 것이다. 그런데 변수에 담지도 않은 객체가 어떻게 계속 살아있는 걸까? 바로 사라져야 하는 것 아닐까?

| 질문 | 답 |
| --- | --- |
| 익명 클래스 객체도 힙에 생기나? | ✅ **그렇다.** 일반 객체와 100% 동일하다. |
| 즉시 GC 되나? | ❌ **아니다.** 스레드가 살아있는 동안은 **절대** 수거되지 않는다. |
| 스레드가 끝나면? | 다른 참조가 없으면 그때 **GC 대상이 된다.** (= "즉시 삭제"는 아님) |

## 12.1 익명 클래스는 "이름 없는 일반 클래스"다

컴파일해보면 바로 보인다.

```bash
$ javac InnerRunnableMainV2.java
$ ls
InnerRunnableMainV2.class     # 바깥 클래스
InnerRunnableMainV2$1.class   # ⭐ 익명 클래스도 자기 클래스 파일을 갖는다
```

즉 `new Runnable() { ... }`은 특별한 문법이 아니라 그냥 이런 뜻이다.

```java
// 우리가 쓴 코드
Runnable runnable = new Runnable() {
    @Override public void run() { log("run() start"); }
};

// 컴파일러가 만드는 것과 사실상 동일
class InnerRunnableMainV2$1 implements Runnable {
    @Override public void run() { log("run() start"); }
}
Runnable runnable = new InnerRunnableMainV2$1();   // ← 평범한 new
```

메모리 배치도 평범하다.

| 요소 | 위치 |
| --- | --- |
| `InnerRunnableMainV2$1` 클래스 정보 + `run()` 바이트코드 | **메서드 영역** |
| `new`로 만든 인스턴스 | **힙** |
| `runnable` 참조 변수 | **main 스택의 프레임** |

## 12.2 ⭐ GC의 기준은 "도달 가능성"이다

GC의 판단 기준은 단 하나다. **"GC Root에서 시작해 참조를 타고 도달할 수 있는가?"**

GC Root에는 여러 가지가 있는데, 지금 중요한 건 이거다.

> ⭐ **살아있는 모든 스레드의 스택에 있는 지역 변수는 GC Root다.**

이걸 그림으로 보면 답이 나온다.

```text
        [ GC Root ]                          [ 힙 ]
   main 스택                        ┌─────────────────────┐
   ┌──────────────┐                 │ 익명 Runnable @x001 │
   │ runnable ────┼────────────────▶│                     │
   │ thread ──────┼──────┐          └─────────▲───────────┘
   └──────────────┘      │                    │
                         ▼                    │ target 필드
   Thread-0 스택   ┌──────────────┐            │
   ┌────────────┐  │ Thread @a01  │────────────┘
   │ this ──────┼─▶│  target      │
   └────────────┘  └──────────────┘
    (실행 중인 스레드 자체도 GC Root)
```

익명 `Runnable` 객체를 붙잡고 있는 손이 최소 3개다.

| 참조 경로 | 설명 |
| --- | --- |
| ① `main` 스택의 `runnable` 지역 변수 | `main()`이 끝날 때까지 유지 |
| ② `Thread` 객체의 `target` 필드 | `Thread` 생성자가 `this.target = target;`로 저장 |
| ③ 실행 중인 `Thread-0` 스레드 | **살아있는 스레드 객체 자체가 GC Root** |

세 개 중 **③번이 결정적**이다. `main()`이 먼저 끝나서 ①이 사라져도, 스레드가 돌고 있는 한 그 스레드는 GC Root이고 → `Thread` 객체가 살아있고 → `target`이 `Runnable`을 가리키므로 **수거될 수가 없다.**

> 💡 사실 당연한 이야기다. **지금 실행되고 있는 코드의 객체를 GC가 치워버린다면 그건 재앙이다.**

## 12.3 변수에 안 담아도 마찬가지다

```java
new Thread(new Runnable() {          // 지역 변수 없음
    @Override public void run() { log("run() start"); }
}).start();                          // Thread 참조조차 변수에 안 담음
```

- 익명 `Runnable` → `Thread`의 `target` 필드가 붙잡고 있음
- `Thread` 객체 → **실행 중인 스레드는 그 자체로 GC Root**

그래서 **변수에 하나도 안 담아도 둘 다 멀쩡히 살아서 실행된다.** 이게 `new Thread(...).start()` 한 줄이 동작하는 이유다.

## 12.4 언제 GC 대상이 되는가

```text
main() 종료 → ① runnable 지역 변수 사라짐
                    │
                    ▼
run() 종료 → Thread-0 스레드 TERMINATED → ③ GC Root에서 제외
                    │
                    ▼
        Thread 객체를 가리키는 참조도 없음
                    │
                    ▼
        익명 Runnable 객체 = 도달 불가능 (unreachable)
                    │
                    ▼
        ✅ GC "대상"이 됨  ≠  ❌ 즉시 메모리에서 삭제됨
                    │
                    ▼
        나중에 GC가 실제로 돌 때 수거됨 (언제일지는 아무도 모름)
```

> ⭐ **"GC 대상이 된다"와 "즉시 삭제된다"는 전혀 다르다.**
> 도달 불가능해지는 건 순간이지만, 실제 수거는 GC 알고리즘·힙 여유·타이밍에 달려 있다. `System.gc()`조차 **"수거해 주세요"라는 요청**일 뿐 강제가 아니다.

## 12.5 ⚠️ 익명 클래스가 진짜 메모리 누수를 만드는 경우

`main`은 `static`이라 문제가 없지만, **인스턴스 메서드 안의 익명 클래스는 바깥 인스턴스를 몰래 붙잡는다.**

```java
class BigService {
    private byte[] hugeCache = new byte[100_000_000];   // 100MB

    void start() {
        new Thread(new Runnable() {        // ⚠️ 암묵적으로 BigService.this 를 참조
            @Override public void run() {
                while (true) { /* 오래 도는 작업 */ }
            }
        }).start();
    }
}
```

익명 클래스(비정적 문맥)는 컴파일 시 `BigService.this` 참조를 숨겨진 필드로 갖는다. 그래서 **스레드가 살아있는 한 `BigService`와 100MB 캐시가 통째로 수거되지 않는다.** 정적 중첩 클래스나 캡처 없는 람다를 쓰면 이 문제가 사라진다.

## 12.6 람다는 조금 다르다

```java
Thread thread = new Thread(() -> log("run()"));
```

| | 익명 클래스 | 람다 |
| --- | --- | --- |
| 클래스 파일 | 컴파일 시 **미리 생성** (`Outer$1.class`) | **생성 안 됨.** `invokedynamic`으로 런타임 생성 |
| 인스턴스 개수 | `new` 할 때마다 **항상 새 객체** | **캡처가 없으면 하나를 재사용**할 수 있음 |
| 힙에 존재 | ✅ | ✅ (역시 힙 객체) |

```java
Runnable r1 = () -> System.out.println("hi");
Runnable r2 = () -> System.out.println("hi");
System.out.println(r1 == r2);
// 익명 클래스였다면 확실히 false
// 캡처 없는 람다라면 true 가 나올 수 있다 (HotSpot이 인스턴스를 캐싱)
```

> ⚠️ 이건 **JVM 구현의 최적화이지 명세가 보장하는 동작이 아니다.** JLS는 "캡처하지 않는 람다는 같은 인스턴스로 평가될 **수도** 있다"고만 규정한다. 따라서 **람다 인스턴스의 동일성(`==`)에 의존하는 코드는 절대 쓰면 안 된다.**

# 마무리 정리

## 헷갈리기 쉬운 포인트 10가지

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | 자바 실행 시 실행 스택은 하나다 | **스레드마다 1개씩** 생성된다 |
| 2 | `new Thread()` 하면 스레드가 만들어진다 | 스택과 OS 스레드는 **`start()` 시점**에 생성된다 |
| 3 | `run()`을 호출하면 스레드가 실행된다 | 그냥 **호출한 스레드가** 메서드를 실행할 뿐이다 |
| 4 | 데몬 여부 기본값은 `false`다 | **부모 스레드의 데몬 여부를 상속**한다 |
| 5 | `setDaemon()`은 아무때나 호출할 수 있다 | **`start()` 이전에만** 가능하다 |
| 6 | `run()`은 예외를 밖으로 던질 수 없다 | **체크 예외만** 불가. 언체크 예외는 던져지고, **그 스레드만** 죽는다 |
| 7 | `run()`의 예외를 `main`에서 잡을 수 있다 | 스택이 다르므로 **절대 잡을 수 없다** |
| 8 | 데몬 스레드도 `finally`는 실행된다 | JVM 종료 시 **정리 기회 없이 잘린다** |
| 9 | `run()` 코드는 힙의 인스턴스 안에 있다 | **메서드 영역에 클래스당 1벌**만 있다 |
| 10 | 람다는 익명 클래스의 축약형이다 | 클래스 파일, 인스턴스 재사용, `this` 모두 **다르다** |

## 한 장으로 요약

```text
        코드          +        상태         +      실행 문맥
    (메서드 영역)            (힙)                  (스택)
     클래스당 1벌        인스턴스당 1개         스레드당 1개
         │                    │                     │
         └──────── 스레드가 이 셋을 엮어서 실행한다 ────┘

  → 지역 변수는 스레드마다 따로라서 안전하다
  → 인스턴스 필드는 공유되므로 동시성 문제가 생긴다
  → 그래서 synchronized, volatile, Atomic 이 필요해진다
```

다음 글에서는 `join()`, `interrupt()`를 포함한 스레드 제어와, 동시성 문제가 실제로 어떻게 터지는지 다룬다.
