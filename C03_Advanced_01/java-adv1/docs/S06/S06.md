# 메모리 가시성

## volatile, 메모리 가시성 - 1

### 주의
- volatile은 예약된 키워드 => 패키지 명으로 사용할 수 없음 => volatile1

### volatile를 사용하지 않았을 때
```java
public class VolatileFlagMain {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread t = new Thread(task, "work");
        log("runFlag = " + task.runFlag);
        t.start();

        sleep(1000);
        log("runFlag를 false로 변경 시도");
        task.runFlag = false;
        log("runFlag = " + task.runFlag);
        log("main 종료");
    }

    static class MyTask implements Runnable {

        boolean runFlag = true;
        // volatile boolean runFlag = true;

        @Override
        public void run() {
            log("task 시작");

            while (runFlag) {
                // runFlag가 false로 변하면 탈출
            }

            log("task 종료");
        }
    }
}
```
- 실행 결과
    ```text
    15:46:01.105 [     main] runFlag = true
    15:46:01.114 [     work] task 시작
    15:46:02.114 [     main] runFlag를 false로 변경 시도
    15:46:02.114 [     main] runFlag = false
    15:46:02.115 [     main] main 종료
    ```
    - runFlag가 false로 변경이 되었지만 프로그램이 종료되지 않음을 관측할 수 있음
    - 주의: while문 안에 뭔가를 작업하면 안됨 => 이후 설명
    - 기대한 동작: runFlag를 변경하고 프로그램이 종료
    - 실제한 동작: runFlag를 변경하고 프로그램이 종료되지 않음 (work thread keep working)

### 주의사항
- 실제 실행결과는 실행 환경에 따라 달라질 수 있음
- 특정 시간이 지나고 task가 종료될 수도 있고, 기대하는데로 동작할 수도 있음
- 가급적 예제 코드랑 동일하게 작성해야 결과가 같을 가능성이 높음

## volatile, 메모리 가시성 - 2

### 메모리 가시성 문제
- memory visibility
- 메인 메모리는 CPU 입장에서 보면 거리도 멀고, 속도도 상대적으로 느림
- CPU 연산은 매우 빠르기 때문에 CPU 연산의 빠른 성능을 따라가려면 CPU 가까이에 매우 빠른 메모리가 필요한데 
  - **캐시 메모리**
- 현대의 CPU 대부분은 코어 단위로 캐시 메모리를 가지고 있음
  - 코어가 공유하는 캐시 메모리도 있음

### 그러면 왜 메모리 가시성 문제가 발생하는 것일까?
- main, work 스레드는 모두 runFlag의 값을 읽음
- CPU는 이 값을 효율적으로 처리하기 위해 먼저 캐시 메모리에 불러옴
- main, work 스레드가 사용하는 runFlag가 각각의 캐시 메모리에 보관됨
- 프로그램의 시작 시점에는 runFlag를 변경하지 않기 때문에 모든 스레드에서 true로 읽음
- work 스레드는 이제 메인 메모리에 있는 runFlag를 읽는 것이 아니라 캐시 메모리에 있는 runFlag를 읽음

### 이때 문제가 발생함
- main 스레드는 runFlag를 false로 설정
- 이때 캐시 메모리의 runFlag가 false로 설정됨
  - 핵심: work 스레드가 돌아가는 코어의 캐시 메모리는 true를 계속 가지고 있음

### 그렇다면 캐시 메모리의 값이 언제 메인 메모리에 반영이 될까?
- 정답: 알 수 없음
- 메인 메모리에 반영을 한다고 해도 문제가 끝나지 않음
- 메인 메모리에 반영을 한 값을 다시 캐시 메모리로 가져와야함
- **주로 컨텍스트 스위칭이 될 때, 캐시 메모리도 함께 갱신됨**

### 메모리 가시성
- 멀티스레드 환경에서 한 스레드가 변경한 값이 다른 스레드에서 언제 보이는지에 대한 문제를 메모리 가시성 문제라고 함
- 이름 그대로 메모리에 변경한 값이 보이는가, 보이지 않는가의 문제

## volatile, 메모리 가시성 - 3

### 성능과의 트레이드 오프
- 캐시 메모리를 사용하면 CPU의 처리 성능을 개선할 수 있음
- 때로는 성능보다 정합성이 더 중요할 때가 있음
- 이때 volatile이라는 키워드를 사용하면 됨
  - 값을 읽을 때, 모두 메인 메모리에 직접 접근

### 예제 코드
```java
public class VolatileFlagMain {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread t = new Thread(task, "work");
        log("runFlag = " + task.runFlag);
        t.start();

        sleep(1000);
        log("runFlag를 false로 변경 시도");
        task.runFlag = false;
        log("runFlag = " + task.runFlag);
        log("main 종료");
    }

    static class MyTask implements Runnable {

//        boolean runFlag = true;
        volatile boolean runFlag = true;

        @Override
        public void run() {
            log("task 시작");

            while (runFlag) {
                // runFlag가 false로 변하면 탈출
            }

            log("task 종료");
        }
    }
}
```
- 실행 결과
    ```text
    16:34:23.842 [     main] runFlag = true
    16:34:23.847 [     work] task 시작
    16:34:24.851 [     main] runFlag를 false로 변경 시도
    16:34:24.852 [     work] task 종료
    16:34:24.854 [     main] runFlag = false
    16:34:24.859 [     main] main 종료
    
    Process finished with exit code 0
    ```
    - 항상 runFlag를 읽을 때, 메이 메모리에 값을 읽거나 추가함\

## volatile, 메모리 가시성 - 4

### volatile 미적용
```java
public class VolatileCountMain {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread t = new Thread(task);
        t.start();

        sleep(1000);

        task.flag = false;
        log("flag = " + task.flag + ", count = " + task.count + " in main()");
    }
    static class MyTask implements Runnable {

        boolean flag = true;
        long count;

//        volatile boolean flag = true;
//        volatile long count;

        @Override
        public void run() {
            while (flag) {
                count++;
                // 1억번에 한 번씩 출력
                if (count % 100_000_000 == 0) {
                    log("flag = " + flag + ", count = " + count + " in while()");
                }
            }
            log("flag = " + flag + ", count = " + count + " 종료");
        }
    }
}
```
- 실행 결과
    ```text
    16:40:37.540 [ Thread-0] flag = true, count = 100000000 in while()
    16:40:37.775 [ Thread-0] flag = true, count = 200000000 in while()
    16:40:37.987 [ Thread-0] flag = true, count = 300000000 in while()
    16:40:38.204 [ Thread-0] flag = true, count = 400000000 in while()
    16:40:38.307 [     main] flag = false, count = 456279216 in main()
    16:40:38.381 [ Thread-0] flag = true, count = 500000000 in while()
    16:40:38.381 [ Thread-0] flag = false, count = 500000000 종료
    ```
    - main에서 false로 변경한 시점이랑 thread에서 이를 확인하는 시점이 다른 것을 확인할 수 있음

### volatile 키워드 적용
```java
public class VolatileCountMain {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread t = new Thread(task);
        t.start();

        sleep(1000);

        task.flag = false;
        log("flag = " + task.flag + ", count = " + task.count + " in main()");
    }
    static class MyTask implements Runnable {

//        boolean flag = true;
//        long count;

        volatile boolean flag = true;
        volatile long count;

        @Override
        public void run() {
            while (flag) {
                count++;
                // 1억번에 한 번씩 출력
                if (count % 100_000_000 == 0) {
                    log("flag = " + flag + ", count = " + count + " in while()");
                }
            }
            log("flag = " + flag + ", count = " + count + " 종료");
        }
    }
}
```
- 실행 결과
    ```text
    16:45:07.755 [ Thread-0] flag = true, count = 100000000 in while()
    16:45:07.997 [     main] flag = false, count = 131314006 in main()
    16:45:07.997 [ Thread-0] flag = false, count = 131314006 종료
    ```
    
### 실행 결과로 보는 성능 차이
- volatile을 적용하지 않았을 때는 4억까지 숫자가 증가하는 것을 확인할 수 있음
- volatile을 적용했을 때는 1억까지 숫자가 증가하는 것을 확인할 수 있음
- 이유: flag 및 count 값을 main 메모리에서 직접 읽고 쓰기 때문에 속도가 느려지는 것

## 자바 메모리 모델 - Java Memory Model

### Java Memory Model
- JMM은 자바 프로그램이 어떻게 메모리에 접근하고 수정할 수 있는지를 규정
- 특히 멀티스레드 프로그래밍 스레드 간의 상호작용을 정의함
- 핵심은 여러 스레드들의 작업 순서를 보장하는 happens-before 관계에 대한 정의

### happens-before 관계
- 자바 메모리 모델에서 스레드 간의 작업 순서를 정의하는 개념
- 만약 A 작업이 B작업보다 happens-before 관계에 있다면 A 작업에서의 모든 메모리 변경 사항은 B 작업에서 볼 수 있음
- A 작업에서 변경된 내용은 B 작업이 시작되기 전에 모두 메모리에 반영됨

- 원리
  - 한 동작이 다른 동작보다 먼저 발생함을 보장함
  - 스레드 간의 메모리 가시성을 보장하는 규칙
  - 관계가 성립하면 한 스레드의 작업을 다른 스레드에서 볼 수 있게 됨
  - 즉, 한 스레드에서 수행한 작ㅇ버을 다른 스레드가 참조할 때 최신 상태가 보장되는 것임

### happens-before 관계가 발생하는 경우
- 프로그램 순서 규칙
  - 단일 스레드 내에서 프로그램의 순서대로 작성된 모든 명령문은 happens-before 순서로 실행됨
  - int a = 1; int b = 2; => a = 1이 b = 2보다 먼저 실행됨

- volatile 변수 규칙
    - 한 스레드에서 volatile 변수에 대한 쓰기 작업은 해당 변수를 읽는 모든 스레드에 보이도록 함
    - volatile 변수에 대한 쓰기 작업은 그 변수를 읽는 작업보다 happens-before 관계를 형성함

- 스레드 시작 규칙
  - Thread.start()를 호출하면 해당 스레드 내의 모든 작업은 호출 이후에 실행된 작업보다 happens-before 관계가 성립됨

- 스레드 종료 규칙
  - 한 스레드에서 Thread.join()을 호출하면 join 대상 스레드의 모든 작업은 join()이 반환된 후의 작업보다 happens-before 관계가 성립함

- 인터럽트 규칙
  - 한 스레드에서 Thread.interrupt()를 호출하는 작업이 인터럽트된 스레드가 인터럽트를 감지하는 시점의 작업보다 happens-before 관계가 성립함

- 그 외 더 있음

### 정리
- volatile 또는 동기화 기법(synchronized, ReentrantLock)을 사용하면 메모리 가시성 문제가 발생하지 않음
