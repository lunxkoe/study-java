## 1. volatile 없이 실행하면 벌어지는 일

### 1.1 코드

```java
public class VolatileFlagMain {

    public static void main(String[] args) {
        MyTask task = new MyTask();
        Thread t = new Thread(task, "work");
        log("runFlag = " + task.runFlag);
        t.start();

        sleep(1000);
        log("runFlag를 false로 변경 시도");
        task.runFlag = false;
        log("runFlag = " + task.runFlag);
        log("main 종료");
    }

    static class MyTask implements Runnable {

        boolean runFlag = true;          // volatile 없음
        // volatile boolean runFlag = true;

        @Override
        public void run() {
            log("task 시작");
            while (runFlag) {
                // 의도적으로 비워둠 (아래 1.3 참고)
            }
            log("task 종료");
        }
    }
}
```

```text
15:46:01.105 [     main] runFlag = true
15:46:01.114 [     work] task 시작
15:46:02.114 [     main] runFlag를 false로 변경 시도
15:46:02.114 [     main] runFlag = false      ← main 은 false 로 보인다
15:46:02.115 [     main] main 종료
                                              ← ⚠️ "task 종료" 가 안 찍힘
                                              ⚠️ 프로그램이 끝나지 않음
```

`main`은 분명 `false`로 바꿨고 자기 눈으로도 `false`를 확인했는데, `work` 스레드는 영원히 `true`를 본다.

### 1.2 왜 프로그램이 안 끝나나

`work`는 **사용자 스레드**라 JVM을 붙잡고 있다. `main`이 끝나도 JVM은 종료되지 않는다. (`setDaemon(true)`였다면 조용히 끝났을 것이다.)

### 1.3 🟡 "while 안에 뭘 넣으면 안 된다"는 경고가 사실 가장 중요한 단서다

원문에 짧게 적힌 이 주의사항이 **문제의 진짜 원인을 가리키는 결정적 힌트**다.

```java
while (runFlag) {
    System.out.println("작업 중");   // 이걸 넣으면 → 정상 종료됨
}

while (runFlag) {
    Thread.sleep(1);                 // 이것도 → 정상 종료됨
}
```

**캐시 때문이라면 왜 `println` 하나 넣었다고 갑자기 캐시가 갱신될까?** 여기에 답이 있다. 2장에서 풀어본다.

🔴 **오타 정정**
- "기대하는데로 동작" → **기대한 대로**
- "실제한 동작" → **실제 동작**
- "메이 메모리" → **메인 메모리**
- "작ㅇ버을" → **작업을**

## 2. ⭐ 진짜 원인은 캐시가 아니다

### 2.1 원문의 설명 (캐시 모델)

```text
      코어 1                        코어 2
  ┌─────────────┐              ┌─────────────┐
  │ main 스레드 │              │ work 스레드 │
  └──────┬──────┘              └──────┬──────┘
         │                            │
  ┌──────▼──────┐              ┌──────▼──────┐
  │  L1 캐시    │              │  L1 캐시    │
  │ runFlag=false│             │ runFlag=true│ ← 계속 옛날 값
  └──────┬──────┘              └──────┬──────┘
         └────────────┬───────────────┘
                ┌─────▼─────┐
                │ 메인 메모리│
                └───────────┘
```

이해를 돕는 **비유**로는 훌륭하다. 그리고 실제로 하드웨어 수준의 가시성 지연은 존재한다. 다만 **x86 환경에서 이 예제가 무한 루프에 빠지는 주된 이유는 캐시가 아니다.**

### 2.2 🔴 현대 CPU의 코어 캐시는 하드웨어가 자동으로 동기화한다

x86 계열 CPU는 **MESI 같은 캐시 일관성(cache coherence) 프로토콜**을 하드웨어로 구현하고 있다. 한 코어가 값을 쓰면 다른 코어의 캐시 라인이 **자동으로 무효화**된다.

> **즉, "한쪽 코어의 캐시에 옛날 값이 영원히 남아 있다"는 일은 x86에서 일어나지 않는다.**

그럼 왜 무한 루프가 생길까?

### 2.3 ⭐ 실제 원인 세 가지

| 원인 | 설명 | 이 예제에서의 비중 |
| --- | --- | --- |
| ① **JIT 컴파일러 최적화** | 반복문 안에서 안 바뀌는 변수를 **레지스터에 올려둠(호이스팅)** | ⭐ **주범** |
| ② **스토어 버퍼** | 쓰기를 캐시에 즉시 반영하지 않고 버퍼에 쌓아둠 | 보조 |
| ③ **명령어 재정렬** | 컴파일러·CPU가 순서를 바꿈 | ARM 등에서 큼 |

### 2.4 JIT가 실제로 하는 일

```java
// 우리가 쓴 코드
while (runFlag) { }

// JIT 가 판단: "이 루프 안에서 runFlag 를 아무도 안 바꾸네?"
// → 읽기를 루프 밖으로 끌어냄 (loop hoisting)
boolean temp = runFlag;      // 레지스터에 한 번만 로드
while (temp) { }             // → 사실상 while(true)
```

**메모리를 아예 다시 읽지 않는다.** 캐시가 최신으로 갱신돼도 소용없다. 애초에 캐시를 보러 가지 않으니까.

```text
[ 최적화 전 ]                   [ JIT 최적화 후 ]

루프마다                        루프 진입 전 딱 한 번
  메모리 → 캐시 → 레지스터        메모리 → 레지스터
  값 확인                         │
  반복                            └─▶ 이후 레지스터만 보고 무한 반복
                                      ⚠️ 메모리를 다시 안 봄
```

### 2.5 💡 직접 증명해보기

**증명 1: JIT를 끄면 정상 종료된다**

```bash
java -Xint VolatileFlagMain     # 인터프리터 모드 (JIT 비활성화)
```

```text
[     main] runFlag를 false로 변경 시도
[     work] task 종료            ← ✅ volatile 없이도 종료된다!
[     main] main 종료
```

**`volatile`을 하나도 안 붙였는데 정상 종료된다.** 캐시 구조는 그대로인데 JIT만 껐더니 문제가 사라졌다. 이게 원인이 JIT라는 직접적인 증거다.

**증명 2: 1.3의 수수께끼 풀이**

```java
while (runFlag) {
    System.out.println("작업 중");   // 넣으면 종료됨
}
```

두 가지가 동시에 일어난다.

1. `println`은 내부적으로 `synchronized`라서 **메모리 배리어**가 생긴다 → 레지스터 캐싱이 무효화됨
2. 메서드 호출이 커서 **JIT가 호이스팅을 포기**한다

**캐시 이론만으로는 이 현상을 설명할 수 없다.** 반면 JIT 최적화로 보면 깔끔하게 설명된다.

### 2.6 🟡 그래도 캐시 모델은 왜 쓰나

| | 캐시 모델 | 실제 |
| --- | --- | --- |
| 설명 난이도 | 쉬움 | 어려움 (JIT, 배리어, 메모리 모델) |
| 직관 | "각자 사본을 본다" | 같은 결론 |
| 정확도 | 🟡 비유 수준 | ✅ |
| 실무 결론 | **동일** | **동일** |

결론이 같기 때문에 **입문 설명으로는 충분히 유효하다.** 다만 다음은 정확히 알아두는 게 좋다.

> ⭐ **JMM(자바 메모리 모델)은 "언제 다른 스레드에게 보이는지"를 아예 규정하지 않는다.**
> 캐시든 JIT든 재정렬이든, **동기화 없이는 보인다는 보장 자체가 없다**는 게 핵심이다.
> 원인을 외우는 것보다 **"보장이 없다"**를 기억하는 편이 실무에서 더 안전하다.

## 3. volatile의 두 가지 기능

### 3.1 적용

```java
static class MyTask implements Runnable {
    volatile boolean runFlag = true;   // ⭐

    @Override
    public void run() {
        log("task 시작");
        while (runFlag) { }
        log("task 종료");
    }
}
```

```text
16:34:23.842 [     main] runFlag = true
16:34:23.847 [     work] task 시작
16:34:24.851 [     main] runFlag를 false로 변경 시도
16:34:24.852 [     work] task 종료      ← ✅ 1ms 만에 반응
16:34:24.854 [     main] runFlag = false
16:34:24.859 [     main] main 종료

Process finished with exit code 0
```

### 3.2 🟡 "메인 메모리에 직접 접근"은 절반의 설명이다

원문은 `volatile`을 **"항상 메인 메모리에서 읽고 쓴다"**로 설명한다. 결과적으로는 맞지만, 실제로 컴파일러가 하는 일은 이렇다.

| 보장 | 내용 |
| --- | --- |
| ① **가시성 (visibility)** | 읽기를 레지스터에 캐싱하지 않는다. 쓰기는 즉시 다른 스레드에 보이게 한다 |
| ② **순서 (ordering)** ⭐ | volatile 읽기/쓰기를 **넘나드는 재정렬을 금지**한다 |

💡 **②번이 원문에 빠져 있는데, 실무에서는 이게 더 자주 문제가 된다.**

```text
        일반 쓰기 A
        일반 쓰기 B
   ─────────────────────  ← volatile 쓰기 (StoreStore 배리어)
        volatile 쓰기 V
   ─────────────────────
   ⭐ A, B 가 V 를 넘어 아래로 내려갈 수 없다
   ⭐ 그래서 V 를 읽은 스레드는 A, B 도 함께 볼 수 있다
```

이걸 **piggyback(업어가기)**이라고 부른다. `volatile` 변수 하나를 읽었을 뿐인데, **그 전에 쓰인 일반 변수들까지 함께 보이는** 효과다.

### 3.3 💡 순서 보장이 결정적인 예 — DCL 싱글톤

```java
public class Singleton {
    private static volatile Singleton instance;   // ⭐ volatile 없으면 버그

    public static Singleton getInstance() {
        if (instance == null) {                    // ① 락 없이 확인
            synchronized (Singleton.class) {
                if (instance == null) {            // ② 락 잡고 다시 확인
                    instance = new Singleton();    // ③
                }
            }
        }
        return instance;
    }
}
```

③번 한 줄이 실제로는 세 단계다.

```text
1. 메모리 할당
2. 생성자 실행 (필드 초기화)
3. instance 에 참조 대입

⚠️ JIT/CPU 가 2와 3을 재정렬할 수 있다

[ 재정렬된 경우 ]
1. 메모리 할당
3. instance 에 참조 대입   ← 다른 스레드가 여기서 ①을 통과해버림
2. 생성자 실행              ← 아직 초기화 안 된 객체를 받아감 💥
```

`volatile`이 2와 3의 재정렬을 막아준다. **"메인 메모리에서 읽는다"만으로는 이 버그를 설명할 수 없다.** 가시성이 아니라 순서의 문제이기 때문이다.

## 4. volatile이 해결하지 못하는 것 💡

### 4.1 ⚠️ 원자성은 보장하지 않는다

원문의 두 번째 예제에 **위험한 코드가 그대로 들어 있다.**

```java
volatile long count;

while (flag) {
    count++;      // ⚠️ volatile 을 붙여도 원자적이지 않다
}
```

```text
count++ 는 실제로 3단계다

① count 값을 읽는다        (read)
② 1을 더한다                (modify)
③ 결과를 저장한다           (write)

⭐ volatile 은 ①과 ③ 각각의 "가시성"만 보장한다
⭐ ①②③ 전체가 "끊기지 않는다"는 보장은 전혀 없다
```

```text
[ 두 스레드가 동시에 count++ 할 때 ]

Thread-A: ① read  → 100
Thread-B: ① read  → 100      ← 같은 값을 읽음
Thread-A: ② +1    → 101
Thread-B: ② +1    → 101
Thread-A: ③ write → 101
Thread-B: ③ write → 101      ← 💥 2번 증가했는데 101
```

원문 예제는 **`count`를 쓰는 스레드가 하나뿐**이라 우연히 문제가 드러나지 않는다. 하지만 코드만 보고 "volatile을 붙였으니 안전하다"고 배우면 **바로 다음 상황에서 터진다.**

### 4.2 volatile로 충분한 경우 vs 아닌 경우

| 패턴 | volatile로 충분? | 이유 |
| --- | --- | --- |
| `flag = false` (단순 대입) | ✅ | 읽기/쓰기 각각이 원자적 |
| `boolean b = flag` (단순 읽기) | ✅ | |
| `count++` | ❌ | 읽기 → 수정 → 쓰기 |
| `if (x == null) x = new A()` | ❌ | check-then-act |
| `list.add(item)` | ❌ | 참조만 volatile, 내용은 아님 |

> ⭐ **규칙: "한 스레드만 쓰고 나머지는 읽기만" 하는 경우에만 volatile로 충분하다.**
> 쓰는 스레드가 둘 이상이거나, 현재 값을 읽어서 새 값을 계산한다면 **volatile은 답이 아니다.**

### 4.3 💡 long/double의 특수한 사정

`long`과 `double`은 64비트인데, **32비트 JVM에서는 읽기/쓰기가 32비트씩 두 번에 나뉠 수 있다.**

```java
long value = 0x1111_1111_2222_2222L;   // 다른 스레드가 쓰는 중

// 다른 스레드가 읽으면?
// 상위 32비트만 갱신된 중간 상태를 볼 수 있다 (word tearing)
// → 0x1111_1111_0000_0000  ← 존재한 적 없는 값!
```

| | non-volatile `long` | `volatile long` |
| --- | --- | --- |
| 워드 티어링 | ⚠️ **발생 가능** (JLS가 허용) | ✅ 방지됨 |
| `count++` 원자성 | ❌ | ❌ **여전히 안 됨** |

`volatile long`은 **찢어진 값이 보이는 것만 막아주고**, 복합 연산의 원자성과는 무관하다.

### 4.4 그럼 카운터는 뭘 써야 하나

```java
// ❌ volatile
volatile long count;
count++;

// ✅ AtomicLong — CAS 기반, 락 없음
AtomicLong count = new AtomicLong();
count.incrementAndGet();

// ✅ LongAdder — 경쟁이 심할 때 더 빠름 (Java 8+)
LongAdder count = new LongAdder();
count.increment();
count.sum();

// ✅ synchronized
synchronized void increment() { count++; }
```

## 5. 성능 트레이드오프

### 5.1 원문의 실험

```java
volatile boolean flag = true;
volatile long count;

while (flag) {
    count++;
    if (count % 100_000_000 == 0) { log(...); }
}
```

| | 1초 동안 증가한 횟수 |
| --- | --- |
| volatile 없음 | 약 **4억** |
| volatile 적용 | 약 **1억** |

🟡 **이 수치를 "volatile은 4배 느리다"로 일반화하면 안 된다.**

- CPU, JDK 버전, JIT 상태에 따라 크게 달라진다
- 무엇보다 **이 루프는 `count++`를 초당 수억 번 하는 극단적인 경우**다

### 5.2 ⭐ 실제 비용은 읽기와 쓰기가 완전히 다르다

| 연산 | x86에서의 비용 |
| --- | --- |
| **volatile 읽기** | 거의 **공짜**. 일반 읽기와 기계어가 같다 (레지스터 캐싱만 금지) |
| **volatile 쓰기** | **비쌈**. `lock addl` 또는 `mfence` 명령 → 스토어 버퍼 플러시 |

원문 예제가 4배 느려진 건 **`count`가 volatile이라 매 반복마다 쓰기 배리어가 걸렸기 때문**이다. `flag`의 volatile 읽기는 거의 영향이 없다.

### 5.3 💡 직접 확인해볼 것 — count의 volatile을 빼보자

```java
volatile boolean flag = true;   // 유지
long count;                     // ⭐ volatile 제거
```

이렇게 하면 **성능은 거의 원래대로 돌아오면서 종료는 정상 동작한다.**

- `flag`는 두 스레드가 주고받으니 volatile이 꼭 필요하다
- `count`는 **work 스레드만 증가시키므로** 루프 안에서는 volatile이 필요 없다

> ⭐ **교훈: volatile은 "필요한 변수에만" 붙인다.**
> 일단 다 붙이고 보는 습관은 성능만 깎아먹는다. "이 변수를 여러 스레드가 주고받는가?"를 변수마다 따로 판단해야 한다.

🟡 다만 `main`이 마지막에 `task.count`를 읽으므로 그 한 번의 가시성은 별도로 챙겨야 한다. 로깅 목적이라 정확도가 덜 중요하다면 그대로 둬도 되고, 정확한 값이 필요하다면 `t.join()` 후에 읽으면 된다. **`join()`이 happens-before를 만들어주기 때문**이다(6장).

## 6. 자바 메모리 모델과 happens-before

### 6.1 happens-before란

> **A happens-before B 이면, A에서 일어난 모든 메모리 변경은 B에서 반드시 보인다.**

### 6.2 🟡 흔한 오해 — "시간 순서"가 아니다

```java
// A 가 시간적으로 먼저 실행됐다고 해서
// A happens-before B 인 것은 아니다!
```

| | 의미 |
| --- | --- |
| ❌ 오해 | "A가 B보다 먼저 실행된다" |
| ✅ 정확 | **"A의 변경 사항이 B에게 보인다는 것을 JMM이 보장한다"** |

시간적으로 아무리 먼저 실행돼도, **happens-before 관계가 없으면 안 보일 수 있다.** 1장의 `runFlag`가 정확히 그 경우다. `main`이 `false`를 쓴 게 시간적으로는 명백히 먼저였지만, 관계가 없으니 보장이 없었다.

### 6.3 happens-before가 성립하는 경우

| 규칙 | 내용 |
| --- | --- |
| **프로그램 순서** | 단일 스레드 내에서 소스 코드 순서대로 |
| **volatile** | volatile 쓰기 → 이후의 volatile 읽기 |
| **스레드 시작** | `start()` 이전의 모든 작업 → 새 스레드의 모든 작업 |
| **스레드 종료** | 대상 스레드의 모든 작업 → `join()` 반환 이후 |
| **인터럽트** | `interrupt()` 호출 → 인터럽트 감지 시점 |
| 🔴 **모니터 락** | `synchronized` **해제 → 이후의 획득** |
| 🔴 **final 필드** | 생성자 완료 → 그 객체의 final 필드 읽기 |
| **전이성** | A→B, B→C 이면 **A→C** |

🔴 **원문에 모니터 락 규칙과 final 필드 규칙이 빠져 있다.** 특히 모니터 락 규칙은 `synchronized`가 가시성을 보장하는 근거이므로 가장 중요한 규칙 중 하나다.

```java
synchronized (lock) {
    sharedData = 100;     // A
}                          // ← 락 해제

// 다른 스레드
synchronized (lock) {      // ← 락 획득
    print(sharedData);     // B — A 가 반드시 보인다
}
```

### 6.4 💡 전이성이 실제로 쓰이는 방식

원문에 "그 외 더 있음"으로 넘어간 부분인데, **실무에서 가장 많이 쓰는 건 전이성**이다.

```text
[ 이전 글의 join() 예제 ]

work 스레드:  result = 1275          (A)
                  │
                  │ ⭐ 스레드 종료 규칙
                  ▼
main 스레드:  join() 반환             (B)
                  │
                  │ ⭐ 프로그램 순서 규칙
                  ▼
              result 읽기              (C)

A → B, B → C  이므로  A → C
⭐ result 의 최신 값이 반드시 보인다
```

```text
[ volatile 플래그의 piggyback ]

writer:  data = 준비완료             (A, 일반 변수!)
         ready = true                 (B, volatile)
                  │ ⭐ volatile 규칙
                  ▼
reader:  if (ready)                   (C, volatile 읽기)
             use(data)                (D)

A → B (프로그램 순서), B → C (volatile), C → D (프로그램 순서)
⭐ 따라서 A → D. data 가 volatile 이 아닌데도 안전하게 보인다
```

이게 3.2에서 말한 **piggyback**의 정확한 근거다. `volatile` 변수 하나만 잘 배치하면, **그 앞에 쓴 일반 변수들이 전부 함께 건너간다.**

## 7. 언제 무엇을 쓸 것인가 💡

### 7.1 도구 비교

| | 가시성 | 원자성 | 재정렬 방지 | 블로킹 | 비용 |
| --- | --- | --- | --- | --- | --- |
| `volatile` | ✅ | ❌ | ✅ | ❌ 없음 | 읽기 저렴 / 쓰기 중간 |
| `Atomic*` | ✅ | ✅ (단일 변수) | ✅ | ❌ 없음 (CAS) | 중간 |
| `synchronized` | ✅ | ✅ (블록 전체) | ✅ | ✅ 있음 | 경쟁 시 높음 |
| `ReentrantLock` | ✅ | ✅ | ✅ | ✅ 있음 | synchronized와 비슷 |
| `final` | ✅ (생성 후) | — | ✅ | ❌ | **공짜** |

### 7.2 선택 가이드

```text
여러 스레드가 이 데이터를 건드리는가?
   │
   ├─ 아니오 → 아무것도 필요 없음 (지역 변수)
   │
   └─ 예
       │
       ├─ 생성 후 절대 안 바뀌는가? → ⭐ final / 불변 객체 (제일 좋다)
       │
       ├─ 한 스레드만 쓰고 나머지는 읽기만? → ⭐ volatile
       │
       ├─ 단일 변수의 증가/교환? → ⭐ AtomicLong, AtomicReference
       │
       └─ 여러 변수를 한 덩어리로 바꿔야 함? → ⭐ synchronized / ReentrantLock
```

### 7.3 💡 사실 제일 좋은 답은 "공유하지 않기"

```java
// ✅ 가장 안전 — 불변 객체
record Config(String host, int port) { }

// ✅ 두 번째 — 스레드 로컬
ThreadLocal<SimpleDateFormat> formatter = ...;

// ✅ 세 번째 — 동시성 컬렉션에 맡기기
ConcurrentHashMap, BlockingQueue, AtomicLong
```

`volatile`이나 `synchronized`를 직접 다루기 전에, **애초에 공유 상태를 없앨 수 있는지부터 보는 게 순서다.**

### 🔴 정정

| # | 원문 | 정정 |
| --- | --- | --- |
| 1 | "캐시 메모리 때문에 가시성 문제 발생" | x86은 **캐시 일관성을 하드웨어가 보장**. 이 예제의 주범은 **JIT 호이스팅** |
| 2 | "주로 컨텍스트 스위칭 때 캐시가 갱신됨" | 캐시는 **일관성 프로토콜로 즉시** 무효화됨. 문제는 **메모리를 다시 안 읽는 것** |
| 3 | `volatile long count; count++;` | **원자성 보장 안 됨.** 예제는 단일 쓰기 스레드라 우연히 안 터질 뿐 |
| 4 | happens-before 규칙 목록 | **모니터 락 규칙**과 **final 필드 규칙** 누락 |
| 5 | "기대하는데로 / 실제한 동작 / 메이 메모리 / 작ㅇ버을" | 기대한 대로 / 실제 동작 / 메인 메모리 / 작업을 |

### 🟡 보강

| # | 항목 | 보강 내용 |
| --- | --- | --- |
| 1 | "while 안에 뭘 넣으면 안 됨" | 이게 **JIT가 원인이라는 결정적 단서**. `println`이 배리어를 만들어서 |
| 2 | "volatile = 메인 메모리 직접 접근" | **가시성 + 순서(재정렬 방지)** 두 가지 |
| 3 | 4억 vs 1억 성능 비교 | 환경 의존적. **읽기는 저렴하고 쓰기가 비싸다**는 게 핵심 |
| 4 | volatile 적용 범위 | `count`는 volatile이 **불필요**. 필요한 변수에만 붙일 것 |
| 5 | happens-before | **시간 순서가 아니라 가시성 보장 관계** |
| 6 | volatile 변수 규칙 | 핵심은 **piggyback** — 앞선 일반 쓰기까지 함께 보임 |

### 이번 글의 핵심 한 줄

> **JMM은 "언제 보이는지"를 규정하지 않는다. 동기화 없이는 보인다는 보장 자체가 없다.**
> `volatile`은 **가시성과 순서**를 보장하지만, **원자성은 보장하지 않는다.**
