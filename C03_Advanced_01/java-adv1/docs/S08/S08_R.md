## 1. synchronized의 한계

| 한계 | 설명 |
| --- | --- |
| **무한 대기** | `BLOCKED` 상태는 락이 풀릴 때까지 무한정 기다린다. 타임아웃도, 인터럽트도 없다 |
| **공정성 없음** | 대기 중인 여러 스레드 중 누가 락을 받을지 알 수 없다. 최악의 경우 **기아(starvation)** |

앞 글에서 정리한 내용이다. 이 두 가지를 해결하려고 나온 것이 `java.util.concurrent` 패키지다.

```text
┌──────────────────────────────────────────────┐
│  synchronized  (언어 키워드, JVM 내장)        │
│   · 자동 해제  · 간결함                       │
│   · 타임아웃 ❌  · 인터럽트 ❌  · 공정성 ❌    │
└──────────────────────────────────────────────┘
                     │ 부족해서
                     ▼
┌──────────────────────────────────────────────┐
│  java.util.concurrent  (라이브러리)           │
│   LockSupport → AQS → ReentrantLock          │
└──────────────────────────────────────────────┘
```

## 2. LockSupport — 가장 저수준의 도구

### 2.1 기능

| 메서드 | 동작 | 결과 상태 |
| --- | --- | --- |
| `park()` | **호출한 스레드**를 대기시킨다 | `WAITING` |
| `parkNanos(nanos)` | **호출한 스레드**를 지정한 나노초만큼 대기시킨다 | `TIMED_WAITING` |
| `unpark(thread)` | **지정한 스레드**를 깨운다 | → `RUNNABLE` |

🟡 **원문의 "LockSupport는 특정 스레드를 Waiting 상태로 변경할 수 있음"은 오해를 부른다.**

```java
LockSupport.park();              // ✅ 나 자신만 재울 수 있다
LockSupport.park(someThread);    // ❌ 이런 메서드는 없다
LockSupport.unpark(someThread);  // ✅ 남을 깨우는 건 가능
```

앞 글의 `Thread.sleep()`과 똑같은 원칙이다. **재우는 건 자기 자신만, 깨우는 건 남도 가능.** `unpark()`에만 매개변수가 있는 이유는 원문 설명대로 **대기 중인 스레드는 자기 코드를 실행할 수 없어서 스스로 깨어날 수 없기 때문**이다.

### 2.2 예제

```java
public class LockSupportMainV1 {

    public static void main(String[] args) {
        Thread thread1 = new Thread(new ParkTest(), "Thread-1");
        thread1.start();

        sleep(100);   // Thread-1 이 park 에 빠질 시간을 줌
        log("Thread-1 state: " + thread1.getState());

        log("main -> unpark(Thread-1)");
        LockSupport.unpark(thread1);
        sleep(100);
        log("Thread-1 state: " + thread1.getState());
    }

    static class ParkTest implements Runnable {
        @Override
        public void run() {
            log("park 시작");
            LockSupport.park();
            log("park 종료, state: " + Thread.currentThread().getState());
            log("인터럽트 상태: " + Thread.currentThread().isInterrupted());
        }
    }
}
```

```text
20:41:33.376 [ Thread-1] park 시작
20:41:33.466 [     main] Thread-1 state: WAITING
20:41:33.466 [     main] main -> unpark(Thread-1)
20:41:33.467 [ Thread-1] park 종료, state: RUNNABLE
20:41:33.468 [ Thread-1] 인터럽트 상태: false
20:41:33.577 [     main] Thread-1 state: TERMINATED
```

### 2.3 인터럽트로도 깨어난다

```java
// LockSupport.unpark(thread1);
thread1.interrupt();
```

```text
20:44:57.592 [ Thread-1] park 종료, state: RUNNABLE
20:44:57.592 [ Thread-1] 인터럽트 상태: true      ← ⭐ 여기가 다르다
```

🔴 **원문 로그 문구 오류**: 코드에서 `unpark`를 주석 처리하고 `interrupt()`를 호출했는데, 로그는 여전히 `main -> unpark(Thread-1)`로 찍힌다. `main -> interrupt(Thread-1)`로 바꾸는 게 맞다.

### 2.4 ⭐ `park()`는 `InterruptedException`을 던지지 않는다

원문 예제가 이 사실을 보여주는데 설명이 없다. **중요한 차이**다.

| 메서드 | 인터럽트 시 |
| --- | --- |
| `Thread.sleep()` | `InterruptedException` **던짐** + 플래그 **초기화** |
| `Object.wait()` | `InterruptedException` **던짐** + 플래그 **초기화** |
| `Thread.join()` | `InterruptedException` **던짐** + 플래그 **초기화** |
| ⭐ `LockSupport.park()` | **아무것도 안 던짐**. 조용히 리턴 + 플래그 **true 유지** |

`park()`는 **저수준 도구라서 정책을 호출자에게 맡긴다.** "인터럽트가 왔으니 예외를 던질지, 무시하고 계속 대기할지"를 자기가 정하지 않는다. 그래서 `ReentrantLock.lock()`은 무시하고, `lockInterruptibly()`는 예외를 던지는 식으로 **같은 `park()` 위에 다른 정책**을 얹을 수 있다.

> ⚠️ **여기서 무한 루프가 생기기 쉽다.**
> ```java
> while (조건) {
>     LockSupport.park();   // 인터럽트 플래그가 true 로 남아 있으면
> }                          // → 다음 park() 도 즉시 리턴 → CPU 100%
> ```
> 인터럽트 플래그가 켜져 있으면 `park()`는 **계속 즉시 리턴한다.** 앞 글에서 다룬 **"인터럽트는 소비하거나 복원해야 한다"**가 여기서도 그대로 적용된다.
> ```java
> if (Thread.interrupted()) {   // 소비하고 처리
>     // 종료 처리
>     return;
> }
> ```

### 2.5 parkNanos

```java
LockSupport.parkNanos(2000_000000);   // 2초
```

```text
20:54:15.214 [ Thread-1] park 시작
20:54:15.289 [     main] Thread-1 state: TIMED_WAITING
20:54:17.222 [ Thread-1] park 종료, state: RUNNABLE     ← 약 2초 뒤
```

🔴 **오타 정정**: "스스**르** 2초 뒤에" → **스스로**, "waiting → runnable" → 정확히는 **`TIMED_WAITING` → `RUNNABLE`**

🔴 **"참고로 밀리초동안 대기하는 스레드는 없음"** → 의도는 **"`parkMillis()` 같은 메서드가 없다"**는 뜻이다. "스레드"가 아니라 "메서드"로 고쳐야 문장이 통한다.

| 메서드 | 기준 |
| --- | --- |
| `parkNanos(nanos)` | **상대 시간** (지금부터 n나노초) |
| `parkUntil(millis)` | **절대 시간** (에포크 기준 특정 시각) |

`parkUntil`은 "2026년 1월 1일 0시에 깨어나라"처럼 미래의 에포크 시각을 지정하는 용도다. 일반적인 타임아웃에는 `parkNanos`를 쓴다.

## 3. ⭐ 퍼밋과 park()가 깨어나는 세 가지 이유

원문에 없는데, `LockSupport`를 이해하려면 반드시 알아야 하는 두 가지다.

### 3.1 퍼밋(permit) — unpark를 먼저 해도 유실되지 않는다

`park()`/`unpark()`는 단순한 "재우기/깨우기"가 아니라 **퍼밋 1개짜리 토큰 시스템**이다.

```text
┌─────────────────────────────────────────────┐
│  각 스레드는 "퍼밋" 을 0개 또는 1개 가진다   │
│                                             │
│  unpark(t) → t 의 퍼밋을 1로 만든다          │
│  park()    → 퍼밋이 1이면 소비하고 즉시 리턴 │
│              퍼밋이 0이면 대기               │
└─────────────────────────────────────────────┘
```

```java
// 순서가 뒤바뀌어도 안전하다
LockSupport.unpark(thread);   // ① 먼저 깨움 → 퍼밋 저장
// ... 시간이 흐름 ...
LockSupport.park();            // ② 퍼밋을 소비하고 즉시 리턴 ✅
```

**이게 `wait/notify`와의 결정적 차이다.**

```java
// wait/notify — 순서가 뒤바뀌면 영원히 멈춘다
synchronized (lock) { lock.notify(); }   // ① 대기자가 없으면 신호 유실 💥
synchronized (lock) { lock.wait(); }      // ② 영원히 대기
```

| | `park/unpark` | `wait/notify` |
| --- | --- | --- |
| 신호를 먼저 보내면 | ✅ **저장됨** (퍼밋) | ❌ **유실됨** |
| 락 필요 | ❌ 불필요 | ✅ `synchronized` 안에서만 |
| 대상 지정 | ✅ 특정 스레드 | ❌ 대기자 중 임의 |

> ⚠️ **퍼밋은 최대 1개만 쌓인다.** `unpark()`를 10번 불러도 `park()`는 **한 번만** 통과한다. 카운팅 세마포어가 아니다.

### 3.2 `park()`는 이유 없이 깨어날 수 있다 (spurious wakeup)

공식 문서에 명시된 내용이다. `park()`가 리턴하는 이유는 **세 가지**다.

```text
      LockSupport.park()
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
① unpark   ② interrupt  ③ 이유 없이 (spurious)
   호출        발생         그냥 리턴
```

> ⭐ **그래서 `park()`는 절대 단독으로 쓰면 안 되고, 반드시 조건 확인 루프 안에 넣어야 한다.**
> ```java
> // ❌ 위험
> LockSupport.park();
> doWork();          // 진짜 깨울 만한 일이 있었는지 확인 안 함
>
> // ✅ 올바른 패턴
> while (!조건이_충족됨()) {
>     LockSupport.park();
>     if (Thread.interrupted()) { /* 인터럽트 처리 */ return; }
> }
> doWork();
> ```

`ReentrantLock` 내부도 정확히 이렇게 되어 있다. 이 복잡함 때문에 **직접 쓰지 말고 고수준 도구를 쓰라**는 것이다.

## 4. BLOCKED vs WAITING 정리

원문의 비교가 정확하다. 표로 정리하면 이렇다.

| | `BLOCKED` | `WAITING` / `TIMED_WAITING` |
| --- | --- | --- |
| **인터럽트 시 상태 변화** | ❌ 대기 상태를 빠져나오지 못함 | ✅ `RUNNABLE`로 깨어남 |
| **인터럽트 플래그** | ✅ `true`가 되긴 함 | ✅ `true` (또는 예외) |
| **용도** | `synchronized` 락 대기 | 조건·시간 대기 |
| **대표 메서드** | `synchronized` 진입 | `join()`, `park()`, `wait()`, `sleep()` |

```text
[ WAITING ]                          [ TIMED_WAITING ]
 Thread.join()                        Thread.sleep(ms)
 Object.wait()                        Object.wait(timeout)
 LockSupport.park()                   Thread.join(millis)
                                      LockSupport.parkNanos(ns)
```

🔴 **오타 정정**: `LockSupport(ns)` → **`LockSupport.parkNanos(ns)`**

> ⭐ **`BLOCKED`는 인터럽트를 걸면 플래그는 `true`가 되지만 상태는 그대로 `BLOCKED`다.** 락이 풀려서 진입한 다음에야 플래그를 확인할 수 있다. 이 하나의 차이가 `ReentrantLock`이 필요한 가장 큰 이유다.

## 5. Lock 인터페이스

### 5.1 정확한 시그니처

🔴 **원문 인터페이스 정의에 오타와 누락이 있다.**

```java
public interface Lock {
    void lock();
    void lockInterruptibly() throws InterruptedException;              // ⭐ 철자 + throws
    boolean tryLock();
    boolean tryLock(long time, TimeUnit unit) throws InterruptedException;  // ⭐ throws
    void unlock();
    Condition newCondition();
}
```

- `lockInterrputibly` → **`lockInterruptibly`** (원문에서 여러 번 반복되는 오타)
- `lockInterruptibly()`와 `tryLock(time, unit)`은 **`throws InterruptedException`**이 붙어 있다. 이게 빠지면 "왜 try-catch를 해야 하지?"가 설명되지 않는다

### 5.2 메서드 비교

| 메서드 | 대기 | 인터럽트 | 타임아웃 | 반환 |
| --- | --- | --- | --- | --- |
| `lock()` | 무한 | ❌ 무시 | ❌ | `void` |
| `lockInterruptibly()` | 무한 | ✅ 예외 | ❌ | `void` |
| `tryLock()` | **없음** | — | 즉시 | `boolean` |
| `tryLock(time, unit)` | 제한 | ✅ 예외 | ✅ | `boolean` |

### 5.3 unlock()

🔴 **오타**: "`IllegalMonitorStateException`**일** 발생할 수 있음" → **이**

🟡 **"발생할 수 있음"보다 "반드시 발생한다"가 정확하다.** 락을 가지지 않은 스레드가 `unlock()`을 호출하면 `ReentrantLock`은 예외를 던진다.

> ⚠️ **`lock()`은 반드시 `try` 블록 밖에 있어야 한다.**
> ```java
> // ✅ 올바른 형태
> lock.lock();
> try {
>     // 임계 영역
> } finally {
>     lock.unlock();
> }
>
> // ❌ 잘못된 형태
> try {
>     lock.lock();          // 여기서 실패하면?
> } finally {
>     lock.unlock();        // 💥 IllegalMonitorStateException
> }
> ```

### 5.4 🟡 "여기서 사용하는 락은 모니터 락이 아니다"

원문이 두 번이나 강조하는데, 정확하다. 한 발 더 나가면 이렇다.

```java
class Account {
    private final Lock lock = new ReentrantLock();

    void a() { lock.lock(); try { ... } finally { lock.unlock(); } }
    synchronized void b() { ... }   // ⚠️ 모니터 락 — 완전히 다른 락!
}
```

**`a()`와 `b()`는 동시에 실행된다.** 앞 글에서 본 "인스턴스 락 vs 클래스 락"과 같은 유형의 함정이다. 8장에서 원문 코드에 실제로 이 문제가 있다.

## 6. lock()과 인터럽트

### 6.1 "인터럽트에 응답하지 않는다"의 정확한 의미

원문 설명이 정확하다. 정리하면 이렇다.

```text
t2 가 lock() 으로 대기 중  (WAITING — 내부적으로 park())
        │
        │ 누군가 interrupt()
        ▼
① park() 가 리턴 → 잠깐 RUNNABLE
        │
② AQS 가 "인터럽트 왔네" 하고 플래그만 기록
        │
③ 락을 아직 못 얻었으므로 다시 park()
        │
        ▼
   ⭐ 다시 WAITING. 겉으로는 아무 일도 없었던 것처럼 보인다
```

즉 **"상태가 안 변한다"가 아니라 "깨어났다가 다시 잠든다"**는 것이다. 원문의 설명이 이 부분을 정확히 짚었다.

### 6.2 💡 인터럽트가 사라지지는 않는다

```java
lock.lock();              // 대기 중 인터럽트가 와도 계속 기다린다
// 락 획득 성공
Thread.currentThread().isInterrupted();   // ⭐ true — 플래그는 복원된다
```

AQS는 락을 얻은 뒤 `selfInterrupt()`를 호출해 **인터럽트 상태를 되살려 놓는다.** "무시한다"는 건 "대기를 중단하지 않는다"는 뜻이지, **"신호를 버린다"는 뜻이 아니다.** 앞 글의 "인터럽트를 삼키지 마라"는 원칙이 JDK 내부에서도 지켜지고 있는 셈이다.

## 7. 공정성

### 7.1 두 모드

```java
private final Lock nonFairLock = new ReentrantLock();       // 비공정 (기본)
private final Lock fairLock = new ReentrantLock(true);      // 공정
```

| | 비공정 (기본) | 공정 |
| --- | --- | --- |
| 순서 | 보장 안 됨 | **대기 큐 순서대로** |
| 선점(barging) | ✅ 가능 | ❌ 불가 |
| 기아 | ⚠️ 가능 | ✅ 방지 |
| 성능 | **빠름** | 느림 |

🔴 **오타**: "락이 돌아왔을 **대**" → **때**, "모드**르** 제공" → **모드를**, "락을 풀었을 **대**" → **때**

### 7.2 💡 공정 모드가 느린 이유

```text
[ 비공정 ]                          [ 공정 ]

t1 이 락 해제
    │                                t1 이 락 해제
    │  마침 t4 가 도착                    │
    ▼                                     ▼
t4 가 그냥 가져감 ✅                 대기 큐 1번(t2)을 깨운다
(컨텍스트 스위칭 0회)                     │
                                          │ unpark → 스케줄링 → 실행
                                          ▼
                                     t2 가 락 획득
                                     (컨텍스트 스위칭 필요)
```

비공정 모드는 **이미 CPU에서 돌고 있는 스레드가 그냥 가져가므로** 컨텍스트 스위칭이 없다. 공정 모드는 매번 대기 중인 스레드를 깨워야 해서, 경쟁이 심하면 **처리량이 수십 배 차이** 나기도 한다.

### 7.3 ⚠️ 공정 모드에서도 `tryLock()`은 새치기한다

이건 실무에서 잘 모르고 당하는 함정이다.

```java
Lock fairLock = new ReentrantLock(true);   // 공정 모드로 만들었는데

fairLock.tryLock();          // ⚠️ 공정성을 무시하고 즉시 가로챈다
fairLock.tryLock(0, TimeUnit.SECONDS);   // ✅ 이건 공정성을 지킨다
```

공식 문서에 **"인자 없는 `tryLock()`은 공정성 설정을 따르지 않는다"**고 명시되어 있다. 대기 중인 스레드가 있어도 락이 비어 있으면 바로 가져간다.

공정성을 유지하면서 "즉시 시도"를 하고 싶다면 **`tryLock(0, TimeUnit.SECONDS)`**를 써야 한다.

## 8. ReentrantLock 활용

### 8.1 코드

```java
public class BankAccountV4 implements BankAccount {

    private final Lock lock = new ReentrantLock();
    private int balance;

    @Override
    public boolean withdraw(int amount) {
        log("거래 시작: " + getClass().getSimpleName());

        lock.lock();                     // ⭐ try 밖
        try {
            log("[검증 시작] ... 잔액: " + balance);
            if (balance < amount) {
                log("[검증 실패] ...");
                return false;             // ✅ finally 가 unlock 해준다
            }
            log("[검증 완료] ...");
            sleep(1000);
            balance -= amount;
            log("[출금 완료] ... 잔액: " + balance);
        } finally {
            lock.unlock();                // ⭐ 반드시 finally
        }

        log("거래 종료: " + getClass().getSimpleName());
        return true;
    }
}
```

```text
21:38:53.292 [     main] t1 state: TIMED_WAITING   ← sleep 중
21:38:53.294 [     main] t2 state: WAITING         ← ⭐ BLOCKED 가 아니다!
21:38:53.839 [       t1] [출금 완료] 출금액: 800, 잔액: 200
21:38:53.840 [       t2] [검증 실패] 출금액: 800, 잔액: 200
21:38:53.841 [     main] 최종 잔액: 200
```

`synchronized`였을 때 `BLOCKED`였던 t2가 이제 **`WAITING`**이다. 내부적으로 `LockSupport.park()`를 쓰기 때문이다. 그래서 **인터럽트와 타임아웃이 가능해진다.**

### 8.2 동작 원리

```text
        ReentrantLock 객체
        ┌────────────────────────────────┐
        │  state = 1  (락 보유 중)        │
        │  owner  = t1                    │
        │  대기 큐 ──▶ [t2] [t3] [t4]     │
        └────────────────────────────────┘
                 │
      t1 이 unlock() 호출
                 │
        ┌────────┴─────────┐
        ▼                  ▼
   [ 비공정 ]          [ 공정 ]
   아무나 깨움       큐 순서대로 깨움
   (새로 온 스레드가   (t2 → t3 → t4)
    가로챌 수도)
```

### 8.3 🔴 원문 V4 코드에 심각한 버그가 있다

```java
public class BankAccountV4 {
    private final Lock lock = new ReentrantLock();

    public boolean withdraw(int amount) {
        lock.lock();              // 🔒 ReentrantLock
        // ...
    }

    @Override
    public synchronized int getBalance() {   // ⚠️⚠️ 모니터 락!
        return balance;
    }
}
```

**`withdraw()`는 `ReentrantLock`을, `getBalance()`는 모니터 락을 쓴다.** 5.4에서 말한 대로 **이 둘은 완전히 다른 락**이라서 상호 배제가 **전혀 되지 않는다.**

```text
t1: withdraw()  → ReentrantLock 획득 🔒A
t2: getBalance() → 모니터 락 획득     🔒B
    ⭐ 서로 막지 않는다 → 출금 도중의 중간 값을 읽을 수 있다
```

원문은 V5부터 이렇게 고친다.

```java
@Override
public int getBalance() {
    lock.lock();          // ✅ 같은 락을 쓴다
    try {
        return balance;
    } finally {
        lock.unlock();
    }
}
```

**V4의 `synchronized`는 앞 장에서 복사해 온 흔적으로 보인다.** 설명 없이 V5에서 바뀌므로, 직접 따라 칠 때 주의해야 한다.

### 8.4 🟡 `sleep(1000)`이 여전히 락 안에 있다

앞 글에서 지적한 문제가 그대로다. `synchronized`를 `ReentrantLock`으로 바꿔도 **락 보유 시간이 1초라는 사실은 변하지 않는다.**

> ⭐ **락의 종류를 바꾸는 것과 락 보유 시간을 줄이는 것은 완전히 다른 문제다.**
> `ReentrantLock`은 "기다리는 방식"을 개선할 뿐, "얼마나 오래 잡고 있는지"는 여전히 설계자의 몫이다.

### 8.5 💡 ReentrantLock도 재진입 가능하다

이름 그대로다.

```java
lock.lock();
lock.lock();        // ✅ 같은 스레드면 OK. 카운터 = 2
try {
    log(((ReentrantLock) lock).getHoldCount());   // 2
} finally {
    lock.unlock();  // 카운터 = 1  (아직 안 풀림)
    lock.unlock();  // 카운터 = 0  ⭐ 여기서 해제
}
```

**`lock()`을 부른 횟수만큼 `unlock()`을 불러야 한다.** `synchronized`는 블록을 벗어나면 자동으로 맞춰지지만, `ReentrantLock`은 직접 맞춰야 한다.

💡 디버깅에 유용한 메서드들:

| 메서드 | 용도 |
| --- | --- |
| `getHoldCount()` | 현재 스레드의 재진입 횟수 |
| `isHeldByCurrentThread()` | 내가 이 락을 쥐고 있나 |
| `isLocked()` | 누군가 쥐고 있나 |
| `getQueueLength()` | 대기 중인 스레드 수 (추정) |

## 9. tryLock — 대기 중단

### 9.1 즉시 포기 (V5)

```java
if (!lock.tryLock()) {
    log("[진입 실패]: 이미 처리 중인 작업이 있습니다.");
    return false;
}

try {
    // 임계 영역
} finally {
    lock.unlock();
}
```

### 9.2 시간 제한 (V6)

```java
try {
    if (!lock.tryLock(1000, TimeUnit.MILLISECONDS)) {
        log("[진입 실패]: 이미 처리 중인 작업이 있습니다.");
        return false;
    }
} catch (InterruptedException e) {
    throw new RuntimeException(e);       // 🟡 아래 참고
}

try {
    // 임계 영역
} finally {
    lock.unlock();
}
```

### 9.3 🟡 `InterruptedException` 처리가 앞 글의 안티패턴이다

```java
catch (InterruptedException e) {
    throw new RuntimeException(e);   // ⚠️ 인터럽트 플래그가 복원되지 않는다
}
```

앞 글에서 정리한 규칙 그대로다. **잡았으면 다시 던지거나 복원하라.**

```java
// ✅ 방법 1 — 시그니처에 전파
public boolean withdraw(int amount) throws InterruptedException {
    if (!lock.tryLock(1000, TimeUnit.MILLISECONDS)) { ... }
}

// ✅ 방법 2 — 복원하고 종료
catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return false;
}
```

### 9.4 ⚠️ 반환값이 이유를 구분해주지 않는다

```java
boolean result = account.withdraw(800);
// false 인데... 왜?
//   ① 잔액 부족?
//   ② 락을 못 얻음 (타임아웃)?
//   ③ 인터럽트?
```

앞 글의 `join(ms)`와 **완전히 같은 문제**다. `boolean` 하나로는 실패 이유를 담을 수 없다.

```java
// ✅ 개선 — 결과 타입을 만들거나
enum WithdrawResult { SUCCESS, INSUFFICIENT_BALANCE, BUSY, INTERRUPTED }

// ✅ 또는 예외로 구분
throw new AccountBusyException();
```

### 9.5 💡 `tryLock`의 진짜 강력한 용도 — 데드락 회피

타임아웃보다 이쪽이 실무에서 더 중요하다.

```java
// ❌ 데드락 위험 — 두 계좌를 순서 없이 잠근다
void transfer(Account from, Account to, int amount) {
    synchronized (from) {
        synchronized (to) {   // ⚠️ 반대 방향 이체가 동시에 일어나면 데드락
            ...
        }
    }
}
```

```text
t1: transfer(A → B)          t2: transfer(B → A)
    A 락 획득 ✅                 B 락 획득 ✅
    B 락 대기 ⏳ ←──────────────→ A 락 대기 ⏳
                  💀 영원히 데드락
```

`synchronized`로는 이 상황에서 빠져나올 방법이 **아예 없다.** `tryLock`을 쓰면 가능하다.

```java
// ✅ tryLock 으로 회피
boolean transfer(Account from, Account to, int amount) {
    while (true) {
        if (from.lock.tryLock()) {
            try {
                if (to.lock.tryLock()) {
                    try {
                        // 실제 이체
                        return true;
                    } finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }
        }
        // 둘 다 못 얻으면 전부 놓고 잠깐 쉬었다 재시도
        Thread.sleep(random.nextInt(50));
    }
}
```

**둘 다 얻지 못하면 가진 것도 놓아버린다.** 이게 데드락이 풀리는 원리다. `synchronized`로는 구현할 수 없는 패턴이다.

## 10. 전체 계층 구조와 다음 단계 💡

### 10.1 무엇 위에 무엇이 서 있나

```text
┌──────────────────────────────────────────────────────┐
│  고수준 도구                                          │
│  BlockingQueue, CountDownLatch, Semaphore,           │
│  ConcurrentHashMap, ExecutorService                  │
└───────────────────────┬──────────────────────────────┘
                        │ 이걸로 만들어짐
┌───────────────────────▼──────────────────────────────┐
│  ReentrantLock, ReadWriteLock, Condition             │
└───────────────────────┬──────────────────────────────┘
                        │ 이걸로 만들어짐
┌───────────────────────▼──────────────────────────────┐
│  AQS (AbstractQueuedSynchronizer)                    │
│   · state(int) + 대기 큐(CLH)                         │
└───────────────────────┬──────────────────────────────┘
                        │ 이걸로 만들어짐
┌───────────────────────▼──────────────────────────────┐
│  LockSupport.park() / unpark()                       │
└───────────────────────┬──────────────────────────────┘
                        │ 이걸로 만들어짐
┌───────────────────────▼──────────────────────────────┐
│  네이티브 (OS 스레드 파킹)                            │
└──────────────────────────────────────────────────────┘
```

원문의 "**LockSupport가 너무 저수준이다**"라는 지적이 정확하다. 퍼밋, spurious wakeup, 인터럽트 정책을 전부 직접 다뤄야 하기 때문이다. **AQS가 그 복잡함을 흡수하고, `ReentrantLock`은 그 위에 얹힌 얇은 껍데기**다.

### 10.2 그래서 무엇을 쓸 것인가

```text
동시성 문제가 생겼다
   │
   ├─ 공유를 없앨 수 있나?      → ⭐ 불변 객체 / ThreadLocal
   │
   ├─ 이미 있는 자료구조로 되나? → ⭐ ConcurrentHashMap, BlockingQueue
   │
   ├─ 단일 변수 연산인가?        → ⭐ AtomicLong, LongAdder
   │
   ├─ 단순한 임계 영역인가?      → ⭐ synchronized (가장 간결)
   │
   ├─ 타임아웃·취소·공정성 필요? → ⭐ ReentrantLock
   │
   ├─ 읽기가 압도적으로 많나?    → ⭐ ReadWriteLock, StampedLock
   │
   └─ 직접 동기화 도구를 만든다  → 🟡 AQS (LockSupport는 거의 안 씀)
```

### 10.3 synchronized vs ReentrantLock 최종 비교

| | `synchronized` | `ReentrantLock` |
| --- | --- | --- |
| 대기 상태 | `BLOCKED` | `WAITING` / `TIMED_WAITING` |
| 해제 | ✅ **자동** (예외 포함) | ⚠️ `finally`에서 직접 |
| 타임아웃 | ❌ | ✅ `tryLock(time, unit)` |
| 인터럽트 | ❌ | ✅ `lockInterruptibly()` |
| 공정성 | 불공정 고정 | ✅ 선택 가능 |
| 조건 변수 | `wait/notify` 1개 | ✅ `Condition` **여러 개** |
| 재진입 | ✅ | ✅ |
| 코드 간결성 | ✅ | 장황함 |
| 성능 | 비슷 | 비슷 |

> 💡 **기본은 `synchronized`, 추가 기능이 필요할 때만 `ReentrantLock`.**
> `try-finally`를 빠뜨리면 락이 영원히 안 풀리는 사고가 나므로, 얻는 게 없다면 `synchronized`가 안전하다.

### 이번 글의 핵심 한 줄

> **`synchronized`는 `BLOCKED`로 기다리고, `ReentrantLock`은 `WAITING`으로 기다린다.**
> 그 한 글자 차이가 **타임아웃과 취소**를 가능하게 만든다.
