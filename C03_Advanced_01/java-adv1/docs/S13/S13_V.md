# [Java] 스레드 풀과 Executor 프레임워크, Callable과 Future

지금까지는 `new Thread()`로 스레드를 직접 만들었다. 실무에서 이렇게 쓰면 세 가지 문제에 부딪힌다.

- 요청이 1만 개 들어오면 스레드도 1만 개를 만들 건가?
- 스레드를 만드는 비용이 작업 자체보다 비싸면?
- `Runnable`은 결과를 돌려주지도, 체크 예외를 던지지도 못한다

이 세 문제를 한 번에 푸는 게 **Executor 프레임워크**다. 그리고 그 내부를 들여다보면, 앞에서 만든 **`BlockingQueue`가 그대로 들어 있다.**

---

## 다루는 내용

- 스레드를 직접 쓸 때의 문제
- 스레드 풀과 `ThreadPoolExecutor`
- ⭐ 스레드가 늘어나는 정확한 규칙
- `Callable`과 `Future`
- ⭐ `submit()`과 `get()`을 분리한 이유
- 취소와 예외 처리
- `invokeAll()` / `invokeAny()`
- ⚠️ 스레드 풀은 반드시 닫아야 한다

# 1. 스레드를 직접 쓸 때의 문제

| 문제 | 내용 |
| --- | --- |
| **생성 비용** | 스택 메모리 할당 + 커널 시스템 콜. 작업보다 생성이 더 오래 걸릴 수 있다 |
| **관리 문제** | 요청마다 스레드를 만들면, 요청 1만 개 = 스레드 1만 개 → 시스템이 버티지 못한다 |
| **Runnable의 불편함** | 반환값이 없고, 체크 예외를 던질 수 없다 |

스레드 하나는 기본적으로 약 **1MB의 스택 공간을 예약**한다(실제 물리 메모리는 쓰는 만큼 늘어난다). 수천 개면 예약 공간만으로도 부담이 크고, 커널 자원은 별도다.

> 💡 첫 글에서 정리한 **"`Thread` 객체 생성은 싸고, 비싼 건 `start()`의 커널 호출과 스택 할당"**이 이 문제의 정체다.

# 2. 스레드 풀

## 2.1 아이디어

```text
① 스레드를 미리 만들어 풀에 넣어둔다
② 작업이 오면 풀에서 놀고 있는 스레드 하나를 꺼내 처리한다
③ 끝나면 종료하지 않고 풀로 돌려보낸다 → 재사용
④ 작업이 없으면 WAITING 으로 대기한다 (CPU 안 씀)
```

| 문제 | 스레드 풀의 해결 |
| --- | --- |
| 생성 비용 | 한 번 만들고 **재사용** |
| 관리 문제 | 풀 크기로 **최대 스레드 수를 제한** |

## 2.2 ⭐ "대기 상태로 관리한다"의 정체

놀고 있는 스레드를 WAITING으로 관리한다는 건 구체적으로 무슨 뜻일까? **이전 두 글에서 만든 그것**이다.

```text
   작업을 넣는 쪽 (생산자)          풀의 스레드들 (소비자)

   es.execute(task) ──▶  BlockingQueue  ──▶ take()
                                              │
                          비어 있으면 ⭐ WAITING 으로 잠듦
                          (Condition.await → LockSupport.park)
                                              │
                          작업이 들어오면 signal 로 깨어남
```

> ⭐ **스레드 풀은 생산자-소비자 문제의 완성품이다.**
> `BlockingQueue`가 작업 큐로 쓰이고, 놀고 있는 스레드는 `take()`에서 `WAITING`으로 잠들어 있다. yield로 양보하는 게 아니라 **잘 자고 있는 것**이다.

## 2.3 Executor 인터페이스

```java
public interface Executor {
    void execute(Runnable command);
}
```

```java
public interface ExecutorService extends Executor, AutoCloseable {
    <T> Future<T> submit(Callable<T> task);
    void shutdown();
    <T> List<Future<T>> invokeAll(Collection<? extends Callable<T>> tasks) throws InterruptedException;
    <T> T invokeAny(Collection<? extends Callable<T>> tasks) throws InterruptedException, ExecutionException;

    @Override
    default void close() { ... }
    // ...
}
```

| | 역할 |
| --- | --- |
| `Executor` | 작업 실행만 (`execute`) |
| `ExecutorService` | + 작업 제출(`submit`), 종료, 일괄 처리. **대부분 이걸 쓴다** |
| `ThreadPoolExecutor` | 대표 구현체 |

> ⚠️ **`AutoCloseable`과 `close()`는 Java 19부터다.** 그 이전 버전에서는 `shutdown()`을 써야 한다. 10장에서 정리한다.

# 3. ThreadPoolExecutor 사용해보기

## 3.1 상태 출력 유틸

```java
public abstract class ExecutorUtils {

    public static void printState(ExecutorService executorService) {
        if (executorService instanceof ThreadPoolExecutor poolExecutor) {
            int pool = poolExecutor.getPoolSize();
            int active = poolExecutor.getActiveCount();
            int queuedTasks = poolExecutor.getQueue().size();
            long completedTask = poolExecutor.getCompletedTaskCount();
            log("[pool=" + pool + ", active=" + active + ", queuedTasks=" + queuedTasks +
                    ", completedTask=" + completedTask + "]");
        } else {
            log(executorService);
        }
    }
}
```

| 메서드 | 의미 |
| --- | --- |
| `getPoolSize()` | 풀이 관리하는 스레드 수 |
| `getActiveCount()` | 지금 작업 중인 스레드 수 |
| `getQueue().size()` | 큐에서 대기 중인 작업 수 |
| `getCompletedTaskCount()` | 완료된 작업 수 |

> 💡 `getActiveCount()`와 `getCompletedTaskCount()`는 **근사값**이다. 조회하는 순간에도 스레드들이 움직이므로 모니터링용이지 흐름 제어용이 아니다.

## 3.2 작업 5개, 스레드 2개

```java
public class RunnableTask implements Runnable {

    private final String name;
    private int sleepMs = 1000;

    public RunnableTask(String name) { this.name = name; }
    public RunnableTask(String name, int sleepMs) { this.name = name; this.sleepMs = sleepMs; }

    @Override
    public void run() {
        log(name + " 시작");
        sleep(sleepMs);
        log(name + " 완료");
    }
}
```

```java
ExecutorService es = new ThreadPoolExecutor(
        2,                          // corePoolSize
        2,                          // maximumPoolSize
        0, TimeUnit.MILLISECONDS,   // keepAliveTime
        new LinkedBlockingQueue<>() // workQueue
);

printState(es);
es.execute(new RunnableTask("taskA"));   // 스레드 1 생성
es.execute(new RunnableTask("taskB"));   // 스레드 2 생성
es.execute(new RunnableTask("taskC"));   // 큐로 들어간다
es.execute(new RunnableTask("taskD"));
es.execute(new RunnableTask("taskE"));
printState(es);

sleep(5000);
printState(es);

es.close();
printState(es);
```

## 3.3 실행 결과 읽기

```text
[     main] [pool=0, active=0, queuedTasks=0, completedTask=0]   ← 처음엔 0개로 시작
[pool-1-thread-1] taskA 시작
[     main] [pool=2, active=2, queuedTasks=3, completedTask=0]   ← 스레드 2개, 큐 3개
[pool-1-thread-2] taskB 시작
[pool-1-thread-2] taskB 완료
[pool-1-thread-1] taskA 완료
[pool-1-thread-2] taskC 시작      ⭐ thread-2 가 재사용됨
[pool-1-thread-1] taskD 시작      ⭐ thread-1 이 재사용됨
[pool-1-thread-1] taskD 완료
[pool-1-thread-1] taskE 시작
[pool-1-thread-2] taskC 완료
[pool-1-thread-1] taskE 완료
[     main] [pool=2, active=0, queuedTasks=0, completedTask=5]   ← 스레드는 남아서 대기
[     main] == shutdown ==
[     main] [pool=0, active=0, queuedTasks=0, completedTask=5]   ← close 후 0
```

**작업은 5개인데 스레드 이름은 `thread-1`, `thread-2` 두 개뿐이다.** 이게 재사용의 증거다.

taskC부터는 스레드를 새로 만들지 않고 **큐에 들어간다.** 그리고 thread-1이나 thread-2가 자기 작업을 끝낸 뒤 **큐에서 taskC를 꺼낼 때** 재사용이 일어난다.

```text
                     main (생산자)
                        │ execute(taskA..E)
                        ▼
 ┌──────────────── ThreadPoolExecutor ────────────────┐
 │                                                    │
 │   BlockingQueue   [taskC] [taskD] [taskE]          │
 │                       │                            │
 │              take()   ▼        take()              │
 │   ┌──────────────────┐   ┌──────────────────┐      │
 │   │ pool-1-thread-1  │   │ pool-1-thread-2  │ 소비자│
 │   │   taskA 실행     │   │   taskB 실행     │      │
 │   └──────────────────┘   └──────────────────┘      │
 └────────────────────────────────────────────────────┘
```

> 💡 `pool-1-thread-1`이라는 이름은 기본 `ThreadFactory`가 붙인다. 첫 글에서 "실무에서는 스레드 이름을 반드시 지어준다"고 했는데, 스레드 풀에서는 **`ThreadFactory`를 직접 넘겨** 의미 있는 이름을 붙인다.

## 3.4 생성자 매개변수

| 매개변수 | 의미 |
| --- | --- |
| `corePoolSize` | 기본으로 유지하는 스레드 수. **0개로 시작**해서 작업이 올 때 만든다 |
| `maximumPoolSize` | 최대 스레드 수 |
| `keepAliveTime`, `unit` | core를 **초과**해서 만든 스레드가, 일이 없을 때 살아있는 시간 |
| `workQueue` | 작업을 보관할 `BlockingQueue` |

# 4. ⭐ 스레드가 늘어나는 정확한 규칙

매개변수를 봤으니 **어떤 순서로 쓰이는지**를 정확히 알아야 한다. 실무에서 가장 많이 오해하는 부분이다.

## 4.1 규칙

```text
execute(task) 호출
   │
   ├─ ① 스레드 수 < corePoolSize ?
   │        → 새 스레드 생성  (⚠️ 놀고 있는 스레드가 있어도 새로 만든다)
   │
   ├─ ② 큐에 넣을 수 있나?
   │        → 큐에 넣는다
   │
   ├─ ③ 스레드 수 < maximumPoolSize ?
   │        → 초과 스레드 생성
   │
   └─ ④ 전부 불가
            → 거절 (RejectedExecutionException)
```

> ⭐ **큐가 가득 차기 전에는 core를 넘는 스레드가 생기지 않는다.**
> "부하가 오면 max까지 늘어나겠지"가 아니라, **"큐가 넘쳐야 늘어난다"**다.

## 4.2 ⚠️ 무한 큐를 쓰면 maximumPoolSize는 장식이다

```java
new ThreadPoolExecutor(
    10, 100,                        // core 10, max 100 으로 설정했지만
    60, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>()     // ⚠️ 크기 = Integer.MAX_VALUE
);
// → 큐가 절대 가득 차지 않는다
// → ③ 단계에 도달하지 못한다
// → 스레드는 영원히 10개. max=100 은 의미가 없다
```

이전 글에서 **"`LinkedBlockingQueue`의 기본 크기는 무한이다"**라고 경고했던 게 여기서 터진다.

## 4.3 ⚠️ newFixedThreadPool의 정체

편하게 쓰는 팩토리 메서드가 사실 이렇게 생겼다.

```java
Executors.newFixedThreadPool(n)
    == new ThreadPoolExecutor(n, n, 0, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<>())
                                                              // ⚠️ 무한 큐
```

| 장점 | 위험 |
| --- | --- |
| 스레드 수가 n개로 고정 → CPU·메모리 예측 가능 | 작업이 처리 속도보다 빨리 쌓이면 **큐가 무한히 커진다** |
| 설정이 간단 | 결국 **OOM**. 응답 지연도 끝없이 늘어난다 |

실무에서는 `ThreadPoolExecutor`를 **직접 생성하고 큐 크기를 명시**하는 경우가 많다. 이전 글의 **"한정된 버퍼가 백프레셔를 만든다"**가 스레드 풀에서도 그대로 적용된다.

# 5. Callable과 Future

## 5.1 Runnable로 결과를 받으려면

```java
static class MyRunnable implements Runnable {
    int value;                              // ⚠️ 결과를 담을 필드

    @Override
    public void run() {
        sleep(2000);
        value = new Random().nextInt(10);
    }
}

MyRunnable task = new MyRunnable();
Thread thread = new Thread(task);
thread.start();
thread.join();                              // 끝날 때까지 기다리고
int result = task.value;                    // 필드에서 꺼낸다
```

**결과를 작업 객체 어딘가에 저장해야 한다.** `return`으로 받을 수 있으면 좋을 텐데.

## 5.2 Callable

```java
public interface Callable<V> {
    V call() throws Exception;
}
```

| | `Runnable` | `Callable<V>` |
| --- | --- | --- |
| 메서드 | `void run()` | `V call() throws Exception` |
| 반환값 | ❌ | ✅ **제네릭 타입 V** |
| 체크 예외 | ❌ | ✅ **던질 수 있다** |

## 5.3 사용

```java
ExecutorService es = Executors.newFixedThreadPool(1);
Future<Integer> future = es.submit(new MyCallable());
Integer result = future.get();              // ⭐ 결과를 "받는다"
log("result value = " + result);
es.close();
```

```java
static class MyCallable implements Callable<Integer> {
    @Override
    public Integer call() throws Exception {
        sleep(2000);
        return new Random().nextInt(10);    // ⭐ 그냥 return
    }
}
```

## 5.4 같은 문제, 두 가지 풀이

이전 글의 1~100 합계를 두 방식으로 비교하면 차이가 선명하다.

| | `Thread` + `join()` | `ExecutorService` + `Future` |
| --- | --- | --- |
| 결과 전달 | 공유 필드 `task.result` | ⭐ **반환값** `future.get()` |
| 기다리기 | `thread.join()` | `future.get()` |
| 체크 예외 | `try-catch` 필수 | ⭐ **`throws Exception`으로 그냥 던짐** |
| 예외 전달 | ❌ main이 못 받음 | ⭐ `ExecutionException`으로 받음 |
| 스레드 관리 | 직접 생성·시작 | ⭐ 풀이 알아서 |
| 코드의 느낌 | 스레드를 다룬다 | **함수를 호출하는 것 같다** |

멀티스레드 코드인데 **싱글스레드처럼 작성하는 느낌**이다. 작업을 던지고, 결과를 받으면 된다.

# 6. Future의 동작 원리

## 6.1 왜 결과 대신 Future를 주나

`submit()`을 호출하는 순간 작업은 **아직 실행되지 않았을 수도 있다.** 풀의 다른 스레드가 **미래의 어느 시점에** 실행하므로, 결과를 즉시 돌려주는 건 불가능하다.

그래서 **결과를 나중에 받을 수 있는 "교환권"**을 준다. 그게 `Future` — **전달한 작업의 미래**다.

## 6.2 내부 흐름

```text
① es.submit(taskA)
        │
        ▼
② FutureTask 생성 (taskA 를 감싼다)
   ┌─────────────────────────────┐
   │ FutureTask                   │
   │   callable = taskA           │
   │   state    = NEW             │   ← Not completed
   │   outcome  = (없음)           │
   └─────────────────────────────┘
        │
        ├──▶ ③ 블로킹 큐에 넣는다 (⭐ taskA 가 아니라 FutureTask 를!)
        │
        └──▶ ④ FutureTask 참조를 즉시 반환  ← submit() 은 여기서 끝
                    │
                    ▼
               요청 스레드는 계속 자기 일을 한다

   ... 그 사이 ...

⑤ 풀 스레드가 큐에서 FutureTask 를 꺼내 run() 실행
        │
        ▼
⑥ FutureTask.run() → taskA.call() → 결과
        │
        ▼
⑦ outcome = 결과, state = COMPLETED
        │
        ▼
⑧ get() 으로 대기 중인 스레드가 있으면 깨운다
```

실제 로그로 보면 **같은 객체의 상태가 바뀐 것**이 보인다.

```text
future 즉시 반환, future = FutureTask@6576fe71[Not completed, task = ...MyCallable@7eda2dbb]
...
future 완료, future = FutureTask@6576fe71[Completed normally]
```

## 6.3 FutureTask가 큐에 들어갈 수 있는 이유

```text
FutureTask implements RunnableFuture
RunnableFuture extends Runnable, Future
```

**`FutureTask`는 `Runnable`이면서 `Future`다.** 스레드 풀 입장에서는 그냥 `Runnable` 하나를 실행하는 것이고, 요청 스레드 입장에서는 `Future`로 결과를 기다린다. 한 객체가 **양쪽에 다른 얼굴**을 보여주는 셈이다.

## 6.4 get()을 호출하면

| Future 상태 | `get()`의 동작 |
| --- | --- |
| 완료 | **즉시** 결과 반환 |
| 미완료 | 완료될 때까지 **블로킹** (`RUNNABLE` → `WAITING`) |

락을 기다릴 때처럼 멈추지만, 상태는 `BLOCKED`가 아니라 **`WAITING`**이다. 내부적으로 이전 글의 **`LockSupport.park()`**를 쓰기 때문이다.

```text
main:    future.get() ──▶ LockSupport.park()   WAITING
                                    ▲
pool-1:  call() 완료 → 결과 저장 → LockSupport.unpark(main)
```

`Thread.join()`, `Future.get()`처럼 다른 작업이 끝날 때까지 호출한 스레드를 멈추게 하는 메서드를 **블로킹 메서드**라고 한다.

## 6.5 ⭐ Future.get()도 가시성을 보장한다

이전 글에서 **"`join()`은 기다림만 주는 게 아니라 가시성도 준다"**고 했다. `Future.get()`도 마찬가지다.

```text
submit() 이전의 요청 스레드 작업
        │  happens-before
        ▼
작업(call) 안의 모든 동작
        │  happens-before
        ▼
future.get() 반환 이후의 요청 스레드 작업
```

그래서 `call()` 안에서 만든 객체를 `get()`으로 받으면, **그 객체의 내부 상태까지 전부 최신으로 보인다.** `volatile`을 붙일 필요가 없다.

# 7. ⭐ 왜 submit과 get을 분리했나

처음 보면 이런 의문이 든다.

> "그냥 `submit()`에서 바로 결과를 반환하면 안 되나? 어차피 `get()`에서 블로킹될 텐데?"

## 7.1 만약 submit이 결과를 바로 반환한다면

```text
시간 ──────────────────────────────────────────▶
        0s          1s          2s          3s          4s

main   │ submit(task1) 블로킹 ─────▶│ submit(task2) 블로킹 ─────▶│
pool-1 │■■■■■ task1 ■■■■■■■■■■■■■■│
pool-2 │   (놀고 있음)               │■■■■■ task2 ■■■■■■■■■■■■■■│

⚠️ 총 4초 — 스레드가 2개인데 하나씩만 일한다. 사실상 단일 스레드.
```

## 7.2 Future를 반환하니까

```text
시간 ──────────────────────────────────────────▶
        0s          1s          2s

main   │submit ×2│ get(f1) 대기 ───▶│get(f2) 즉시│
pool-1 │■■■■■ task1 ■■■■■■■■■■■■■■■│
pool-2 │■■■■■ task2 ■■■■■■■■■■■■■■■│

✅ 총 2초 — 두 작업이 동시에 돈다
```

`future1.get()`에서 2초를 기다리는 동안 task2도 이미 돌고 있었으므로, `future2.get()`은 **기다릴 필요 없이 즉시** 반환된다. 이전 글의 `join()`에서 정리한 **"대기 시간은 `t1 + t2`가 아니라 `max(t1, t2)`"**와 같은 원리다.

> ⭐ **submit은 "시작해줘", get은 "결과 줘"다.**
> 둘을 분리했기 때문에 **여러 작업을 먼저 다 시작시켜 놓고**, 결과는 필요할 때 모을 수 있다.

## 7.3 ⚠️ 잘못 쓰면 분리한 의미가 사라진다

```java
// ❌ 제출하자마자 기다림 — 4초
Future<Integer> future1 = es.submit(task1);
future1.get();                               // 여기서 2초 멈춤. task2 는 아직 제출도 안 됨
Future<Integer> future2 = es.submit(task2);
future2.get();

// ❌ 같은 실수의 축약형 — 4초
es.submit(task1).get();
es.submit(task2).get();

// ✅ 제출은 몰아서, 기다림은 나중에 — 2초
Future<Integer> future1 = es.submit(task1);
Future<Integer> future2 = es.submit(task2);
Integer r1 = future1.get();
Integer r2 = future2.get();
```

## 7.4 1~100 합계

```java
ExecutorService es = Executors.newFixedThreadPool(2);
Future<Integer> future1 = es.submit(new SumTask(1, 50));
Future<Integer> future2 = es.submit(new SumTask(51, 100));

Integer result1 = future1.get();
Integer result2 = future2.get();
log("result = " + (result1 + result2));     // 5050

es.close();
```

```java
static class SumTask implements Callable<Integer> {
    private final int startValue;
    private final int endValue;

    @Override
    public Integer call() throws Exception {
        log("작업 시작");
        Thread.sleep(2000);                  // ⭐ try-catch 없이 그냥 씀
        int sum = 0;
        for (int i = startValue; i <= endValue; i++) sum += i;
        log("작업 완료 result = " + sum);
        return sum;
    }
}
```

```text
16:30:25.863 [pool-1-thread-1] 작업 시작
16:30:25.863 [pool-1-thread-2] 작업 시작
16:30:27.879 [pool-1-thread-1] 작업 완료 result = 1275
16:30:27.879 [pool-1-thread-2] 작업 완료 result = 3775
16:30:27.885 [     main] result = 5050
```

스레드에 대한 코드가 한 줄도 없다. 그리고 `call()`이 `throws Exception`이라 `Thread.sleep()`을 `try-catch` 없이 쓸 수 있다.

# 8. Future API와 취소

## 8.1 인터페이스

```java
public interface Future<V> {
    boolean cancel(boolean mayInterruptIfRunning);
    boolean isCancelled();
    boolean isDone();

    V get() throws InterruptedException, ExecutionException;
    V get(long timeout, TimeUnit unit)
        throws InterruptedException, ExecutionException, TimeoutException;

    // Java 19+
    enum State { RUNNING, SUCCESS, FAILED, CANCELLED }
    default State state() { ... }
    default V resultNow() { ... }
    default Throwable exceptionNow() { ... }
}
```

| 메서드 | 기능 | 비고 |
| --- | --- | --- |
| `get()` | 완료까지 대기 후 결과 | ⚠️ 무한 대기 가능 |
| `get(timeout, unit)` | 제한 시간만큼만 대기 | 초과 시 `TimeoutException` |
| `cancel(bool)` | 취소 시도 | 8.3 참고 |
| `isCancelled()` | 취소됐나 | |
| `isDone()` | 끝났나 | ⚠️ 8.2 참고 |
| `state()` | `RUNNING` / `SUCCESS` / `FAILED` / `CANCELLED` | Java 19+ |
| `resultNow()` | 완료된 결과를 **블로킹 없이** 꺼냄 | Java 19+ |
| `exceptionNow()` | 실패한 예외를 **블로킹 없이** 꺼냄 | Java 19+ |

> 💡 **`get(timeout, unit)`을 기본으로 쓰는 습관을 들이자.** 인자 없는 `get()`은 작업이 영원히 안 끝나면 요청 스레드도 영원히 멈춘다. `join()` 대신 `join(ms)`를 쓰던 것과 같은 이유다.

## 8.2 ⚠️ isDone()은 "성공"이 아니다

| 끝난 방식 | `isDone()` | `isCancelled()` | `state()` |
| --- | --- | --- | --- |
| 정상 완료 | `true` | `false` | `SUCCESS` |
| 예외로 종료 | ⚠️ **`true`** | `false` | `FAILED` |
| 취소됨 | ⚠️ **`true`** | `true` | `CANCELLED` |

**`isDone() == true`를 보고 "성공했구나"라고 판단하면 안 된다.** 정상 완료, 취소, 예외 모두 `true`다. 성공 여부는 `get()`에서 예외가 나는지 보거나, Java 19+라면 `state()`로 확인한다.

## 8.3 cancel(false) — 결과를 버린다

1초마다 "작업 중"을 찍는 작업을 3초 후에 취소해보자.

```java
Future<String> future = es.submit(new MyTask());
sleep(3000);
boolean cancelResult = future.cancel(false);
future.get();                                       // → CancellationException
```

```text
[pool-1-thread-1] 작업 중: 0
[pool-1-thread-1] 작업 중: 1
[pool-1-thread-1] 작업 중: 2
[     main] future.cancel(false) 호출
[     main] cancel(false) result: true
[     main] Future는 이미 취소되었습니다.
[pool-1-thread-1] 작업 중: 3        ⚠️ 작업은 계속 돈다
[pool-1-thread-1] 작업 중: 4
...
[pool-1-thread-1] 작업 중: 9
```

**`cancel(false)`는 "결과를 받지 않겠다"는 선언일 뿐 작업을 멈추지 않는다.** Future는 취소 상태가 되고 `get()`은 `CancellationException`을 던지지만, 풀 스레드는 끝까지 일한다. `join(ms)` 타임아웃처럼 **기다리기를 포기할 뿐 상대를 중단시키지 않는다.**

## 8.4 cancel(true) — 인터럽트를 건다

```text
[pool-1-thread-1] 작업 중: 2
[     main] future.cancel(true) 호출
[pool-1-thread-1] 인터럽트 발생           ⭐ 작업이 멈췄다
[     main] cancel(true) result: true
[     main] Future는 이미 취소되었습니다.
```

> ⭐ **`cancel(true)`의 정체는 결국 `Thread.interrupt()`다.**
> 인터럽트 글에서 정리한 원칙이 그대로 적용된다.

| 작업이 이렇게 되어 있다면 | `cancel(true)` 결과 |
| --- | --- |
| `sleep()` / `wait()` / `take()` 등으로 대기 중 | ✅ `InterruptedException`으로 깨어남 |
| 루프에서 `Thread.interrupted()`를 확인 | ✅ 멈춤 |
| CPU 연산 루프만 돌고 확인 안 함 | ❌ **안 멈춘다** |
| 블로킹 I/O (`socket.read()`) 중 | ❌ **안 멈춘다** |
| `InterruptedException`을 잡고 **삼킨다** | ❌ **안 멈춘다** |

**취소는 협력적이다.** 작업 쪽에서 인터럽트에 반응하도록 짜여 있어야 한다.

> 💡 작업이 `catch`에서 `return "Interrupted"`를 해도 **이 값은 아무도 받지 못한다.** Future가 이미 `CANCELLED`로 확정됐기 때문에 뒤늦은 반환값은 무시되고, `get()`은 여전히 `CancellationException`이다.

# 9. 예외 처리

## 9.1 ExecutionException

```java
static class ExCallable implements Callable<Integer> {
    @Override
    public Integer call() throws Exception {
        throw new IllegalStateException("ex!");
    }
}

try {
    future.get();
} catch (ExecutionException e) {
    log("e = " + e);
    log("cause = " + e.getCause());          // ⭐ 원본 예외
}
```

```text
[     main] future.get() 호출 시도, future.state(): FAILED
[     main] e = java.util.concurrent.ExecutionException: java.lang.IllegalStateException: ex!
[     main] cause = java.lang.IllegalStateException: ex!
```

```text
작업 스레드: call() 에서 IllegalStateException 발생
                   │
                   ▼
      FutureTask 가 잡아서 내부에 저장 (state = FAILED)
                   │
                   ▼
요청 스레드: get() 호출 → ExecutionException 으로 감싸서 던짐
                   │
                   ▼
            e.getCause() → 원본 IllegalStateException
```

## 9.2 ⭐ 첫 글의 한계가 여기서 풀린다

첫 글에서 이렇게 정리했다.

> "`run()`에서 예외가 나면 그 스레드만 죽고, **main은 이 예외를 절대 catch할 수 없다** — 스택이 다르므로."

`Future`가 이 문제를 해결한다. 다른 스레드의 스택에서 터진 예외를 **`FutureTask`가 붙잡아 보관**했다가, **요청 스레드의 `get()` 호출 시점에 다시 던져준다.** 스택이 달라서 전달할 길이 없던 예외에 **우회로**를 만든 것이다.

## 9.3 ⚠️ execute()와 submit()의 예외는 완전히 다르게 처리된다

실무에서 정말 많이 당하는 함정이다.

```java
es.execute(() -> { throw new RuntimeException("펑"); });
es.submit(() -> { throw new RuntimeException("펑"); });
```

| | `execute(Runnable)` | `submit(...)` |
| --- | --- | --- |
| 예외 발생 시 | 스레드 밖으로 전파 | ⭐ **Future 안에 저장** |
| 콘솔 출력 | ✅ 스택 트레이스가 찍힌다 | ❌ **아무것도 안 찍힌다** |
| 풀 스레드 | 죽고, 풀이 **새 스레드로 교체** | 멀쩡히 계속 쓰임 |
| 예외를 확인하는 법 | `UncaughtExceptionHandler` | `future.get()` |

> ⚠️ **`submit()`으로 제출하고 `get()`을 안 부르면, 예외가 조용히 사라진다.**
> 로그 한 줄 없이 작업이 실패해 있는 상황이 된다. 결과가 필요 없는 작업이라도 `submit()`을 썼다면 `get()`으로 확인하거나, 작업 안에서 직접 `try-catch`로 로그를 남겨야 한다.

# 10. invokeAll과 invokeAny

## 10.1 예제 작업

```java
public class CallableTask implements Callable<Integer> {

    private final String name;
    private int sleepMs = 1000;

    public CallableTask(String name) { this.name = name; }
    public CallableTask(String name, int sleepMs) { this.name = name; this.sleepMs = sleepMs; }

    @Override
    public Integer call() throws Exception {
        log(name + "실행");
        sleep(sleepMs);          // 인터럽트되면 "인터럽트 발생, ..." 로그를 남기는 유틸
        log(name + "완료");
        return sleepMs;
    }
}
```

## 10.2 invokeAll — 전부 기다린다

```java
List<CallableTask> tasks = List.of(
        new CallableTask("task1", 1000),
        new CallableTask("task2", 2000),
        new CallableTask("task3", 3000));

List<Future<Integer>> futures = es.invokeAll(tasks);   // ⭐ 여기서 3초 블로킹
for (Future<Integer> future : futures) {
    log("value = " + future.get());                    // 이미 끝났으니 즉시 반환
}
```

```text
[pool-1-thread-1] task1실행
[pool-1-thread-2] task2실행
[pool-1-thread-3] task3실행
[pool-1-thread-1] task1완료
[pool-1-thread-2] task2완료
[pool-1-thread-3] task3완료          ← 가장 느린 작업이 끝나야
[     main] value = 1000            ← 그제서야 반환
[     main] value = 2000
[     main] value = 3000
```

- `invokeAll()`이 반환한 시점에는 모든 Future가 완료 상태라 `get()`은 블로킹하지 않는다. 다만 **작업이 예외로 끝났다면 `get()`에서 `ExecutionException`이 여전히 나온다.**
- 타임아웃 버전 `invokeAll(tasks, timeout, unit)`은 시간이 초과되면 **완료되지 않은 작업을 취소**하고 반환한다.

## 10.3 invokeAny — 첫 성공만 받는다

```java
Integer value = es.invokeAny(tasks);
```

```text
[pool-1-thread-1] task1실행
[pool-1-thread-2] task2실행
[pool-1-thread-3] task3실행
[pool-1-thread-1] task1완료
[pool-1-thread-2] 인터럽트 발생, sleep interrupted     ⭐ 나머지는 취소
[pool-1-thread-3] 인터럽트 발생, sleep interrupted
[     main] value = 1000
```

- 정확히는 **"가장 먼저 완료된"이 아니라 "가장 먼저 성공한"** 작업의 결과를 돌려준다. 가장 빠른 작업이 예외로 끝나면 무시하고 다음 성공을 기다린다. 전부 실패하면 `ExecutionException`이다.
- 나머지 작업이 "인터럽트 발생"을 찍은 건 `invokeAny()`가 내부적으로 **`cancel(true)`**를 호출하기 때문이다.
- **용도**: 같은 데이터를 여러 서버에 동시에 요청하고 **가장 빨리 온 응답만 쓰는** 경우.

| | `invokeAll` | `invokeAny` |
| --- | --- | --- |
| 기다리는 대상 | **전부** | **첫 성공 하나** |
| 반환 | `List<Future<T>>` | `T` (결과 그 자체) |
| 나머지 작업 | — | ⭐ **취소** (`cancel(true)`) |
| 걸리는 시간 | 가장 **느린** 작업 | 가장 **빠른 성공** 작업 |

# 11. ⚠️ 스레드 풀은 반드시 닫아야 한다

## 11.1 안 닫으면 프로그램이 끝나지 않는다

```java
public static void main(String[] args) {
    ExecutorService es = Executors.newFixedThreadPool(1);
    Future<String> future = es.submit(new MyTask());
    ...
    // ⚠️ es.close() 를 빠뜨리면?
}
```

**main이 끝나도 프로그램이 종료되지 않는다.** 첫 글에서 정리한 규칙 때문이다.

> **사용자 스레드가 하나라도 남아 있으면 JVM은 종료되지 않는다.**

```text
main 종료
   │
   ▼
pool-1-thread-1 은? → 사용자 스레드 (기본 ThreadFactory 는 non-daemon 으로 만든다)
   │
   ▼
할 일이 없으니 BlockingQueue.take() 에서 WAITING
   │
   ▼
⚠️ 영원히 기다린다 → JVM 이 끝나지 않는다
```

`newFixedThreadPool`의 core 스레드는 **일이 없어도 사라지지 않는다**(keepAliveTime은 core 초과분에만 적용된다). 그래서 명시적으로 닫아야 한다.

## 11.2 닫는 방법

**Java 19+**

```java
// ✅ try-with-resources — AutoCloseable 이므로
try (ExecutorService es = Executors.newFixedThreadPool(2)) {
    Future<Integer> f = es.submit(task);
    log(f.get());
}   // ⭐ 자동으로 close()
```

**Java 18 이하**

```java
es.shutdown();                                   // 새 작업 거부, 기존 작업은 계속
try {
    if (!es.awaitTermination(10, TimeUnit.SECONDS)) {
        es.shutdownNow();                        // 실행 중인 작업에 interrupt
    }
} catch (InterruptedException e) {
    es.shutdownNow();
    Thread.currentThread().interrupt();          // ⭐ 인터럽트 상태 복원
}
```

| 메서드 | 새 작업 | 큐의 작업 | 실행 중 작업 | 기다리나 |
| --- | --- | --- | --- | --- |
| `shutdown()` | 거부 | 처리함 | 계속 | ❌ 즉시 반환 |
| `shutdownNow()` | 거부 | **버리고 반환** | `interrupt()` | ❌ 즉시 반환 |
| `awaitTermination()` | — | — | — | ✅ 종료까지 대기 |
| `close()` (19+) | 거부 | 처리함 | 계속 | ✅ **끝날 때까지** |

# 헷갈리기 쉬운 포인트

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | core를 넘으면 바로 max까지 스레드가 늘어난다 | **큐가 가득 차야** 늘어난다 |
| 2 | `newFixedThreadPool`은 안전하다 | **무한 큐**라 작업이 쌓이면 OOM |
| 3 | 놀고 있는 스레드가 있으면 재사용한다 | core 미만이면 **새로 만든다** |
| 4 | `submit()`이 작업을 실행한다 | **큐에 넣고 Future를 즉시 반환**할 뿐 |
| 5 | `get()` 대기 중이면 `BLOCKED`다 | **`WAITING`** (`LockSupport.park`) |
| 6 | `submit(t).get()`도 병렬이다 | **순차 실행**이 된다. 제출을 먼저 몰아야 함 |
| 7 | `isDone()`이 `true`면 성공이다 | **예외·취소도 `true`** |
| 8 | `cancel()`하면 작업이 멈춘다 | `false`는 **계속 돈다**. `true`도 **협력해야** 멈춤 |
| 9 | `submit()`의 예외는 콘솔에 찍힌다 | **`get()`을 안 부르면 사라진다** |
| 10 | main이 끝나면 풀도 끝난다 | 풀 스레드는 **사용자 스레드**. 안 닫으면 안 끝남 |

```text
                         ExecutorService
 ┌──────────────────────────────────────────────────────────┐
 │                                                          │
 │  submit(Callable) ─▶ FutureTask 로 감싸서 ─▶ BlockingQueue │
 │        │                                       │         │
 │        │ 즉시 반환                       take() │         │
 │        ▼                                       ▼         │
 │     Future ◀──── 결과 / 예외를 저장 ──── 풀 스레드 (재사용) │
 │        │                                                 │
 └────────┼─────────────────────────────────────────────────┘
          │
      get()  ─ 완료: 즉시 반환
             ─ 미완료: WAITING 으로 대기
             ─ 실패: ExecutionException (getCause 로 원본)
```

## 핵심 개념

| 개념 | 한 줄 요약 |
| --- | --- |
| **스레드 풀** | 스레드를 **재사용**하고 **수를 제한**한다. 정체는 생산자-소비자 |
| **놀고 있는 풀 스레드** | `BlockingQueue.take()`에서 `WAITING` |
| **스레드 생성 순서** | core까지 생성 → **큐** → 큐가 차야 max까지 → 거절 |
| **Callable** | 반환값 + 체크 예외 |
| **Future** | 작업의 **미래 결과를 담는 교환권** (구현체 `FutureTask`) |
| **submit / get** | submit은 **즉시**, get은 **블로킹** |
| **예외** | `ExecutionException`으로 감싸져 `get()`에서 나온다 |
| **cancel(true)** | 결국 `interrupt()`. 작업이 협력해야 멈춘다 |
| **invokeAll / Any** | 전부 기다림 / **첫 성공**만 받고 나머지 취소 |
| **종료** | 풀 스레드는 사용자 스레드 → **반드시 `close()`** |

## 이것만은 기억

> **① 제출은 몰아서, `get()`은 나중에** — 그래야 병렬로 돈다
> **② `submit()`의 예외는 `get()`을 부르기 전까지 보이지 않는다**
> **③ 무한 큐를 쓰면 `maximumPoolSize`는 동작하지 않는다**
> **④ 스레드 풀은 반드시 닫는다**
