# [Java] 스레드 풀 전략과 거절 정책, 우아하게 종료하기

스레드 풀을 만들 때 가장 흔히 쓰는 코드는 이것이다.

```java
ExecutorService es = Executors.newFixedThreadPool(10);
```

편하고, 스레드 수가 고정이라 안정적으로 보인다. 그런데 이벤트가 대성공해서 요청이 폭증하면 **CPU와 메모리는 여유로운데 사용자만 점점 느려지는** 이상한 장애가 난다.

반대로 `newCachedThreadPool()`을 쓰면 요청이 오는 족족 스레드를 만들어 빠르게 처리하는데, 같은 상황에서 **시스템 전체가 멈춘다.**

두 장애의 원인은 사실 하나다. 이 글은 그 원인과, 스레드 풀을 **어떻게 설계하고 어떻게 거절하고 어떻게 종료할지**에 대한 이야기다.

---

## 다루는 내용

- 우아한 종료(graceful shutdown)
- ⚠️ `close()`와 `isShutdown()`의 오해
- 스레드 수가 늘고 줄어드는 실제 과정
- 고정 풀 / 캐시 풀 / 사용자 정의 풀 전략
- ⭐ 두 기본 전략의 공통 문제
- 거절 정책 4가지
- ⚠️ 영원히 끝나지 않는 Future

# 1. 우아한 종료

## 1.1 왜 필요한가

서버를 재시작하는데 고객의 주문이 처리되는 도중이라면? 진행 중인 주문은 끝까지 처리하고, 새 주문만 받지 않은 채 종료하는 게 맞다. 이것을 **우아한 종료(graceful shutdown)**라고 한다.

## 1.2 메서드 정리

| 메서드 | 새 작업 | 큐의 작업 | 실행 중 작업 | 호출 스레드 |
| --- | --- | --- | --- | --- |
| `shutdown()` | 거부 | ✅ **처리한다** | 계속 | 즉시 반환 (논블로킹) |
| `shutdownNow()` | 거부 | ❌ **꺼내서 반환** | `interrupt()` | 즉시 반환 (논블로킹) |
| `awaitTermination(t)` | — | — | — | ⭐ **최대 t 동안 대기** (블로킹) |
| `close()` (Java 19+) | 거부 | ✅ 처리한다 | 계속 | ⭐ **끝날 때까지 대기** (블로킹) |

| 상태 확인 | 의미 |
| --- | --- |
| `isShutdown()` | **종료 요청이 들어왔나** |
| `isTerminated()` | **모든 작업이 끝나고 실제로 종료됐나** |

## 1.3 ⚠️ isShutdown()은 "종료됐나"가 아니다

```java
es.shutdown();
es.isShutdown();     // ✅ true — 즉시 true 가 된다
es.isTerminated();   // ⚠️ false — 작업은 아직 돌고 있을 수 있다
```

이름 때문에 헷갈리기 쉽다. `isShutdown()`은 **종료 요청이 들어왔는지**만 알려준다. 이게 `true`라고 자원을 정리해버리면 **아직 실행 중인 작업이 자원을 잃는다.** 실제로 끝났는지는 `isTerminated()`나 `awaitTermination()`으로 확인해야 한다.

## 1.4 ⚠️ close()는 시한이 없다

Java 19부터 `ExecutorService`가 `AutoCloseable`이 되면서 `close()`가 생겼다. `shutdown()`과 비슷해 보이지만 **블로킹 메서드**다. 실제 JDK 구현을 보면 이렇다.

```java
default void close() {
    boolean terminated = isTerminated();
    if (!terminated) {
        shutdown();
        boolean interrupted = false;
        while (!terminated) {                              // ⭐ 끝날 때까지 무한 반복
            try {
                terminated = awaitTermination(1L, TimeUnit.DAYS);   // 하루 단위로 확인할 뿐
            } catch (InterruptedException e) {
                if (!interrupted) {
                    shutdownNow();                         // ⭐ 인터럽트됐을 때만 강제 종료
                    interrupted = true;
                }
            }
        }
        if (interrupted) {
            Thread.currentThread().interrupt();            // ⭐ 인터럽트 상태 복원
        }
    }
}
```

`awaitTermination(1L, TimeUnit.DAYS)` 때문에 "하루 기다리고 강제 종료"로 읽기 쉬운데, **하루는 마감 시한이 아니라 확인 주기다.** 하루가 지나도 안 끝나면 **또 하루를 기다린다.** `shutdownNow()`는 `close()`를 호출한 스레드가 **인터럽트됐을 때만** 불린다.

> ⚠️ **그래서 `close()`는 무한히 블로킹될 수 있다.**
> `while (true) { }`처럼 끝나지 않는 작업이 하나라도 있으면 `close()`는 영원히 반환되지 않는다. **시한이 있는 종료가 필요하면 직접 구현해야 한다.**

마지막 줄의 `Thread.currentThread().interrupt()`는 인터럽트 글에서 정리한 **"잡았으면 복원하라"**를 JDK가 그대로 지키는 모습이다.

## 1.5 shutdownNow()는 버리는 게 아니라 돌려준다

```java
List<Runnable> notExecuted = es.shutdownNow();
log("실행되지 못한 작업 " + notExecuted.size() + "개");   // 로그를 남기거나 저장해 복구
```

큐에 있던 작업을 실행하지 않고 **목록으로 돌려준다.** 로그로 남기거나, 다음 실행 때 재처리하도록 저장할 수 있다.

# 2. 우아한 종료 구현

## 2.1 코드

`shutdown()`으로 우아하게 요청하고, 10초 안에 안 끝나면 `shutdownNow()`로 강제 종료하는 방식이다.

```java
public class ExecutorShutdownMain {

    public static void main(String[] args) {
        ExecutorService es = Executors.newFixedThreadPool(2);
        es.execute(new RunnableTask("taskA"));
        es.execute(new RunnableTask("taskB"));
        es.execute(new RunnableTask("taskC"));
        es.execute(new RunnableTask("longTask", 100_000));   // 100초
        printState(es);
        log("== shutdown 시작 ==");

        shutdownAndAwaitTermination(es);

        log("== shutdown 완료 ==");
    }

    private static void shutdownAndAwaitTermination(ExecutorService es) {
        es.shutdown();                                        // ① 우아하게 요청
        try {
            if (!es.awaitTermination(10, TimeUnit.SECONDS)) { // ② 10초 기다림
                log("서비스 정상 종료 실패 -> 강제 종료 시도");
                es.shutdownNow();                             // ③ 강제 종료
                if (!es.awaitTermination(10, TimeUnit.SECONDS)) {   // ④ 또 10초
                    log("서비스가 종료되지 않았습니다.");
                }
            }
        } catch (InterruptedException e) {
            es.shutdownNow();
            Thread.currentThread().interrupt();               // ⭐ 인터럽트 상태 복원
        }
    }
}
```

## 2.2 실행 결과 읽기

```text
16:15:00.408 [     main] [pool=2, active=2, queuedTasks=2, completedTask=0]
16:15:00.411 [     main] == shutdown 시작 ==
16:15:01.423 [pool-1-thread-1] taskA 완료
16:15:01.423 [pool-1-thread-2] taskB 완료
16:15:01.424 [pool-1-thread-2] longTask 시작      ⭐ shutdown 이후인데 시작됐다
16:15:01.424 [pool-1-thread-1] taskC 시작
16:15:02.436 [pool-1-thread-1] taskC 완료
16:15:10.414 [     main] 서비스 정상 종료 실패 -> 강제 종료 시도
16:15:10.415 [pool-1-thread-2] 인터럽트 발생, sleep interrupted
16:15:10.417 [     main] == shutdown 완료 ==
Exception in thread "pool-1-thread-2" java.lang.RuntimeException: ... sleep interrupted
```

```text
시간 ──────────────────────────────────────────────────────▶
      0s       1s       2s                            10s

main  │shutdown()│←──────── awaitTermination(10s) ────────▶│shutdownNow()
                                                           │
thread-1 │■ A ■│■ C ■│  (대기)                             │
thread-2 │■ B ■│■■■■■■■■■■ longTask ■■■■■■■■■■■■■■■■■■■■■■■│💥 interrupt
                ▲
   ⭐ shutdown 은 "새 작업"만 거부한다. 이미 큐에 있던 C, longTask 는 실행된다
```

여기서 읽어낼 것이 세 가지다.

1. **`shutdown()` 이후에도 큐의 작업은 실행된다.** 호출 시점에 taskC와 longTask는 큐에 있었는데 둘 다 시작됐다. "새 작업을 받지 않는다"이지 "대기 중인 작업을 버린다"가 아니다.
2. **예외 스택 트레이스가 콘솔에 찍혔다.** `execute()`로 제출했기 때문이다. 지난 글에서 정리한 **"`execute()`는 예외가 찍히고, `submit()`은 Future에 삼켜진다"**가 그대로 보인다.
3. `== shutdown 완료 ==`가 스택 트레이스보다 먼저 찍힌 건, 로그(표준 출력)와 예외(표준 에러)가 **다른 스트림**이라 순서가 섞일 수 있기 때문이다.

## 2.3 shutdownNow() 다음에도 왜 기다리나

| 이유 | 예 |
| --- | --- |
| 인터럽트는 **요청**일 뿐이다 | 작업이 반응하는 데 시간이 걸린다 |
| 인터럽트 후 **정리 작업**이 있을 수 있다 | 파일 닫기, 트랜잭션 롤백 |
| 인터럽트에 **아예 반응하지 않는** 작업이 있다 | `while (true) { }`, 블로킹 I/O |

인터럽트 글에서 정리한 **"인터럽트가 통하지 않는 경우"**가 여기서 현실이 된다. 두 번째 대기마저 실패하면 로그를 남기는 게 최선이다. 그 스레드는 사용자 스레드라 **JVM도 끝나지 않는다.**

## 2.4 한 장으로

```text
shutdown()                  ← 새 작업 거부, 기존 작업은 계속
   │
awaitTermination(10초)
   │
   ├─ 끝남 ──────────────────────▶ ✅ 우아한 종료
   │
   └─ 안 끝남
        │
     shutdownNow()           ← 큐 비우고, 실행 중인 작업에 interrupt
        │
     awaitTermination(10초)
        │
        ├─ 끝남 ─────────────────▶ ⚠️ 강제 종료
        │
        └─ 안 끝남 ──────────────▶ 💀 로그 남기기 (인터럽트를 무시하는 작업)
```

# 3. 스레드 수가 늘고 줄어드는 과정

## 3.1 코드

지난 글에서 정리한 스레드 생성 규칙을 실제로 확인해보자. core 2, max 4, 큐 2로 작업 7개를 넣는다.

```java
ArrayBlockingQueue<Runnable> workQueue = new ArrayBlockingQueue<>(2);
ExecutorService es = new ThreadPoolExecutor(
        2,                           // core
        4,                           // max
        3000, TimeUnit.MILLISECONDS, // keepAlive
        workQueue                    // 크기 2
);

es.execute(new RunnableTask("task1"));
printState(es, "task1");
// ... task2 ~ task6 도 동일
try {
    es.execute(new RunnableTask("task7"));
} catch (RejectedExecutionException e) {
    log("task7 실행 거절 예외 발생: " + e);
}
```

상태 출력 유틸에 작업 이름을 받는 오버로드를 추가했다.

```java
public static void printState(ExecutorService executorService, String taskName) {
    if (executorService instanceof ThreadPoolExecutor poolExecutor) {
        int pool = poolExecutor.getPoolSize();
        int active = poolExecutor.getActiveCount();
        int queuedTasks = poolExecutor.getQueue().size();
        long completedTask = poolExecutor.getCompletedTaskCount();
        log(taskName + " -> [pool=" + pool + ", active=" + active + ", queuedTasks=" + queuedTasks +
                ", completedTask=" + completedTask + "]");
    } else {
        log(taskName + " -> " + executorService);
    }
}
```

## 3.2 작업마다 무슨 일이 일어났나

```text
task1 -> [pool=1, active=1, queuedTasks=0]
task2 -> [pool=2, active=2, queuedTasks=0]
task3 -> [pool=2, active=2, queuedTasks=1]
task4 -> [pool=2, active=2, queuedTasks=2]
task5 -> [pool=3, active=3, queuedTasks=2]     ⭐ 큐가 가득 차자 긴급 스레드
task6 -> [pool=4, active=4, queuedTasks=2]
task7 실행 거절 예외 발생: RejectedExecutionException
```

| 작업 | 판단 | 결과 |
| --- | --- | --- |
| task1 | 스레드 0 < core 2 | 스레드1 생성 |
| task2 | 스레드 1 < core 2 | 스레드2 생성 |
| task3 | core 가득 → 큐에 자리 있음 | 큐 `[3]` |
| task4 | 큐에 자리 있음 | 큐 `[3, 4]` |
| task5 | 큐 가득 → 스레드 2 < max 4 | ⭐ 스레드3 생성 → **task5 바로 실행** |
| task6 | 큐 가득 → 스레드 3 < max 4 | 스레드4 생성 → task6 바로 실행 |
| task7 | 큐 가득 + 스레드 4 = max | 💥 **거절** |

> ⭐ **큐가 가득 차야만 긴급 스레드가 생긴다.**
> 그리고 새로 만든 스레드는 큐 맨 앞의 task3이 아니라 **자기를 만들게 한 task5를 바로 실행한다.** 먼저 온 task3, task4가 나중에 온 task5, task6보다 늦게 시작된다.

## 3.3 근사값이 실제로 드러난 장면

```text
16:57:56.856 [pool-1-thread-1] task1 완료
16:57:56.871 [pool-1-thread-4] task6 완료
16:57:56.871 [pool-1-thread-2] task2 완료
16:57:56.871 [pool-1-thread-3] task5 완료
16:57:56.872 [     main] [pool=4, active=3, queuedTasks=0, completedTask=3]   ← ?
```

로그로 세어보면 이 시점에 **완료 4개**(task1, 6, 2, 5), **실행 중 2개**(task3, 4)다. 그런데 상태는 `active=3, completedTask=3`이다.

지난 글에서 `getActiveCount()`와 `getCompletedTaskCount()`가 **근사값**이라고 했는데, 그게 실제로 드러난 장면이다. task5가 "완료" 로그를 찍은 직후, 카운터를 갱신하기 직전에 조회가 끼어든 것이다. **모니터링용 수치로 로직을 짜면 안 되는 이유**다.

## 3.4 ⚠️ "초과 스레드"라는 종류는 없다

```text
16:57:59.882 [     main] == maximumPoolSize 대기 시간 초과 ==
16:57:59.882 [     main] [pool=2, active=0, queuedTasks=0, completedTask=6]   ← 4 → 2
```

keepAlive 3초가 지나 스레드가 2개로 줄었다. 여기서 오해하기 쉬운 점이 있다.

> ⚠️ **스레드에 "core 스레드", "초과 스레드"라는 꼬리표는 없다.**
> 풀은 **개수**만 본다. "지금 core보다 많으면, 누구든 keepAlive 동안 일이 없던 스레드가 종료된다."

이 로그의 타이밍으로 추론해보면 이렇다.

| 스레드 | 생성 순서 | 마지막 작업 종료 | 59.88 시점 대기 시간 | 결과 |
| --- | --- | --- | --- | --- |
| thread-1 | 기본 | 57.87 (task3) | 약 2초 | 생존 |
| thread-2 | ⚠️ **기본** | 56.87 (task2) | ⚠️ **약 3초** | ⚠️ **종료** |
| thread-3 | 초과 | 56.87 (task5) | 약 3초 | 종료 |
| thread-4 | ⚠️ **초과** | 57.89 (task4) | 약 2초 | ⚠️ **생존** |

**기본으로 만들어진 thread-2가 사라지고, 초과로 만들어진 thread-4가 살아남았을 가능성이 높다.** "긴급 스레드만 따로 퇴근한다"가 아니라 **"인원수가 core로 돌아올 때까지 오래 쉰 사람부터 퇴근한다"**다.

> 💡 `allowCoreThreadTimeOut(true)`로 설정하면 core 수 아래로도 줄어든다. 일이 없을 때 스레드를 0개까지 줄이고 싶을 때 쓴다.

## 3.5 스레드 미리 만들기

응답 시간이 중요한 서버라면, 첫 요청이 오기 전에 스레드를 미리 만들어둘 수 있다.

```java
ExecutorService es = Executors.newFixedThreadPool(1000);
ThreadPoolExecutor poolExecutor = (ThreadPoolExecutor) es;
poolExecutor.prestartAllCoreThreads();      // core 만큼 미리 생성
```

```text
[     main] [pool=1000, active=0, queuedTasks=0, completedTask=0]
```

| 메서드 | 동작 |
| --- | --- |
| `prestartAllCoreThreads()` | core 수만큼 **전부** 미리 생성 |
| `prestartCoreThread()` | **하나만** 미리 생성 |

> 💡 `newSingleThreadExecutor()`는 이 캐스팅이 안 된다(`ClassCastException`). `ThreadPoolExecutor`를 **래퍼로 한 번 감싸서** 반환하기 때문이다. 누군가 캐스팅해서 스레드 수를 늘려버리면 "단일 스레드"라는 약속이 깨지니까 막아둔 것이다.

# 4. 고정 풀 전략

## 4.1 기본 제공 전략

| 팩토리 | 실체 |
| --- | --- |
| `newSingleThreadExecutor()` | `(1, 1, 0L, ms, LinkedBlockingQueue)` + 래퍼 |
| `newFixedThreadPool(n)` | `(n, n, 0L, ms, LinkedBlockingQueue)` |
| `newCachedThreadPool()` | `(0, MAX_VALUE, 60s, SynchronousQueue)` |

`newSingleThreadExecutor()`는 간단히 쓰거나 테스트 용도로 쓴다.

## 4.2 동작

```java
ExecutorService es = Executors.newFixedThreadPool(2);
for (int i = 0; i <= 6; i++) {
    es.execute(new RunnableTask("task" + i));
    printState(es);
}
```

```text
[pool=1, active=1, queuedTasks=0]
[pool=2, active=2, queuedTasks=0]
[pool=2, active=2, queuedTasks=1]     ← 이후로는 큐만 늘어난다
[pool=2, active=2, queuedTasks=2]
[pool=2, active=2, queuedTasks=3]
[pool=2, active=2, queuedTasks=4]
[pool=2, active=2, queuedTasks=5]
```

**스레드는 2개에서 절대 늘지 않는다.** core = max이고 큐가 무한이라 긴급 스레드가 생길 여지가 없다.

## 4.3 장점이 단점이 되는 순간

| 장점 | 폭증 시 |
| --- | --- |
| 스레드 수 고정 → CPU·메모리 **예측 가능** | 스레드 수가 **병목**이 된다 |
| 큐가 무한 → 작업을 **다 받아준다** | 큐에 **수만 건이 쌓인다** |

```text
          서버 상태                       사용자 경험
  CPU     ▁▁▁▁▁▁▁▁  여유                  응답   ▁▂▃▅▆▇██  계속 느려짐
  메모리  ▁▁▁▁▂▂▃▃  서서히 증가              
  큐      ▁▂▃▅▆▇██  ⚠️ 폭증
```

서비스가 잘 돼서 사용자가 늘거나, 이벤트로 요청이 폭증하면 이렇게 된다. **서버 자원에는 여유가 있는데 사용자만 점점 느려진다.** 요청을 처리하는 속도보다 쌓이는 속도가 빠르기 때문이다.

> ⚠️ 그리고 느려지기만 하는 게 끝이 아니다. 큐에 쌓인 작업은 **힙 메모리를 차지한다.** 이 상태가 계속되면 결국 **`OutOfMemoryError`**로 서버가 죽는다.

# 5. 캐시 풀 전략

## 5.1 구성

```java
new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, TimeUnit.SECONDS, new SynchronousQueue<Runnable>());
```

| 설정 | 의미 |
| --- | --- |
| core = 0 | 기본 스레드가 **없다** |
| max = 무한 | 스레드를 **제한 없이** 만든다 |
| keepAlive = 60초 | 60초 동안 일이 없으면 종료 |
| `SynchronousQueue` | **저장 공간이 0인 큐.** 생산자와 소비자가 직접 거래 |

```text
[pool=1, active=1, queuedTasks=0]
[pool=2, active=2, queuedTasks=0]
[pool=3, active=3, queuedTasks=0]
[pool=4, active=4, queuedTasks=0]
[pool=5, active=5, queuedTasks=0]     ← 작업 수만큼 스레드가 생긴다. 큐는 항상 0
```

모든 요청을 대기 없이 바로 처리하므로 **매우 빠르고 유연하다.**

## 5.2 ⭐ 캐시 풀은 어떻게 스레드를 재사용하나

"놀고 있는 스레드가 있으면 재사용한다"는데, 큐도 없이 어떻게? **그 메커니즘이 `SynchronousQueue`**다.

```text
[ SynchronousQueue.offer() 의 규칙 ]

  대기 중인 소비자가 있다  → ✅ 그 소비자에게 직접 건네주고 성공
  대기 중인 소비자가 없다  → ❌ 저장할 곳이 없으니 즉시 실패
```

이걸 스레드 생성 규칙에 대입하면 이렇다.

```text
execute(task)
   │
   ├─ ① 스레드 < core(0) ?        → 절대 해당 안 됨
   │
   ├─ ② 큐에 넣을 수 있나?
   │      = "놀고 있는 스레드가 poll() 로 기다리고 있나?"
   │      ├─ 있다 → ✅ 그 스레드가 바로 받는다  ← ⭐ 이게 "재사용"
   │      └─ 없다 → ❌ 실패
   │
   └─ ③ 스레드 < max(무한) ?      → 항상 해당 → 새 스레드 생성
```

> ⭐ **`SynchronousQueue` 덕분에 ②단계가 "놀고 있는 스레드가 있나?"라는 질문으로 바뀐다.**
> 있으면 재사용하고 없으면 새로 만든다. 큐에 쌓이는 게 원천적으로 불가능하므로 대기 없이 즉시 처리된다.

## 5.3 단점

사용자가 점진적으로 늘 때는 초기에 문제가 잘 드러나지 않는다. 하지만 동시 요청 수에 비례해 스레드가 늘어나는 구조라, 폭증하면 이렇게 된다.

```text
요청 1만 건 동시 도착
   │
   ▼
스레드 1만 개 생성 시도
   │
   ├─ 스택 예약만 1만 × 1MB ≈ 10GB
   ├─ 컨텍스트 스위칭 폭증 → CPU 가 일보다 전환에 시간을 쓴다
   │
   ▼
💀 OutOfMemoryError: unable to create native thread
   또는 CPU 100% 로 시스템 전체 정지
```

`unable to create native thread`는 첫 글에서 **"`start()`를 10만 번 하면 나는 에러"**로 봤던 바로 그 에러다.

# 6. ⭐ 두 전략의 공통 문제 — 어딘가가 무한이다

두 전략의 단점을 나란히 놓으면 **같은 문제의 두 얼굴**이다.

| | 고정 풀 | 캐시 풀 |
| --- | --- | --- |
| 스레드 | 유한 (n개) | ⚠️ **무한** |
| 큐 | ⚠️ **무한** | 0 |
| 폭증 시 쌓이는 것 | **작업** | **스레드** |
| 증상 | 응답 지연 → OOM | 자원 고갈 → 시스템 정지 |
| 거절 | ❌ 절대 안 한다 | ❌ 절대 안 한다 |

> ⭐ **둘 다 "절대 거절하지 않는다"는 게 진짜 문제다.**
> 거절하지 않으려면 어딘가는 무한해야 하고, 컴퓨터에 무한한 자원은 없다.
> 고정 풀은 무한을 **큐**에 떠넘기고, 캐시 풀은 **스레드**에 떠넘겼을 뿐이다.

그래서 해법은 **스레드도 큐도 유한하게** 잡고, 넘치면 **거절**하는 것이다.

> 💡 이 때문에 많은 기업의 코딩 규칙(예: 알리바바 자바 코딩 가이드라인)이 **`Executors` 팩토리 메서드 사용을 금지하고 `ThreadPoolExecutor`를 직접 생성하도록** 요구한다. 팩토리 메서드는 이 "무한"을 숨기기 때문이다.

# 7. 사용자 정의 풀 전략

## 7.1 세 단계 대응

| 단계 | 대응 |
| --- | --- |
| **일반** | 기본 스레드로 안정적 운영. 자원 예측 가능 |
| **긴급** | 요청 폭증 시 스레드를 추가 투입해 빠르게 처리 |
| **거절** | 그래도 감당 못 하면 거절 |

```java
ExecutorService es = new ThreadPoolExecutor(
        100,                                    // 평소: 기본 스레드 100개
        200,                                    // 긴급: 최대 200개까지
        60, TimeUnit.SECONDS,                   // 긴급 투입분은 60초 쉬면 정리
        new ArrayBlockingQueue<Runnable>(1000)  // 대기: 최대 1000개
);
```

## 7.2 작업 수를 바꿔가며 실행

```java
for (int i = 1; i <= TASK_SIZE; i++) {
    try {
        es.execute(new RunnableTask("task" + i));
    } catch (RejectedExecutionException e) {
        log("task" + i + " -> " + e);
    }
}
```

| 작업 수 | 구성 | 스레드 | 시간 |
| --- | --- | --- | --- |
| 1100 | 100(스레드) + 1000(큐) | 100 | 약 **11.2초** |
| 1200 | 100 + 1000 + **100(긴급)** | ⭐ 200 | 약 **6.8초** |
| 1201 | 100 + 1000 + 100 + **1(거절)** | 200 | 약 6.8초 + 거절 1건 |

```text
task1201 -> RejectedExecutionException: ... [Running, pool size = 200, active threads = 200, queued tasks = 1000, ...]
```

**요청이 더 많은데 더 빨리 끝났다.** 긴급 스레드 100개가 투입됐기 때문이다.

| 지표 | 1100개 | 1200개 | 변화 |
| --- | --- | --- | --- |
| 소요 시간 | 11.2초 | 6.8초 | **약 39% 감소** |
| 처리량 | 약 98개/초 | 약 176개/초 | ⭐ **약 1.8배** |

> ⚠️ **이게 가능했던 전제 조건**: 예제 작업이 `sleep(1000)`, 즉 **CPU를 쓰지 않고 기다리는 작업**이기 때문이다. 스레드를 두 배로 늘리니 거의 두 배 빨라졌다. **CPU를 계속 쓰는 계산 작업이었다면** 코어 수를 넘는 스레드는 오히려 컨텍스트 스위칭만 늘려서 느려진다.

## 7.3 큐 크기가 "긴급 투입 시점"을 결정한다

```text
긴급 스레드가 생기는 조건 = 큐가 가득 찼을 때

큐 1000 → 이미 1000명이 기다리고 나서야 긴급 투입  (늦지만 거절도 늦게)
큐 100  → 100명만 기다리면 바로 긴급 투입          (빠르지만 거절도 빨리)
```

| 큐 크기 | 긴급 투입 | 거절 시점 | 대기 중 최대 지연 |
| --- | --- | --- | --- |
| 크게 | 늦다 | 늦다 | ⚠️ 길다 |
| 작게 | 빠르다 | 빠르다 | 짧다 |

> ⭐ **큐 크기는 "사용자를 최대 얼마나 기다리게 할 것인가"를 정하는 값이다.** 무조건 크게 잡는다고 좋은 게 아니다.

## 7.4 그럼 100, 200은 어떻게 정하나

출발점으로 쓰는 공식이 있다.

| 작업 성격 | 스레드 수 출발점 |
| --- | --- |
| **CPU 바운드** (계산) | 코어 수 + 1 |
| **I/O 바운드** (DB, 네트워크 대기) | 코어 수 × (1 + 대기 시간 / 계산 시간) |

```text
예: 8코어, 요청 하나당 DB 대기 90ms + 계산 10ms
    → 8 × (1 + 90/10) = 80개
```

공식은 출발점일 뿐이고 **답은 부하 테스트가 준다.** 현재 트래픽에서 측정하고, 병목이 보일 때 조정한다.

## 7.5 ⚠️ 실무에서 가장 흔한 실수

```java
new ThreadPoolExecutor(100, 200, 60, SECONDS, new LinkedBlockingQueue<>());
//                                              ⚠️ 크기를 안 주면 무한
// → 큐가 절대 차지 않는다 → 긴급 스레드 200 은 영원히 안 생긴다
```

**큐를 무한으로 두면 긴급 스레드는 절대 생기지 않는다.** 큐가 가득 찬 이후에야 초과 스레드가 생기기 때문이다.

# 8. 거절 정책

소비자가 감당할 수 없을 만큼 요청이 쏟아지면, 그 요청을 어떻게 할지 정해야 한다. 최소한 **로그를 남기고**, 사용자에게 문제가 있다고 **알리는 것**이 중요하다.

## 8.1 종류

| 정책 | 동작 | 비고 |
| --- | --- | --- |
| `AbortPolicy` | `RejectedExecutionException` 던짐 | ⭐ **기본값** |
| `DiscardPolicy` | 새 작업을 **조용히 버림** | ⚠️ 흔적이 없다 |
| `DiscardOldestPolicy` | 큐에서 **가장 오래된** 작업을 버리고 새 작업을 넣음 | ⚠️ 우선순위 큐와 쓰면 위험 |
| `CallerRunsPolicy` | **제출한 스레드가 직접 실행** | 백프레셔 효과 |
| 사용자 정의 | `RejectedExecutionHandler` 구현 | 로그, 메트릭 등 |

정책은 `ThreadPoolExecutor` 생성자의 마지막 인자로 넘긴다. 모두 `RejectedExecutionHandler`의 구현체다. `shutdown()` 이후에 들어온 작업도 같은 정책으로 거절된다.

> 💡 `DiscardOldestPolicy`를 `PriorityBlockingQueue`와 함께 쓰면, 큐의 맨 앞이 "가장 오래된 것"이 아니라 **"우선순위가 가장 높은 것"**이라서 **가장 중요한 작업을 버리게 된다.**

> 💡 **모든 거절 핸들러는 "작업을 제출한 스레드"에서 실행된다.** `CallerRunsPolicy`가 특별한 게 아니라, 핸들러 안에서 그냥 `r.run()`을 호출할 뿐이다.

## 8.2 AbortPolicy — 예외를 던진다

```java
ThreadPoolExecutor es = new ThreadPoolExecutor(
        1, 1, 0, TimeUnit.SECONDS,
        new SynchronousQueue<>(),
        new ThreadPoolExecutor.AbortPolicy()
);

es.submit(new RunnableTask("task1"));
try {
    es.submit(new RunnableTask("task2"));   // 💥 여기서 바로 예외
} catch (RejectedExecutionException e) {
    log("요청 초과");
    // 포기, 재시도 등 대응
}
```

> ⭐ **거절은 `submit()`에서도 즉시 예외가 난다.**
> 지난 글에서 "`submit()`의 예외는 Future 안에 저장된다"고 했는데, 그건 **작업 실행 중** 예외 이야기다. 거절은 **제출 시점**에 일어나므로 Future에 담길 틈도 없이 `submit()` 호출에서 바로 터진다.

| 예외 종류 | `submit()`의 동작 |
| --- | --- |
| 작업 **실행 중** 예외 | Future에 저장 → `get()`에서 `ExecutionException` |
| 작업 **거절** (Abort) | ⭐ `submit()` 호출에서 즉시 `RejectedExecutionException` |

## 8.3 DiscardPolicy — 조용히 버린다

```java
es.submit(new RunnableTask("task1"));
es.submit(new RunnableTask("task2"));   // 조용히 버려짐
es.submit(new RunnableTask("task3"));   // 조용히 버려짐
es.submit(new RunnableTask("task4"));   // 조용히 버려짐
```

```text
[pool-1-thread-1] task1 시작
[pool-1-thread-1] task1 완료      ← task2~4 는 흔적도 없다
```

**로그도 예외도 없다.** 작업이 사라졌다는 사실을 아무도 모른다. 버려도 되는 작업(통계 샘플링 등)에만 써야 한다.

## 8.4 CallerRunsPolicy — 제출한 스레드가 직접 한다

```text
[     main] task2 시작                ⭐ main 이 직접 실행
[pool-1-thread-1] task1 시작
[     main] task2 완료
[pool-1-thread-1] task1 완료
[     main] task3 시작                ⭐ 또 main 이 실행 (풀 스레드가 바빴음)
[     main] task3 완료
[pool-1-thread-1] task4 시작          ← 이때는 풀 스레드가 놀고 있어서 넘겨받음
```

> ⭐ **CallerRunsPolicy는 백프레셔다.**
> main이 task2를 직접 처리하는 동안에는 **task3을 제출할 수 없다.** 생산자가 소비자 일을 떠안으면서 **생산 속도가 저절로 소비 속도에 맞춰진다.** 이전 글들에서 계속 말한 백프레셔를 거절 정책으로 구현한 것이다.

주의할 점도 있다.

| 상황 | 문제 |
| --- | --- |
| 제출 스레드가 **요청 처리 스레드**(예: 웹 서버 스레드) | 그 스레드가 무거운 작업을 떠안느라 **다른 요청을 못 받는다** |
| 제출 스레드가 **UI 스레드** | 화면이 멈춘다 |
| 순서 | task2가 task1보다 먼저 시작됐다. **실행 순서가 보장되지 않는다** |

그리고 `shutdown()` 이후에는 동작이 달라진다. 실제 구현은 이렇다.

```java
public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
    if (!e.isShutdown()) {     // ⭐ 종료 요청이 들어왔으면
        r.run();               //    실행하지 않는다
    }
}
```

| 상황 | `CallerRunsPolicy`의 동작 |
| --- | --- |
| 평소 거절 | 제출한 스레드가 **직접 실행** |
| `shutdown()` **이후** 거절 | ⚠️ **실행하지 않고 조용히 버린다** |

이 체크가 없다면 `shutdown()` 이후에 들어온 작업을 호출 스레드가 계속 실행해버려서 **"새 작업을 받지 않는다"는 약속이 무너진다.** 대신 그 결과로 **종료 이후 제출한 작업은 예외도 없이 사라진다.**

## 8.5 사용자 정의 — 원하는 대로

```java
static class MyRejectExecutionHandler implements RejectedExecutionHandler {

    static AtomicInteger count = new AtomicInteger(0);

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        int i = count.incrementAndGet();
        log("[경고] 거절된 누적 작업 수: " + i);
    }
}
```

```text
[     main] [경고] 거절된 누적 작업 수: 1
[     main] [경고] 거절된 누적 작업 수: 2
[     main] [경고] 거절된 누적 작업 수: 3
```

> 💡 **`AtomicInteger`를 쓴 이유**: 여러 스레드가 동시에 작업을 제출하면 핸들러도 **여러 스레드에서 동시에** 호출된다. CAS 글에서 본 원자적 카운터가 정확히 이 자리에 필요하다.

# 9. ⚠️ 거절 + submit() = 영원히 끝나지 않는 Future

위 예제들은 전부 `submit()`을 쓴다. 여기에 실무에서 치명적인 함정이 숨어 있다.

## 9.1 무슨 일이 일어나나

```java
ThreadPoolExecutor es = new ThreadPoolExecutor(1, 1, 0, SECONDS,
        new SynchronousQueue<>(), new ThreadPoolExecutor.DiscardPolicy());

es.submit(task1);
Future<?> future2 = es.submit(task2);   // 거절됐지만 예외 없이 Future 를 돌려받는다
future2.get();                           // 💀 영원히 반환되지 않는다
```

```text
submit(task2)
   │
   ▼
FutureTask 생성 (state = NEW)
   │
   ▼
execute() → 거절 → DiscardPolicy → 아무것도 안 함
   │
   ▼
submit() 은 그 FutureTask 를 그대로 반환
   │
   ▼
⚠️ 이 FutureTask 는 아무도 실행하지 않는다
⚠️ state 는 영원히 NEW
   │
   ▼
future2.get() → LockSupport.park() → 💀 깨워줄 스레드가 없다
```

## 9.2 같은 함정이 생기는 경우

| 상황 | Future의 운명 |
| --- | --- |
| `DiscardPolicy`로 거절 | 💀 영원히 미완료 |
| 아무것도 안 하는 **사용자 정의 핸들러** (위 8.5 예제) | 💀 영원히 미완료 |
| `shutdown()` 이후 `CallerRunsPolicy`로 거절 | 💀 영원히 미완료 |
| `DiscardOldestPolicy`로 **밀려난 쪽** 작업 | 💀 영원히 미완료 |
| `shutdownNow()`가 큐에서 꺼낸 작업 | 💀 영원히 미완료 |

## 9.3 대처

```java
// ✅ 방법 1 — get 은 항상 타임아웃과 함께
future.get(5, TimeUnit.SECONDS);

// ✅ 방법 2 — 거절 핸들러에서 Future 를 취소 상태로 만들어준다
public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
    log.warn("거절됨");
    if (r instanceof Future<?> f) {
        f.cancel(false);     // → get() 이 CancellationException 으로 즉시 반환
    }
}

// ✅ 방법 3 — 기본값 AbortPolicy 를 유지해 제출 시점에 실패를 알린다
```

> ⭐ 지난 글의 결론 **"인자 없는 `get()` 대신 `get(timeout)`을 기본으로 쓰자"**가 여기서 결정적으로 중요해진다. 거절 정책까지 고려하면, 타임아웃 없는 `get()`은 **언제든 영원히 멈출 수 있는 코드**다.

# 10. 실무 전략 선택

## 10.1 무엇을 쓸 것인가

| 전략 | 적합한 상황 |
| --- | --- |
| 고정 풀 | 트래픽이 일정하고 안정성이 가장 중요할 때 (단, 큐는 유한하게 직접 생성) |
| 캐시 풀 | 작업이 아주 짧고(수 밀리초), 동시 요청 수가 구조적으로 제한될 때 |
| ⭐ 사용자 정의 | 폭증 가능성이 있는 대부분의 서비스 |

```text
트래픽 패턴이 어떤가?
   │
   ├─ 일정하고 예측 가능          → 고정 풀 (큐 크기는 반드시 유한하게)
   │
   ├─ 짧은 작업, 동시성이 낮음     → 캐시 풀 (동시 요청 상한이 보장될 때만)
   │
   └─ 폭증 가능성 있음 / 대부분    → ⭐ 사용자 정의
                                     core·max·큐 모두 유한 + 거절 정책 명시
```

## 10.2 가장 좋은 최적화는 최적화하지 않는 것

사용자가 얼마 없는데 서버를 최적화하는 것은 **가장 비싼 서버를 사는 것**과 같다. 개발자의 시간이 가장 비싸다. 예측 불가능한 먼 미래보다 **현재 상황에 맞게** 최적화하는 것이 중요하다.

그리고 이번 글 전체를 관통하는 한 문장.

> **적절한 거절은 서버에도, 우리의 삶에도 모두 필요하다.**

# 헷갈리기 쉬운 포인트

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | `isShutdown()`이 `true`면 다 끝났다 | **요청됐을 뿐.** 완료는 `isTerminated()` |
| 2 | `close()`는 하루 뒤 강제 종료한다 | **무한히 기다린다.** 인터럽트될 때만 `shutdownNow()` |
| 3 | `shutdown()`하면 큐의 작업은 버려진다 | **끝까지 처리한다.** 버리는 건 `shutdownNow()` |
| 4 | `shutdownNow()`하면 작업이 즉시 멈춘다 | `interrupt()`일 뿐. **협력해야** 멈춘다 |
| 5 | 초과 스레드가 따로 정리된다 | 꼬리표 없음. **개수로만** 관리 |
| 6 | 고정 풀은 안전하다 | **큐가 무한**이라 폭증 시 OOM |
| 7 | 캐시 풀은 큐가 없어서 재사용을 못 한다 | **`SynchronousQueue` 직거래**로 재사용한다 |
| 8 | 큐를 크게 잡으면 안전하다 | 긴급 투입이 **늦어지고** 대기가 길어진다 |
| 9 | 거절된 `submit()`은 Future에 예외가 담긴다 | Abort면 **즉시 예외**, Discard면 **영원히 미완료** |
| 10 | `CallerRunsPolicy`는 항상 실행해준다 | `shutdown()` 이후엔 **조용히 버린다** |

# 최종 정리

## 작업이 들어왔을 때

```text
execute(task)
   │
   ├─ 스레드 < core ───────────▶ 새 스레드
   ├─ 큐에 자리 있음 ──────────▶ 큐에서 대기
   ├─ 스레드 < max ────────────▶ 긴급 스레드 (keepAlive 동안 놀면 정리)
   └─ 전부 불가 ───────────────▶ 거절 정책
                                   ├ Abort         예외 (기본)
                                   ├ Discard       조용히 버림
                                   ├ DiscardOldest 가장 오래된 것 버림
                                   └ CallerRuns    제출한 스레드가 직접 실행
```

## 전략 비교

| 전략 | 스레드 | 큐 | 폭증하면 |
| --- | --- | --- | --- |
| 고정 풀 | n | ⚠️ 무한 | **작업**이 쌓여 느려지다 OOM |
| 캐시 풀 | ⚠️ 무한 | 0 | **스레드**가 쌓여 시스템 정지 |
| 사용자 정의 | core ~ max | 유한 | 긴급 투입 → 그래도 넘치면 **거절** |

## 종료

| | 한 줄 요약 |
| --- | --- |
| `shutdown()` | 새 작업만 거부. 큐의 작업은 끝까지 처리 |
| `shutdownNow()` | 큐는 꺼내서 반환, 실행 중인 작업엔 `interrupt()` |
| `isShutdown()` / `isTerminated()` | 요청됐나 / 실제로 끝났나 |
| `close()` | 끝날 때까지 **무한히** 기다린다 |
| 실무 패턴 | `shutdown` → 기다림 → `shutdownNow` → 기다림 |

## 이것만은 기억

> **① 거절하지 않는 풀은 어딘가가 무한하다** — 고정 풀은 큐, 캐시 풀은 스레드
> **② 긴급 스레드는 큐가 가득 차야 생긴다** — 큐 크기가 투입 시점을 정한다
> **③ `close()`는 시한이 없다** — 시한이 필요하면 직접 구현한다
> **④ 거절될 수 있는 풀에서 `get()`은 반드시 타임아웃과 함께**
