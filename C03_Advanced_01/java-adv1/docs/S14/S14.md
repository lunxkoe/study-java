# 스레드 풀과 Executor 프레임워크 2

## ExecutorService 우아한 종료 - 소개

### 필요 상황 
- 만약 서버 기능을 업데이트를 위해서 서버를 재시작해야한다고 가정
- 서버가 고객의 주문을 처리하고 있는 도중에 갑자기 재시작된다면, 해당 고객의 주문이 제대로 진행되지 못할 것임
- 이미 진행중인 주문은 모두 완료한 다음에 서버를 재시작하는 것이 좋음
- 이런 방법은 **graceful shutdown**이라고 함

### ExecutorService의 종료 메서드
- 서비스 종료
  - void shutdown()
    - 새로운 작업을 받지 않고, 이미 제출된 작업을 모두 완료한 후에 종료함
    - 논 블로킹 메서드(이 메서드를 호출한 스레드는 대기하지 않고 즉시 다음 코드를 호출함)
  - List<Runnable> shutdownNow()
    - 실행 중인 작업을 중단하고, 대기 중인 작업을 즉시 종료함
    - 실행 중인 작업을 중단하기 위해 인터럽트를 발생시킴
    - 논 블로킹 메서드

- 서비스 상태 확인
  - boolean isShutdown()
    - 서비스가 종료되었는지 확인함
  - boolean isTerminated()
    - shutdown(), shutdownNow() 호출 후, 모든 작업이 완료되었는지를 확인함


- 작업 완료 대기
  - boolean awaitTermination(long timeout, TimeUnit unit) throws InterruptedException
    - 서비스 종료 시 모든 작업이 완료될 때까지 대기함
    - 지정된 시간까지만 대기
    - 블로킹 메서드

- close()
  - 자바 19부터 지원하는 메서드
  - shutdown()과 같다고 생각하면 됨
  - 더 정확히는 shutdown()을 호출하고 하루를 기다려도 작업이 완료되지 않으면 shutdownNow()를 호출함
  - 호출한 스레드가 인터럽트가 발생해도 shutdownNow()를 호출함

## ExecutorService 우하한 종료 - 구현

### 구현
- shutdown()을 호출해서 우아한 종료를 시도하고, 10초 간 종료되지 않으면 shutdownNow()를 통해 강제로 종료하는 방식을 구현
```java
public class ExecutorShutdownMain {

    public static void main(String[] args) {
        ExecutorService es = Executors.newFixedThreadPool(2);
        es.execute(new RunnableTask("taskA"));
        es.execute(new RunnableTask("taskB"));
        es.execute(new RunnableTask("taskC"));
        es.execute(new RunnableTask("longTask", 100_000)); // 100초 대기
        printState(es);
        log("== shutdown 시작 ==");

        shutdownAndAwaitTermination(es);

        log("== shutdown 완료 ==");
    }

    private static void shutdownAndAwaitTermination(ExecutorService es) {
        es.shutdown(); // non-blocking, 새로운 작업을 받지 않음, 처리 중이거나 큐에 대기중인 작업은 처리. 이후에 풀의 스레드를 종료
        try {
            // 이미 대기 중인 작업을 모두 완료할 때까지 10초 기다림
            if (!es.awaitTermination(10, TimeUnit.SECONDS)) {
                // 정상 종료가 너무 오래 걸리면...
                log("서비스 정상 종료 실패 -> 강제 종료 시도");
                es.shutdownNow();
                // 작업이 취소될 때까지 대기함
                if (!es.awaitTermination(10, TimeUnit.SECONDS)) {
                    log("서비스가 종료되지 않았습니다.");
                }
            }
        } catch (InterruptedException e) {
            // awaitTermination()으로 대기 중인 현재 스레드가 인터럽트 될 수 있음
            es.shutdownNow();
        }
    }
}
```

- shutdownNow()를 호출하고는 왜 기다릴까?

  - 근데 인터럽트를 호출하더라도 여러가지 이유로 작업에 시간이 걸릴 수 있음
  - 인터럽트 이후 자원을 정리하는 어떤 간단한 작업을 수행할 수도 있음

## Executor 스레드 풀 관리

### ThreadPoolExecutor의 생성자
- corePoolSize: 스레드 풀에서 관리되는 기본 스레드의 수
- maximumPoolSize: 스레드 풀에서 관리되는 최대 스레드 수
- keepAliveTime, TimeUnit unit: 기본 스레드 수를 초과해서 만들어진 스레드가 생존할 수 있는 대기 시간, 이 시간 동안 처리할 작업이 없다면 초과 스레드는 제거됨
- BlockingQueue workQueue: 작업을 보관할 블로킹 큐

### corePoolSize vs maximumPoolSize의 차이
```java
public class PoolSizeMainV1 {

    public static void main(String[] args) {
        ArrayBlockingQueue<Runnable> workQueue = new ArrayBlockingQueue<>(2);
        ExecutorService es = new ThreadPoolExecutor(
                2,
                4,
                3000,
                TimeUnit.MILLISECONDS,
                workQueue
        );

        printState(es);

        es.execute(new RunnableTask("task1"));
        printState(es, "task1");

        es.execute(new RunnableTask("task2"));
        printState(es, "task2");

        es.execute(new RunnableTask("task3"));
        printState(es, "task3");

        es.execute(new RunnableTask("task4"));
        printState(es, "task4");

        es.execute(new RunnableTask("task5"));
        printState(es, "task5");

        es.execute(new RunnableTask("task6"));
        printState(es, "task6");

        try {
            es.execute(new RunnableTask("task7"));
        } catch (RejectedExecutionException e) {
            log("task7 실행 거절 예외 발생: " + e);
        }

        sleep(1000);
        log("== 작업 수행 완료 ==");
        printState(es);

        sleep(3000);
        log("== maximumPoolSize 대기 시간 초과 ==");
        printState(es);

        es.close(); // blocking 메서드
        log("== shutdown 완료 ==");
        printState(es);
    }
}
```

## Executor 스레드 풀 관리 - 분석

### 분석
- task1 ~ 2까지는 스레드 풀에 스레드를 생성함 (작업을 요청해야 스레드를 생산하기 시작함)
- task3 ~ 4까지는 블로킹 큐에 작업을 넣음 (블로킹 큐 사이즈 최대 2)
- task5가 들어오면 큐에 보관을 시도함
  - 요청이 많다는 의미
  - **이때 초과 스레드 생성** - maximumPoolSize까지 초과 스레드를 생성하기 시작함
- task6까지 초과 스레드로 생성함
- **이때 큐에 들어갔던 작업보다 초과 스레드로 돌아가는 작업이 먼저 수행됨**
  - 큐에 작업이 가득 차서 pool에서 초과 스레드를 생성해서 작업을 바로 수행하기 시작함
- task7이 들어오면 풀도, 큐도, 초과 스레드도 다 사용 중이기 때문에 RejectExecutionException이 발생함 (작업을 거절함)
- 모든 작업이 완료되고, 3초(초과 스레드 제거 시간)이 완료되면 초과 스레드를 제거함
- 이후 close()를 호출(블로킹 메서드)하고, 스레드 풀에 있는 모든 스레드를 정리함

### 스레드 미리 생성하기
- 응답 시간이 아주 중요한 서버라면, 서버가 고객의 처음 요청을 받기 전에 스레드를 미리 생성해서 스레드 풀에 넣어놓을 수 있음
- ThreadPoolExecutor.prestartAllCoreThreads()를 사용하면 기본 스레드를 미리 생성할 수 있음
```java
public class PreStartPoolMain {

    public static void main(String[] args) {
        ExecutorService es = Executors.newFixedThreadPool(1000);
        ThreadPoolExecutor poolExecutor = (ThreadPoolExecutor) es;
        poolExecutor.prestartAllCoreThreads();
        sleep(1000);
        printState(es);
    }
}
```
- 실행 결과
```text
17:30:42.988 [     main] [pool=1000, active=0, queuedTasks=0, completedTask=0]
```

## Executor 전략 - 고정 풀 전략

### Executor 스레드 풀 관리 - 다양한 전략
- corePoolSize: 스레드 풀에서 관리되는 기본 스레드의 수
- maximumPoolSize: 스레드 풀에서 관리되는 기본 스레드의 수
- keepAliveTime, TimeUnit unit: 기본 스레드 수를 초과해서 만들어진 스레드가 생존할 수 있는 대기 시간, 이 시간동안 처리할 작업이 없다면 초과 스레드는 제거됨
- BlockingQueue workQueue: 작업을 보관할 블로킹 큐

### 제공되는 전략
- newSingleThreadPool(): 단일 스레드 전략
- newFixedThreadPool(nThreads): 고정 스레드 풀 전략
- newCachedThreadPool(): 캐시 스레드 풀 전략

### newSingleThreadPool()
- 스레드 풀에 기본 스레드 1개만 사용
- 큐 사이즈에 제한이 없음 (LinkedBlockingQueue)
- 주로 간단히 사용하거나, 테스트 용도로 사용함
- `new ThreadPoolExecutor(1, 1, OL, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<Runnable>())`

### 고정 풀 전략
- newFixedThreadPool(nThreads)
  - 스레드 풀에 nThreads만큼의 기본 스레드를 생성함
  - **초과 스레드는 생성하지 않음**
  - 스레드 수가 고정되어있기 때문에 CPU, 메모리 리소스가 어느정도 예측 가능한 안정적인 방식
  - `new ThreadPoolExecutor(nThreads, nThreads, 0L, TimeUnit.MILLISECONS, new LinkedBlockingQueue<Runnable>())`
```java
public class PoolSizeMainV2 {

    public static void main(String[] args) {
        ExecutorService es = Executors.newFixedThreadPool(2);
//        ExecutorService es =
//                new ThreadPoolExecutor(2, 2, 0L, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<Runnable>());?

        log("pool 생성");
        printState(es);

        for (int i = 0; i <= 6; i++) {
            String taskName = "task" + i;
            es.execute(new RunnableTask(taskName));
            printState(es);
        }

        es.close();
        printState(es);
    }
}
```

### 고정 풀 전략 단점
- 상황 1 - 점진적인 사용자 확대
  - 개발한 서비스가 잘 되어서 사용자가 점점 늘어남
  - 응답이 점점 느려진다는 항의가 들어옴

- 상황 2 - 갑작스러운 요청 증가
  - 이벤트가 대성공하면 사용자가 폭증함
  - 고객은 응답을 받지 못한다고 항의함

- 확인
  - CPU, 메모리 사용량을 확인해보는데 안정적으로 서비스가 운영되고 있음
  - 고정 스레드 전략은 실행되는 스레드 수가 고정되어 있어 사용자 수에 따라 리소스 소모량이 확 늘어낙지 않음
  - 큐 사이즈를 확인해보니 요청이 수 만건 쌓여있음
  - 요청을 처리하는 시간보다 쌓이는 시간이 더 빠름
  - 서버 자원에는 여유가 있는데, 사용자만 점점 느려지는 문제가 발생한 것임

## Executor 전략 - 캐시 풀 전략

### newCachedThreadPool()
- 기본 스레드를 사용하지 않고, 60초 생존 주기를 가진 스레드만 사용함
- 초과 스레드의 수는 제한이 없음
- 큐에 작업을 저장하지 않음 (SynchronousQueue)
  - 대신에 생산자의 요청을 스레드 풀의 소비자 스레드가 직접 받아서 바로 처리함
- 모든 요청이 대기하지 않고 스레드가 바로바로 처리함, 따라서 바른 처리가 가능함
- `new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, TimeUnit.SECONDS, new SynchronousQueue<Runnable>()`

### SynchronousQueue는 아주 특별한 블로킹 큐
- BlockingQueue 인터페이스의 구현체 중 하나
- 내부에 저장공간이 없음
- 대신에 생산자의 작업을 직접 소비자 스레드에게 전달함
- 생산자와 소비자를 동기화하는 큐 (스레드 간 직거래 방식)

### 예제 코드

```java
    public static void main(String[] args) {

        log("pool 생성");

            String taskName = "task" + i;

        }

        es.close();
```

### 어떻게 초과 스레드만 만들 수 있을까?
- 작업을 요청하면 core 사이즈 만큼 스레드를 생성
  - core 사이즈가 없음 => 바로 core 사이즈를 초과함
- core 사이즈를 초과하면 큐에 작업을 넣음
  - 큐에 작업을 넣을 없음
- 큐를 초과하면 max 사이즈만큼 스레드를 만듦
  - 초과 스레드가 생성. 물론 풀에 대기하는 초과 스레드가 있으면 재사용함
- max 사이즈를 초과하면 요청을 거절함
  - 참고로 max 사이즈가 무제한 초과 스레드를 무제한으로 만들 수 있음

- 상황 1 - 점진적인 사용자 확대
  - 개발한 서비스가 잘 되어서 사용자가 점점 늘어남
  - 큰 문제가 없음

- 상황 2 - 갑작스러운 요청 증가
  - 이벤트 성공으로 폭증
  - 고객은 응답을 받지 못한다고 항의함

- 상황 2 - 확인
  - 리소스 사용량 확인 => 리소스 사용량 100%
  - 시스템이 멈추는 장애가 발생함

## Executor 전략 - 사용자 정의 풀 전략

### 어떻게 해야할까?
- 일반: 일반적인 상황에는 CPU, 메모리 자원을 예측할 수 있도록 고정 크기의 스레드로 서비스를 안정적으로 운영
- 긴급: 사용자의 요청이 갑자기 폭증하면 긴급하게 스레드를 추가로 투입해서 작업을 빠르게 처리
- 거절: 사용자의 요청이 폭증해서 긴급 대응도 어렵다면 사용자의 요청을 거절

### 세분화 전략
```java
ExecutorService es = new ThreadPoolExecutor(100, 200, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<Runnable>(1000));
```
- 100개의 기본 스레드를 사용
- 추가로 긴급 대응 가능한 긴급 스레드 100개를 사용함
- 긴급 스레드는 60초의 생존 주기를 가짐
- 1000개의 작업이 큐에 대기할 수 있음

### 일반적인 상황

## Executor 예외 정책

### 소비자가 처리할 수 없을 정도로 생산 요청이 가득 차면 어떻게 할지를 결정해야함
- 로그
- 사용자에게 시스템에 문제가 있다고 알리는 것도 중요함

### ThreadPoolExecutor의 작업 거절 방식
- AbortPolicy: 새로운 작업을 제출할 때 RejectedExecutionException을 발생시킴. 기본 정책
- DiscardPolicy: 새로운 작업을 조용히 버림
- CallerRunsPolicy: 새로운 작업을 제출한 스레드가 대신해서 직접 작업을 실행함
- 사용자 정의(RejectedExecutionHandler): 개발자가 직접 정의한 거절 정책을 사용할 수 있음
- 참고: ThreadPoolExecutor를 shutdown()하면 이후에 요청하는 작업을 거절하는데, 이때도 같은 정책이 사용됨

### AbortPolicy
```java
public class RejectMainV1 {

    public static void main(String[] args) {
        ThreadPoolExecutor es = new ThreadPoolExecutor(
                1, 1,
                0, TimeUnit.SECONDS,
                new SynchronousQueue<>(),
                new ThreadPoolExecutor.AbortPolicy()
        );

        es.submit(new RunnableTask("task1"));
        try {
            es.submit(new RunnableTask("task2"));
        } catch (RejectedExecutionException e) {
            log("요청 초과");
            // 포기, 다시 시도 등 다양한 고민을 하면 됨
            log(e);
        }

        es.close();
    }
}
```
- 실행 결과
```text

19:12:22.321 [pool-1-thread-1] task1 시작
19:12:22.324 [     main] java.util.concurrent.RejectedExecutionException: Task java.util.concurrent.FutureTask@b1bc7ed[Not completed, task = java.util.concurrent.Executors$RunnableAdapter@1ddc4ec2[Wrapped task = thread.executor.RunnableTask@133314b]] rejected from java.util.concurrent.ThreadPoolExecutor@5b6f7412[Running, pool size = 1, active threads = 1, queued tasks = 0, completed tasks = 0]
```

### RejectedExecutionHandler
- 마지막에 전달한 AbortPolicy는 RejectedExecutionHandler의 구현체
- ThreadPoolExecutor 생성자는 RejectedExecutionHandler의 구현체를 전달 받음

### CallerRunsPolicy의 특징
- 생산자 스레드가 소비자 대신 일을 수행하는 것도 있지만
- 생산자 스레드가 대신 일을 수행하는 덕분에 작업의 생산 자체가 느려짐
- 덕분에 작업의 생산 속도가 너무 빠르다면 생산 속도를 조절할 수 있음
- main이 task2를 완료하고 나서야 task3을 생산할 수 있음 (블로킹 됨)
- 참고
  - ThreadPoolExecutor를 shutdown()을 하면 이후에 요청하는 작업을 거절하는데 이때도 같은 정책이 적용됨
  - 그런데 CallerRunsPolicy 정책은 shutdown() 이후에도 작업을 수행해버림
  - 따라서 shutdown() 조건을 체크해서 이 경우에는 작업을 수행하지 않도록 함
    - 이게 왜 이렇냐면 main 스레드 자체는 shutdown()을 해도, 작업이 있는 것으로 판단되기 때문에 종료되지 않음
    - 내부 구현에 이렇게 되어있다는 것임

### 사용자 정의
```java
public class RejectMainV4 {

    public static void main(String[] args) {
        ThreadPoolExecutor es = new ThreadPoolExecutor(
                1, 1,
                0, TimeUnit.SECONDS,
                new SynchronousQueue<>(),
                new MyRejectExecutionHandler()
        );

        es.submit(new RunnableTask("task1"));

        es.submit(new RunnableTask("task2"));
        es.submit(new RunnableTask("task3"));
        es.submit(new RunnableTask("task4"));

        es.close();
    }

    static class MyRejectExecutionHandler implements RejectedExecutionHandler {

        static AtomicInteger count = new AtomicInteger(0);

        @Override
        public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
            int i = count.incrementAndGet();
            log("[경고] 거절된 누적 작업 수: " + i);
        }
    }
}
```

## 정리

### 실무 전략 선택
- 고정 스레드 풀 전략: 트래픽이 일정하고, 시스템 안정성이 가장 중요할 때
- 캐시 스레드 풀 전략: 일반적인 성장하는 서비스
- 사용자 정의 풀 전략: 다양한 상황에 대응

### 가장 좋은 최적화는 최적화하지 않는 것임
- 사용자가 얼마 없는데 서버를 최적화는 것은 가장 비싼 서버를 사는 거랑 같은 효과
- 개발자 몸값이 제일 비쌈
- 예측 불가능한 먼 미래보다는 현재 상황에 맞게 최적화하는 것이 중요함
- **적절한 거절은 서버도 우리의 삶에도 모두 필요함**
