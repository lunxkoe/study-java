# 생산자 소비자 문제 - 1

## 생산자 소비자 문제 - 소개

### 기본 개념
- 생산자: 데이터를 생성하는 역할을 함
  - 파일에서 데이터를 읽어오거나 네트워크에서 데이터를 받아오는 스레드가 생산자 역할을 수행함
- 소비자: 생성된 데이터를 사용하는 역할을 함
  - 데이터를 처리하거나 저장하는 스레드가 소비자 역할을 수행함
- 버퍼: 생산자가 생성한 데이터를 일시적으로 저장하는 공간
  - 한정된 크기를 가지며, 생산자와 소비자가 이 버퍼를 통해 데이터를 주고 받음

### 문제 상황
- 생산자가 너무 빠를 떄
  - 버퍼가 가득차서 더 이상 데이터를 넣을 수 없을 때까지 생산자가 데이터를 생성
  - 버퍼가 가득 찬 경우 생산자는 버퍼에 빈 공간이 생길 때까지 기다려야 함
- 소비자가 너무 빠를 때
  - 버퍼가 비어서 더 이상 소비될 데이터가 없을 때까지 소비자가 데이터를 처리함
  - 소비자는 버퍼에 새로운 데이터가 들어올 때까지 기다려야 
- **한정된 버퍼의 문제**

## 생산자 소비자 문제 - 소개
```java
public interface BoundedQueue {

    void put(String data);

    String take();
}
```
- BoundedQueue: 버퍼 역할을 하는 큐의 인터페이스
- put(data): 버퍼에 데이터를 보관 (생산자 스레드가 호출하고, 데이터를 생산함)
- take(): 버퍼에 보관된 값을 가져감 (소비자 스레드가 호출하고, 데이터를 소비함)

```java
public class BoundedQueueV1 implements BoundedQueue {

    private final Queue<String> queue = new ArrayDeque<>();
    // - synchronized를 사용해서 한 번 한 스레드에서만 호출할 수 있기 때문에 동기화 문제가 발생하지 않음
    private final int max;

    public BoundedQueueV1(int max) {
        this.max = max;
    }

    @Override
    public synchronized void put(String data) {
        if (queue.size() == max) {
            MyLogger.log("[put] 큐가 가득 참. 버림: " + data);
            return;
        }

        queue.offer(data);
    }

    @Override
    public synchronized String take() {
        if (queue.isEmpty()) {
            return null;
        }

        return queue.poll();
    }

    @Override
    public String toString() {
        return queue.toString();
    }
}
```
- 한정된 버퍼 역할을 하는 단순한 구현체
- 주의
  - 원칙적으로 toString에도 synchronized를 사용해야함
  - 예제 코드를 단순화하기 위해서 일단 뺌

### 임계 영역
- 핵심 공유 자원: queue(ArrayDeque)
- synchronized를 사용해서 한 번에 한 스레드만 접근할 수 있음
- synchronized는 모니터 락을 사용하기 때문에 put(data), take() 조차도 동시에 실행될 가능성이 없음

### 예제 코드
```java
public class ProducerTask implements Runnable {

    private final BoundedQueue queue;
    private final String request;

    public ProducerTask(BoundedQueue queue, String request) {
        this.queue = queue;
        this.request = request;
    }

    @Override
    public void run() {
        log("[생산 시도] " + request + " -> " + queue);
        queue.put(request);
        log("[생산 완료] " + request + " -> " + queue );
    }
}
```

```java
public class ConsumerTask implements Runnable {

    private final BoundedQueue queue;

    public ConsumerTask(BoundedQueue queue) {
        this.queue = queue;
    }

    @Override
    public void run() {
        log("[소비 시도]        ? <- " + queue);
        String data = queue.take();
        log("[소비 완료] " + data + " <- " + queue);
    }
}
```

```java
public class BoundedMain {

    public static void main(String[] args) {
        // 1. BoundedQueue 선택
        BoundedQueue queue = new BoundedQueueV1(2);

        producerFirst(queue); // 생산자 먼저 실행
//        consumerFirst(queue); // 소비자 먼저 실행

    public static void producerFirst(BoundedQueue queue) {
        log("== [생산자 먼저 실행] 시작, " + queue.getClass().getSimpleName() + " ==");
        List<Thread> threads = new ArrayList<>();
        startProducer(queue, threads);
        printAllState(queue, threads);
        startConsumer(queue, threads);
        printAllState(queue, threads);
        log("== [생산자 먼저 실행] 종료, " + queue.getClass().getSimpleName() + " ==");
    }

    public static void consumerFirst(BoundedQueue queue) {
        log("== [소비자 먼저 실행] 시작, " + queue.getClass().getSimpleName() + " ==");
        List<Thread> threads = new ArrayList<>();
        startConsumer(queue, threads);
        printAllState(queue, threads);
        startProducer(queue, threads);
        printAllState(queue, threads);
        log("== [소비자 먼저 실행] 종료, " + queue.getClass().getSimpleName() + " ==");
    }

    public static void startProducer(BoundedQueue queue, List<Thread> threads) {
        System.out.println();
        log("생산자 시작");
        for (int i = 1; i <= 3; i++) {
            Thread producer = new Thread(new ProducerTask(queue, "data" + i), "producer" + i);
            threads.add(producer);
            producer.start();
            sleep(100); // 스레드 순서를 가능한 순서대로 제어하기 위해서 사용
        }
    }

    public static void startConsumer(BoundedQueue queue, List<Thread> threads) {
        System.out.println();
        log("소비자 시작");
        for (int i = 1; i <= 3; i++) {
            Thread consumer = new Thread(new ConsumerTask(queue), "consumer" + i);
            threads.add(consumer);
            consumer.start();
            sleep(100); // 스레드 순서를 가능한 순서대로 제어하기 위해서 사용
        }
    }

    public static void printAllState(BoundedQueue queue, List<Thread> threads) {
        System.out.println();
        log("현재 상태 출력, 큐 데이터: " + queue);
        for (Thread thread : threads) {
            log(thread.getName() + ": " + thread.getState());
        }
    }
}
```

## 생산자 소비자 문제 - 소비자 우선

### 분석
- 소비자 스레드가 순차적으로 락을 획득하고 데이터를 소비
- 모든 소비자 스레드가 null을 받음
- 생산자 스레드가 순차적으로 락을 획득하고 데이터를 생산

### 대안
- 큐에 데이터가 찰 때까지 소비자가 대기
- 큐에 공간이 없으면 소비자가 소비할 때까지 대기

### 결론
- 큐가 가득찼을 때: 소비자가 소비할 때까지 생산자 대기 - 데이터를 버리지 않기
- 큐가 비어있을 때: 생산자가 생산할 때까지 소비자 대기 - null을 반환받지 않기

## 생산자 소비자 문제 - 예제 2 분석

### 위의 결과에 대한 이유 (생산자 먼저든 소비자 먼저든)
- 결론: sleep()을 하면 점유했던 모니터 락을 반납하지 않고 대기하기 때문
  - sleep() 상태의 스레드 => timed_waiting + 모니터 락을 점유 중
  - 모니터 락을 점유하지 못한 모든 스레드 => blocked
- 결과: 무한 대기 문제 발생!

### 왜 이런 결론이 나왔을까
- synchronized 메서드 특징
  - 한 객체의 모니터락을 가지고 있음
  - 락을 획득하지 못하면 blocked 상태가 됨
  - synchronized가 락을 반납하는 경우는 해당 메서드가 완료되었을 때 반납함
    - 메서드 안에서 sleep()을 호출하면 락을 절대 반납하지 않음

### 어떻게 해결할 수 있을까?
- 자바의 Object.wait(), Object.notify()를 사용하면 락을 가지고 대기하는 스레드가 대기하는 동안 다른 스레드에게 락을 양보할 수 있음

## Object - wait, notify - 예제 3 코드

### 해결 방안
- synchronized를 사용한 임계 영역 안에서 락을 가지고 무한 대기하는 문제를 흥미롭게도 Object 클래스에 해결 방안이 있음
- Object.wait() / Object.notify(): 모든 자바 언어의 기본 기능

### wait(), notify()
- Object.wait()
  - 현재 스레드가 가진 락을 반납하고 waiting함
  - synchronized 블록이나 메서드에서 락을 소유하고 있을 때만 호출 가능
  - 대기 상태로 전환된 스레드는 다른 스레드가 notify() 또는 notifyAll()을 호출할 때까지 대기 상태를 유지

- Object.notify()
  - waiting 중인 스레드 하나를 깨움
  - 이 메서드는 synchronized 블록이나 메서드에서 호출되어야함
  - 깨운 스레드는 락을 다시 획득할 기회를 얻게 됨
  - 만약 대기 중인 스레드가 여러 개라면, 그 중 하나만 깨워지게 됨

- Object.notifyAll()
  - waiting 중인 모든 스레드를 깨움
  - 이 메서드 역시 synchronized 블록이나 메서드에서 호출되어야 함
  - 대기 중인 모든 스레드가 락을 획득할 수 있는 기회를 얻게 됨
  - 모든 스레드를 깨워야하는 경우에 유용함

### 예제 코드
```java
public class BoundedQueueV3 implements BoundedQueue {

    private final Queue<String> queue = new ArrayDeque<>();
    // - synchronized를 사용해서 한 번 한 스레드에서만 호출할 수 있기 때문에 동기화 문제가 발생하지 않음
    private final int max;

    public BoundedQueueV3(int max) {
        this.max = max;
    }

    @Override
    public synchronized void put(String data) {
        while (queue.size() == max) {
            log("[put] 큐가 가득 참. 대기: " + data);
            try {
                wait(); // Runnable -> Waiting + 락 반납
                log("[put] 생산자 깨어남"); // Runnable
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        }

        queue.offer(data);
        log("[put] 생산자 데이터 저장, notify() 호출");
        notify(); // 대기 스레드, Wait -> Blocked
    }

    @Override
    public synchronized String take() {
        while (queue.isEmpty()) {
            log("[take] 큐에 데이터가 없음. 소비자 대기");
            try {
                wait();
                log("[take] 소비자 깨어남");
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        }
        String data = queue.poll();
        log("[take] 소비자 데이터 획득, notify() 호출");
        notify(); // 대기 스레드 Wait -> Blocked
        return data;
    }

    @Override
    public String toString() {
        return queue.toString();
    }
}
```

## 생산자 소비자 문제 - 예제 3 - 생산자 우선

### 스레드 대기 집합 (wait set)
- synchronized 임계 영역 안에서 Object.wait()를 호출하면 스레드는 대기 상태에 들어감
- 대기 상테에 들간 스레드를 관리하는 것을 대기 집합이라고 함
- 참고로 모든 객체는 각자의 대기 집합을 가지고 있음
- 모든 객체는 모니터 락과 대기 집합을 가지고 있음

### 분석
- 락을 반납하고 Waiting 상태로 전환
- notify()로 Waiting 상태의 스레드를 Blocked 상태로 깨움

### notify(): Waiting -> Blocked
- notify는 락을 주는 것이 아니라 대기를 풀어주는 것
- waiting 상태에서 벗어남
- 깨어난 스레드가 실행을 이어가려면 다시 락을 획득해야함 근데 notify()를 부른 시점에 notify()를 부른 애가 락을 아직 쥐고 있음
- 락을 획득해야 Runnable 상태로 갈 수 있으므로 순간적 Blocked 상태임
  - 그래서 if가 아닌 while을 사용해야하는 것 => 락을 얻었을 때 같이 달라질 수 있음
  - 다른 스레드가 락을 먼저 획득하고 값을 변경할 수 있기 때문에 다시 검사해야함
  - notifyAll()은 모든 스레드를 Blocked로 바꿈을 참고

## Object - wait, notify - 한계

### 비효율
- 생산자 실행 
  - 생산자가 생산자가 깨우는 예시 (큐가 가득 찬 경우)
  
- 소비자 실행
  - 소비자가 소비자를 깨우는 예시 (큐가 비어있는 경우)

### 해결
- noitfy() 대신 notifyAl()을 사용하는 방법이 있음
- 스레드 대기 집합에 있는 모든 스레드를 깨움
  - 락을 획득하지 못하면 전부 Blocked 상태가 됨
  - 하지만 다시 락을 획득하고 조건을 보고 다시 wait() 상태로 들어갈 수 있음

### 고민
- 소비자 먼저 실행 시 소비자가 소비자를 깨우는 문제를 해결할 수는 없음
- 다만, 스레드 기아 현상에 대한 정의를 생산자, 소비자 스레드가 대기 집합에 공존할 때로 한다면
- notify()는 생산자가 대기 집합에 있는데도 불구하고 소비자가 소비자를 깨울 수 있지만
- notifyAll()은 전부 깨워서 경합하기 때문에 이를 해결 할 수도 있음

### notifyAll()
- 이걸 사용해도 모든 스레드가 깨어났다가 다시 waiting 상태로 가는 비효율을 막을 수는 없음
