## 1. 생산자 소비자 문제란

### 1.1 구조

```text
   ┌──────────┐      put()      ┌─────────────┐     take()     ┌──────────┐
   │  생산자   │ ──────────────▶ │   버퍼      │ ─────────────▶ │  소비자   │
   │Producer  │                 │ (한정 크기)  │                │ Consumer │
   └──────────┘                 └─────────────┘                └──────────┘
    파일 읽기                     max = 2                       처리 / 저장
    네트워크 수신
```

| 역할 | 하는 일 |
| --- | --- |
| **생산자** | 데이터를 만들어 버퍼에 넣는다 (파일 읽기, 네트워크 수신) |
| **소비자** | 버퍼에서 데이터를 꺼내 쓴다 (처리, 저장) |
| **버퍼** | 생산자와 소비자 사이의 **한정된 크기** 저장 공간 |

### 1.2 두 가지 문제 상황

```text
[ 생산자가 빠를 때 ]              [ 소비자가 빠를 때 ]

 생산자 ▶▶▶                       생산자 ▶
 ┌─────────┐                      ┌─────────┐
 │■■■■■■■■■│ 가득 참!              │         │ 텅 빔!
 └─────────┘                      └─────────┘
 소비자 ▶                          소비자 ▶▶▶

 → 넣을 자리가 없다                → 꺼낼 데이터가 없다
 → 자리가 생길 때까지 대기해야 함   → 데이터가 올 때까지 대기해야 함
```

이것을 **한정된 버퍼 문제(bounded buffer problem)**라고 한다.

🔴 **오타 정정**: "생산자가 너무 빠를 **떄**" → **때**, "기다려야 " → **기다려야 함**

## 2. V1 — 버리고 null 반환

### 2.1 코드

```java
public interface BoundedQueue {
    void put(String data);
    String take();
}
```

```java
public class BoundedQueueV1 implements BoundedQueue {

    private final Queue<String> queue = new ArrayDeque<>();
    private final int max;

    public BoundedQueueV1(int max) {
        this.max = max;
    }

    @Override
    public synchronized void put(String data) {
        if (queue.size() == max) {
            log("[put] 큐가 가득 참. 버림: " + data);
            return;                          // ⚠️ 데이터를 버린다
        }
        queue.offer(data);
    }

    @Override
    public synchronized String take() {
        if (queue.isEmpty()) {
            return null;                     // ⚠️ null 을 반환한다
        }
        return queue.poll();
    }

    @Override
    public String toString() {
        return queue.toString();
    }
}
```

### 2.2 임계 영역 분석

| 항목 | 내용 |
| --- | --- |
| 공유 자원 | `queue` (`ArrayDeque`) |
| 보호 방법 | `synchronized` (모니터 락) |
| 결과 | `put()`과 `take()`조차 **동시에 실행될 수 없다** |

`ArrayDeque`는 스레드 안전하지 않지만, **모든 접근이 `synchronized`로 감싸져 있으므로** 안전하다. 앞 글에서 본 `ConcurrentLinkedQueue`를 안 써도 되는 이유다.

🟡 **원문의 `toString()` 주의사항이 생각보다 중요하다.**

```java
@Override
public String toString() {      // ⚠️ synchronized 없음
    return queue.toString();
}
```

그리고 실제로 이렇게 호출된다.

```java
log("[생산 시도] " + request + " -> " + queue);   // ⚠️ 락 밖에서 호출
queue.put(request);
```

**락을 쥐지 않은 상태에서 `ArrayDeque`를 순회하는 것**이므로, 다른 스레드가 동시에 수정하면 깨진 출력이나 `ConcurrentModificationException`이 날 수 있다. 예제를 단순화하려고 뺀 것이지만, **실제 코드라면 버그**다.

### 2.3 결과

| 시나리오 | 결과 |
| --- | --- |
| 생산자 먼저 | data1, data2는 저장. **data3는 버려짐**. consumer3는 **null** |
| 소비자 먼저 | 소비자 3명 전부 **null**. 이후 data3는 **버려짐** |

### 2.4 원하는 동작

> - 큐가 **가득 찼을 때**: 소비자가 소비할 때까지 **생산자 대기** → 데이터를 버리지 않기
> - 큐가 **비었을 때**: 생산자가 생산할 때까지 **소비자 대기** → null을 반환하지 않기

## 3. V2 — sleep으로 기다려보기

### 3.1 코드

```java
@Override
public synchronized void put(String data) {
    while (queue.size() == max) {
        log("[put] 큐가 가득 참. 대기: " + data);   // 🔴 원문은 "버림"
        sleep(1000);
    }
    queue.offer(data);
}

@Override
public synchronized String take() {
    while (queue.isEmpty()) {
        log("[take] 큐에 데이터가 없음. 소비자 대기");
        sleep(1000);
    }
    return queue.poll();
}
```

🔴 **원문 V2의 로그 문구가 여전히 "버림"이다.** 이제 버리지 않고 대기하는데 `[put] 큐가 가득 참. **버림**: data3`가 1초마다 반복 출력된다. **"대기"로 바꿔야 코드와 로그가 맞는다.**

(V3 코드는 "대기"로 고쳐져 있는데, V3 실행 결과 로그에는 또 "버림"이 남아 있다. 강의 자료가 여러 버전을 오간 흔적으로 보인다.)

### 3.2 실행 결과 — 멈춰버린다

```text
15:46:17.374 [producer3] [생산 시도] data3 -> [data1, data2]
15:46:17.375 [producer3] [put] 큐가 가득 참. 대기: data3

15:46:17.484 [     main] producer3: TIMED_WAITING     ← 자는 중

15:46:17.488 [consumer1] [소비 시도]        ? <- [data1, data2]
15:46:17.588 [consumer2] [소비 시도]        ? <- [data1, data2]
15:46:17.688 [consumer3] [소비 시도]        ? <- [data1, data2]

15:46:17.790 [     main] consumer1: BLOCKED           ← ⚠️ 셋 다 진입조차 못 함
15:46:17.790 [     main] consumer2: BLOCKED
15:46:17.791 [     main] consumer3: BLOCKED

15:46:18.389 [producer3] [put] 큐가 가득 참. 대기: data3
15:46:19.395 [producer3] [put] 큐가 가득 참. 대기: data3
15:46:20.398 [producer3] [put] 큐가 가득 참. 대기: data3
// 영원히 반복...
```

**큐에 데이터가 두 개나 들어 있는데 소비자 셋이 전부 `BLOCKED`다.** 소비 시도 로그는 찍혔는데 실제 소비는 한 번도 못 했다.

## 4. ⭐ 왜 멈췄나 — sleep은 락을 반납하지 않는다

### 4.1 그림으로 보기

```text
        BoundedQueueV2 객체
 ┌──────────────────────────────────────────┐
 │  queue = [data1, data2]  ← 데이터는 있다! │
 │                                          │
 │  🔒 모니터 락                             │
 │     owner: producer3  ← 자면서도 쥐고 있음 │
 │                                          │
 │  🚪 진입 대기 (BLOCKED)                   │
 │     [consumer1] [consumer2] [consumer3]  │
 └──────────────────────────────────────────┘

 producer3: "자리가 생기면 넣어야지" → sleep(1000) → 깨어남 → 아직 가득 참 → sleep...
 consumer들: "데이터 꺼내야지" → 락이 없어서 메서드 진입조차 불가 💀
```

> ⭐ **핵심**
> - `sleep()` 중인 스레드 → **`TIMED_WAITING` + 모니터 락 보유**
> - 락을 못 얻은 나머지 → 전부 **`BLOCKED`**
> - **자리를 만들어 줄 사람이 영원히 들어오지 못한다**

이건 앞 글들에서 계속 강조한 **"`sleep()`은 락을 반납하지 않는다"**가 만들어내는 최악의 시나리오다.

### 4.2 🟡 이건 "데드락"이 아니다

원문은 "무한 대기 문제"라고 표현했는데 정확한 선택이다. 용어를 구분해두면 좋다.

| 용어 | 정의 | 이 상황은? |
| --- | --- | --- |
| **데드락** | 서로가 서로의 락을 기다리는 **순환 대기** | ❌ 아니다 |
| **라이브락** | 계속 움직이는데 진전이 없음 | ❌ 아니다 |
| **기아(starvation)** | 특정 스레드가 자원을 못 얻어 굶음 | ✅ **가깝다** |

producer3는 **계속 깨어나서 조건을 확인하고 있다.** 멈춰 있는 게 아니다. 다만 락을 놓지 않으니 소비자들이 영원히 굶는다.

### 4.3 synchronized가 락을 반납하는 시점

🟡 **원문의 "메서드가 완료되었을 때 반납"에 한 가지를 더해야 한다.**

| 락이 반납되는 경우 | |
| --- | --- |
| 메서드/블록을 **정상적으로 벗어날 때** | ✅ |
| 메서드/블록에서 **예외로 빠져나갈 때** | ✅ |
| ⭐ **`wait()`를 호출할 때** | ✅ **← 이게 해결책** |
| `sleep()` 중 | ❌ |
| `join()` 대기 중 | ❌ |
| I/O 대기 중 | ❌ |

## 5. wait와 notify

### 5.1 세 가지 메서드

```java
public class Object {
    public final void wait() throws InterruptedException { ... }
    public final void wait(long timeout) throws InterruptedException { ... }
    public final native void notify();
    public final native void notifyAll();
}
```

| 메서드 | 동작 |
| --- | --- |
| `wait()` | **락을 반납하고** 대기 집합에 들어간다 (`WAITING`) |
| `wait(timeout)` | 시간 제한을 두고 대기 (`TIMED_WAITING`) |
| `notify()` | 대기 집합의 **스레드 하나**를 깨운다 |
| `notifyAll()` | 대기 집합의 **모든 스레드**를 깨운다 |

### 5.2 🟡 원문에 빠진 제약 두 가지

**① `synchronized` 안에서만 호출할 수 있다**

```java
public void wrong() {
    wait();      // 💥 IllegalMonitorStateException
}

public synchronized void right() throws InterruptedException {
    wait();      // ✅
}
```

**락을 쥔 상태**에서만 호출 가능하다. 당연하다 — 반납할 락이 있어야 반납할 수 있으니까.

**② `wait()`는 `InterruptedException`을 던진다**

원문 예제가 `try-catch`로 감싸는 이유다. `sleep()`, `join()`과 같은 계열이고, 앞 글에서 본 `LockSupport.park()`(예외를 안 던짐)와는 다르다.

```java
catch (InterruptedException e) {
    throw new RuntimeException(e);   // 🟡 인터럽트 플래그 유실 (앞 글 참고)
}
```

### 5.3 💡 Object에 이 기능이 있는 이유

원문이 "흥미롭게도 `Object` 클래스에 해결 방안이 있다"고 했는데, 이유가 있다.

> **`synchronized`는 어떤 객체에든 걸 수 있다. 그러니 "그 객체의 대기 집합"도 모든 객체가 가져야 한다.**

```java
synchronized (anyObject) {
    anyObject.wait();      // 이 객체의 대기 집합에 들어간다
}
```

**모니터 락과 대기 집합은 한 쌍**이고, 락이 모든 객체에 있으니 대기 집합도 모든 객체에 있어야 한다. 그래서 `Object`의 메서드가 된 것이다.

## 6. V3 — 대기 집합과 진입 집합

### 6.1 코드

```java
@Override
public synchronized void put(String data) {
    while (queue.size() == max) {
        log("[put] 큐가 가득 참. 대기: " + data);
        try {
            wait();                       // ⭐ RUNNABLE → WAITING + 락 반납
            log("[put] 생산자 깨어남");
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
    queue.offer(data);
    log("[put] 생산자 데이터 저장, notify() 호출");
    notify();                             // ⭐ 대기 집합의 하나를 WAITING → BLOCKED
}

@Override
public synchronized String take() {
    while (queue.isEmpty()) {
        log("[take] 큐에 데이터가 없음. 소비자 대기");
        try {
            wait();
            log("[take] 소비자 깨어남");
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
    String data = queue.poll();
    log("[take] 소비자 데이터 획득, notify() 호출");
    notify();
    return data;
}
```

### 6.2 ⭐ 모든 객체는 세 가지를 가진다

원문은 "모니터 락 + 대기 집합"이라고 했는데, **집합이 두 개**라는 걸 구분하면 로그가 훨씬 잘 읽힌다.

```text
            모든 자바 객체의 내부 구조
 ┌──────────────────────────────────────────────────┐
 │                                                  │
 │  🔒 모니터 락        ← 한 번에 한 스레드만 보유    │
 │                                                  │
 │  🚪 진입 집합 (Entry Set)        상태: BLOCKED    │
 │     synchronized 진입을 기다리는 스레드들          │
 │     → 락이 풀리면 자동으로 경쟁                    │
 │                                                  │
 │  💤 대기 집합 (Wait Set)         상태: WAITING    │
 │     wait() 로 스스로 들어간 스레드들               │
 │     → notify() 없이는 절대 안 나옴                 │
 │                                                  │
 └──────────────────────────────────────────────────┘
```

| | 진입 집합 (Entry Set) | 대기 집합 (Wait Set) |
| --- | --- | --- |
| 상태 | `BLOCKED` | `WAITING` |
| 들어가는 법 | `synchronized` 진입 실패 | **`wait()` 호출 (자발적)** |
| 나오는 법 | 락이 풀리면 자동 경쟁 | **`notify()` / `notifyAll()` 필요** |
| 락 보유 | ❌ | ❌ (반납하고 들어감) |

### 6.3 전체 흐름

```text
   RUNNABLE
      │ synchronized 진입 시도
      ▼
  ┌─ 락 획득 성공? ─┐
  │ NO             │ YES
  ▼                ▼
BLOCKED         RUNNABLE (임계 영역 안)
(진입 집합)          │
  │                 │ 조건 불충족 → wait()
  │                 ▼
  │            ⭐ 락 반납 + WAITING (대기 집합)
  │                 │
  │                 │ 다른 스레드가 notify()
  │                 ▼
  │            BLOCKED ← ⭐ 여기! 락을 다시 얻어야 함
  │                 │
  └─────────────────┤ 락 획득
                    ▼
                 RUNNABLE
                    │
                    │ while 조건 재검사
                    ▼
             통과하면 작업 진행
```

### 6.4 ⭐ `notify()`는 락을 주는 게 아니다

원문 설명이 정확하다. 정리하면 이렇다.

```java
notify();          // 대기 집합 → 진입 집합으로 옮길 뿐
// ⚠️ 이 시점에 notify() 를 호출한 스레드가 아직 락을 쥐고 있다
// ⚠️ 메서드가 끝나야 비로소 락이 풀린다
```

```text
producer3가 wait() 중 (WAITING)
       │
consumer1이 데이터를 꺼내고 notify() 호출
       │
       ▼
producer3: WAITING → BLOCKED    ⭐ RUNNABLE 이 아니다
       │
consumer1의 take() 가 끝나고 락 반납
       │
       ▼
producer3: BLOCKED → RUNNABLE   ⭐ 이제야 실행
```

### 6.5 V2와의 결정적 차이

| | V2 (`sleep`) | V3 (`wait`) |
| --- | --- | --- |
| producer3의 상태 | `TIMED_WAITING` | **`WAITING`** |
| 락 보유 | ⚠️ **쥐고 있음** | ✅ **반납함** |
| 소비자들의 상태 | `BLOCKED` (영원히) | 정상 진입 |
| 결과 | 💀 무한 대기 | ✅ 정상 동작 |

실행 결과에서 `producer3: WAITING`이 찍히는 순간이 이 차이를 보여준다.

## 7. ⭐ while을 써야 하는 두 가지 이유

```java
while (queue.isEmpty()) {   // ⭐ if 가 아니라 while
    wait();
}
```

원문은 **첫 번째 이유만** 설명한다. 두 번째도 공식적인 이유다.

### 7.1 이유 ① — 깨어나도 상황이 바뀌어 있을 수 있다

```text
consumer1: wait() 중 (큐가 비어서)
    │
producer1: 데이터 넣고 notify()
    │
consumer1: WAITING → BLOCKED (아직 락 없음)
    │
    │ ⚠️ 이 틈에 consumer2 가 먼저 락을 획득!
    │ ⚠️ consumer2 가 데이터를 가져감
    ▼
consumer1: 락 획득 → 큐가 다시 비어 있음
    │
    ▼
 if 였다면 → queue.poll() → null 💥
 while 이면 → 조건 재검사 → 다시 wait() ✅
```

**`notify()`를 받은 것이 "조건이 충족됐다"는 보장이 아니다.** 락을 얻을 때까지의 틈에 다른 스레드가 끼어들 수 있다.

### 7.2 💡 이유 ② — 가짜 깨어남 (spurious wakeup)

`Object.wait()` 공식 문서에 명시된 내용이다.

> **`wait()`는 `notify()` 없이도, 아무 이유 없이 깨어날 수 있다.**

앞 글에서 본 `LockSupport.park()`의 spurious wakeup과 **같은 성질**이다. 그래서 공식 문서도 **"항상 루프 안에서 사용하라"**고 권고한다.

```java
// ❌ 절대 이렇게 쓰면 안 된다
if (queue.isEmpty()) {
    wait();
}
return queue.poll();   // 💥 NoSuchElementException / null

// ✅ 표준 관용구
synchronized (lock) {
    while (조건이_충족되지_않음()) {
        lock.wait();
    }
    // 여기서는 조건이 확실히 충족됨
    작업();
}
```

### 7.3 💡 왜 신호 유실(missed signal)이 안 일어나나

`notify()`는 **대기자가 없으면 그냥 사라진다.** 앞 글의 `LockSupport.unpark()`가 퍼밋으로 저장되는 것과 정반대다.

| | `wait/notify` | `park/unpark` |
| --- | --- | --- |
| 신호를 먼저 보내면 | ❌ **유실됨** | ✅ 퍼밋으로 저장 |

그런데 왜 이 코드는 안전할까?

```java
synchronized (this) {           // ⭐ 락을 쥔 상태에서
    while (queue.isEmpty()) {   // ⭐ 조건을 확인하고
        wait();                 // ⭐ 대기에 들어간다 — 이 전체가 원자적
    }
}
```

**조건 확인과 `wait()` 진입 사이에 다른 스레드가 끼어들 수 없다.** 락을 쥐고 있으니 `notify()`를 부를 수 있는 스레드도 없다. 그래서 "조건을 확인했는데 그 직후에 신호가 와서 놓치는" 상황이 원천적으로 불가능하다.

> ⭐ **`synchronized` + `while` + `wait()` 이 세 개가 한 세트인 이유가 이것이다.** 하나라도 빠지면 깨진다.

## 8. notify의 한계

### 8.1 엉뚱한 쪽을 깨운다

```text
        하나의 대기 집합에 두 종류가 섞여 있다
 ┌────────────────────────────────────────────┐
 │  💤 대기 집합                                │
 │     [producer3]  "자리 나면 깨워줘"          │
 │     [consumer2]  "데이터 오면 깨워줘"        │
 │     [consumer3]  "데이터 오면 깨워줘"        │
 └────────────────────────────────────────────┘
              ▲
              │ consumer1 이 데이터를 꺼내고 notify()
              │ 의도: "생산자야, 자리 생겼어!"
              │
              ⚠️ 하지만 consumer2 가 깨어날 수도 있다
              ⚠️ consumer2: 큐가 비었네 → 다시 wait()
              ⚠️ producer3 는 계속 자고 있음
```

실행 결과에서 **"소비자가 소비자를 깨우는"** 로그가 반복되는 이유다.

```text
16:35:52.857 [consumer1] [take] 소비자 데이터 획득, notify() 호출
16:35:52.857 [consumer2] [take] 소비자 깨어남
16:35:52.857 [consumer2] [take] 큐에 데이터가 없음. 소비자 대기   ← 헛수고
```

### 8.2 notifyAll()

```java
notifyAll();   // 대기 집합 전원을 진입 집합으로
```

| | `notify()` | `notifyAll()` |
| --- | --- | --- |
| 깨우는 대상 | **하나** (누구일지 모름) | **전부** |
| 엉뚱한 쪽만 깨울 위험 | ⚠️ 있음 | ✅ 없음 (전부 깨우니까) |
| 헛수고 | 적음 | ⚠️ **많음** (대부분 다시 wait) |
| 안전성 | ⚠️ 조건부 | ✅ **항상 안전** |

🟡 **원문의 결론이 정확하다.** `notifyAll()`도 "모든 스레드가 깨어났다가 다시 `wait()`으로 가는 비효율"은 막지 못한다. 다만 **엉뚱한 쪽만 깨우고 끝나는 상황은 확실히 막는다.**

💡 이 비효율에는 이름이 있다. **thundering herd(우르르 몰려드는 무리)** 문제다. N개 스레드가 전부 깨어나 락을 놓고 경쟁하는데 결국 하나만 진행하므로, 컨텍스트 스위칭이 낭비된다.

## 9. ⚠️ notify()는 생각보다 위험하다 💡

### 9.1 🔴 "문제는 없음"은 이 예제에서만 맞다

원문은 소비자가 소비자를 깨우는 상황을 두고 이렇게 결론짓는다.

> "문제는 없음 (while로 다시 wait()로 들어가기 때문에)"

**비효율이라는 뜻이라면 맞다. 하지만 일반화하면 위험하다.** `notify()`는 **전체가 멈추는 버그**를 만들 수 있다.

### 9.2 멈추는 시나리오

```text
상황: 버퍼 max=2, 큐 = [data1, data2] (가득 참)
      대기 집합 = [producer3, producer4, consumer1]

① consumer2 가 데이터 하나를 꺼냄 → 큐 = [data2]
② consumer2 가 notify() 호출
③ ⚠️ 하필 producer3 가 깨어남 → 자리가 생겼으니 data3 삽입 → 큐 = [data2, data3]
④ producer3 가 notify() 호출
⑤ ⚠️ 하필 producer4 가 깨어남 → 큐가 가득 참 → 다시 wait()
⑥ producer4 는 notify() 를 호출하지 않고 잠듦

   → 아무도 더 이상 notify() 를 부르지 않는다
   → consumer1 은 대기 집합에서 영원히 나오지 못한다  💀
```

`while` 루프는 **깨어난 스레드가 잘못된 값을 쓰는 것**을 막아줄 뿐, **깨어나지 못한 스레드**는 구제하지 못한다.

### 9.3 ⭐ 안전 규칙

> **`notify()`를 안전하게 쓸 수 있는 조건은 둘 다 만족할 때뿐이다.**
> ① 대기 중인 모든 스레드가 **같은 조건**을 기다린다
> ② 한 번의 신호로 **정확히 하나**만 진행할 수 있다
>
> **생산자와 소비자가 같은 대기 집합을 쓰는 구조는 ①을 위반한다.**
> → **`notifyAll()`을 써야 한다.**

```java
// ✅ 안전한 기본값
notifyAll();

// 🟡 notify() 는 위 두 조건을 확인한 뒤에만
```

💡 실무 관례는 명확하다. **의심스러우면 `notifyAll()`.** 성능 최적화가 정말 필요하고 두 조건을 증명할 수 있을 때만 `notify()`로 바꾼다.

## 10. 다음 단계 — Condition과 BlockingQueue 💡

### 10.1 진짜 해법 — 대기 집합을 나눈다

`notifyAll()`도 근본 해결은 아니다. **애초에 생산자와 소비자를 다른 대기 집합에 넣으면** 헛깨움이 사라진다.

```text
[ synchronized — 대기 집합 1개 ]      [ ReentrantLock — Condition 여러 개 ]

  💤 대기 집합                          💤 notFull  : [producer3, producer4]
     [producer3]                        💤 notEmpty : [consumer1, consumer2]
     [consumer1]
     [consumer2]                        ⭐ 필요한 쪽만 정확히 깨울 수 있다
  ⚠️ 섞여 있어서 골라 깨울 수 없다
```

```java
private final Lock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();   // 생산자 대기실
private final Condition notEmpty = lock.newCondition();   // 소비자 대기실

public void put(String data) throws InterruptedException {
    lock.lock();
    try {
        while (queue.size() == max) {
            notFull.await();        // 생산자는 여기서 대기
        }
        queue.offer(data);
        notEmpty.signal();          // ⭐ 소비자만 정확히 깨운다
    } finally {
        lock.unlock();
    }
}

public String take() throws InterruptedException {
    lock.lock();
    try {
        while (queue.isEmpty()) {
            notEmpty.await();       // 소비자는 여기서 대기
        }
        String data = queue.poll();
        notFull.signal();           // ⭐ 생산자만 정확히 깨운다
        return data;
    } finally {
        lock.unlock();
    }
}
```

앞 글에서 본 `Lock.newCondition()`이 바로 이것이다.

| | `synchronized` + `wait/notify` | `ReentrantLock` + `Condition` |
| --- | --- | --- |
| 대기 집합 | **1개** (고정) | ✅ **여러 개** |
| 대기 | `wait()` | `await()` |
| 깨우기 | `notify()` / `notifyAll()` | `signal()` / `signalAll()` |
| 대상 지정 | ❌ 불가 | ✅ **Condition 단위로** |
| 헛깨움 | ⚠️ 발생 | ✅ 거의 없음 |

### 10.2 최종 답 — 이미 만들어져 있다

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(2);

queue.put("data");      // 가득 차면 대기
String data = queue.take();   // 비어 있으면 대기
```

내부가 정확히 10.1의 `ReentrantLock` + 두 개의 `Condition`으로 구현되어 있다. 앞 글의 프린터 예제에서 `yield()` 대신 쓰라고 했던 그 도구다.

### 10.3 학습 경로 정리

```text
① V1: 버리고 null 반환        → 데이터 유실
② V2: sleep 으로 대기          → 💀 락을 쥔 채 자서 전체 정지
③ V3: wait / notify            → ✅ 동작하지만 헛깨움
④     notifyAll                → ✅ 안전하지만 비효율
⑤ Condition (대기 집합 분리)   → ✅ 정확히 필요한 쪽만
⑥ BlockingQueue               → ⭐ 이미 만들어져 있음
```

지금 `wait/notify`를 배우는 건 최종 답이어서가 아니라, **`BlockingQueue` 안에서 무슨 일이 벌어지는지 알기 위해서**다.
