# [Java] 스레드 제어와 생명 주기, sleep과 join의 차이

이전 글에서 스레드를 **만들고 실행하는** 법을 정리했다. 이번에는 한 단계 더 들어가서, 만들어진 스레드를 **관찰하고 제어하는** 방법을 다룬다.

핵심 질문은 하나다.

> **"내가 시킨 작업이 끝날 때까지 어떻게 기다릴 것인가?"**

`sleep()`으로 적당히 기다리면 안 될까? 안 된다. 그 이유가 단순히 "시간 낭비라서"가 아니라는 게 이 글의 핵심이다.

---

## 다루는 내용

- 스레드가 가진 정보 (ID, 이름, 우선순위, 그룹, 상태)
- 스레드 생명 주기 6가지 상태와 전이
- `BLOCKED`와 `WAITING`의 결정적 차이
- `run()`이 체크 예외를 던질 수 없는 진짜 이유
- `sleep()`과 `wait()`의 차이
- `join()` — 기다림, 그리고 메모리 가시성
- `join(ms)`의 함정

# 1. 스레드가 가진 정보

## 1.1 조회해보기

```java
public class ThreadInfoMain {

    public static void main(String[] args) {
        // main 스레드
        Thread mainThread = Thread.currentThread();
        log("mainThread = " + mainThread);
        log("mainThread.threadId() = " + mainThread.threadId());
        log("mainThread.getName() = " + mainThread.getName());
        log("mainThread.getPriority() = " + mainThread.getPriority());
        log("mainThread.getThreadGroup() = " + mainThread.getThreadGroup());
        log("mainThread.getState() = " + mainThread.getState());

        // 직접 만든 스레드
        Thread myThread = new Thread(new HelloRunnable(), "myThread");
        log("myThread = " + myThread);
        log("myThread.getState() = " + myThread.getState());
    }
}
```

```text
[main] mainThread = Thread[#1,main,5,main]
[main] mainThread.threadId() = 1
[main] mainThread.getName() = main
[main] mainThread.getPriority() = 5
[main] mainThread.getThreadGroup() = java.lang.ThreadGroup[name=main,maxpri=10]
[main] mainThread.getState() = RUNNABLE
[main] myThread = Thread[#21,myThread,5,main]
[main] myThread.getState() = NEW
```

| 항목 | 메서드 | 특징 |
| --- | --- | --- |
| 스레드 ID | `threadId()` | JVM이 부여, **직접 지정 불가** |
| 이름 | `getName()` / `setName()` | **중복 가능** |
| 우선순위 | `getPriority()` / `setPriority()` | 1~10, 기본 5 |
| 스레드 그룹 | `getThreadGroup()` | 부모 스레드의 그룹을 상속 |
| 상태 | `getState()` | 6가지 중 하나 |

> ⚠️ **`threadId()`는 Java 19부터 쓸 수 있다.** 그 이전 버전에서는 `getId()`를 써야 한다. Java 19에서 `getId()`가 deprecated 되고 `threadId()`로 대체됐다. JDK 17로 실습 중이라면 위 코드는 컴파일되지 않는다.

> 💡 `Thread.toString()` 출력도 버전마다 다르다. Java 18 이하는 `Thread[main,5,main]`, Java 19+는 `Thread[#1,main,5,main]`처럼 ID가 붙는다.

## 1.2 스레드 ID

JVM이 부여하는 고유 식별자고, 직접 지정할 수 없다. 여기서 주의할 점 하나.

> ⚠️ **스레드 ID를 영속적인 식별자로 쓰면 안 된다.**
> "유일하다"는 건 **동시에 살아있는 스레드들 사이에서**의 이야기다. 오래된 JDK에서는 종료된 스레드의 ID가 재사용될 수 있다고 명시되어 있었다. DB나 캐시의 키로 쓰지 말고 로그 추적용으로만 쓰자.

## 1.3 우선순위 — 기대하지 말 것

1~10 사이의 값이고 기본값은 5다. 숫자가 클수록 우선순위가 높다.

```java
Thread.MIN_PRIORITY   // 1
Thread.NORM_PRIORITY  // 5  ← 기본값
Thread.MAX_PRIORITY   // 10
```

문제는 이게 **스케줄러에 대한 힌트일 뿐**이라는 것이다. 그것도 아주 약한 힌트다.

| 환경 | 반영 정도 |
| --- | --- |
| Linux (일반 권한) | **거의 무시됨**. nice 값을 낮추려면 root 권한 필요 |
| Windows | 어느 정도 반영 |
| macOS | 부분 반영 |

> ⚠️ **우선순위로 실행 순서를 제어하려는 코드는 버그다.** 순서가 중요하면 `join()`, 락, 큐 같은 **명시적 동기화**를 써야 한다.

> 💡 우선순위와 데몬 여부는 **둘 다 부모 스레드에서 상속된다.** `Thread` 생성자가 부모의 값을 그대로 복사한다.

## 1.4 스레드 그룹

기본적으로 모든 스레드는 **자신을 생성한 스레드(부모 스레드)와 같은 그룹**에 속한다. `main`이 만든 스레드는 `main` 그룹에 들어간다.

> 💡 사실상 폐기된 기능이라 "이런 게 있구나" 정도로 넘어가도 된다. Java 19부터 `ThreadGroup`은 기능이 축소(degraded)되었고 `suspend()`, `resume()`, `stop()`은 제거 예정으로 deprecated 됐다. 실무에서 스레드를 묶어 관리하려면 `ExecutorService`를 쓴다.

# 2. 스레드의 생명 주기

## 2.1 상태 전이도

```text
                      new Thread()
                           │
                           ▼
                     ┌───────────┐
                     │    NEW    │  객체만 생성. OS 스레드 없음
                     └─────┬─────┘
                           │ start()
                           ▼
        ┌────────────────────────────────────┐
        │             RUNNABLE               │
        │  (CPU 실행 중 + 실행 대기열 + I/O) │
        └──┬──────────┬──────────┬───────┬───┘
           │          │          │       │
  synchronized     wait()    sleep(n)    │ run() 종료 / 예외
    진입 실패      join()    join(n)     │
           │          │      wait(n)     │
           ▼          ▼          ▼       ▼
     ┌─────────┐ ┌─────────┐ ┌──────────────┐  ┌────────────┐
     │ BLOCKED │ │ WAITING │ │TIMED_WAITING │  │ TERMINATED │
     └────┬────┘ └────┬────┘ └──────┬───────┘  └────────────┘
          │           │             │            (재시작 불가)
          │        notify()      시간 만료
       락 해제    notifyAll()    / notify()
          │       대상 종료         │
          └───────────┴─────────────┘
                      │
                      ▼
                  RUNNABLE 로 복귀
```

| 상태 | 의미 | 진입 계기 | CPU 사용 |
| --- | --- | --- | --- |
| `NEW` | 객체만 생성됨 | `new Thread()` | ❌ |
| `RUNNABLE` | 실행 중이거나 실행 준비됨 | `start()` | ✅ |
| `BLOCKED` | `synchronized` 락 대기 | 락 경합 | ❌ |
| `WAITING` | 무기한 대기 | `wait()`, `join()` | ❌ |
| `TIMED_WAITING` | 시간 제한 대기 | `sleep(n)`, `join(n)`, `wait(n)` | ❌ |
| `TERMINATED` | 실행 종료 | `run()` 반환 또는 예외 | ❌ |

`BLOCKED`, `WAITING`, `TIMED_WAITING` 셋을 묶어서 편의상 **"일시 중지 상태"**라고 부르기도 한다. 다만 `PAUSED` 같은 자바 공식 상태값이 따로 있는 건 아니다. 셋의 공통점은 **CPU를 거의 쓰지 않고 기다린다**는 것이다.

그리고 이 셋은 `RUNNABLE`의 하위 상태가 아니라, **`RUNNABLE`에서 갈라져 나갔다가 다시 돌아오는 형제 상태**다.

## 2.2 ⚠️ RUNNABLE은 생각보다 넓다

이게 실무에서 가장 많이 헷갈리는 부분이다.

```java
socket.read();          // 커널에서 블록되어 있음. 그런데 getState()는 RUNNABLE
Files.readAllBytes();   // 마찬가지
```

JVM은 OS의 "실행 중(running)"과 "실행 대기(ready)"를 구분하지 않는다. 심지어 **소켓이나 파일 I/O로 커널에서 블록된 스레드도 `RUNNABLE`로 표시**된다.

> 💡 스레드 덤프에서 `RUNNABLE` 스레드가 잔뜩 쌓여 있는데 CPU 사용률이 0%라면, 십중팔구 **I/O 대기**다.

## 2.3 ⭐ BLOCKED와 WAITING은 뭐가 다를까

둘 다 "멈춰서 기다린다"인데, 성격이 완전히 다르다.

| | `BLOCKED` | `WAITING` |
| --- | --- | --- |
| 원인 | `synchronized` 진입 실패 | `wait()`, `join()`, `LockSupport.park()` |
| 깨어나는 방식 | 락이 풀리면 **자동으로** 재시도 | 다른 스레드의 **명시적 신호** 필요 |
| 기다리는 대상 | **락** | **사건(신호)** |
| `interrupt()` 반응 | ❌ **반응하지 않음** | ✅ `InterruptedException` |
| 대응하는 락 | `synchronized` | `ReentrantLock`, `wait/notify` |

> ⭐ **`synchronized`로 `BLOCKED`된 스레드는 인터럽트로 깨울 수 없다.** 이게 `ReentrantLock`이 존재하는 가장 큰 이유 중 하나다 (`lockInterruptibly()`).

한 가지 더. `BLOCKED`는 **오직 `synchronized`에만** 해당한다. `ReentrantLock` 같은 `java.util.concurrent` 락을 기다리면 내부적으로 `LockSupport.park()`를 쓰기 때문에 `WAITING`이나 `TIMED_WAITING`으로 나타난다.

## 2.4 ⭐ wait()에서 깨어나면 바로 실행될까

아니다. 여기에 한 단계가 더 있다.

```text
   ┌──────────┐  wait()  ┌─────────┐ notify() ┌─────────┐ 락 획득 ┌──────────┐
   │ RUNNABLE │─────────▶│ WAITING │─────────▶│ BLOCKED │────────▶│ RUNNABLE │
   └──────────┘          └─────────┘          └─────────┘         └──────────┘
                                                   ▲
                    ⭐ notify()를 받아도 바로 실행되지 않는다.
                       wait()는 모니터 락을 반납했으므로, 다시 얻어야 한다.
```

`wait()`는 락을 **반납하고** 기다린다. 그래서 신호를 받아도 **락을 다시 얻기 전까지는 `BLOCKED` 상태를 거친다.** 나중에 `wait/notify`를 배울 때 이 그림을 기억해두면 헷갈릴 일이 없다.

> 💡 `wait()`는 반드시 `synchronized` 블록 안에서 호출해야 한다. 아니면 `IllegalMonitorStateException`이 터진다. 어디서나 호출 가능한 `sleep()`과 대조적이다.

# 3. 생명 주기 직접 확인하기

## 3.1 코드

```java
public class ThreadStateMain {

    public static void main(String[] args) throws InterruptedException {
        Thread thread = new Thread(new MyRunnable(), "myThread");

        log("state1 = " + thread.getState());   // NEW
        log("start()");
        thread.start();

        Thread.sleep(1000);
        log("state3 = " + thread.getState());   // TIMED_WAITING

        Thread.sleep(4000);
        log("state5 = " + thread.getState());   // TERMINATED
    }

    static class MyRunnable implements Runnable {

        @Override
        public void run() {
            log("start");
            log("state2 = " + Thread.currentThread().getState());   // RUNNABLE
            log("sleep() start");
            try {
                Thread.sleep(3000);
                log("sleep() end");
                log("state4 = " + Thread.currentThread().getState()); // RUNNABLE
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        }
    }
}
```

```text
18:50:27.417 [     main] state1 = NEW
18:50:27.419 [     main] start()
18:50:27.420 [ myThread] start
18:50:27.421 [ myThread] state2 = RUNNABLE
18:50:27.421 [ myThread] sleep() start
18:50:28.430 [     main] state3 = TIMED_WAITING
18:50:30.429 [ myThread] sleep() end
18:50:30.430 [ myThread] state4 = RUNNABLE
18:50:32.440 [     main] state5 = TERMINATED
```

```text
시간 ──────────────────────────────────────────────────────────▶
        0s          1s          2s          3s          4s     5s

main   │state1│     │state3│    ·           ·           ·   │state5│
       │start()│    TIMED_      ·           ·           ·   TERMINATED
       │ sleep(1000) │  ←───── sleep(4000) ─────────────────▶│

myThread      │state2│ ←────── sleep(3000) ──────▶│state4│
              RUNNABLE      TIMED_WAITING          RUNNABLE  종료
```

## 3.2 ⭐ state2와 state4가 RUNNABLE인 건 당연하다

```java
log("state2 = " + Thread.currentThread().getState());
```

이 줄을 **실행하고 있다**는 것 자체가 그 스레드가 `RUNNABLE`이라는 뜻이다. 그래서 **자기 자신의 상태를 조회하면 무조건 `RUNNABLE`이 나온다.** 다른 값이 나올 방법 자체가 없다.

`sleep()` 중인 상태(`TIMED_WAITING`)를 확인하려면 **반드시 다른 스레드가 관찰해야 한다.** 이 예제에서 `main`이 굳이 `sleep(1000)`을 걸고 `state3`을 찍는 구조가 그래서 나온 것이다.

## 3.3 ⚠️ getState()로 흐름을 제어하지 말 것

`getState()`는 **모니터링·디버깅 전용**이다.

```java
// ❌ 절대 하면 안 되는 패턴
while (thread.getState() != Thread.State.TERMINATED) {
    // busy waiting — CPU 낭비 + 조회한 순간 이미 과거 정보
}

// ✅ 올바른 방법
thread.join();
```

`getState()`가 값을 반환하는 순간, 그 상태는 이미 바뀌었을 수 있다. **상태 조회로 흐름을 제어하려는 코드는 전부 경쟁 상태(race condition)다.**

# 4. run()은 왜 체크 예외를 못 던질까

`Thread.sleep()`을 쓰면 `InterruptedException`을 반드시 처리해야 한다. 그런데 `run()` 밖으로 던지려고 하면 컴파일 에러가 난다. 왜일까?

## 4.1 재정의 규칙

```java
public interface Runnable {
    void run();   // ⭐ throws 절이 없다
}
```

| 예외 종류 | 재정의 시 규칙 |
| --- | --- |
| **체크 예외** | 부모가 던지지 않으면 **자식도 던질 수 없음**. 던지더라도 **부모가 선언한 예외의 하위 타입만** |
| **언체크 예외** | **제약 없음**. 얼마든지 던질 수 있음 |

```java
static class CheckedRunnable implements Runnable {

    @Override
    public void run() {
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);   // ✅ 언체크로 바꿔 던지는 건 가능
        }
    }

    // ❌ 컴파일 에러 — 부모 run()에 throws가 없다
    // @Override
    // public void run() throws Exception {
    //     throw new Exception();
    // }
}
```

## 4.2 진짜 이유

"안전을 위해 일부러 막았다"고 설명하기 쉬운데, 인과관계를 정확히 따지면 이렇다.

```text
① Runnable.run() 에 throws 가 없다  ← 인터페이스 설계 결정
        │
        ▼
② 자바의 오버라이딩 규칙이 적용된다  ← 언어 규칙
        │
        ▼
③ 결과적으로 체크 예외를 못 던진다  ← 결과
        │
        ▼
④ 그래서 개발자가 반드시 처리하게 된다  ← 부수 효과
```

그럼 `Runnable.run()`은 왜 애초에 `throws`를 선언하지 않았을까? **`run()`을 호출하는 주체가 JVM/스레드 자신이라, 예외를 받아줄 호출자가 없기 때문**이다. 던져봐야 받을 사람이 없다.

## 4.3 ⚠️ 다만 "비정상 종료 방지"는 절반만 맞다

체크 예외를 막았다고 스레드가 안 죽는 게 아니다. 언체크 예외는 여전히 던져지고, **그 스레드는 그대로 죽는다.**

```java
new Thread(() -> {
    throw new RuntimeException("펑");   // ✅ 컴파일 통과
}).start();
// → 이 스레드는 죽고, UncaughtExceptionHandler 가 스택 트레이스만 출력
// → main 은 이 예외를 catch 할 수 없다 (스택이 다르므로)
```

정확히 말하면 컴파일러가 막아주는 건 **"체크 예외를 던졌는데 아무도 받지 못하는 상황"**이다.

## 4.4 Callable이 이 한계를 해결한다

| | `Runnable` | `Callable<V>` |
| --- | --- | --- |
| 메서드 | `void run()` | `V call() throws Exception` |
| 반환값 | ❌ 없음 | ✅ **있음** |
| 체크 예외 | ❌ 못 던짐 | ✅ **던질 수 있음** |
| 결과 수집 | 공유 필드 + `join()` | `Future.get()` |
| 예외 전파 | 불가 | `ExecutionException`으로 **호출자에게 전달** |

```java
Callable<Integer> task = () -> {
    Thread.sleep(1000);   // ✅ 체크 예외 그대로 던져도 됨
    return 1275;
};
```

이 글 뒤에서 나올 "결과를 공유 필드에 담고 `join()`으로 기다리는" 패턴은, 나중에 `Callable` + `Future`로 훨씬 깔끔하게 대체된다.

# 5. sleep() 제대로 알기

`join()`으로 넘어가기 전에 `sleep()`을 정확히 짚고 가자. 여기서 정리해두면 나중에 `wait()`를 배울 때 큰 도움이 된다.

## 5.1 ⚠️ sleep()은 static 메서드다

```java
Thread.sleep(1000);                    // ✅ 권장
Thread.currentThread().sleep(1000);    // ⚠️ 동작은 같지만 오해를 부름
thread1.sleep(1000);                   // ⚠️⚠️ 함정!
```

세 줄 전부 **"이 코드를 실행 중인 스레드"**가 잠든다. `thread1.sleep(1000)`이라고 써도 **`thread1`이 자는 게 아니라 호출한 스레드(main)가 잔다.**

`sleep()`이 `static`이기 때문이다. 인스턴스 참조로 static 메서드를 호출하면 컴파일러가 그냥 `Thread.sleep()`으로 바꿔버린다. IDE가 경고를 띄우는 이유다.

> ⭐ **다른 스레드를 재우는 메서드는 자바에 없다.** 잠드는 건 오직 자기 자신뿐이다. 다음 글에서 볼 `interrupt()`와 정반대 성격이다 — `interrupt()`는 **남에게** 거는 것이고, `sleep()`은 **자기에게만** 거는 것이다.

## 5.2 ⭐ sleep()과 wait()의 결정적 차이

| | `Thread.sleep(n)` | `object.wait()` |
| --- | --- | --- |
| 소속 | `Thread`의 **static** 메서드 | `Object`의 **인스턴스** 메서드 |
| 상태 | `TIMED_WAITING` | `WAITING` / `TIMED_WAITING` |
| **모니터 락** | ⭐ **반납하지 않음** | ⭐ **반납함** |
| 호출 위치 | 어디서나 | **반드시 `synchronized` 안** |
| 깨어나는 법 | 시간 만료 또는 `interrupt()` | `notify()`/`notifyAll()` 또는 `interrupt()` |

> ⚠️ **`sleep()`은 락을 쥔 채로 잔다.** `synchronized` 블록 안에서 `sleep()`을 부르면 그 시간 동안 다른 스레드는 전부 `BLOCKED`로 대기한다. 데드락에 가까운 성능 저하를 만드는 흔한 실수다.

## 5.3 sleep(n)의 시간은 "최소 보장"이다

```java
long start = System.currentTimeMillis();
Thread.sleep(100);
long elapsed = System.currentTimeMillis() - start;
// elapsed 는 100 이상. 105, 112 처럼 더 클 수 있다
```

`sleep()`은 **"최소 n밀리초 동안은 실행 대기열에 올리지 않는다"**는 약속이다. 깨어난 뒤에도 CPU를 배정받아야 실행되므로 정확히 n밀리초 뒤에 재개된다는 보장이 없다.

## 5.4 학습용 sleep 유틸

앞으로 나올 예제에서 `sleep(2000)`처럼 짧게 쓰기 위해 유틸을 하나 만들어두자.

```java
package util;

public abstract class ThreadUtils {

    public static void sleep(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
}
```

```java
import static util.ThreadUtils.sleep;
```

> ⚠️ **실무에서 이렇게 쓰면 안 된다.** `InterruptedException`을 `RuntimeException`으로 바꿔 던지면 **인터럽트 상태 플래그가 지워져서** 상위 코드가 "종료 요청이 왔다"는 사실을 알 수 없게 된다. 예제 코드를 짧게 만들려는 학습용 장치일 뿐이다. 올바른 처리는 다음 글에서 다룬다.

# 6. join()이 필요한 상황

## 6.1 문제 ① main이 먼저 끝난다

```java
public class JoinMainV0 {

    public static void main(String[] args) {
        log("start");

        Thread thread1 = new Thread(new Job(), "thread-1");
        Thread thread2 = new Thread(new Job(), "thread-2");

        thread1.start();
        thread2.start();

        log("end");
    }

    static class Job implements Runnable {
        @Override
        public void run() {
            log("작업 시작");
            sleep(2000);
            log("작업 완료");
        }
    }
}
```

```text
19:24:14.160 [     main] start
19:24:14.167 [     main] end          ← main 이 먼저 끝남
19:24:14.168 [thread-1] 작업 시작
19:24:14.168 [thread-2] 작업 시작
19:24:16.181 [thread-1] 작업 완료
19:24:16.181 [thread-2] 작업 완료
```

`main`이 `end`를 찍고 끝났는데도 JVM이 종료되지 않았다. `thread1`, `thread2`가 **사용자 스레드**라서 JVM을 붙잡고 있기 때문이다. 만약 둘 다 데몬 스레드였다면 "작업 시작"조차 못 찍고 프로그램이 끝났을 것이다.

## 6.2 문제 ② 결과를 못 받는다

1부터 100까지를 두 스레드로 나눠서 더해보자.

```java
public class JoinMainV1 {

    public static void main(String[] args) {
        log("start");

        SumTask task1 = new SumTask(1, 50);
        SumTask task2 = new SumTask(51, 100);

        Thread thread1 = new Thread(task1, "thread-1");
        Thread thread2 = new Thread(task2, "thread-2");

        thread1.start();
        thread2.start();

        log("task1.result = " + task1.result);
        log("task2.result = " + task2.result);

        int sumAll = task1.result + task2.result;
        log("sumAll = " + sumAll);

        log("end");
    }

    static class SumTask implements Runnable {

        int startValue;
        int endValue;
        int result = 0;

        public SumTask(int startValue, int endValue) {
            this.startValue = startValue;
            this.endValue = endValue;
        }

        @Override
        public void run() {
            log("작업 시작");
            sleep(2000);

            int sum = 0;
            for (int i = startValue; i <= endValue; i++) {
                sum += i;
            }
            result = sum;

            log("작업 완료 result = " + result);
        }
    }
}
```

```text

19:31:24.414 [thread-1] 작업 시작
19:31:24.414 [     main] task1.result = 0    ← 아직 계산 전
19:31:24.415 [thread-2] 작업 시작
19:31:24.419 [     main] task2.result = 0
19:31:24.420 [     main] sumAll = 0          ← 기대값은 5050
19:31:24.425 [     main] end
19:31:26.425 [thread-1] 작업 완료 result = 1275
19:31:26.428 [thread-2] 작업 완료 result = 3775
```

```text
main    │──────────▶ result 읽음 (0) ──▶ end
                ▲
                │ 아직 계산 안 끝남!
thread1 │──── sleep(2000) ────▶ result = 1275
thread2 │──── sleep(2000) ────▶ result = 3775
                                    ▲
                              main 은 이미 떠난 뒤
```

> ⚠️ **이 코드는 "항상 0이 나오는 코드"가 아니라 "0이 나올 수도 있는 코드"다.** 만약 `sleep(2000)`이 없었다면 계산이 워낙 빨라서 `main`이 읽기 전에 끝났을 수도 있다. 그리고 이쪽이 더 나쁘다. 개발 환경에서는 잘 되다가 운영에서 터지는 전형적인 패턴이기 때문이다.

## 6.3 참고 — this의 정체

여기서 잠깐. `run()` 안의 `result`는 왜 `main`도 볼 수 있고, `sum`은 왜 아무도 못 볼까?

```text
① 메서드를 호출하는 건 언제나 "특정 스레드"다
② 메서드 호출 = 그 스레드의 스택에 스택 프레임을 push
③ 인스턴스 메서드라면, 어느 인스턴스인지 기억해야 한다
④ 그래서 프레임 안에 그 인스턴스의 참조값을 저장한다
⑤ ⭐ 이게 바로 this
```

```text
task1.run() 을 thread-1 이 실행할 때

thread-1 스택
┌────────────────────────┐
│ run() 프레임           │
│   this = @task1주소    │ ← ③④⑤
│   sum  = 0             │ ← 지역 변수 (스레드마다 독립)
│   i    = 1             │
└────────────────────────┘
          │ this 를 타고
          ▼
힙: SumTask@x001 { startValue=1, endValue=50, result=0 }
```

`result`는 **인스턴스 필드라 힙에 있어서** main도 볼 수 있고, `sum`은 **지역 변수라 스택에 있어서** 아무도 못 본다.

# 7. sleep으로 때우면 안 되는 이유

`main`이 기다리게 만들면 되지 않을까?

```java
thread1.start();
thread2.start();

sleep(10000);   // ⚠️ 10초면 되겠지?

int sumAll = task1.result + task2.result;   // 5050 — 값은 맞다
```

값은 맞게 나온다. 하지만 문제가 셋이다.

| 문제 | 설명 |
| --- | --- |
| ① 시간을 예측할 수 없다 | 실제 작업은 2초인데 10초를 기다림. 8초 낭비 |
| ② 너무 짧으면 틀린다 | 작업이 12초 걸리면 그대로 실패 |
| ③ ⭐ **가시성 보장이 없다** | 아래 설명 |

## ⭐ ③번이 진짜 문제다

`sleep()`으로 충분히 기다려서 **타이밍상 계산이 끝났더라도**, `main` 스레드가 `result`의 **최신 값을 본다는 보장이 자바 메모리 모델(JMM) 상 없다.** CPU 캐시나 컴파일러 최적화 때문에 `main`이 예전 값(0)을 계속 읽을 수도 있다.

```text
[ sleep 으로 기다림 ]                [ join 으로 기다림 ]

thread-1: result = 1275              thread-1: result = 1275
    │  (CPU 캐시에만 있을 수도)          │
    │                                   │ join() 이 happens-before 를 만듦
    ▼                                   ▼
main: result 읽기 → ??? 보장 없음     main: result 읽기 → ✅ 1275 확실
```

> ⭐ **`join()`은 "기다림"만 주는 게 아니라 "메모리 가시성"도 함께 준다.**
> 자바 언어 명세(JLS 17.4.5)에 이렇게 규정되어 있다.
> **"한 스레드의 모든 동작은, 다른 스레드가 그 스레드에 대해 `join()`에서 정상적으로 반환하는 시점보다 happens-before 관계에 있다."**

`sleep()`으로 스레드 완료를 기다리는 코드가 위험한 진짜 이유가 이것이다. 시간을 아무리 넉넉히 줘도 해결되지 않는 종류의 문제다.

# 8. join() 사용

## 8.1 코드

```java
public class JoinMainV3 {

    public static void main(String[] args) throws InterruptedException {
        log("start");

        SumTask task1 = new SumTask(1, 50);
        SumTask task2 = new SumTask(51, 100);

        Thread thread1 = new Thread(task1, "thread-1");
        Thread thread2 = new Thread(task2, "thread-2");

        thread1.start();
        thread2.start();

        log("join() - main 스레드가 thread1, thread2 종료까지 대기");
        thread1.join();   // main 이 WAITING 으로
        thread2.join();
        log("main 스레드 대기 완료");

        int sumAll = task1.result + task2.result;
        log("sumAll = " + sumAll);   // ✅ 5050

        log("end");
    }
}
```

```text
20:09:58.195 [     main] start
20:09:58.200 [     main] join() - ... 종료까지 대기
20:09:58.200 [thread-1] 작업 시작
20:09:58.201 [thread-2] 작업 시작
20:10:00.216 [thread-2] 작업 완료 result = 3775
20:10:00.216 [thread-1] 작업 완료 result = 1275
20:10:00.218 [     main] main 스레드 대기 완료    ← 작업 완료 2ms 만에 깨어남
20:10:00.221 [     main] sumAll = 5050
```

```text
시간 ─────────────────────────────────────────────────▶
       0s              1s              2s

main   │■■│ ←──────── WAITING ────────→ │■■■■■■│
          ▲                             ▲
          join() 호출                   thread 종료 → 즉시 깨어남
                                        (sleep 처럼 낭비 없음)

thread1 │■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■│
thread2 │■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■│
```

로그 시간을 보면 작업이 완료된 직후 `main`이 곧바로 깨어난다. `sleep()`처럼 남는 시간을 버리지 않는다.

## 8.2 동작 순서

| 순서 | 동작 | main의 상태 |
| --- | --- | --- |
| ① | `thread1.join()` 호출 | `RUNNABLE` → `WAITING` |
| ② | thread1 종료 | `WAITING` → `RUNNABLE` |
| ③ | `thread2.join()` 호출 | thread2가 이미 `TERMINATED`면 **대기 없이 즉시 통과** |
| ④ | 결과 읽기 | 가시성 보장됨 |

## 8.3 ⚠️ 헷갈리기 쉬운 부분

`thread1.join(); thread2.join();`을 순서대로 호출한다고 **대기 시간이 더해지는 게 아니다.**

두 스레드는 **이미 동시에 돌고 있기 때문에** 총 대기 시간은 `t1 + t2`가 아니라 **`max(t1, t2)`**다. 위 로그에서 각 작업이 2초인데 전체가 2초 만에 끝난 것이 그 증거다.

```text
❌ 오해: join(t1) → 2초, join(t2) → 2초, 총 4초
✅ 실제: 둘이 병렬로 2초, 총 2초
```

## 8.4 ⚠️ Thread 객체를 락으로 쓰지 말 것

`join()`은 내부적으로 `wait()`를 쓴다. (플랫폼 스레드 기준)

```java
// Thread.join() 의 대략적인 구현
public final synchronized void join(long millis) throws InterruptedException {
    while (isAlive()) {
        wait(0);
    }
}
```

`Thread` 객체 자체를 모니터로 사용한다. 여기서 안티패턴이 나온다.

```java
// ❌ 하면 안 되는 것들
synchronized (thread) { ... }   // join() 을 막아버릴 수 있음
thread.notify();                 // join() 의 wait 를 건드림
thread.wait();                   // 예측 불가능한 동작
```

**`Thread` 객체는 절대 락 객체로 쓰지 말자.** 전용 락 객체를 따로 만드는 게 정석이다.

> 💡 `join()`은 `WAITING` 상태이므로 `interrupt()`로 깨울 수 있고, `InterruptedException`을 던진다. `synchronized`의 `BLOCKED`와 대조되는 지점이다.

# 9. join(ms) — 시간 제한 대기

## 9.1 두 종류

| 메서드 | 동작 | 상태 |
| --- | --- | --- |
| `join()` | 대상이 끝날 때까지 **무기한** 대기 | `WAITING` |
| `join(ms)` | **최대 ms만큼만** 대기 | `TIMED_WAITING` |
| `join(ms, ns)` | 나노초 단위까지 지정 | `TIMED_WAITING` |

> ⚠️ **함정: `join(0)`은 "0초 대기"가 아니라 "무한 대기"다.**
> ```java
> thread.join(0);    // ⚠️ join() 과 완전히 동일 — 영원히 기다림
> thread.join(1);    // 1밀리초 대기
> ```
> `0`을 "기다리지 않음"으로 착각하면 프로그램이 그대로 멈춘다. `Object.wait(0)`도 같은 규칙이다.

## 9.2 예제

```java
public class JoinMainV4 {

    public static void main(String[] args) throws InterruptedException {
        log("start");

        SumTask task1 = new SumTask(1, 50);
        Thread thread1 = new Thread(task1, "thread-1");
        thread1.start();

        log("join(1000) - 최대 1초만 대기");
        thread1.join(1000);     // 작업은 2초 걸림 → 타임아웃
        log("main 스레드 대기 완료");

        log("task1.result = " + task1.result);   // ⚠️ 0
        log("end");
    }
}
```

```text
20:30:08.904 [     main] start
20:30:08.911 [     main] join(1000) - 최대 1초만 대기
20:30:08.911 [thread-1] 작업 시작
20:30:09.914 [     main] main 스레드 대기 완료    ← 1초 뒤 타임아웃
20:30:09.915 [     main] task1.result = 0        ← ⚠️ 결과 없음
20:30:09.916 [     main] end
20:30:10.915 [thread-1] 작업 완료 result = 1275  ← main 떠난 뒤 완료
```

## 9.3 ⚠️ 타임아웃인지 완료인지 구분할 수 없다

`join(ms)`를 쓰면 반드시 마주치는 문제다.

> **`join(ms)`는 `void`를 반환한다.**
> 그래서 **"시간이 만료돼서 나온 건지, 스레드가 정말 끝나서 나온 건지 구분할 수 없다."**

구분하려면 `isAlive()`로 직접 확인해야 한다.

```java
thread1.join(1000);

if (thread1.isAlive()) {
    log("⏱ 타임아웃 — 아직 작업 중");
    // 계속 기다릴지, 포기할지, interrupt 할지 결정
} else {
    log("✅ 정상 완료");
    log("result = " + task1.result);
}
```

> ⚠️ 이것도 완벽하진 않다. `join(1000)`이 반환된 직후에 스레드가 끝나면, `isAlive()`를 호출하는 찰나에 `false`가 될 수 있다. **`join(ms)` 기반 코드는 본질적으로 경쟁 상태를 안고 있다.**

## 9.4 타임아웃 후에도 스레드는 계속 돈다

위 로그를 다시 보자. `main`이 끝난 뒤에도 `작업 완료 result = 1275`가 찍혔다.

**`join(ms)`는 "기다리기를 포기"할 뿐이지 "상대를 중단"시키지 않는다.** 진짜로 중단시키려면 `interrupt()`가 필요하고, 그게 다음 글의 주제다.

# 10. join()의 한계와 그 다음

## 10.1 지금까지의 패턴

```java
SumTask task = new SumTask(1, 50);      // ① 결과를 담을 필드를 가진 객체
Thread t = new Thread(task);
t.start();
t.join();                                // ② 끝날 때까지 대기
int result = task.result;                // ③ 필드에서 결과 꺼내기
```

동작은 하지만 구조적으로 아쉬운 점이 많다.

| 문제 | 설명 |
| --- | --- |
| 결과 전달이 지저분함 | 반환값이 아니라 **공유 필드**를 통해 주고받음 |
| 예외 전달 불가 | `run()`에서 터진 예외를 main이 알 방법이 없음 |
| 타임아웃 구분 불가 | `join(ms)`가 `void` 반환 |
| 취소 불가 | 기다리기를 포기할 뿐 중단시킬 수 없음 |
| 스레드 재사용 불가 | 작업마다 `new Thread()` → 비용 큼 |

## 10.2 최종 목적지 미리보기

```java
ExecutorService es = Executors.newFixedThreadPool(2);

Future<Integer> f1 = es.submit(() -> sum(1, 50));     // Callable — 반환값 있음
Future<Integer> f2 = es.submit(() -> sum(51, 100));

int sumAll = f1.get() + f2.get();                      // 결과를 "받아온다"
// f1.get(1, TimeUnit.SECONDS);   → 타임아웃 시 TimeoutException (구분 가능!)
// f1.cancel(true);               → 취소 가능
// run() 의 예외는 ExecutionException 으로 전달됨
```

| | `Thread` + `join()` | `ExecutorService` + `Future` |
| --- | --- | --- |
| 결과 | 공유 필드 | ✅ `get()` 반환값 |
| 예외 | 전달 안 됨 | ✅ `ExecutionException` |
| 타임아웃 | 구분 불가 | ✅ `TimeoutException` |
| 취소 | ❌ | ✅ `cancel()` |
| 스레드 재사용 | ❌ | ✅ 풀 |

지금 `join()`을 배우는 이유는 이게 최종 답이어서가 아니라, **`Future.get()`이 내부적으로 뭘 하고 있는지 이해하기 위해서**다.

# 마무리 정리

## 한 줄 요약

> **`sleep()`은 "시간"을 기다리고, `join()`은 "사건"을 기다린다.**
> 그리고 `join()`만이 결과의 **가시성**까지 보장해준다.

## 헷갈리기 쉬운 포인트 10가지

| # | 흔한 오해 | 정확한 사실 |
| --- | --- | --- |
| 1 | `RUNNABLE`이면 CPU를 쓰고 있다 | **I/O 대기도 `RUNNABLE`**이다 |
| 2 | `BLOCKED`는 모든 락 대기다 | **`synchronized`에만** 해당. `ReentrantLock`은 `WAITING` |
| 3 | `notify()` 받으면 바로 실행된다 | 락을 다시 얻어야 해서 **`BLOCKED`를 거친다** |
| 4 | `synchronized` 대기도 인터럽트로 깰 수 있다 | **`BLOCKED`는 인터럽트에 반응하지 않는다** |
| 5 | `thread1.sleep(1000)`은 thread1을 재운다 | **호출한 스레드가 잔다.** static 메서드라서 |
| 6 | `sleep()`은 락을 놓는다 | **놓지 않는다.** `wait()`만 놓는다 |
| 7 | `sleep(100)`은 정확히 100ms다 | **최소 100ms.** 더 길 수 있다 |
| 8 | `join(0)`은 기다리지 않는다 | **무한 대기**다 |
| 9 | `join()` 두 번 = 대기 시간 두 배 | **`max(t1, t2)`**. 이미 병렬로 돌고 있다 |
| 10 | 오래 `sleep()`하면 결과를 읽을 수 있다 | **가시성 보장이 없다.** `join()`이 필요한 진짜 이유 |

## 상태와 메서드 대응표

| 메서드 | 진입 상태 | 락 반납 | 인터럽트 반응 |
| --- | --- | --- | --- |
| `Thread.sleep(n)` | `TIMED_WAITING` | ❌ | ✅ |
| `thread.join()` | `WAITING` | — | ✅ |
| `thread.join(n)` | `TIMED_WAITING` | — | ✅ |
| `object.wait()` | `WAITING` | ✅ | ✅ |
| `synchronized` 진입 실패 | `BLOCKED` | — | ❌ |

다음 글에서는 `interrupt()`를 다룬다. `join(ms)`로 기다리다 포기했을 때, **상대 스레드를 실제로 중단시키는 방법**에 대한 이야기다.
